# 界鉴 JIEJIAN 1.0.12

> 面向 Vibe Coding 的权限意图持续验证与断裂诊断系统。

界鉴记住人已经确认的权限要求。Agent 可以继续修改代码和提出建议，但不能把原来的权限考题改简单；界鉴会独立检查真实业务结果，并定位当前证据能够证明的最早权限断裂。

## 为什么代码改对了，权限仍可能被悄悄改坏

Vibe Coding 让功能迭代变快，也让后续修改更容易绕开原来的权限约束。页面可能仍然显示“没有权限”，接口也可能返回 `403`，但后台动作已经继续，最终业务结果仍然发生。只看表面响应，无法确认权限要求是否真的守住了。

## Alice 和 Bob 的业务故事

在官方“协作空间”里，Alice 是项目负责人，Bob 是普通成员。人已经确认：Bob 可以查看日常协作资料，但不能导出完整项目交付包。

当 Bob 发起导出时，页面和接口都显示拒绝，但后台仍然生成了资料包。界鉴不会因为看到 `403` 就宣布安全，而会继续核对 Bob 的实际身份、权限决定、后台执行和最终文件，确认这个本不应该发生的业务后果是否真的出现。

## 界鉴怎样继续检查真实结果

界鉴把人的长期权限要求冻结进每次检查，通过受控浏览器、隔离执行和独立观察确认资源最终发生了什么。若代码后来改变，界鉴会重新确认真实文件变化，找出需要重验的权限要求，并继续用人之前确认的同一套要求检查，而不是让 Agent 自己选择考题或结论。

当禁止发生的业务后果被确认时，界鉴沿着已发布证据还原实际路径，定位当前证据能够证明的最早权限断裂；关键证据不足时则明确给出 `INCONCLUSIVE`，不会把“没看见”说成安全。

## 现场验证与可追问证据

检查结果可以进入“现场验证”。页面把人确认的权限考题、预期与实际业务路径、当前证据允许支持的结论并排展示。精确断裂、断裂区间、只能确认违规和证据不足使用不同表达，前端不会把模糊证据画成唯一断点。

点击路径节点可以打开同一份证据说明，依次查看发生了什么、数据从哪里来、能证明什么、不能证明什么，以及为什么属于本轮。修复复验继续使用原权限考题，并在同一种路径视图中对照“必须消失、必须保持、不能改变”。长期历史默认按权限要求组织；无法可靠归到单条要求的 Run 会明确保留不确定性。

## 从孤儿后果到同题复验

每个受保护的业务后果都应该能追溯到仍然有效的权限决定。如果结果真实发生，却找不到合法授权来源，界鉴会把它识别为“孤儿后果”，再结合实际身份、后台执行和最终资源，判断授权连续性从哪里开始断开。

确认问题后，界鉴形成一份不能改写原权限要求、受保护效果和证据标准的修复要求。Agent 可以据此修改代码，但复验仍使用人原先确认的同一道权限考题，同时检查问题效果已经消失、合法主体的正常功能仍然保留。修复是否成立由新的真实执行和证据决定，不接受 Agent 自己声明完成。

## 人、Agent 与界鉴的职责

| 参与者 | 可以做什么 | 不能做什么 |
| --- | --- | --- |
| 人 | 确认谁可以做什么、哪些真实业务结果绝不能发生 | 把审批责任交给 Agent 或自动化 |
| Agent | 修改代码、说明改动、提出待审建议、启动已批准的检查 | 改写人的权限要求、降低证据标准或决定安全结论 |
| 界鉴 | 保存人的考题、独立验证真实后果、形成三态结论和断裂诊断 | 用模型、状态码或 Agent 声明替代已形成的事实 |

## AI 工具连接

GUI 顶部的“AI 工具”进入独立 `/tools` 页面，可连接 Codex、DSH 或其他 MCP 客户端。长期凭据只保存在 SecretStore/Windows Credential Manager；界鉴不会写 `token.json`，也不会自动修改 Codex 配置。

权限分为 `READ / PREPARE / EXECUTE`。`PREPARE` 可重新分析源码、提交建议并准备已经批准的检查；`EXECUTE` 可启动或停止受控任务。两者都不能批准权限变化。

Codex 使用固定端点 `http://127.0.0.1:8765/mcp` 和用户显式配置的 `JIEJIAN_MCP_TOKEN`：

```powershell
codex mcp add jiejian `
  --url "http://127.0.0.1:8765/mcp" `
  --bearer-token-env-var JIEJIAN_MCP_TOKEN
```

Agent 完成代码修改后，可以提交一条有界的变化说明。界鉴会重新分析已经授权的源码，以服务端看到的真实文件变化为准，再判断哪些现有权限要求需要重验。Agent 不能自行指定权限、用例或安全结论；实现映射有疑问时，检查会停在权限页，等人确认后再继续。

```text
Agent 提交变化说明
→ 界鉴重算真实文件变化
→ 关联现有权限要求
→ 必要时由人复核实现映射
→ 按当前完整检查范围重新验证
→ 在结果与历史中标记代码变化重验
```

## 完成一次检查

1. 选择应用目录，确认本地地址并授权只读源码分析。
2. 确认业务权限组和关键业务动作。
3. 为权限组准备测试账号；密码始终由用户在独立浏览器中输入。
4. 演示一次业务动作；界鉴自动整理业务含义，只在真实歧义时请用户选择。
5. 缺独立验证或恢复方法时，按页面提示补录对应操作；补录不创建新业务 Flow 或权限要求。
6. 人在权限页确认谁应该允许或拒绝，然后启动受控检查。
7. 在结果、现场验证和历史中追问真实效果、证据边界、断裂位置与变化轨迹。

后续代码有变化时，不需要重建一套权限规则。Agent 提交变化说明后，界鉴沿用人的长期权限意图，重新确认实现映射并冻结本次重验上下文。

## 三态结果

| 结果 | 含义 |
| --- | --- |
| `PASS` | 当前已执行规则与可用证据范围内未发现确认问题 |
| `BLOCK` | 已确认权限要求与真实效果冲突 |
| `INCONCLUSIVE` | 必需证据不足，不能说安全，也不能确认漏洞 |

执行失败和结果完整性无效是独立状态，不冒充第四种安全结论。

## 官方 Sample

仓库只保留一个官方 Web Sample：“协作空间：项目资料管理应用”。同一导出动作会呈现漏洞、修复、关键观察受限三种状态，Bob 的日常查看则作为修复后必须保持的独立合法路径；Sample 不预制 Verdict。普通用户可从工作台启动“评委导览”；开发说明见 [Samples 说明](samples/README.md)。

## 30 Case 方法验证

开发验证集使用官方协作空间和一个 tests-only 多租户记录应用，覆盖五类权限断裂及漏洞、保护有效、证据不足三种状态，共 30 个 Case。每个 Case 都有独立的正常功能对照。private oracle 不在被测应用的授权源码根内，不进入产品输入或 MCP 输出，也不参与产品 Verdict；它只由 sample-test 外层验收器读取并比较实际结果。这是验证输入与答案的流程隔离，不表示 Coding Agent 在物理上无法读取整个开发仓库。

这组验证用于证明当前方法能够在固定矩阵中区分 `BLOCK / PASS / INCONCLUSIVE`，并校准授权连续性、孤儿后果和断点精度。第二应用不会出现在普通产品导航中，验证结果也不代表界鉴已经支持任意应用、主动探针全集或全自动修复。

## 启动界鉴

Windows 源码仓库在项目根目录运行：

```bat
.\start.cmd
```

启动器按锁文件准备项目专用环境、Chromium、数据库和前端资源，运行数据只写入 `var/`。首次准备需要网络；后续复用未变化依赖。

仓库支持构建 Windows x64 Portable，目前没有已发布的 GitHub Release。开发者按[修改发布与便携版](docs/02_开发指南/任务/修改发布与便携版.md)在仓库外验收构建产物。

## CLI 与 Machine 自动化

CLI 只保留有独立非交互价值的控制任务：

```text
status / serve
application list/show/remove
check preview/prepare/run/cancel
result show/report
history
system doctor/repair/clean
```

示例：

```powershell
jiejian status
jiejian check preview <project_id>
jiejian result show --project <project_id>
jiejian --json status
```

人类模式只输出业务语言；完整稳定结构使用 `--json`；诊断使用 `system doctor`。首次应用接入、登录与 Recording 只在 GUI 完成，Agent 自动化使用 MCP。

## 当前范围

界鉴当前只检查用户明确授权的本机 Web 应用。被测 CLI、MCP/Agent Target、主动探针和全自动修复不在当前范围；第二验证应用只属于 tests / competition validation，本地 MCP 只是现有 Web 产品的控制入口。
