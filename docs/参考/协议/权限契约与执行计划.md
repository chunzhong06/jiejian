# 权限契约与执行计划

> 状态：CURRENT。本文解释权限数据族之间的安全边界，不复制 JSON Schema 字段表。

## 目的与消费者

当前协议连接正式 Business Boundary、Permission v2、完整纯计划与 CHECK 后端；旧 Contract 家族只作为保留协议，不进入当前执行。

## 先理解：用户需求、执行计划和结论不是同一份数据

用户确认“普通协作成员不得导出项目负责人的完整项目交付包”时，`PermissionIntentRevision` 引用正式 `BusinessActorRevision`、`BusinessActionRevision`，保存关系、DENY 预期与受保护 effect IDs，不保存 Candidate、具体账号、Cookie、HTTP 或 Observer。Actor/Action implementation binding 独立保存当前 Candidate 定位；`MISSING` binding 不阻止业务语义确认，只阻止后续把它冒充为可验证实现。

执行后形成的 Evidence 与 Verdict 不回写 PermissionIntent。换一个测试账号可能让既有技术绑定失效，却不能静默改变用户已经确认的权限需求；缺代表形成 coverage gap，也不能删除 DENY。

## 当前执行计划边界

`PersistedExecutionRequestV3` 是 schema_version="3" 的独立根，完整冻结 ExecutionAction、ExecutionCase、Twin、ALLOW 回归、proof、来源与策略身份。`CheckRuntimeBundle` 格式1冻结运行叶配置，通过 config_fingerprint 关联；Runner 不拼接旧 Contract/Profile。正式 ACTOR/ACTION/Permission revision 与技术绑定分离；身份、资源、合法对照、恢复或证明 gap 阻止提交，不能缩减完整计划。

当前消费入口为 `workflows/checks/service.py`、`infra/runtime/check_runner/` 与 `core/verification/checks.py`，Schema 为 `schemas/runner/persisted-execution-request-v3.schema.json` 和 `check-*.schema.json`。

## 独立保留格式

`PermissionContract`、`NormalizedPermissionPlan`、`PermissionMutationPlan` 与 `DifferentialExperimentPlan` 由 `product/backend/core/verification/permissions/` 的纯规则和对应协议 reader 消费。其根格式与 canonical 由 `product/protocols/schemas/contracts/` 及模型治理；业务版本与 Schema 版本分开。它们不是当前业务权限写入或 CHECK 提交的第二套入口。

Coverage 包含 cases、预算、seed、fingerprint、覆盖与 gaps；Differential 固定合法对照、拒绝变体、允许变化维度与不变量。缺失覆盖不得删除规则或默认通过。直接测试在 `tests/backend/core/verification/permissions/`，原有稳定输入与 golden 保留；不要用当前输出倒推预期值。

正式 BusinessActor/Action、Permission revision、Proposal 和 implementation binding 由 `product/backend/core/boundaries/` 与 `product/backend/workflows/business_boundaries/` 负责；当前计划由 `product/backend/core/checks/plan.py`、请求由 `product/backend/workflows/checks/service.py` 负责。审批与执行输入的关系见[快照决策](../../决策/ADR-0030-契约与执行快照绑定.md)。
