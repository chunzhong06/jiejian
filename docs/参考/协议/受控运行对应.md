# 受控运行对应

> 状态：CURRENT。本文说明受控 Python 启动、交付加载和检查前后运行核对。当前已接入 Windows 官方示例；普通外部应用不自动获得运行对应能力，完整版本验收另行记录。

## 支持范围

当前基础实现仅支持受控解释器中的 Python 目录应用，入口为目录内一个明确的顶层 `.py` 文件。启动清单逐项列出全部复制文件、字节数与内容指纹，依赖配置通过清单中的文件引用冻结；解释器指纹沿用已有启动器核验的运行环境身份。此方式不声明支持 Node 构建产物、容器、远端部署或任意 Python 包入口。

控制者从已授权源码清单复制到运行目录的独立副本。副本不会跟随工作区修改；下一批源码需要新的启动副本与实例。副本的运行期间只允许读取，临时文件和业务数据必须写入另一个运行目录。仅完成副本创建还不表示进程已启动或应用已就绪。

## 独立文档及所有者

| 文档 | Writer | Reader | 含义 |
| --- | --- | --- | --- |
| `RuntimeLaunchManifest`，格式 1 | 控制者的 `create_runtime_artifact` | 独立 `process.target` 启动模块、控制者 | 实例、固定入口、源码清单、依赖配置引用、解释器指纹 |
| `RuntimeLaunchReceipt`，格式 1 | 已被进程树闸门放行的启动模块 | 持有真实进程对象的控制者 | 导入目标前已核对的实例、清单和进程 ID |

启动模块先核对解释器身份、工作目录、缺失/多余/变更文件，再以排他创建方式写回执；旧实例回执不能被第二次启动覆盖。以已核对的绝对入口文件执行目标，不通过同名已安装包猜入口。清单和回执只保存引用、指纹和公开身份，不包含环境全量、秘密、源码正文或安全结论。

只有独立 Target 进程在完成副本核验后，将该副本的绝对目录加入导入路径，以支持应用自己的同目录模块。API、Worker 与其他产品进程不修改 `sys.path`；此边界不能用于把仓库源码补进产品安装视图。架构测试同时限制允许位置、唯一目录表达式和先核验后导入的顺序。

`receipt_matches` 只做对应关系比较。调用者必须先用既有受控进程树验证所有权和存活，再匹配实际持有的进程 ID；不能将端口、健康响应中的自报版本、PID 相等或 Git HEAD 相等当成独立所有权证明。启动回执写入发生在目标执行前，所以还须另行核对应用就绪。

## 交付和检查接线边界

检查使用格式 2 的 `ControlledCheckRuntimeBundle` 冻结实例引用，Runner 核对 Windows Job 所有权、存活、OS 进程创建时间、启动清单与全部副本文件。检查前无法确认时停止目标执行；检查后漂移保留已观察事实，但运行适用性为未确认。格式 2 的结果独立保存前后状态；发布器核对请求与结果中的精确引用。格式 1 的历史输入与结果继续按原 reader 读取，不补造身份。

交付加载由 GUI 显式发起，使用稳定操作键和 `RuntimeActivationReceipt`。先持久化 PENDING，再调用现有有界样例进程生命周期。回执丢失时只回读实例并补齐回执，不重新启动试探。进程内执行集仅用于区分本进程仍在执行与未知状态，不是幂等依据。加载仅重启同一示例应用的进程，保留权限、材料与历史；全新启动示例仍创建独立项目。此操作不替代正式检查的 Job/lease/fence。

精确交付通过 `development_check_runs` 与 Run 关联，不以时间接近或源码相同推测。运行适用性不改变历史 Verdict，也不能使普通 PASS 自动成为原题修复成功。任何未接入受控启动的应用均显示受限支持。

源码指纹与 Changes 快照采用相同的排序路径及文件内容摘要算法；清单身份另将实例、入口、依赖和解释器纳入。相同源码不等于相同运行实例。依赖配置文件的指纹不证明任意第三方包内容、外部服务状态或宿主系统可信；当前支持范围仅覆盖已有受控解释器环境。

## 限制和验证

本机制防止普通开发中的旧进程、入口混淆和源码修改未加载。它不对恶意宿主、进程内存篡改或检查中修改后又还原文件提供可信执行证明，也不替代账号身份、业务证据或检查完整性判断。

直接测试：`tests/backend/infra/runtime/process/test_target_artifact.py`。包含真实受控子进程执行独立副本，工作区修改不改变本次执行，错误进程/实例/清单拒绝，多余、缺失、变更文件拒绝，以及复制期间源码变化不发布可启动清单。
