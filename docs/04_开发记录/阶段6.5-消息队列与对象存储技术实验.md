# 阶段 6.5 消息队列与对象存储技术实验

## 当前状态

消息队列与对象存储最小只读实验均已完成并通过。Queue Peek 与 Blob Object 适配器随后在 Runner 隔离域实现并通过本机动态验证，现由 Runner V2 调度并生成 Evidence/Result；实验脚本本身仍是已删除的独立验证资产，不是生产入口。阶段 6 未新增 Queue/Blob 专属普通用户配置或动态黄金样例。

## 实验范围与协议结论

实验使用本机 `127.0.0.1` 上的 Azurite Queue 服务和已准备的 Azure Queue SDK。setup/producer 使用完整 SharedKey，仅用于创建、写入和清理专用测试队列；observer 只使用该队列的短期 Queue SAS `r` 权限。

observer 的最小行为是：对显式授权的专用队列调用 `peekMessages`，每次不超过 32 条；按稳定消息字段规范化、筛选精确 `case_tag` 与 `resource_id`、去重并计算内容 SHA-256。observer 不 receive、dequeue、delete、clear，不提交 offset，也不创建消费者。

| 面向 | 实测结论 | 阶段边界 |
| --- | --- | --- |
| 协议 | Queue SAS 的 `r` 权限可以完成 Peek；消息体中的 `case_tag`、`sequence`、`resource_id` 可作为有界关联字段 | 尚未形成生产协议或 Schema |
| 只读性 | 连续两次 Peek 的匹配内容和哈希一致，Peek 前后 `dequeueCount` 不变；send、receive、clear、delete 均被 403 拒绝 | setup 的 destructive 操作不属于 observer 路径 |
| 因果性 | 专用队列内精确匹配目标 `case_tag` 得到两条消息；重复 Peek 哈希稳定，不依赖时间或 message ID 相似性 | 共享队列不能仅凭邻近消息补齐因果 |
| 负观察 | Peek 没有 continuation；第 34 条目标消息在前 33 条无关消息之后不可见 | 达到 32 条上限或队列可能超限时只能 INCONCLUSIVE |
| 启停 | 本机可离线启动、就绪、停止并用同一数据目录重启；无需管理员权限或外网 | 仅具备进入生产实现候选的条件 |

## 实测证据

本次使用 Azurite 3.36.0、`@azure/storage-queue` 12.31.0。实验结果为：安装工具目录统计 7,365,446 字节；首次就绪 4,057 ms；同一命令离线重启后第二次就绪 4,041 ms；两次 Peek 合计 20 ms；首次停止 10 ms。主队列 Peek 到 4 条消息并精确匹配目标 2 条，重复哈希相等；setup 随后 receive 到的 4 条消息 `dequeueCount` 均为 1。边界队列 Peek 到 32 条，服务报告约 34 条，目标第 34 条不可见。

启动本地模拟器时使用了 `--skipApiVersionCheck`，它只解决本地 Azurite 与当前 SDK 的版本头差异，不放宽真实 Azure 服务或未来生产观察器的版本校验。实验临时脚本、队列数据和日志均已清理，未提交完整 key、SAS、URL query、端口或临时绝对路径。

## 负观察与后续边界

只有在单 case/单 run 专用队列、producer 明确保证消息总量不超过 32、Peek 未达到上限且响应内容完整时，才可把“未发现目标 case”作为有界负观察。共享队列、达到 32 条上限、消息可能继续写入或没有 continuation 的情况必须标记 PARTIAL/INCONCLUSIVE；不得用 message ID、时间接近或资源相似性推断不存在。

实验说明 Queue Peek 能提供只读窗口和显式 case tag 关联，但没有证明轮询、任务终态、队列外因果或生产环境服务兼容性。若进入后续实现，至少需要专用队列约束、消息数量/字节预算、重复与冲突去重、SAS 最小权限、不可用和超限的 INCONCLUSIVE 语义，以及不把 setup 凭据带入 observer 输入、输出或日志。

## 复现概要与结论

在已准备的离线实验工具目录中，以固定 Node 运行时启动 Azurite Queue（绑定回环地址并使用 `--skipApiVersionCheck`），由临时 Node 脚本创建专用队列、写入有界 JSON 消息、生成 `r` 权限 Queue SAS、连续 Peek、尝试破坏性操作、执行 32 条上限边界实验，再由 setup 清理并重启验证。临时脚本不是生产代码，本批已删除。

结论：消息队列只读观察假设在本机 Azurite Queue 上通过，具备进入生产适配器设计候选的条件；本批不实现生产 observer、不修改公共协议、不新增依赖、不修改 Runner/V1 工件。对象存储实验结论见下节。

## 对象存储最小只读实验

### 范围与权限

本次使用本机 `127.0.0.1` 上的 Azurite Blob 服务和已准备的 `@azure/storage-blob` SDK。setup/producer 使用完整 SharedKey，仅用于创建、覆盖、修改 metadata、删除和清理唯一测试 container；observer 只使用固定 container 的短期 Container SAS `r+l` 权限，并限定到 `cases/<case_tag>/` 前缀。observer 只执行有界 list、head 和 get，不列举其他 container，不扫描前缀外对象。

同一只读 SAS 对 upload/create、overwrite、setMetadata、delete 的调用均返回 403。setup 的写入和清理不属于 observer 路径，完整 key、SAS、URL query、端口和临时绝对路径均未进入结果或文档。

### 四类变化与因果结论

| 变化 | 实测事实 | 结论 |
| --- | --- | --- |
| 创建 | 专用 prefix 初始 list 为零；setup 创建 5 个对象后，有界 list、head、get 精确发现并读取对象，连续两次规范视图哈希一致 | `case_tag`、`resource_id` 和固定 prefix 可形成有界关联 |
| 覆盖 | setup 覆盖同名对象后，ETag 和内容 SHA-256 均改变 | 覆盖事实不依赖时间接近，可由版本/内容视图确认 |
| metadata-only | setup 只修改 metadata；内容 SHA-256 不变，ETag 和规范 metadata SHA-256 改变 | 可区分内容变化与 metadata 变化 |
| 删除 | setup 删除目标后，完整 prefix list 不再出现目标，head/get 均为 404 | 仅在分页穷尽、预算未触发且专用命名空间完整时可作权威负观察 |

### 分页、预算与规范化

实验使用固定页大小 2，实际对象集超过一页；观察按 continuation 分页，按相对对象名稳定排序、去重，记录非秘密 prefix、ETag、长度、内容 SHA-256、允许的 metadata 及 metadata 哈希。最大页数、最大对象数、累计 bytes 和单对象 get bytes 均为显式预算。

将最大页数或最大对象数收紧后，观察结果明确为不完整；目标落在未扫描页或超过对象预算时只能 PARTIAL/INCONCLUSIVE，不得判断未创建或已删除。对象视图不包含 SAS、绝对路径、原始响应或未允许 metadata。

### 实测成本与结论

本次使用 Azurite 3.36.0、`@azure/storage-blob` 12.33.0。Azurite 与 Blob SDK 工具目录合计 19,149,869 字节；首次就绪 4,094 ms；同一数据目录离线重启后第二次就绪 4,068 ms；首次停止 16 ms。实验只使用本机回环，不访问外网，不需要管理员权限。启动时使用 `--skipApiVersionCheck` 仅解决本地模拟器与当前 SDK 的版本头差异，不放宽真实 Blob 服务或未来生产观察器校验。

对象存储实验结论：固定 container + prefix、Container SAS `r+l`、显式分页和有界 list/head/get 足以支持进入生产适配器设计候选；生产实现仍需补充严格 locator、预算、重试/超时、完整性和不可用的 INCONCLUSIVE 语义，并保持写入、覆盖、metadata、删除完全位于 setup/producer 边界。本批不实现生产 observer、不修改公共协议、不新增依赖、不修改 Runner/V1 工件。临时脚本、数据和日志已清理。

## 6.5A Queue/Blob Observer V2 协议

6.5A 已冻结协议模型和 Schema。Queue 使用 `AZURE_QUEUE_PEEK` locator/provenance，限定独立测试队列、`env:` SAS 引用、有限字段、Queue Peek 预算和 `EVENTUAL` 阶段；Blob 使用 `AZURE_BLOB_OBJECT` locator/provenance，限定独立测试 container、`env:` SAS 引用、固定 request-marker prefix、metadata allowlist、分页/对象/字节预算和 `BEFORE/AFTER/EVENTUAL` 阶段。两类 Runner 隔离适配器均已实现、通过本机动态验证并接入 Runner V2；未提供 Queue/Blob 专属普通用户配置与动态黄金样例。

## 6.5B Azure Queue Peek 只读观察器

`runner/queue_observer.py` 由 Runner-side supervisor 调用包内 `azure_queue_observer_process` 子进程。子进程只支持 `AZURE_QUEUE_PEEK`，使用 `httpx` 的 `trust_env=false`、`follow_redirects=false` 和固定 `x-ms-version: 2023-11-03`，只发送 Queue REST `GET .../messages?peekonly=true&numofmessages=N`。Queue Service SAS 必须来自单一 `env:` 变量，解析后要求 `sr=q`、`sp=r` 和 `sv/se/sig`，不写入输入、输出、日志、异常或状态。

适配器对 XML、base64 JSON、重复键、字段/标量、单消息/累计字节、重试、超时、取消和父进程输出执行有界校验；状态只保存规范化消息、扫描/匹配计数、窗口完整性和 hash。重复 event_id 同内容去重，冲突或 Peek 返回数达到 `max_messages` 返回 `PARTIAL/INCONCLUSIVE`；未达到上限的专用队列空匹配才可返回完整负观察。真实 Azurite 动态验证证明两次观察 hash 稳定、Peek 后 setup receive 的 `dequeueCount` 仍为首次值，32 条无 continuation 边界不被误判为完整。

该适配器实现子批未单独增加样例、Runner V2 输入、V2 Evidence 或数据库迁移；后续阶段 6 批次已完成 Runner V2 编排、Evidence/Result、Profile 和 Worker/publication 接线，仍未增加 Queue/Blob 专属 GUI 配置。

公共服务 endpoint 只接受规范 HTTPS account host；本机实验 endpoint 仅在 `allow_loopback_http=true` 时接受 `127.0.0.1`、显式端口和单一 account path。SAS 不进入协议正文、错误或 Schema，只以 `env:` 引用表达。Queue/Blob locator 的测试命名空间、字段/prefix allowlist、嵌套预算和阶段约束均由 Observer V2 模型严格校验，required 不完整仍为 `INCONCLUSIVE`。

六份 Observer Schema 均直接等于对应模型的原生 `model_json_schema()`。由于 `ObserverSpecV2` 是共享定义，新增 Azure 类型会机械扩展 audit/async invocation Schema 的 `$defs`；这不是旧 invocation 运行语义变化。旧有效实例的 canonical JSON/hash、V1 Runner/Evidence/Verdict 和现有观察器行为由实例兼容测试保护。
