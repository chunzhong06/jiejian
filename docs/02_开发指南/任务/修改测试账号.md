# 修改测试账号

> 状态：CURRENT。用于修改 TestIdentity、独立登录准备、Cookie/Bearer 归约、SecretStore 和运行时身份注入。

## 这是什么

测试账号是绑定项目、已确认角色、endpoint 和 ApplicationUnderstanding revision 的产品资产。它说明“用哪个测试角色准备会话”，不是 Contract Subject、运行时 Cookie jar，也不是密码保管器。用户在独立有头浏览器中自行登录；只有明确确认保存后，受控进程才把当前目标所需的有限 Cookie 或单一 Bearer 写入共享 SecretStore，并把非秘密引用交回 ApplicationCore。

账号元数据存数据库，秘密正文存 Windows Credential Manager 等受控 SecretStore，短期准备请求与结果走严格协议。Recording/Runner 只按冻结请求解析所需引用并最小注入；API、日志、Evidence、报告和普通数据库字段都看不到秘密值。

## 正常修改路线

先区分账号元数据、秘密存储、浏览器准备、运行时注入和展示。新增状态或动作时从 TestIdentity service 的事务和协议状态机开始；浏览器进程只负责用户登录、目标 scope 校验和有限状态归约；SecretStore 只提供按引用写入/读取/删除；页面只显示账号是否已准备和可恢复动作。

Cookie 路径最多保存当前目标 host 的 32 个 Cookie，每项只回传名称、域、路径、过期等非秘密元数据和独立 `secret_ref`。Bearer 只允许当前 origin 的单一引用。两者同时存在、多个 Bearer、跨 scope 状态或无法安全归约时 fail closed，并引导高级配置；不能为了“更好用”保存完整 storage state、localStorage 或密码。

准备进程在写入秘密前原子记录 `secret-refs.json` journal。正常提交后删除；进程或服务异常退出时，ApplicationCore 依据已提交 TestIdentity 引用做精确补偿，不枚举全部 Credential Manager，也不靠 PID 猜测是否有效。

## 不能破坏

- 密码永不保存；Cookie/Token 正文不经 stdout、API、数据库、日志、异常、Evidence 或报告。
- `secret_ref` 不是秘密值，但也只在受控协议和冻结执行输入中传播，不能展示给普通用户。
- 登录阶段不采集 RecordingEvent；身份准备浏览器与 Recording 浏览器是不同进程和生命周期。
- 缺少某个角色账号只形成 coverage/representative gap，不能删除或改写已确认 ALLOW/DENY。
- 角色、endpoint 或 understanding revision 漂移时旧账号不可继续冒充 CURRENT；重新准备不会复活旧冻结请求。
- Windows Credential Manager 的持久化和当前交互用户身份边界不能因自动测试环境而放宽。

## 怎么验证

普通变化优先 fake SecretStore 和受控进程协议测试，覆盖 Cookie/Bearer 正常路径、混合状态拒绝、scope/预算、journal 提交与补偿、删除幂等和异常脱敏。只有修改 Windows Credential Manager 或真实 headed 登录边界时，才由主线程在当前交互用户环境运行相应 Windows L5；不要用普通单测假装证明系统凭据闭环。

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 test tests/backend/workflows/test_identities tests/protocols/test_identity_preparation.py tests/backend/infra/identity
```

## 失败先查哪里

账号显示未准备先查 TestIdentity revision 与已提交引用，不直接查看秘密正文。保存失败先区分 target scope、Cookie/Bearer 归约、SecretStore 写入和 result 关联；cleanup 问题看 journal 是否仍在。真实 Windows 只在 Codex 沙箱失败而交互用户成功时，应归类为用户会话/凭据上下文边界，不改产品持久化常量或把秘密降级到文件。
