# 竞赛追问账

> 状态：CURRENT。用于把常见竞赛追问对应到产品入口、正式证据和当前限制；没有普通产品入口或真实证据的问题不得标为“已备齐”。

## Agent 为什么不能自己决定怎么检查

- 问题：为什么不能让 Agent 自己检查并决定权限是否安全？
- 一句话回答：Agent 可以提交代码变化、准备检查和启动已获准的任务，但权限要求由本机用户确认，结论由正式执行事实形成。
- 产品中打开位置：工作台 → AI 工具；权限与检查 → 权限要求。
- 证据来源：`PermissionIntentRevision`、`HumanApproval`、MCP 权限分级和公开控制入口清单。
- 能证明什么：普通 GUI 之外的 Agent、CLI、MCP 和自动准备流程没有批准权限要求或决定 Verdict 的产品入口。
- 仍有限制：这是产品控制面边界，不表示拥有操作系统权限的进程在物理上无法读取或篡改整个开发环境。
- 状态：已备齐

## 怎样证明实际身份

- 问题：怎么证明真正执行操作的是计划中的测试账号？
- 一句话回答：现场验证读取本次 Run 已发布的实际身份事实；无法独立确认时明确显示证据不足。
- 产品中打开位置：检查结果 → 现场验证 → “实际执行身份”；路径节点 → 证据说明。
- 证据来源：测试会话、`ExecutionTrace` 身份节点和 ResultPresentation 的 Claim Boundary。
- 能证明什么：当前 Run 的实际主体是否已被正式 Trace 归因，以及该事实关联到哪条检查路径。
- 仍有限制：身份节点不能单独证明最终业务后果；身份来源不可用时不能据此给出 `PASS`。
- 状态：已备齐

## 最终产物为什么属于本轮

- 问题：怎样证明最终文件或数据不是前一次运行留下的？
- 一句话回答：证据说明展示当前 Run 的请求标记、已发布 Evidence 引用和观察来源，只接受与本轮关联的业务结果。
- 产品中打开位置：现场验证 → 点击实际路径节点 → “为什么属于本轮”。
- 证据来源：当前 Run 的 Evidence、请求标记、Observer 结果和 ResultDiagnosis。
- 能证明什么：展示的业务后果由本轮已发布证据引用，而不是从页面文本或相邻时间推测。
- 仍有限制：只能覆盖本次配置的观察来源和关联范围，不能扩大为其他路径也产生了相同后果。
- 状态：已备齐

## 中间消息为什么不能证明最终效果

- 问题：队列里出现一条消息，为什么还不能说明最终资料包已经生成？
- 一句话回答：中间消息只能证明任务进入了某个环节，最终效果仍需独立观察最终文件、数据或业务状态。
- 产品中打开位置：现场验证 → 证据说明 → “能证明什么 / 不能证明什么”。
- 证据来源：各 Observer 的 `EvidenceExplanation` 和 `does_not_prove` 边界。
- 能证明什么：消息、任务、审计、数据库和最终对象各自承担哪一段证明责任。
- 仍有限制：某一来源缺失时，其他中间来源不能自动补成最终效果证明。
- 状态：已备齐

## 断裂点怎样形成

- 问题：红色断裂点是前端画出来的，还是后端算出来的？
- 一句话回答：前端只渲染已发布 `ResultDiagnosis`；断裂类型和最大可支持精度由正式 `BreakpointLocator` 形成。
- 产品中打开位置：检查结果 → 现场验证 → 预期与实际业务路径。
- 证据来源：`ExecutionTrace`、授权连续性结果和 `BreakpointLocator.locate()`。
- 能证明什么：`EXACT` 可以标一个精确断裂边，`RANGE` 只能标区间，`VIOLATION_ONLY` 只确认违规而不伪造位置。
- 仍有限制：结论只适用于当前已发布 Trace；证据不足时不会补猜更精确的位置。
- 状态：已备齐

## BLOCK 是否写死

- 问题：官方示例里的 `BLOCK` 会不会是按 Case 名称写死的？
- 一句话回答：产品 Verdict 使用正式权限判断函数，Sample 名称和 private oracle 不进入产品判定输入。
- 产品中打开位置：检查结果；现场验证 → 当前可支持的主张。
- 证据来源：`evaluate_permission_case()`、正式 Result publication、30 Case validation 的外层 oracle 对比。
- 能证明什么：固定矩阵中的漏洞、保护有效和证据缺失三态由同一生产判断路径区分，漏洞错误 `PASS` 与证据缺口错误 `PASS` 均为 0。
- 仍有限制：这只证明当前 30 Case × 1 validation，不代表任意应用、任意缺陷或重复稳定性。
- 状态：已备齐

## 修复是否只是关闭整个功能

- 问题：修复后没有再生成资料包，会不会只是把整个导出功能关掉了？
- 一句话回答：修复复验同时要求违规效果消失、合法主体的正常功能保留，并保持原权限要求和关键证据标准不变。
- 产品中打开位置：现场验证 → 修复前后沿同一业务路径核对。
- 证据来源：`RepairRequirement`、ALLOW 对照、`RepairVerification` 和修复前后两次正式 Run。
- 能证明什么：当前修复是否满足“必须消失、必须保持、不能改变”三组要求。
- 仍有限制：只有后端发布 `VERIFIED` 才能说修复通过；前端没有自行判定权限。
- 状态：已备齐

## 关键证据看不到为什么不能 PASS

- 问题：页面已经拒绝，为什么关键结果看不到时不能判安全？
- 一句话回答：表面拒绝不能证明后台和最终业务后果没有发生，关键观察不可用时只能给出 `INCONCLUSIVE`。
- 产品中打开位置：现场验证 → “验证关键结果不可读取时会怎样”。
- 证据来源：正式 Observation unavailable 机制、新 Run 的 Evidence 和 Claim Boundary。
- 能证明什么：观察不可用会产生新的真实检查，不是把已发布页面上的节点隐藏后改写结论。
- 仍有限制：`INCONCLUSIVE` 既不等于安全，也不等于已经确认漏洞。
- 状态：已备齐

## 谁批准权限要求

- 问题：谁决定 Bob 能不能导出资料包？
- 一句话回答：本机用户在权限页确认完整业务权限句子，服务端保存 Human Approval 和不可静默改写的 revision。
- 产品中打开位置：权限与检查 → 权限要求；历史变化 → 按权限要求查看。
- 证据来源：Human-only approval transaction、`PermissionIntentRevision`、`policy_epoch` 和审批记录。
- 能证明什么：每次检查锁定的是哪一条 P-编号、哪一版业务规则，以及由哪个人类审批通道确认。
- 仍有限制：界鉴不会替用户发明业务权限要求；实现映射有歧义时仍需用户复核。
- 状态：已备齐

## Agent 能否把 DENY 改成 ALLOW

- 问题：Agent 修改代码后，能不能顺手把原来的 `DENY` 改成 `ALLOW`？
- 一句话回答：Agent 只能提交变化说明或 Proposal；正式权限 revision 只能经本机 GUI 的人类审批事务改变。
- 产品中打开位置：AI 工具 → Oracle 边界；权限与检查 → 待复核实现映射。
- 证据来源：MCP/CLI tool inventory、Proposal 与 Human Approval 分离、PermissionIntent 历史。
- 能证明什么：Agent 控制入口不能直接修改 ALLOW/DENY、批准正式映射或让人的规则静默退出检查范围。
- 仍有限制：这不是对操作系统管理员或仓库外恶意进程的安全隔离承诺。
- 状态：已备齐

## 第二应用能证明什么

- 问题：除了官方协作空间，是否在另一种应用结构上验证过？
- 一句话回答：tests-only 多租户记录应用参与同一 30 Case validation，用来减少结论只依赖单一 Sample 结构的风险。
- 产品中打开位置：普通产品没有第二应用入口；开发证据见[竞赛验证主张与证据](竞赛验证主张与证据.md)。
- 证据来源：`tests/validation/apps/tenant_records/`、公开 registry、private oracle 外层比较和 validation 汇总。
- 能证明什么：同一生产 Verdict、Continuity 和 Breakpoint 路径在两种受控 Web 应用结构的固定矩阵中工作。
- 仍有限制：第二应用只属于测试，不表示产品已经覆盖任意 Web 架构。
- 状态：部分支持

## 30 Case 怎样衡量 wrong PASS

- 问题：30 Case 怎样判断“把漏洞或证据不足错判为安全”？
- 一句话回答：外层 evaluator 用 private oracle 比较产品实际 Verdict，并把漏洞错误 `PASS` 和证据缺口错误 `PASS` 作为硬失败计数。
- 产品中打开位置：普通产品不展示 validation 指标；开发证据见[竞赛验证主张与证据](竞赛验证主张与证据.md)。
- 证据来源：`sample-test validation` 的公开汇总和 private oracle 外层计数。
- 能证明什么：2026-08-30 的 30 Case × 1 validation 中，两类 wrong PASS 都是 0。
- 仍有限制：单轮 validation 不构成重复稳定性证明；未运行 `competition` 就没有三轮结果。
- 状态：部分支持
