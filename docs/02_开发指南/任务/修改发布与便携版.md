# 修改发布与便携版

> 状态：CURRENT。适用于界鉴 Web V1 的 Windows x64 Portable 发行、内部 Wheel、固定运行时、full/nosamples 双 ZIP、校验和与仓库外验收。

## 这套发行能力解决什么问题

源码仓库启动服务于开发者：它允许准备 Conda、uv、Node/pnpm、editable 源码和共享构建缓存。Portable 服务于普通 Windows 用户：下载并解压后即可双击 `start.cmd`，不要求机器预装 Conda、uv、Node、pnpm，也不从网络安装产品依赖。

两条启动链共享同一个产品 CLI 和 ApplicationCore，但运行身份不同：

```text
源码仓库
start.cmd
→ scripts/start.ps1
→ scripts/dev.ps1 prepare
→ editable product.backend.cli serve

Windows x64 Portable
发行根 start.cmd
→ runtime/start.ps1
→ 包内 CPython 3.13
→ 非 editable product.backend.cli serve
```

Portable 不是把源码仓库复制给用户，也不是内部 Wheel 的别名。正式交付物必须同时包含 Python、锁定的生产依赖、产品 Wheel、Wheel 内前端、Playwright Chromium、相对路径启动器和发行元数据。

## 快速找到修改位置

| 我想修改什么 | 主要位置 | 通常需要一起核对 |
| --- | --- | --- |
| `dev.ps1 package` 的准备、分派与固定输出 | `scripts/dev/package.ps1` | `scripts/dev.ps1`、`tests/scripts/test_dev_script.py` |
| 产品版本、Wheel 版本和发行文件名 | `product/backend/__init__.py` 的 `__version__` | `pyproject.toml`、FastAPI/CLI/System、`scripts/build/portable.py`、`scripts/dev/package.ps1` |
| Base Tree、启动器、双 ZIP 和 SHA256 | `scripts/build/portable.py` | `tests/scripts/test_portable.py` |
| Wheel 内容和前端映射 | `scripts/build/hatch_build.py` | `pyproject.toml`、`scripts/dev/frontend.ps1` |

精确函数和 PowerShell 入口见[开发脚本模块](../模块/scripts.md)与[自动代码参考](../../03_参考手册/代码/scripts.md)。

## 版本唯一真源

Web V1 1.0.8 的唯一产品版本真源是：

```text
product/backend/__init__.py::__version__
```

`pyproject.toml` 通过 Hatch 动态读取该值；FastAPI metadata、`/api/system/status`、全局 `jiejian --version`、Portable `release.json`、Wheel 版本、ZIP 目录名和 `scripts/dev/package.ps1` 的 artifacts 名称都必须消费同一值。前端 `package.json` 不维护第二个产品版本，GUI 只从系统状态在“运行环境”页显示服务端版本。

发布前同时检查“源码版本、安装 Wheel 版本、release.json、ZIP 名称、GUI、CLI”一致。不要只改文件名，也不要把协议 `schema_version`、Alembic revision 或 Portable runtime layout version 一起机械改成 `1.0.8`；它们有各自独立兼容语义。

目标产品版本由正式版本任务按交付范围冻结；阶段号和内部任务名不充当对外版本。修改版本时只更新唯一真源及真正依赖版本的测试和文案，不借机升级独立协议版本。

## 生成正式交付物

在 Windows x64 仓库根运行：

```powershell
.\scripts\dev.ps1 package
```

需要明确排除已有前端 build 复用时才使用：

```powershell
.\scripts\dev.ps1 package -ForcePrepare
```

正式输出固定在 `var/development/release/artifacts/`：

```text
JieJian-WebV1-1.0.8-Windows-x64.zip
JieJian-WebV1-1.0.8-Windows-x64-nosamples.zip
SHA256SUMS.txt
```

内部 `jiejian-*.whl` 只在 build staging 中作为组装材料，不能留在正式 artifacts，也不能单独交给普通用户。`package` 每次开始都会移除 artifacts 中的旧内部 Wheel 和同名旧发行物，避免新旧交付混杂。

## 看懂六阶段输出

打包是长流程，必须持续暴露稳定阶段，不允许把复制、安装与两次压缩藏在一个黑箱里：

```text
[1/6] 复制固定 CPython 与 Playwright 运行时
[2/6] 安装 frozen 生产依赖与内部 Wheel
[3/6] 生成元数据并校验唯一 Base Tree
[4/6] 生成包含官方 Sample 的 full ZIP
[5/6] 生成不包含 Sample 的 nosamples ZIP
[6/6] 核对双包产品树并写入 SHA256
```

长耗时的依赖安装直接流式显示 uv 的受控进度。构建器为子进程显式提供 `var/development/release/build/temp` 作为 `TEMP/TMP`；裁剪环境时不能依赖 `C:\Windows` 或用户全局临时目录回退。

阶段失败时先保留第一条有效错误和当前阶段。修复后只重跑 `package`；不要因为发行组装失败而运行完整自动 L5。

## 唯一 Base Tree 与双包关系

`scripts/build/portable.py` 只组装一个 Base Tree。full 和 nosamples 必须从同一个 Base Tree 生成，除 `samples/` 外所有文件的相对路径和 SHA256 完全一致。

ZIP 解压后只有一个顶层目录，根布局固定为：

```text
JieJian-WebV1-1.0.8-Windows-x64/
├── start.cmd
├── README.txt
├── runtime/
│   ├── start.ps1
│   ├── release.json
│   ├── python/
│   └── playwright/
└── samples/              # 只在 full 版存在
```

前端不是发行根的第二份目录。Hatch build hook 把已准备的 production build 写入 Wheel，Portable 从包内 `product/frontend/dist` 提供页面。这样 Python 包、CLI 和页面来自同一个 Wheel，不会出现“根前端和安装包前端版本不同”的双真源。

`release.json` 至少记录产品、发行版本、平台、架构、运行布局版本、包版本、Python、Playwright 与 Chromium revision。它描述交付组成，不保存构建机器路径、环境变量或秘密。

## Portable 启动必须保持相对和离线

发行根 `start.cmd` 是 ASCII 薄壳，只通过：

```text
%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe
```

调用相邻 `runtime/start.ps1`。启动不能依赖 PATH 中碰巧存在的 `pwsh`、Python、Conda 或 uv。

`runtime/start.ps1` 只做以下工作：

1. 从自身位置解析发行根和包内运行时；
2. 校验 `release.json`、CPython、Wheel 内前端和唯一 Chromium；
3. 创建发行根自己的 `var/temp`，设置最小 Portable 运行身份；
4. 用包内 Python 校验 runtime fingerprint；
5. 进入安装后的正式 CLI `serve`，并在 full 版显式传入官方 Sample 根。

普通启动不得执行 pip/uv install、pnpm、Vite build、源码 prepare、Git 探测或网络下载。首次运行产生的数据库、日志、证据、锁和临时文件只进入发行根 `var/`。

## Portable 身份与子进程

Portable 主进程必须同时证明：

- `sys.executable` 和 `sys.prefix` 位于当前发行根 `runtime/python`；
- `product` 及生产依赖均来自发行根内非 editable 的 `site-packages`；
- Chromium executable 与 `PLAYWRIGHT_BROWSERS_PATH` 位于当前发行根 `runtime/playwright`；
- `JIEJIAN_RUNTIME_MODE=portable`，并有当前 `JIEJIAN_RELEASE_ROOT` 和 runtime fingerprint；
- 不存在 `JIEJIAN_PROJECT_ROOT`、源码 `PYTHONPATH`、用户 site-packages 或 Wheel `direct_url.json` 泄漏。

Worker、Runner、Recording Process 和官方 Sample 等受控子进程继续使用 `minimal_process_environment()`。Portable 模式下它们必须继承同一发行根、Python、fingerprint 和浏览器身份；不能因为主进程已经校验过，就让子进程重新从 PATH、cwd 或用户环境猜运行时。

修改身份字段时至少同步：

```powershell
.\scripts\dev.ps1 test tests/backend/infra/runtime/process/test_identity.py tests/backend/infra/runtime/process/test_environment.py
```

## 修改 Python、依赖或 Wheel 输入

发行 CPython 的精确版本和 uv-managed distribution 名称由 `product/config/toolchain.json` 冻结。改变它们前必须先证明新解释器能够安装当前 frozen 生产依赖、运行 Playwright、形成非 editable Wheel 身份并通过仓库外搬迁；不要只把版本字符串改成“最新”。

生产依赖来自 `uv.lock` 的 `uv export --frozen --no-dev --no-emit-project`。dev dependency 不进入 Portable，`pywinauto` 等 L5 工具也不能进入产品 Wheel。

Wheel 由 `uv build --wheel` 生成。`scripts/build/hatch_build.py` 只映射已经准备好的前端产物，不运行 Node/pnpm。新增产品包、数据文件或前端入口时，要同时检查 Wheel 内容、安装后的 import origin、`release.json` 和 Base Tree 路径扫描。

## 修改 full 与 nosamples 的 Sample 边界

full 版从明确的 `samples/` 输入复制官方 Sample；nosamples 版完全不传 Sample 输入。构建器不能按 cwd、仓库邻近目录或环境变量自动扫描 Sample。

两版产品行为差异只允许是：

```text
full       /api/experience/official-sample → available=true
nosamples  /api/experience/official-sample → available=false
           GUI 显示“当前版本未包含官方示例”，入口按钮禁用
```

nosamples 仍然是完整界鉴产品，能够接入用户自己的本地 Web 应用；不能通过删减 Worker、Runner、Chromium、前端或数据库能力来缩小体积。

## 仓库外真实验收

直接合同先运行：

```powershell
.\scripts\dev.ps1 test `
  tests/scripts/test_dev_script.py::test_package_routes_one_base_tree_to_fixed_windows_x64_portable_outputs `
  tests/scripts/test_portable.py
```

生成 artifacts 后，再明确打开真实 Portable 门禁：

```powershell
$env:JIEJIAN_RUN_PORTABLE_PROBE = '1'

.\scripts\dev.ps1 test `
  tests/scripts/test_portable.py::test_real_full_and_nosamples_portables_start_outside_repository `
  -s

Remove-Item Env:JIEJIAN_RUN_PORTABLE_PROBE -ErrorAction SilentlyContinue
```

该测试把两个 ZIP 分别解压到仓库外的中文空格路径，并从另一个 cwd 启动。它必须证明：

- 校验和与 ZIP 真实内容一致；
- full 和 nosamples 都到达 `/ready`，Worker 为 running，Workbench 可见；
- Sample API、页面文案和按钮状态符合两版组成；
- 通过正式 `/api/system/shutdown` 返回，根进程与进程树结束；
- 默认控制端口关闭，ServeLock 和 Worker lifetime lock 释放；
- 临时仓库外目录在成功或失败后都被清理。

这是 Portable 直接验收，不是自动 L5。只有正式发布收口卡明确要求时，才运行完整 `dev.ps1 sample-test`。

## 失败时先查哪里

- `[1/6]` 失败：检查 toolchain distribution、共享 CPython/Playwright 是否存在，以及目标是否仍在 `var/development/release`。
- `[2/6]` 失败：先看 frozen export、包下载和 `TEMP/TMP`；出现 `C:\Windows\.tmp` 表示裁剪环境没有使用任务自有临时目录。
- `[3/6]` 失败：检查非 editable origin、`direct_url.json`、仓库绝对路径、Wheel 内前端和唯一 Chromium。
- `[4/6]` 或 `[5/6]` 失败：检查磁盘空间、目标 ZIP 临时文件和 Sample 输入；不要分别重建两套 Base Tree。
- `[6/6]` 失败：full/nosamples 产品文件已经分叉，先比较非 Sample 路径，不修改校验器掩盖差异。
- Portable ready 但受控 API 返回 403：先确认验收客户端是否使用页面取得的控制会话；不能放宽控制面隔离来迁就无会话测试请求。
- 默认端口已占用：停止并提示用户处理已有程序；不得杀用户进程或自动换端口绕过默认路径。

确认本轮 package/验收进程已经停止后，可以删除 `var/development/release/build` 清理 staging。正常情况下保留 `var/development/tools`、`var/development/cache` 和前端不可变 build，它们是可复用开发工具，不是失败残留。

## 最终检查清单

```text
正式 artifacts 只有 full ZIP、nosamples ZIP、SHA256SUMS 和占位文件
两个 ZIP 只在 samples/ 组成上不同
根 start.cmd 为 ASCII，runtime/start.ps1 保持 Windows PowerShell 5.1 UTF-8 BOM
启动不依赖 PATH、cwd、Git、Conda、uv、Node、pnpm、editable 或网络下载
Python、产品包、依赖和 Chromium 全部属于当前发行根
所有受控子进程继承同一 Portable 身份
full 官方 Sample 可用；nosamples 清楚显示未包含且不削弱其他产品能力
仓库外中文空格路径真实启动、Workbench 和正式 shutdown 通过
端口、进程树和锁完全收口
```
