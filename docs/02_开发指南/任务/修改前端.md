# 修改前端

> 状态：CURRENT。适用于界鉴 Web V1 的路由、产品壳、页面结构、状态投影、API DTO、结果解释、响应式布局、可访问性和编辑器类型解析。

## 前端解决什么问题

界鉴前端把后端已经确认的应用事实和业务边界组织成动作级工作区。`/permissions` 首次建立或持续维护 Business Boundary 与 Permission v2，`/tests` 承载动作准备和受控身份/录制操作；工作台只消费 `WorkspaceView` 与唯一 `PrimaryTask`，不能重算 currentness、优先级或安全结论。

一级导航为当前工作、权限规则、代码变化、检查历史，分别对应 `/workspace`、`/permissions`、`/changes`、`/history`。先在 ControlShell 核对装配：当前工作直接展开服务端 PrimaryTask 指定的任务，自由进入权限规则仍使用同一编辑状态；前端不创建另一套主任务。

`/application`、`/tests` 是具体工作深链；`/changes` 同时保留精确修复引用。当前 `/history` 使用新的有界 CHECK 读模型，不恢复旧 History/ResultPresentation 引擎；旧 `/identities`、`/flows`、`/preparation`、`/validation`、`/results`、`/verification` 不据文件存在恢复旧状态机。

## 先判断谁拥有事实

页面展示一个值之前，先确定它的权威来源。前端只能翻译或组织事实，不能因为页面上“看起来合理”而补推断。

| 页面问题 | 权威来源 | 前端可以做什么 | 前端不能做什么 |
| --- | --- | --- | --- |
| 工作区区域状态与本版主待办 | 后端 `WorkspaceService` | 按 Project、ApplicationUnderstanding、pending Proposal、正式 Boundary、Permission 与实时 implementation inspection 展示区域和唯一 `PrimaryTask` | 从旧 Preparation、Run、mapping count 或页面本地状态伪造 tests ready、check runnable 或 delivery ready |
| Candidate、Actor、Action、Effect 与 Permission | Business Boundary preview/current/proposal API | Candidate 仅作建议；草稿使用业务语言；审批前展示完整摘要 | 从名称自动合并、把 Candidate ID 写入正式语义、在浏览器构造 revision 或审批主体 |
| 动作准备与下一项 | 后端 `PreparationView` 与 `WorkspaceView.primary_task` | 按 action 展示身份、执行、资源、结果证明、恢复及服务端主任务 | 重算 requirement/优先级、调用旧 prepare-safe、自动登录或用齐备状态创建 Run |
| 业务权限与实现定位 | 正式 Business Boundary View 及 Actor/Action binding | 分开显示“业务权限已确认”和 `CURRENT/MISSING/STALE` 代码定位 | 把缺 TestIdentity/Flow 或 binding MISSING 写成权限未确认 |
| 生命周期和执行错误 | Run、Job、ErrorDiagnosis | 区分运行中、完成、失败、安全停止并给恢复入口 | 把执行失败显示成发现漏洞 |
| PASS/BLOCK/INCONCLUSIVE | 后端 Verification 与 `ResultStory` | 原样组织结论和解释 | 根据 HTTP 状态、标签或 Evidence 文本重算 Verdict |
| 当前修复状态 | 后端 `ProjectRepair`、不可变原题合同与复验投影 | 展示七态、精确源 Run/变化/复验入口 | 用 Agent 声明、单次普通结果或修改权限推导修复完成 |
| 计划使用的账号 | 已验证的冻结请求快照 | 显示计划账号名称；技术 ID 只进入 Machine 输出、证据、报告或开发文档 | 把页面选择值说成目标实际识别身份 |
| 目标实际识别的账号 | 独立可信执行或观察事实 | 有事实才显示；当前缺失时明确“无法独立确认” | 用计划身份、subject binding 或角色名称冒充实际身份 |
| 检查记录与原题结果 | 当前 Run 列表、ResultStory 与 ProjectRepair | 按精确 Run 读取已发布结果并关联原题 | 因某次记录缺失就推断问题已解决 |

秘密边界始终成立：密码、Cookie、Token 和 API Key 只通过受控输入与 secret reference 使用，不进入普通 DTO、浏览器持久化、日志、错误正文或 Git。模型服务 API Key 只写入秘密存储，页面不回显。

## 页面怎样组成连续任务

普通页面采用同一结构：

```text
PageTaskHeader
→ 当前任务或阶段说明
→ 后端事实形成的主要内容
→ 必要时提供具体的识别依据或证据入口
→ 需要提交时提供 TaskActionBar
```

`PageTaskHeader` 只放标题、短说明和状态。普通返回、只读刷新放在内容流内，不悬浮；确有提交的长表单才使用粘滞 TaskActionBar，保持表单范围、内容对齐和最后一项可见。刷新不能产生新检查或覆盖输入；有副作用的重新开始需说明后果并明确确认。

RetainedWorkPages 在当前项目会话内保留工作输入、权限草稿、历史筛选和返回位置。导航隐藏工作页时关闭 Evidence Portal；项目切换或明确重试重建。设置与密钥页面不保留，以上工作状态不写 localStorage。

当前工作直接装配 PrimaryTask 指向的权限、应用或 CurrentTestsPage。活动 Run 作为当前上下文；REGISTER_SOURCE_CHANGE 默认说明 Coding Agent 通过 MCP 登记，人工登记放在手动接管。保存登录只证明准备状态，不是实际身份 MATCH。操作成功与权威同步失败分开提示，重试同步不能重复提交。

Business Boundary 编辑页只维护浏览器内草稿。HIGH/MEDIUM Candidate 可预选但不显示技术 ID，LOW 只列为可能项；用户可以明确合并、排除、重命名或手工补充。Effect 使用业务语言映射固定枚举，权限关系使用“自己的资源 / 同权限组另一个账号 / 其他权限组的资源”。提交后 review 页面正文不可编辑；返回修改创建新草稿，Approve 携带服务端 Proposal 的 ID 与 fingerprint，并在成功后刷新 Boundary 和工作区状态。

权限总览使用左侧动作索引与右侧规则摘要，业务结果与实现定位按需展开。已有规则的单条编辑由 `PermissionRuleForm` 保存独立副本，取消不改变草稿；保存只合并该规则，统一审阅时仍提交完整 desired state。业务主体、动作和实现映射在独立业务对象工作面管理。首次建立边界按业务对象、权限规则分开编辑。权限按当前 `BusinessAction` 组织完整句子，分别说明谁操作、资源属于谁、执行什么动作及允许或拒绝的业务结果。切换草稿中的动作时保留其他动作的未提交内容；显式采用 AI 建议只更新草稿。Proposal 审阅展示服务端确认的真实前后差异，仍须由用户显式 Human Approval 才形成正式权限，不能把 AI 采用或草稿切换当作批准。

### 当前检查与结果

`api/currentChecks.ts` 是当前检查客户端。总览只读 `check-preview` 与项目 Run 列表；只有服务端 `can_execute` 才启用开始检查，不能从 Preparation 完成标记推算。显式提交先回读活动 Run 与最新计划指纹，POST 使用格式 2 和同一次请求的幂等键；回执不明时先读记录，重试不生成新键。

选中 Run 后只在活动状态有限刷新，停止、失败或读取异常后不继续轮询；达到自动刷新上限后保留手动刷新入口。显式提交和终态结果读取后刷新服务端 Workspace，使工作台恢复最新主任务；同步失败保留已发布故事并提供独立重试，不在前端猜下一步。只有 `result_integrity=VALID` 且 Story 与所选项目/Run/结论相符时展示安全判断；进度、HTTP 状态与准备材料不能形成结论。

运行中只显示已知阶段、计数和 `progress.current_case` 对应的计划考题；该字段只来自同 Run 经校验的冻结 request/bundle，并可能为空。计划账号、资源所有者及正常对照/拒绝验证不是即时执行证据；发布前的页面响应、后台执行和最终效果仍标为未确认，不能据进度制造逐节点事实或安全结论。

`CurrentResultStory` 默认展示当前 Case 的已发布执行路径和业务事实对照，不要求编号报告布局。复制服务端显式父边，保留 partial 与精度，点击节点读取承载路径的 CheckEvidence 文档；缺 Trace 不补图。计划操作人、资源所有者与独立确认的实际身份分别显示，HTTP 403 保持中性。桌面证据为不挤压画布的 complementary 浮层，优先放在右侧、避开所选事实，窄屏为 dialog，关闭后恢复焦点；来源与定位证据分别回答四问。证据读取或完整性校验失败时，CurrentTestsPage 撤下当前 Run 故事与安全结论，并显示明确错误；未校验内容不能用于新结论。

结果 AI 复用 AssistantPanel，但调用当前 `assistant/result-explanation`；GET 冷读取，用户点击 POST 才生成受限解释。它不修改 Verdict、Breakpoint、精度或证据。当前组件直接测试覆盖提交幂等、指纹漂移、活动 Run 恢复、旧项目响应隔离、完整性失效和证据两次点击路径。

### 动作准备与当前检查的边界

动作准备展示必须消费 GET preparation 的 `PreparationView`，使用 SATISFIED/NEEDS_USER/STALE/BLOCKED/NOT_REQUIRED；下一材料操作只读取 Workspace 的 PrimaryTask。`/tests` 携精确 `task_id` 直达当前缺口，Preparation 只展开这项缺口；完成后重读局部材料与 Workspace，再根据最新主任务续接，不按旧 task_id 或列表顺序自行选择下一项。材料齐备后返回检查总览，由服务端预览确认是否可以执行。旧 ProjectPreparation 的 AUTO、next_item_key、prepare-safe 与“全部 READY 即可运行”不再是当前合同。真实账号按 slot 展示，不写死两个账号；身份和录制写入后先刷新局部事实，再刷新 Workspace。

当前业务边界维护写入成功后先重读当前 Boundary，再调用工作区 `refreshCurrent()`；该方法返回精确的 `{projects, selectedProjectId, workspace}`，页面以服务端的新 Workspace 快照续接。同步失败时保留已成功操作并给出重试提示。TestIdentity 与 Recording 展示同样必须先刷新本地事实，再读取最新 Workspace；不能依赖进入页面前固定好的 `onNext`。

当前 CHECK Worker 已接通，但具体项目仍须满足服务端预览的运行配置与准备条件。OfficialSamplePanel 只控制官方环境的启动、重置、停止及问题版/证据受限版/修复版条件，版本名称不表达预期安全结论。ControlShell 只有在真实活动 experience 的 project_id 精确匹配时，才向普通权限页提供“使用已提供的权限提案”、向普通 Preparation 当前缺口提供“使用已提供的测试材料”。两者只是可选输入：提案仍须普通 Human Approval，材料采用后重读 Preparation/Workspace，不能成为第二套审批或判断。版本切换只登记真实 SourceChange；原题修复携精确引用，经 Changes 的“复验原题”进入普通 `/tests`，由用户显式开始检查。普通应用使用自己的 Candidate、草稿和 Proposal，不能按项目名称猜测 Sample。

当前结果、证据与修复使用普通 CurrentTestsPage、ResultStory、局部 Evidence 区和 Changes/RepairComparison。修复要求按需展开，保留全部合法回归；精确引用链接使用 `/history?run_id=...&case_id=...`。不保留 Sample 专用展示页，也不从预期结果补结论。

## 视觉、布局与响应式约束

检查准备页遇到 `SELECT_ALLOW_CONTROL` 时，展示服务端返回的 DENY 规则和全部同级正常对照；不预选，不按名称或编号打破并列。确认只提交技术绑定与候选指纹，成功后重读准备材料和 Workspace。新演示仅使用主任务指定的操作账号、资源所有者及两个身份槽；页面分别说明“谁执行”和“资源属于谁”，账号不同时要求明确确认测试资源归属。没有当前主任务时不从账号列表猜测组合。

Web V1 使用安静且可核验的原生亮暗双主题。顶部“设置与更多”菜单中的主题入口允许跟随系统、亮色和暗色三种选择；`src/app/ThemeContext.tsx` 只在 `localStorage` 保存这项轻量偏好，并把同一个解析结果同时投影给 Ant Design 和自有 CSS。颜色、间距、字号、圆角、线宽和动画的唯一真源是 `src/shared/ui/tokens.ts`；`app/theme.ts` 映射 Ant Design，ThemeContext 将同一对象投影为 CSS custom properties。全局布局在 styles.css，共享任务排版在 shared/styles/editorial.css。页面功能 CSS 留在对应 feature 内，不依赖浏览器强制反色。

Input 与 Select 必须在暗色下使用独立深色底、可见边框和清楚的禁用文字，而不是只依赖浏览器或 Ant Design 默认反色。结果故事与局部 Evidence 区使用同一主题；独立 Report HTML 不属于当前 GUI 入口。

视觉职责真源见[前端模块](../模块/frontend.md)：中性浅灰/白完整工作面、有限深度和局部深色执行路径，具体尺寸与色值只维护于 tokens.ts。亮暗主题均须有清楚的状态文字、输入边界与焦点，不以颜色代替结论。

- 核心任务使用完整工作面，以标题、留白、分隔、对照和有限深度组织。容器服务于操作边界，不设置全透明或固定卡片数量的普遍规则，也不把每项事实拆成同级卡片。
- 去掉容器边框后阅读顺序仍须清楚。每个视口最多一个主要深证据区域，普通状态与统计不能强行套证据面。
- 字号只从 tokens.ts 读取：正文 15px、次级 13px、标签 12px、节标题 22px、主标题 26～34px。颜色、尺度和动画从统一 token 获取，feature CSS 不另写十六进制颜色。
- 桌面导航 200px、顶部 60px、窄屏摘要 52px、内容最大 1460px；三视口与亮暗主题共用 tokens.ts。窄屏保留证据 Drawer 和焦点恢复；普通返回与刷新保持内容流，主提交才在表单内粘滞。
- 输入控件在亮暗主题下均保持可辨底色、边框、禁用文字和键盘焦点。长中文、ID 与路径必须换行或进入受控技术区域；不允许意外横向滚动。
- 动效只表达状态，使用统一 180ms token 并保持 prefers-reduced-motion 等价；进度不能提前表达安全成功。

AI 工具连接页也遵循“主结论 + 一个当前任务表面”的层级，不把不同客户端做成并列卡片墙。页面第一屏先说明当前是否真正连接以及下一步，只用一行选择器切换 Codex、TRAE、Qoder、CodeBuddy 和 DSH；下方固定使用五步新手向导：“选择工具 → 准备本机连接 → 添加 jiejian → 保存凭据 → 重启并检查”。每步必须说明打开哪里、复制什么、粘贴到哪里和完成标志，不展示原始配置面板、命令行备选或协议术语。配置创建、配置复制、Bearer 通过和 initialize 完成仍是后端不同事实；普通页面统一翻译为“界鉴已准备、凭据已通过、连接成功”，只有 `connection_state=CONNECTED` 才显示客户端名称、最近活动和逐应用允许范围。连接成功后的日常说明固定为“任务开始读取基线 → 完成整个用户任务后一次登记整批变化 → 界鉴核对影响并安排复验”，不能暗示每次保存或单个文件修改都要调用界鉴。

普通页面不显示 READ、PREPARE、EXECUTE 等内部 level 名称，统一翻译为“只查看、协助整理、执行已确认任务”。调整入口使用“这次允许 AI 工具做到哪一步”，逐项说明能做什么和不能做什么；连接凭据可以长期保留，但超过只查看的范围仅在本次打开界鉴期间有效。需要把 Bearer 写入请求头的客户端仍必须把无秘密配置骨架与凭据复制分开，并明确本地保存风险。

AI 辅助设置只提供一个默认模型连接，普通用户只选择供应商、填写一次性 API Key、读取可用模型并保存。Profile 名称、兼容服务地址、secret reference、预算、超时、字节限制、本机 HTTP 开关和推理强度不进入普通界面；后端 Profile 仍作为持久化和供应商适配边界存在。

新增或重排页面时，不能只看单一截图。先以 2560×1440 分别核对亮色和暗色的现场展示密度，再同时检查约 1280px 和 600px：标题是否换行、双列表单是否变单列、底部动作是否在滚动中持续可触达、弹层焦点是否正确、是否出现横向溢出。

## 展示用语标准

界面使用“专业、直接、以业务事实为中心”的书面表达：普通用户不需要先理解系统内部模块，评委也能从页面直接看到规则、身份、响应、真实后果和结论。正式但不官样，不使用“搞定了”“一键封神”等过度口语或营销表达。

用语分三层：

1. 主界面先用业务主体、动作、资源、状态和下一项可执行任务，例如“Bob 不得导出完整项目交付包”“后台任务已创建”“还需准备 Bob 的测试账号”。
2. 证据详情在用户主动展开后使用必要技术词，例如 HTTP 403、后台任务、消息、ZIP、Evidence；每个技术词都必须同时说明它证明什么，不能用术语代替结论。
3. Machine、报告和开发文档保留 `ALLOW/DENY`、Verdict、revision、policy epoch、ID、Schema 与 reason code；普通页面翻译为“允许/拒绝”“检查结论”“权限规则版本”，不直接堆叠内部字段。

结果页面和展示模式必须复用同一条事实链：“人确认的权限规则 → 目标实际识别的账号 → 页面或接口回应 → 后台真实后果 → 正式结论”。403 只表示表面请求被拒绝，不能使用代表安全的绿色，也不能替代真实业务后果。状态色固定为蓝色信息、红色问题、绿色已由证据确认符合规则、黄色证据或准备不足、灰色尚无事实；颜色之外必须有文字结论。

## 修改 API DTO 和页面状态

`src/api/` 只描述当前 loopback HTTP 合同并调用统一 `request`。不要在多个页面手写同一响应结构，也不要为了让旧页面继续编译保留后端已经不存在的状态别名。

正常步骤：

1. 先核对后端实际返回模型、稳定错误码和缺失值语义。
2. 在唯一 API 文件更新 DTO 与调用函数；字段可选性必须与真实协议一致。
3. 在页面中区分加载、空状态、可用状态、失败和陈旧请求。
4. 异步请求使用失效标记或等价机制，旧响应不能覆盖新的项目、Run 或选择。
5. 诊断跳转使用后端返回的结构化 route；不能按错误码或错误文字用正则猜页面。
6. 同步更新直接页面测试和 `ControlShell` 闭环测试。

前端本地状态只保存当前会话的交互。完成态、最近可信 Run、权限缺口与历史可用性必须回读服务端。有界回读 Workspace/MCP/Run 时，连接与授权不等于活动工作，结束不自动导航；短检查可通过新 latest_result 的精确 Run 确认完成，首次加载历史结果不发新通知。localStorage 仅用于明确允许的轻量偏好，不存工作草稿或秘密。

## 修改权限与测试内部任务

权限写入只通过当前 BusinessBoundaryPage 的 Proposal 审阅与 Human Approval；旧 checks 页面及其客户端已删除，旧 URL 只显示不可用，不形成兼容执行路径。

当前边界页至少验证：无正式边界时可从 Candidate 或手工内容形成草稿；Proposal review 不可原地编辑；返回修改最终 POST 新 Proposal；Approve 后刷新为正式 Actor/Action/Effect/Permission；DENY without ALLOW 显示“权限已确认，还需完整允许对照”；允许对照存在时不使用旧合同完整度占位字段描述当前检查是否可用；没有 TestIdentity/Flow 时仍显示业务权限已确认；官方合同形成两个 Actor、两个 Action 和三条 Permission。

## 前端依赖和编辑器解析

正式源码位于 `product/frontend`，但项目不在该目录生成 `node_modules`。`scripts/dev.ps1` 把依赖视图建立在：

```text
var/development/frontend/workspace
```

生产静态资源进入 `var/runtime/frontend`。使用仓库根的 `jiejian.code-workspace`；执行一次 `prepare -ForcePrepare` 后，工作区 TypeScript 插件会只读解析受控依赖。出现 `react`、`antd`、`vitest` 或 `@testing-library/react` 红线时，先确认受控工作区存在、允许使用工作区 TypeScript，再执行 “TypeScript: Restart TS Server”。不要在源码目录运行 `pnpm install`，也不要用手写模块声明掩盖依赖解析问题。

编辑器解析探针 `scripts/editor/verify-controlled-workspace-resolver.cjs` 使用当前 `features/testing/CheckHistoryPage.tsx` 及其测试作为真实样本；样本存在性由脚本直接门禁保护，不固定已淘汰页名。

## 测试、构建和真实页面验证

所有命令从仓库根运行。完整前端测试：

```powershell
.\scripts\dev.ps1 frontend-test
```

定向测试参数会原样传给受控前端工作区中的 Vitest，因此路径必须以该工作区为基准，使用 `src/...`，不能写仓库根形式的 `product/frontend/src/...`：

```powershell
.\scripts\dev.ps1 frontend-test src/features/testing/CurrentResultStory.test.tsx
```

生产 TS/TSX 或构建输入变化还要运行：

```powershell
.\scripts\dev.ps1 prepare -ForcePrepare
```

它同时完成 TypeScript 检查和 Vite production build。依赖、缓存和产物只能位于 `var/`；完成后确认源码树没有 `node_modules`、`dist`、`coverage` 或 `*.tsbuildinfo`。

自动化测试至少覆盖：权威 DTO 输入、加载/空/失败状态、陈旧响应隔离、关键按钮门禁、结构化错误恢复、键盘可访问名称和跨页面主流程。不要用快照替代“点击后到了哪里、使用了哪项后端事实”的行为断言。

重要视觉或持续流程变化需要 `dev.ps1 sample-test` 的唯一自动 L5 技术闭环和主线程展示验收；具体顺序服从已接受的任务验证合同。展示验收核对 2560×1440 主展示、1280px 桌面和 600px 窄屏、应用切换、区域状态、主待办引用、全部待办仍可到达、刷新与重置差异、错误恢复、键盘/焦点、安全退出，以及比赛演示节奏和当前修改直接涉及的真实业务状态；不要为了准备展示清空用户数据。

自动 L5 从真实 `start.cmd` 启动隔离实例，Recording headed Chromium 由正式独立 Recording Process 创建，并由 Windows UI Automation 按 accessible role/name 与 InvokePattern 操作。展示验收可以使用本轮正常产品窗口检查桌面与 600px，截图和横向溢出等度量写入 `var/audit/<任务>/`，不签入 Git。Codex 内置浏览器或用户 Chrome 只用于必须复用已有登录态、扩展或用户浏览器会话的临时检查，不能替代自动 L5。

官方 Sample 页面变化必须保留普通业务语言和正常可访问性。Recording 所需动作应使用真实 `<button>` 和稳定 accessible name，优先修正页面可访问性，不能给生产页面增加测试按钮、隐藏控制接口、remote debugging 或地址栏脚本旁路。

## 常见失败怎样定位

- `No test files found`：先看定向参数是否误写成 `product/frontend/src/...`；受控工作区只接受 `src/...`。
- TypeScript 报大量第三方模块不存在：先修复受控依赖工作区或 VS Code 解析，不要新增假的声明文件。
- 页面显示完成但 Workspace 不允许下一步：核对后端 PreparationView、PrimaryTask 和页面所选项目，不要用 route 或本地 state 强行改成完成。
- 旧请求覆盖新页面：检查 effect 清理、项目/Run 依赖和 active/abort 边界。
- 页面同时出现顶部、Card 右上角和底部多个主操作：把普通操作收敛到 `TaskActionBar`，页头只留状态。
- 桌面正常但 600px 横向滚动：检查固定宽度、grid 最小列宽、长 ID、Select popup、表格和嵌套 Card，不要只加全局 `overflow: hidden` 掩盖内容越界。
- PASS/BLOCK/INCONCLUSIVE 与证据文字冲突：停止前端修补，回查 ResultStory 和发布事实；页面不能自行选择其中一个。
