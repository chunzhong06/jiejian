# 修改前端

> 状态：CURRENT。适用于界鉴 Web V1 的路由、产品壳、页面结构、状态投影、API DTO、结果解释、响应式布局、可访问性和编辑器类型解析。

## 前端解决什么问题

界鉴前端把后端已经确认的应用事实、Agent 代码变化、权限规则、测试准备、执行状态和安全结果组织成可长期使用的持续验证工作区。它负责让用户知道“当前基线是什么、哪些变化需要处理、哪些区域可用、发生了什么”，但不是第二套业务或安全真源，也不把应用的一次接入保存成线性向导进度。

正式 Web V1 只有以下普通路由：

```text
/workspace     项目概览
/application   应用接入与理解
/changes       Agent 变化与待办
/permissions   权限规则
/preparation   测试准备总览
/identities    测试账号明细
/flows         业务流程明细
/validation    验证运行
/results       检查结果
/verification  现场验证
/history       历史变化
```

路由使用 `HashRouter`；未知路径回到 `/workspace`。旧 `/apps/*`、`/checks/*` 和基于 URL 参数切换报告的路径不是兼容入口。完整报告是 `/results` 内部视图。

## 先判断谁拥有事实

页面展示一个值之前，先确定它的权威来源。前端只能翻译或组织事实，不能因为页面上“看起来合理”而补推断。

| 页面问题 | 权威来源 | 前端可以做什么 | 前端不能做什么 |
| --- | --- | --- | --- |
| 工作区区域状态、全部待办、最近 Agent 变化与最近结果 | 后端 `ProductStatus` | 并列展示可用、需处理、运行中、已有结果或暂无数据 | 生成唯一下一步，或根据当前 URL 猜项目已完成 |
| 应用、角色、动作、账号和流程 | 对应后端只读/治理 API | 用任务语言展示、收集明确确认 | 从名称自动推导权限规则 |
| 测试准备清单与下一项 | 后端 `ProjectPreparation` | 展示四态清单；按 `next_item_key` 和 `next_path` 调用 prepare-safe 或进入现有人工页面 | 解析 permission gap、生成另一套优先级、自动登录/录制/确认候选 |
| 权限要求与本次可执行范围 | PermissionIntent matrix/proposal、CheckPreview | 预览 Human Approval、审阅 Agent 建议、展示缺口与提交门禁 | 在浏览器构造 revision、批准 Agent 建议或绕过旧 preview 失效 |
| 生命周期和执行错误 | Run、Job、ErrorDiagnosis | 区分运行中、完成、失败、安全停止并给恢复入口 | 把执行失败显示成发现漏洞 |
| PASS/BLOCK/INCONCLUSIVE | 后端 Verification 与 `ResultPresentation` | 原样组织结论和解释 | 根据 HTTP 状态、标签或 Evidence 文本重算 Verdict |
| 计划使用的账号 | 已验证的冻结请求快照 | 显示计划账号名称；技术 ID 只进入 Machine 输出、证据、报告或开发文档 | 把页面选择值说成目标实际识别身份 |
| 目标实际识别的账号 | 独立可信执行或观察事实 | 有事实才显示；当前缺失时明确“无法独立确认” | 用计划身份、subject binding 或角色名称冒充实际身份 |
| 历史变化 | 后端 `HistoryView` | 展示新发现、仍存在、已解决、证据不足、本次未覆盖 | 因某次记录缺失就推断问题已解决 |

秘密边界始终成立：密码、Cookie、Token 和 API Key 只通过受控输入与 secret reference 使用，不进入普通 DTO、浏览器持久化、日志、错误正文或 Git。模型服务 API Key 只写入秘密存储，页面不回显。

## 页面怎样组成连续任务

普通页面采用同一结构：

```text
PageTaskHeader
→ 当前任务或阶段说明
→ 后端事实形成的主要内容
→ 必要时提供具体的识别依据或证据入口
→ TaskActionBar
```

`PageTaskHeader` 只放标题、短说明和短状态，不放刷新或主操作。`TaskActionBar` 位于页面底部，按统一顺序承载：返回相关区域、只读刷新、必要时重新开始当前任务、当前主动作。刷新不能产生新的检查或覆盖用户输入；有副作用的重新开始必须说明会清除或重建什么，并要求明确确认。

长期工作区固定为“项目概览、变化与待办、权限规则、测试准备、验证运行、结果与历史”六个并列区域。应用接入、测试账号、业务流程、现场验证和历史是这些区域下的具体任务页。Agent 每次提交代码变化后，SourceChange 与 ProductStatus 重新给出受影响权限、准备缺口和待重验基线；用户不必删除应用或重新走一遍接入。权限规则页只处理 Human Approval 与 Agent proposal；验证运行页只处理检查条件、范围、进度和结果入口，二者共享同一后端事实而不混成一次性向导。

测试准备页直接消费 `ProjectPreparation` 的 IDENTITY/FLOW/RESOURCE/OBSERVATION/RECOVERY/EFFECT/PROFILE 清单和 READY/AUTO/USER/BLOCKED 四态，只保留一个“继续准备”主操作。AUTO 调用 prepare-safe 后刷新整个工作区；USER 和 external blocker 按后端路径进入现有详细页；BLOCKED 只显示原因和建议；全部 READY 才进入验证运行。页面不显示 candidate ID、fingerprint、Profile ID 或 reason code，也不在 React Context/localStorage 保存完成态。

官方示例仍通过这套正式步骤准备和检查。工作台只提供“启动官方示例”与“进入展示模式”两个不同动作：前者建立真实本机 Sample 和产品上下文，后者只重排当前正式 Run、Evidence、ResultPresentation 与权限版本。展示模式不是普通业务路由，不显示七步准备导航，不创建新 Run、Verdict 或预置结果；退出后回到进入前的正式产品上下文。

展示模式四页各自保持单一任务：项目结论只压缩权限、表面响应、真实后果与当次数字；现场验证读取 ResultPresentation、Trace、ClaimBoundary 和 EvidenceExplanation；修复前后读取当前与源 Run 的 RepairVerification，缺少独立非回归事实时必须显示“尚未证明”；数据与边界只读取 `sample-test` 成功后发布的净化 validation 汇总，并明确它不是当前产品 Run。页面不得从 Trace semantic key、旧竞赛材料或 private oracle 补结论、审批、关联、修复成功或验证数字。

## 视觉、布局与响应式约束

Web V1 使用浅色、安静且可核验的产品视觉。全局语义色和 Ant Design token 在 `src/app/theme.ts`，CSS 变量与产品壳布局在 `src/styles.css`。页面功能 CSS 留在对应 feature 内。

当前基础色：页面背景 `#F6F8FB`、表面 `#FFFFFF`、主文字 `#172033`、次文字 `#667085`、弱边框 `#E4E7EC`、主操作 `#3659D9`、安全 `#188765`、警告 `#B87512`、危险 `#C83C3C`、AI 辅助 `#7556D9`。颜色只能辅助状态，文字、图标或结构必须同时表达含义。

布局遵循以下规则：

- 2560×1440 是现场展示和录制的主基准；产品壳主内容最大宽度约 1760px，长说明和表单仍保持可读行长，不把宽屏变成长行文本。
- 桌面页面一级区块间距使用 24px；600px 窄屏收敛为 16px，页面边距进一步收敛但不能出现横向滚动。
- 同一任务内的标题、说明和控件靠近；不同任务单元用间距或边框分开。不要用空白把同组内容推到两端，也不要把不相关操作挤在一起。
- `Card` 只表示真正独立的信息单元，避免 `Card` 套 `Card`。普通字段表不能作为页面主叙事；用户先看到“发生了什么和下一步”。技术字段不进入普通任务页，也不使用通用“高级信息”收纳；确有产品价值时提供范围明确的只读入口，例如“查看证据”。
- 桌面显示长期工作区区域侧栏；600px 使用当前区域摘要和 Drawer。Drawer 打开后焦点进入当前区域，关闭后回到触发按钮。
- 控件字号由主题统一，Select、Input 和 Button 不在页面内单独放大。长 ID、路径和 JSON 必须换行或在受控区域滚动。

新增或重排页面时，不能只看单一截图。先以 2560×1440 核对现场展示密度，再同时检查约 1280px 和 600px：标题是否换行、双列表单是否变单列、底部动作是否可触达、弹层焦点是否正确、是否出现横向溢出。

## 展示用语标准

界面使用“专业、直接、以业务事实为中心”的书面表达：普通用户不需要先理解系统内部模块，评委也能从页面直接看到规则、身份、响应、真实后果和结论。正式但不官样，不使用“搞定了”“一键封神”等过度口语或营销表达。

用语分三层：

1. 主界面先用业务主体、动作、资源、状态和下一项可执行任务，例如“Bob 不得导出完整项目交付包”“后台任务已创建”“还需准备 Bob 的测试账号”。
2. 证据详情在用户主动展开后使用必要技术词，例如 HTTP 403、后台任务、消息、ZIP、Evidence；每个技术词都必须同时说明它证明什么，不能用术语代替结论。
3. Machine、报告和开发文档保留 `ALLOW/DENY`、Verdict、revision、policy epoch、ID、Schema 与 reason code；普通页面翻译为“允许/拒绝”“检查结论”“权限规则版本”，不直接堆叠内部字段。

结果页面和展示模式必须复用同一条事实链：“人确认的权限规则 → 目标实际识别的账号 → 页面或接口回应 → 后台真实后果 → 正式结论”。403 只表示表面请求被拒绝，不能使用代表安全的绿色，也不能替代真实业务后果。状态色固定为蓝色信息、红色问题、绿色已由证据确认符合规则、黄色证据或准备不足、灰色尚无事实；颜色之外必须有文字结论。

## 修改 API DTO 和页面状态

`src/api/` 只描述当前 loopback HTTP 合同并调用统一 `request`。不要在多个页面手写同一响应结构，也不要为了让旧页面继续编译保留后端已经不存在的状态别名。

正常步骤：

1. 先核对后端实际返回模型、稳定错误码和缺失值语义。
2. 在唯一 API 文件更新 DTO 与调用函数；字段可选性必须与真实协议一致。
3. 在页面中区分加载、空状态、可用状态、失败和陈旧请求。
4. 异步请求使用失效标记或等价机制，旧响应不能覆盖新的项目、Run 或选择。
5. 诊断跳转使用后端返回的结构化 route；不能按错误码或错误文字用正则猜页面。
6. 同步更新直接页面测试和 `ControlShell` 闭环测试。

前端本地状态只保存临时交互，例如当前 tab、筛选器、Drawer 开关和用户尚未提交的输入。应用完成状态、最近可信 Run、权限缺口和历史可用性必须重新从后端读取。`localStorage` 只能保存允许的轻量选择；陈旧项目必须经过后端项目列表校验后清除。

## 修改权限规则与验证运行

`PermissionCheckPage` 复用同一事实读取，但通过 `mode="permissions"` 和 `mode="validation"` 分成两个用户任务：

```text
权限规则：确认 Human Approval / 审阅 Agent proposal
验证运行：准备检查条件 → 核对本次范围 → 开始检查 → 查看进度与结果
```

权限 cell 变化先打开确认 Modal，展示当前值、目标值、受保护业务后果和权限版本影响；取消不调用 API，只有“确认权限变更”才进入服务端 Human Approval。Agent proposal 只显示当前值、建议、原因和批准/拒绝，前端不构造 revision；Matrix、proposal 和 CheckPreview 都必须从后端刷新。页面任何时刻只显示一个由当前 matrix/proposal/gap 事实选择的 AssistantPanel。

权限保存、proposal 批准或重新准备后，旧 CheckPreview 必须失效；新 preview 返回且与当前权限规则版本一致前，不能提交检查。检查条件只通过 `/check-preparation` 形成，不保留旧直接 compile 入口。取消当前检查和重新检查属于有副作用动作，必须使用现有后端动作并明确后果。只读刷新只重新读取状态，不产生新的 Run。

修改这条链时同时核对：权限矩阵、保存门禁、prepare、preview、submit、活动 Run、终态 Run、取消/重试和底部动作。通过一个局部组件测试不能证明整条链仍成立。

## 修改结果、证据和历史

`ResultPresentation` 是唯一人类结果表达；`report.json` 仍是机器语义真源，HTML/SARIF/JUnit 是投影。结果页不重新读取原始字段来发明另一套结论。

普通结果和展示模式通过共享 `ResultFactChain` 按固定顺序展示：

```text
原本应该怎样
→ 计划使用的账号
→ 目标实际识别的账号或“无法独立确认”
→ 页面或接口怎样回应
→ 真实资源发生了什么
→ 最终结论以及为什么
```

Evidence 只展开已发布事实，统一使用“已发现、未发现、无法确认”的语言。HTTP 403 与真实资源变化必须仍能清楚同时出现，且结论保持后端 `BLOCK`；观察不足必须保持 `INCONCLUSIVE`。技术 ID、Occurrence、Evidence ref、reason code 和原始 JSON 不进入普通页面，只保留在 Machine、Evidence 或 Report 等正式技术交付物中。

每个结果故事还直接消费 `evidence_sources`，按“目标业务状态、只读数据库、结构化审计记录、后台任务、消息通道、最终对象/文件”展示当前实际接入来源。普通视图把 `KEY/SUPPORTING` 翻译为“关键来源/佐证来源”，把 `FOUND/NOT_FOUND/UNAVAILABLE` 翻译为“已发现/未发现/无法确认”；前端不得按来源数量、颜色或文案重算 Verdict。

结果页和每条历史变化都显示冻结的“本次检查依据权限版本 X”；策略 fingerprint、intent ID、revision 和 intent hash 不进入普通页面。历史页不复制结果故事，只展示问题相对前次的变化。`NOT_COVERED` 不能显示为已解决；“已解决”必须来自后端对同一权限要求取得充分安全证据。

进入结果页或历史页时必须重新读取当前项目的权威 Run 状态。前端工作区中的完成态只用于当前交互反馈，不能长期替代服务端最新 Run；否则自动检查已经推进到新三态结果时，页面仍可能展示旧运行。API Evidence 列表是发布索引，Evidence detail 才是完整六来源文档，页面和测试不得把这两层 DTO 混成同一种结构。

结果相关变化还要阅读[修改结果与报告](修改结果与报告.md)、[修改官方示例与整链验收](修改官方示例与整链验收.md)、[权限验证与结果](../../01_系统地图/权限验证与结果.md)和[报告与格式投影协议](../../03_参考手册/协议/报告与格式投影协议.md)。

## 前端依赖和编辑器解析

正式源码位于 `product/frontend`，但项目不在该目录生成 `node_modules`。`scripts/dev.ps1` 把依赖视图建立在：

```text
var/development/frontend/workspace
```

生产静态资源进入 `var/runtime/frontend`。使用仓库根的 `jiejian.code-workspace`；执行一次 `prepare -ForcePrepare` 后，工作区 TypeScript 插件会只读解析受控依赖。出现 `react`、`antd`、`vitest` 或 `@testing-library/react` 红线时，先确认受控工作区存在、允许使用工作区 TypeScript，再执行 “TypeScript: Restart TS Server”。不要在源码目录运行 `pnpm install`，也不要用手写模块声明掩盖依赖解析问题。

## 测试、构建和真实页面验证

所有命令从仓库根运行。完整前端测试：

```powershell
.\scripts\dev.ps1 frontend-test
```

定向测试参数会原样传给受控前端工作区中的 Vitest，因此路径必须以该工作区为基准，使用 `src/...`，不能写仓库根形式的 `product/frontend/src/...`：

```powershell
.\scripts\dev.ps1 frontend-test src/features/checks/CheckResultsPage.test.tsx
```

生产 TS/TSX 或构建输入变化还要运行：

```powershell
.\scripts\dev.ps1 prepare -ForcePrepare
```

它同时完成 TypeScript 检查和 Vite production build。依赖、缓存和产物只能位于 `var/`；完成后确认源码树没有 `node_modules`、`dist`、`coverage` 或 `*.tsbuildinfo`。

自动化测试至少覆盖：权威 DTO 输入、加载/空/失败状态、陈旧响应隔离、关键按钮门禁、结构化错误恢复、键盘可访问名称和跨页面主流程。不要用快照替代“点击后到了哪里、使用了哪项后端事实”的行为断言。

重要视觉或持续流程变化先由 `dev.ps1 sample-test` 完成唯一自动 L5 技术闭环，再做展示验收。展示验收核对 2560×1440 主展示、1280px 桌面和 600px 窄屏、应用切换、区域状态、全部待办、刷新与重置差异、错误恢复、键盘/焦点、安全退出，以及比赛演示节奏和当前修改直接涉及的真实业务状态；不要为了准备展示清空用户数据。

自动 L5 从真实 `start.cmd` 启动隔离实例，Recording headed Chromium 由正式独立 Recording Process 创建，并由 Windows UI Automation 按 accessible role/name 与 InvokePattern 操作。展示验收可以使用本轮正常产品窗口检查桌面与 600px，截图和横向溢出等度量写入 `var/audit/<任务>/`，不签入 Git。Codex 内置浏览器或用户 Chrome 只用于必须复用已有登录态、扩展或用户浏览器会话的临时检查，不能替代自动 L5。

官方 Sample 页面变化必须保留普通业务语言和正常可访问性。Recording 所需动作应使用真实 `<button>` 和稳定 accessible name，优先修正页面可访问性，不能给生产页面增加测试按钮、隐藏控制接口、remote debugging 或地址栏脚本旁路。

## 常见失败怎样定位

- `No test files found`：先看定向参数是否误写成 `product/frontend/src/...`；受控工作区只接受 `src/...`。
- TypeScript 报大量第三方模块不存在：先修复受控依赖工作区或 VS Code 解析，不要新增假的声明文件。
- 页面显示完成但 Readiness 不允许下一步：核对后端 readiness 和页面所选项目，不要用 route 或本地 state 强行改成完成。
- 旧请求覆盖新页面：检查 effect 清理、项目/Run 依赖和 active/abort 边界。
- 页面同时出现顶部、Card 右上角和底部多个主操作：把普通操作收敛到 `TaskActionBar`，页头只留状态。
- 桌面正常但 600px 横向滚动：检查固定宽度、grid 最小列宽、长 ID、Select popup、表格和嵌套 Card，不要只加全局 `overflow: hidden` 掩盖内容越界。
- PASS/BLOCK/INCONCLUSIVE 与证据文字冲突：停止前端修补，回查 ResultPresentation 和发布事实；页面不能自行选择其中一个。

## 最终检查清单

前端变化至少确认：

```text
正式路由和持续工作区没有恢复旧 `/check`、直接 compile 或线性步骤 alias

刷新没有副作用，重置和重试明确说明后果
结果没有重算 Verdict，计划身份没有冒充实际身份
桌面与 600px 没有横向溢出，键盘和焦点可用
直接前端测试、必要的 ControlShell 闭环和 production build 通过
依赖、缓存和生成物只进入 var/
```
