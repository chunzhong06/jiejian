# 修改前端

> 状态：CURRENT。适用于界鉴 Web V1 的路由、产品壳、页面结构、状态投影、API DTO、结果解释、响应式布局、可访问性和编辑器类型解析。

## 前端解决什么问题

界鉴前端把后端已经确认的应用事实、Agent 代码变化、权限规则、测试准备、执行状态和安全结果组织成可长期使用的持续验证工作区。它负责让用户知道“当前基线是什么、哪些变化需要处理、哪些区域可用、发生了什么”，但不是第二套业务或安全真源，也不把应用的一次接入保存成线性向导进度。

正式 Web V1 使用一个主控工作台和三个当前专项工作模块。产品语义上它们是辅助区域，界面分组名称统一使用“专项工作”，避免把工作台误读为四个同级模块之一：

```text
/workspace     主控工作台
/changes       辅助模块：变化
/permissions   辅助模块：权限
/tests         辅助模块：测试
```

`/application` 是工作台内的接入任务；`/identities` 与 `/flows` 是权限模块内的账号和业务流程任务；`/preparation`、`/validation`、`/results`、`/verification` 与 `/history` 是测试模块内的条件、运行、结果和证据任务。这些详细路由不作为并列产品模块，也不进入主导航。辅助模块不是固定数量；只有形成独立、高频、可持续处理的业务职责时才新增，设置、AI 工具和诊断仍留在全局工具层。路由使用 `HashRouter`；未知路径回到 `/workspace`。旧 `/apps/*`、`/checks/*` 和基于 URL 参数切换报告的路径不是兼容入口。完整报告是 `/results` 内部视图。

## 先判断谁拥有事实

页面展示一个值之前，先确定它的权威来源。前端只能翻译或组织事实，不能因为页面上“看起来合理”而补推断。

| 页面问题 | 权威来源 | 前端可以做什么 | 前端不能做什么 |
| --- | --- | --- | --- |
| 工作区区域状态、全部待办、当前主待办、最近 Agent 变化、项目修复与最近结果 | 后端 `ProductStatus` 中的 `primary_attention_key`、`ProjectRevalidation`、`ProjectRepair` | 用显式 key 突出一项主任务；长期区域继续并列展示可用、需处理、运行中、已有结果或暂无数据 | 根据待办数组位置、mapping count、Sample repair ID、历史结果或变化列表位置重算优先级、变化或修复状态 |
| 应用、角色、动作、账号和流程 | 对应后端只读/治理 API | 用任务语言展示、收集明确确认 | 从名称自动推导权限规则 |
| 测试准备清单与下一项 | 后端 `ProjectPreparation` | 展示四态清单；item 查询只判断 AUTO，文案和路由使用顶层 `next_label/next_path` | 解析 permission gap、回退读取 item 路由、生成另一套优先级、自动登录/录制/确认候选 |
| 权限要求与本次可执行范围 | PermissionDraft、PermissionIntent matrix/proposal、CheckPreview | 消费 `can_confirm`、`requires_human_confirmation`、`confirmation_blockers` 与顶层阻断确认数；在明确点击后显示不生效草稿并执行 Human Approval | 把全部可确认 cell 总数当成必选数、读取 `review_reasons` 猜按钮状态、在浏览器构造 revision 或绕过失效 preview |
| 生命周期和执行错误 | Run、Job、ErrorDiagnosis | 区分运行中、完成、失败、安全停止并给恢复入口 | 把执行失败显示成发现漏洞 |
| PASS/BLOCK/INCONCLUSIVE | 后端 Verification 与 `ResultPresentation` | 原样组织结论和解释 | 根据 HTTP 状态、标签或 Evidence 文本重算 Verdict |
| 最新证据不足后的下一步 | 后端 `ProductStatus.inconclusive_recovery` | 显示旧结论永久保留，并用唯一按钮导航到服务端给出的现有路由 | 比较 intent、准备度或 reason code 自行选择路由；点击后自动 prepare、submit 或创建 Run |
| 当前修复状态 | 后端 `ProductStatus.repair` | 展示修复要求、状态与服务端续接按钮；READY_TO_VERIFY 时进入正式验证 | 用 Sample repair ID、Agent 声明或普通结果推导修复完成；增加“发送给 Agent”假动作 |
| 当前是否可以交付 | 后端 `DeliveryCheck` | 用户点击工作台按钮后显示本次现场结论和后端下一步 | 页面加载自动检查、缓存结论或从 ProductStatus/结果卡片重算 |
| 计划使用的账号 | 已验证的冻结请求快照 | 显示计划账号名称；技术 ID 只进入 Machine 输出、证据、报告或开发文档 | 把页面选择值说成目标实际识别身份 |
| 目标实际识别的账号 | 独立可信执行或观察事实 | 有事实才显示；当前缺失时明确“无法独立确认” | 用计划身份、subject binding 或角色名称冒充实际身份 |
| 历史变化 | 后端 `HistoryView` | 展示新发现、仍存在、已解决、证据不足、本次未覆盖 | 因某次记录缺失就推断问题已解决 |

秘密边界始终成立：密码、Cookie、Token 和 API Key 只通过受控输入与 secret reference 使用，不进入普通 DTO、浏览器持久化、日志、错误正文或 Git。模型服务 API Key 只写入秘密存储，页面不回显。

## 页面怎样组成连续任务

普通页面采用同一结构：

```text
PageTaskHeader
→ 当前任务或阶段说明
→ 后端事实形成的主要内容
→ 必要时提供具体的识别依据或证据入口
→ TaskActionBar
```

`PageTaskHeader` 只放标题、短说明和短状态，不放刷新或主操作。`TaskActionBar` 位于页面底部，按统一顺序承载：返回相关区域、只读刷新、必要时重新开始当前任务、当前主动作。动作栏本身承担粘滞定位，不能依赖外层恰好存在的 Ant `Space` 包装；权限与验证运行等直接 Grid 页面在长内容滚动时也必须保持操作可见。刷新不能产生新的检查或覆盖用户输入；有副作用的重新开始必须说明会清除或重建什么，并要求明确确认。

长页面的 `TaskActionBar` 在内容框架内粘滞于底部，不固定到浏览器右下角，也不脱离 1440px 内容对齐线。它使用带轻度模糊和浮层阴影的控制层材质，不能遮住页面最后一项内容；窄屏收敛为整行操作组。

长期工作区以工作台为唯一主控，变化、权限、测试是当前三个辅助模块，不与工作台同级。产品壳必须把工作台作为带独立主色和说明的单独入口，三个辅助模块统一收在“专项工作”分组内。工作台首屏展示当前应用、后端 `primary_attention_key` 指定的一项当前判断与主任务、最近可信结果，再摘要专项工作的状态和入口；其余待办留在对应模块，交付前检查和最近事实属于次级内容。变化模块核对 Agent 声明、真实源码差异、受影响权限和修复状态；权限模块维护权限规则、测试账号与业务流程；测试模块并列汇总测试条件、运行检查、结果与历史，三者可自由进入，不组成一次性向导。Agent 每次提交代码变化后，SourceChange inspection 与 ProjectRevalidation 重新给出映射审阅、准备、可重验、已验证或失效状态；用户不必删除应用或重新接入。

测试准备页直接消费 `ProjectPreparation` 的 IDENTITY/FLOW/RESOURCE/OBSERVATION/RECOVERY/EFFECT/PROFILE 清单和 READY/AUTO/USER/BLOCKED 四态，只保留一个“继续准备”主操作。页面用 `next_item_key` 找到顶层下一项，仅据此判断 AUTO；按钮名称与路由始终取顶层 `next_label/next_path`。AUTO 调用 prepare-safe 后刷新整个工作区；USER 和 external blocker 按顶层路径进入现有详细页；BLOCKED 只显示原因和建议；全部 READY 才进入验证运行。页面不显示 candidate ID、fingerprint、Profile ID 或 reason code，也不在 React Context/localStorage 保存完成态。

测试账号、业务流程和权限规则等详细页不能接收进入页面前固定好的 `onNext`。写入成功后先重读本页事实，再调用工作区 `refreshCurrent()`；该方法返回精确的 `{status, readiness, runs}`，页面以这份新快照续接。同步失败时保留已成功操作并给出重试提示。TestIdentity PREPARED 命中和 Recording 最终保存会触发一次工作区刷新，普通轮询 tick 不触发；回调传入 effect 或 polling 时必须保持稳定引用，避免依赖变化反复发请求。

官方示例仍通过正式产品服务准备和检查。未选择应用时，工作台交代背景并提供唯一“启动官方示例”入口；应用接入页也只提供同一个“由界鉴启动官方示例”入口，不要求用户先手工启动它。确认后进入 Agent 写错的问题版，一键应用公开合同，再由用户分别运行问题、修复和证据受限检查。普通未知应用仍由用户显式启动并确认 loopback 地址，界鉴不执行仓库中的未知启动命令。只有当前应用就是活动官方示例时，工作台主表面才显示统一控制器，把当前版本、该版本是否已独立检查、唯一主动作、版本切换和辅助入口放在一起；控制器不跨页面常驻。每次切换先展示真实变化说明，切换后回到工作台并把旧结果明确标为属于上一版本，按钮本身不创建 Run、Verdict 或预置结果。展示模式不是普通业务路由，只重排当前正式权限版本、Change、Run、Evidence 与 ResultPresentation；退出后回到进入前的正式产品上下文。

展示模式用一个样例组织四幕，可按顺序推进也可直接跳转：第一幕“发现矛盾”并列表面响应和后台真实后果；第二幕“回看变化”并列人的权限基线、提交来源、变化登记回执、Agent 声明路径、界鉴实际 diff 与受影响权限；第三幕“展开证据”并列预期路径、表面响应轨、后台效果轨、首个可证明断裂与证据责任；第四幕“验证修复”读取当前与源 Run 的 RepairVerification，分别展示 DENY 后果消失、ALLOW 保留和独立回归控制。问题变化必须由该 Run 的 `change_verification.change_id` 精确引用，修复变化必须由修复 Run 精确引用；不得取“最近一条变化”拼接故事。缺少 Change、审批、源 Run、执行链或独立非回归事实时必须显示缺口。旧“项目结论 / 现场验证 / 修复前后 / 数据与边界”四页及竞赛 validation 汇总不再属于主演示。页面不得从 Trace semantic key、旧竞赛材料或 private oracle 补结论、审批、关联、修复成功或验证数字。

## 视觉、布局与响应式约束

Web V1 使用安静且可核验的原生亮暗双主题。顶部“设置与更多”菜单中的主题入口允许跟随系统、亮色和暗色三种选择；`src/app/ThemeContext.tsx` 只在 `localStorage` 保存这项轻量偏好，并把同一个解析结果同时投影给 Ant Design 和自有 CSS。全局语义色和 Ant Design token 在 `src/app/theme.ts`，CSS 变量与产品壳布局在 `src/styles.css`。页面功能 CSS 留在对应 feature 内，不依赖浏览器强制反色。

Input 与 Select 必须在暗色下使用独立深色底、可见边框和清楚的禁用文字，而不是只依赖浏览器或 Ant Design 默认反色。完整报告 iframe 与“在新窗口打开”必须继承产品当前解析主题；报告 HTML 同时支持系统暗色和显式暗色 fragment，导出的语义内容不随主题变化。

中性色必须占普通产品界面的绝大部分；品牌青只用于选择和动作，蓝色表示事实，绿色只表示证据已经确认符合规则，黄色表示准备或证据不足，红色只表示已确认问题。普通页面不使用渐变、大面积品牌色、常规 Card 阴影或高饱和状态填充。亮色背景/表面/弱表面固定为 `#F6F7F8 / #FFFFFF / #F1F3F4`，暗色固定为 `#0E1214 / #151A1D / #1B2226`；品牌、事实、安全、警告和问题色分别以 `theme.ts` 和 `styles.css` 的同名 token 为唯一实现。颜色之外必须有文字、图标或结构表达含义。

布局遵循以下规则：

- 2560×1440、浏览器 100% 是现场展示和录制的主基准；侧栏 224px、顶部栏 52px、主内容最大宽度 1440px、内容边距 24px。工作台第一屏必须同时看到当前应用、当前判断、唯一主任务、最近可信结果和变化/权限/检查三项摘要。
- 桌面页面一级区块间距使用 24px；600px 窄屏收敛为 16px，页面边距进一步收敛但不能出现横向滚动。
- 同一任务内的标题、说明和控件靠近；不同任务单元用间距或边框分开。不要用空白把同组内容推到两端，也不要把不相关操作挤在一起。
- 普通页面默认只保留 2～3 个主要表面：一个承担当前判断或主任务，一个组织专项内容，必要时再有一个次级事实区域。它不是机械上限，但新增表面必须代表真正独立的用户任务。
- 视觉容器只有 Page、Section、Panel、FocusPanel、FloatingSurface 五种；普通页面最多一个 FocusPanel。普通圆角以 7～12px 为限，阴影只属于 FocusPanel 的极轻层级和 FloatingSurface，交互 hover 不上移、不缩放。
- `Card` 只表示真正独立的信息单元，避免 `Card` 套 `Card`，也不得把每条摘要、指标或入口都做成独立卡片。同组内容优先放入一个共享表面，以标题、留白、细分栏和弱分隔线建立层级；普通字段表不能作为页面主叙事，用户先看到“发生了什么和下一步”。技术字段不进入普通任务页，也不使用通用“高级信息”收纳；确有产品价值时提供范围明确的只读入口，例如“查看证据”。
- 桌面侧栏只显示工作台、变化与修复、权限边界、检查与结果；导航项不使用图标底块或第二行状态文案，状态只在右侧以可悬停解释的短标记出现。顶部保留应用切换、活动任务、AI 工具连接和“设置与更多”；AI 辅助、运行环境、模型、主题和安全退出都进入该菜单，退出始终为末项。约 1100～1200px 收为当前区域摘要和 Drawer；Drawer 打开后焦点进入当前区域，关闭后回到触发按钮。
- Ant Design 5 使用 compactAlgorithm 作为密度基线；普通控件 34px、重要主按钮 36px、紧凑控件 28px。正文只使用 400/500/600 字重，中文字体链与等宽字体链由全局 token 统一。长 ID、路径和 JSON 必须换行或在受控区域滚动。
- 动效时长只使用 90/140/180/220/280ms，普通状态切换使用标准缓动；禁止 hover 位移或缩放，并尊重 `prefers-reduced-motion`。

AI 工具连接页也遵循“主结论 + 一个当前任务表面”的层级，不把不同客户端做成并列卡片墙。页面第一屏先说明当前是否真正连接以及下一步，只用一行选择器切换 Codex、TRAE、Qoder、CodeBuddy 和 DSH；下方固定使用五步新手向导：“选择工具 → 准备本机连接 → 添加 jiejian → 保存凭据 → 重启并检查”。每步必须说明打开哪里、复制什么、粘贴到哪里和完成标志，不展示原始配置面板、命令行备选或协议术语。配置创建、配置复制、Bearer 通过和 initialize 完成仍是后端不同事实；普通页面统一翻译为“界鉴已准备、凭据已通过、连接成功”，只有 `connection_state=CONNECTED` 才显示客户端名称、最近活动和逐应用允许范围。连接成功后的日常说明固定为“任务开始读取基线 → 完成整个用户任务后一次登记整批变化 → 界鉴核对影响并安排复验”，不能暗示每次保存或单个文件修改都要调用界鉴。

普通页面不显示 READ、PREPARE、EXECUTE 等内部 level 名称，统一翻译为“只查看、协助整理、执行已确认任务”。调整入口使用“这次允许 AI 工具做到哪一步”，逐项说明能做什么和不能做什么；连接凭据可以长期保留，但超过只查看的范围仅在本次打开界鉴期间有效。需要把 Bearer 写入请求头的客户端仍必须把无秘密配置骨架与凭据复制分开，并明确本地保存风险。

AI 辅助设置只提供一个默认模型连接，普通用户只选择供应商、填写一次性 API Key、读取可用模型并保存。Profile 名称、兼容服务地址、secret reference、预算、超时、字节限制、本机 HTTP 开关和推理强度不进入普通界面；后端 Profile 仍作为持久化和供应商适配边界存在。

新增或重排页面时，不能只看单一截图。先以 2560×1440 分别核对亮色和暗色的现场展示密度，再同时检查约 1280px 和 600px：标题是否换行、双列表单是否变单列、底部动作是否在滚动中持续可触达、弹层焦点是否正确、是否出现横向溢出。

## 展示用语标准

界面使用“专业、直接、以业务事实为中心”的书面表达：普通用户不需要先理解系统内部模块，评委也能从页面直接看到规则、身份、响应、真实后果和结论。正式但不官样，不使用“搞定了”“一键封神”等过度口语或营销表达。

用语分三层：

1. 主界面先用业务主体、动作、资源、状态和下一项可执行任务，例如“Bob 不得导出完整项目交付包”“后台任务已创建”“还需准备 Bob 的测试账号”。
2. 证据详情在用户主动展开后使用必要技术词，例如 HTTP 403、后台任务、消息、ZIP、Evidence；每个技术词都必须同时说明它证明什么，不能用术语代替结论。
3. Machine、报告和开发文档保留 `ALLOW/DENY`、Verdict、revision、policy epoch、ID、Schema 与 reason code；普通页面翻译为“允许/拒绝”“检查结论”“权限规则版本”，不直接堆叠内部字段。

结果页面和展示模式必须复用同一条事实链：“人确认的权限规则 → 目标实际识别的账号 → 页面或接口回应 → 后台真实后果 → 正式结论”。403 只表示表面请求被拒绝，不能使用代表安全的绿色，也不能替代真实业务后果。状态色固定为蓝色信息、红色问题、绿色已由证据确认符合规则、黄色证据或准备不足、灰色尚无事实；颜色之外必须有文字结论。

## 修改 API DTO 和页面状态

`src/api/` 只描述当前 loopback HTTP 合同并调用统一 `request`。不要在多个页面手写同一响应结构，也不要为了让旧页面继续编译保留后端已经不存在的状态别名。

正常步骤：

1. 先核对后端实际返回模型、稳定错误码和缺失值语义。
2. 在唯一 API 文件更新 DTO 与调用函数；字段可选性必须与真实协议一致。
3. 在页面中区分加载、空状态、可用状态、失败和陈旧请求。
4. 异步请求使用失效标记或等价机制，旧响应不能覆盖新的项目、Run 或选择。
5. 诊断跳转使用后端返回的结构化 route；不能按错误码或错误文字用正则猜页面。
6. 同步更新直接页面测试和 `ControlShell` 闭环测试。

前端本地状态只保存临时交互，例如当前 tab、筛选器、Drawer 开关和用户尚未提交的输入。应用完成状态、最近可信 Run、权限缺口和历史可用性必须重新从后端读取。`localStorage` 只能保存允许的轻量选择；陈旧项目必须经过后端项目列表校验后清除。

## 修改权限与测试内部任务

`PermissionCheckPage` 复用同一事实读取，但通过 `mode="permissions"` 和 `mode="validation"` 分成权限模块页面与测试模块内部运行页面：

```text
权限规则：显式整理自然语言草稿 → 确认 Human Approval / 审阅 Agent proposal
验证运行：准备检查条件 → 核对本次范围 → 开始检查 → 查看进度与结果
```

权限页加载、刷新和进入路由都不得触发 PermissionDraft。只有用户点击“整理成待确认规则”才提交最多 2000 字的当前文本；页面显示用户原话、业务单元、当前规则、建议规则和精确原文依据，并把每条标为待确认。`PARTIAL` 保留已验证建议并提示人工查看矩阵，`UNAVAILABLE` 只关闭自然语言整理。确认草稿先打开与普通 cell 相同的确认 Modal，最后仍调用现有 Human Approval；忽略只删除当前响应内的本地草稿项。

权限 cell 变化先打开确认 Modal，展示当前值、目标值、受保护业务后果和权限版本影响；取消不调用 API，只有“确认权限变更”才进入服务端 Human Approval。Agent proposal 只显示当前值、建议、原因和批准/拒绝，前端不构造 revision；Matrix、proposal 和 CheckPreview 都必须从后端刷新。页面仅用 `can_confirm` 决定 cell 是否可操作，用 `requires_human_confirmation` 与 `required_confirmation_count` 展示真正待确认项，用 `confirmation_blockers` 解释前置事实；`review_reasons` 不参与业务逻辑。验证入口先使用 `ProjectRepair=READY_TO_VERIFY` 关联的 change ID；没有正式修复任务时，才使用 `ProjectRevalidation=READY` 的服务端 change ID。映射待审、准备不足、已验证或 stale 状态先回到服务端指定区域；页面不比较 latest change 与 latest result。验证页的解释性 AssistantPanel 仍只由当前 matrix/gap 事实选择。

权限保存、proposal 批准或重新准备后，旧 CheckPreview 必须失效；新 preview 返回且与当前权限规则版本一致前，不能提交检查。检查条件只通过 `/check-preparation` 形成，不保留旧直接 compile 入口。取消当前检查和重新检查属于有副作用动作，必须使用现有后端动作并明确后果。只读刷新只重新读取状态，不产生新的 Run。

修改这条链时同时核对：权限矩阵、保存门禁、prepare、preview、submit、活动 Run、终态 Run、取消/重试和底部动作。通过一个局部组件测试不能证明整条链仍成立。

## 修改结果、证据和历史

`ResultPresentation` 是唯一人类结果表达；`report.json` 仍是机器语义真源，HTML/SARIF/JUnit 是投影。结果页不重新读取原始字段来发明另一套结论。

普通结果和现场验证通过共享 `ResultDecisionNarrative` 按固定顺序展示：

```text
整轮唯一结论与覆盖范围
→ 当前检查项的本项判断
→ 权限要求 / 表面响应 / 独立观察到的真实结果
→ 已发布诊断支持的断裂位置与精度
→ 决定性证明链：在哪里看到 / 看到什么 / 因此支持
→ 按需展开完整诊断、来源、执行路径和边界
```

Evidence 只展开已发布事实，统一使用“已发现、未发现、无法确认”的语言。HTTP 403 与真实资源变化必须仍能清楚同时出现，且结论保持后端 `BLOCK`；观察不足必须保持 `INCONCLUSIVE`。技术 ID、Occurrence、Evidence ref、reason code 和原始 JSON 不进入普通页面，只保留在 Machine、Evidence 或 Report 等正式技术交付物中。

现场验证不能把所有事实平铺成同级三栏。首层先显示核心矛盾和正式结论；第二层只保留解释矛盾所需且语义去重的执行节点；第三层逐条说明“在哪里看到、看到什么、因此支持”。单项不能证明的内容集中到本项或整轮可说明边界，不在每条证据后重复大段警告；权限版本、完整路径和技术引用也放入按需展开层。同一执行链中的不同最终事件必须按业务语义命名，例如“完整项目交付包已经生成”与“后台导出任务已经完成”，不能都显示为“最终业务效果形成”。

每个结果故事还直接消费 `evidence_sources`，按“目标业务状态、只读数据库、结构化审计记录、后台任务、消息通道、最终对象/文件”展示当前实际接入来源。普通视图把 `KEY/SUPPORTING` 翻译为“关键来源/佐证来源”，把 `FOUND/NOT_FOUND/UNAVAILABLE` 翻译为“已发现/未发现/无法确认”；前端不得按来源数量、颜色或文案重算 Verdict。

结果页和每条历史变化都显示冻结的“本次检查依据权限版本 X”；策略 fingerprint、intent ID、revision 和 intent hash 不进入普通页面。历史页不复制结果故事，只展示问题相对前次的变化。`NOT_COVERED` 不能显示为已解决；“已解决”必须来自后端对同一权限要求取得充分安全证据。

最新结果为 INCONCLUSIVE 时，结果页还可以消费 `ProductStatus.inconclusive_recovery`。页面必须明确说明本次结论和证据永久保留，只渲染后端给出的 summary、next label 与 next path，并且只保留一个恢复动作。权限考题是否变化、变化是否待审、准备是否就绪都由后端判断；前端不能根据缺口、路径文字或本地状态另算。按钮只做路由导航，重新检查仍由用户在验证页明确提交。

结果页还消费 `ProductStatus.repair`，统一显示等待修复、变化已提交、可复验、已验证、未验证、证据不足和失效。它只显示正式 `ProjectRepair` 的要求、状态和后端路由；旧的 Sample 专用验证开关、`canVerifyOfficialFix/verifyOfficialFix` 以及“发送给 Agent”按钮都不是普通产品能力。工作台的“检查是否可以交付”则显式调用 Delivery Check API，每次展示本次 live 结果，不保存在前端缓存。

进入结果页或历史页时必须重新读取当前项目的权威 Run 状态。前端工作区中的完成态只用于当前交互反馈，不能长期替代服务端最新 Run；否则自动检查已经推进到新三态结果时，页面仍可能展示旧运行。API Evidence 列表是发布索引，Evidence detail 才是完整六来源文档，页面和测试不得把这两层 DTO 混成同一种结构。

结果相关变化还要阅读[修改结果与报告](修改结果与报告.md)、[修改官方示例与整链验收](修改官方示例与整链验收.md)、[权限验证与结果](../../01_系统地图/权限验证与结果.md)和[报告与格式投影协议](../../03_参考手册/协议/报告与格式投影协议.md)。

## 前端依赖和编辑器解析

正式源码位于 `product/frontend`，但项目不在该目录生成 `node_modules`。`scripts/dev.ps1` 把依赖视图建立在：

```text
var/development/frontend/workspace
```

生产静态资源进入 `var/runtime/frontend`。使用仓库根的 `jiejian.code-workspace`；执行一次 `prepare -ForcePrepare` 后，工作区 TypeScript 插件会只读解析受控依赖。出现 `react`、`antd`、`vitest` 或 `@testing-library/react` 红线时，先确认受控工作区存在、允许使用工作区 TypeScript，再执行 “TypeScript: Restart TS Server”。不要在源码目录运行 `pnpm install`，也不要用手写模块声明掩盖依赖解析问题。

## 测试、构建和真实页面验证

所有命令从仓库根运行。完整前端测试：

```powershell
.\scripts\dev.ps1 frontend-test
```

定向测试参数会原样传给受控前端工作区中的 Vitest，因此路径必须以该工作区为基准，使用 `src/...`，不能写仓库根形式的 `product/frontend/src/...`：

```powershell
.\scripts\dev.ps1 frontend-test src/features/checks/CheckResultsPage.test.tsx
```

生产 TS/TSX 或构建输入变化还要运行：

```powershell
.\scripts\dev.ps1 prepare -ForcePrepare
```

它同时完成 TypeScript 检查和 Vite production build。依赖、缓存和产物只能位于 `var/`；完成后确认源码树没有 `node_modules`、`dist`、`coverage` 或 `*.tsbuildinfo`。

自动化测试至少覆盖：权威 DTO 输入、加载/空/失败状态、陈旧响应隔离、关键按钮门禁、结构化错误恢复、键盘可访问名称和跨页面主流程。不要用快照替代“点击后到了哪里、使用了哪项后端事实”的行为断言。

重要视觉或持续流程变化先由 `dev.ps1 sample-test` 完成唯一自动 L5 技术闭环，再做展示验收。展示验收核对 2560×1440 主展示、1280px 桌面和 600px 窄屏、应用切换、区域状态、主待办引用、全部待办仍可到达、刷新与重置差异、错误恢复、键盘/焦点、安全退出，以及比赛演示节奏和当前修改直接涉及的真实业务状态；不要为了准备展示清空用户数据。

自动 L5 从真实 `start.cmd` 启动隔离实例，Recording headed Chromium 由正式独立 Recording Process 创建，并由 Windows UI Automation 按 accessible role/name 与 InvokePattern 操作。展示验收可以使用本轮正常产品窗口检查桌面与 600px，截图和横向溢出等度量写入 `var/audit/<任务>/`，不签入 Git。Codex 内置浏览器或用户 Chrome 只用于必须复用已有登录态、扩展或用户浏览器会话的临时检查，不能替代自动 L5。

官方 Sample 页面变化必须保留普通业务语言和正常可访问性。Recording 所需动作应使用真实 `<button>` 和稳定 accessible name，优先修正页面可访问性，不能给生产页面增加测试按钮、隐藏控制接口、remote debugging 或地址栏脚本旁路。

## 常见失败怎样定位

- `No test files found`：先看定向参数是否误写成 `product/frontend/src/...`；受控工作区只接受 `src/...`。
- TypeScript 报大量第三方模块不存在：先修复受控依赖工作区或 VS Code 解析，不要新增假的声明文件。
- 页面显示完成但 Readiness 不允许下一步：核对后端 readiness 和页面所选项目，不要用 route 或本地 state 强行改成完成。
- 旧请求覆盖新页面：检查 effect 清理、项目/Run 依赖和 active/abort 边界。
- 页面同时出现顶部、Card 右上角和底部多个主操作：把普通操作收敛到 `TaskActionBar`，页头只留状态。
- 桌面正常但 600px 横向滚动：检查固定宽度、grid 最小列宽、长 ID、Select popup、表格和嵌套 Card，不要只加全局 `overflow: hidden` 掩盖内容越界。
- PASS/BLOCK/INCONCLUSIVE 与证据文字冲突：停止前端修补，回查 ResultPresentation 和发布事实；页面不能自行选择其中一个。
