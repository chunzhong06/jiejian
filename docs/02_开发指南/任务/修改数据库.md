# 修改数据库

> 状态：CURRENT。适用于界鉴的 SQLite 结构、SQLAlchemy Storage、Alembic migration、事务和数据恢复；不负责结果工件发布或产品发行包。

## 什么时候需要这篇指南

新增或修改持久化字段、表、索引、约束、Repository、事务边界或数据库升级路线时使用本指南。结果、Evidence、Report 的不可变发布由[修改结果与报告](修改结果与报告.md)负责；Windows Portable 与发行 ZIP 由[修改发布与便携版](修改发布与便携版.md)负责。

## 快速找到修改位置

| 我想修改什么 | 主要位置 | 通常需要一起核对 |
| --- | --- | --- |
| SQLAlchemy 表与约束 | `product/backend/infra/storage/` 中对应垂直聚合 | Repository、migration、直接 storage 测试 |
| Repository 与查询语义 | `product/backend/infra/storage/` 中对应垂直聚合 | `unit_of_work.py`、调用 Workflow、事务测试 |
| 完整 ORM metadata 登记 | `product/backend/infra/storage/orm_registry.py` | Row-bearing 模块集合、Alembic env、兼容检查、架构测试 |
| 数据库创建与升级 | `product/backend/infra/storage/db.py` | `product/backend/migrations/`、启动和 Worker 容器 |
| 新增 Alembic revision | `product/backend/migrations/versions/` | 当前 head、upgrade/downgrade、Schema 漂移测试 |
| 运行目录中的数据库位置 | `product/backend/infra/runtime/paths.py` | `default_database_path()`、VarDir 隔离 |

详细数据分区、事务与生命周期见[数据与持久化](../../01_系统地图/数据与持久化.md)。

## 正常修改路线

当前数据库 head 是 `0002_business_boundary_maintenance`，唯一允许前驱是不可改写的 fresh 基线 `0001_business_boundary_v2`。允许精确 0001 原地升级并保留正式业务事实；其他旧 1.x revision、未知 revision 和结构漂移继续拒绝。后续结构变化必须新增 migration，不能改写 0001/0002 或引入 compatibility wrapper。

1. 先确定变化属于数据库结构、Repository 行为还是业务 Workflow；不要把业务状态机塞进 Repository。
2. 结构变化只通过新的 Alembic migration 表达，并同时更新 SQLAlchemy 当前模型。
3. 新增或移动 Row-bearing 模块时，同步更新固定的 `orm_registry.py`；需要完整 metadata 的 Alembic 和数据库兼容边界必须显式调用 Registry，不依赖聚合之间的 import 副作用。
4. 按当前兼容决策验证路径：必须证明 fresh DB 可幂等建立、精确 0001 可升级且保留事实、当前 0002 可重复启动，其他 revision 与结构漂移只读拒绝。
5. 在 Unit of Work 边界内保持事务原子性，失败时由正式异常与补偿路线收口。
6. 运行被修改 Repository/migration 的直接测试，再按公共影响选择更高等级验证。

数据库文件只能位于当前 VarDir 的 `data/` 分区。测试不得把临时 SQLite、迁移缓存或导出副本写回源码目录。

## 不能破坏的边界

- 数据库结构只经 migration 演进，不能在启动或测试中用临时 SQL 悄悄补列。
- 普通字段不得保存密码、Cookie、Bearer、SAS、Owner token 或其他 secret value；秘密只使用受控引用。
- Repository 只保存和读取正式数据，不决定 Verification、Finding、Gate 或权限规则。
- 数据库表可以用字符串 ForeignKey 形成关系；聚合模块不得为了登记 ORM mapping 互相 import Row，完整登记只由 `orm_registry.py` 负责。
- 运行中断后的恢复必须遵守正式状态机；不能直接改数据库伪造 Job、Recording、Run 或 Report 终态。
- 数据库升级失败与产品 serve 失败要保留真实主错误，不能用后续清理异常覆盖。

## 直接验证

优先运行本次 migration、Repository 和调用 Workflow 的直接测试，例如：

```powershell
.\scripts\dev.ps1 test tests/backend/infra/storage tests/backend/migrations
```

实际路径以当前测试树为准。公共持久化语义、跨进程状态或恢复变化再根据[验证与测试](../../04_工程约束/验证与测试.md)选择 L3/L4；不要机械运行完整自动 L5。

## 失败时先查哪里

- 空库成功、旧库失败：检查 revision 顺序、数据回填、NOT NULL/唯一约束和 downgrade 对称性。
- SQLite lock：先确认是否存在真实 Worker/Runner/serve 持有者，不删除正在使用的锁或数据库。
- Repository 测试通过、Workflow 失败：检查事务提交时机、fresh read 和生命周期前置条件。
- 数据库状态与公开结果不一致：从正式 publication/finalization 链查消费者，不直接修表内结果来迎合页面。
