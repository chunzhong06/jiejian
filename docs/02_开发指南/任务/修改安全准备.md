# 修改安全准备

> 状态：CURRENT。用于修改录制后的测试资源、观察方式、恢复方式、安全效果确认、确定性编译与 CheckPreview。

## 这是什么

安全准备把一个已审阅业务 Flow 补齐为“可以安全执行并能解释结果”的事实集合。用户分别确认测试资源、怎样观察真实结果、怎样恢复现场以及真正需要防止的安全效果；这些事实随后由 `SecuritySetupCompiler` 与 `PermissionIntent` 确定性编译为唯一 Contract/Profile 链。

候选只是系统根据录制事件和当前 Sample/应用事实提出的有限选项，不是安全结论。`TestResource`、`ObservationBinding`、`RecoveryBinding` 与 `SecurityEffectConfirmation` 各有稳定 ID 和事实所有者；`ActionSafetySetupService.inspect_action()` 把当前 Flow、五类安全资产及其 CURRENT/MISSING/STALE 状态收敛为只读检查结果，`ProjectPreparation` 再与权限、身份和 CheckPreview 组合成准备清单。

## 正常修改路线

先确认变化属于候选生成、用户确认、只读检查、编译还是展示。候选层可以利用当前 Flow、已脱敏事件和应用理解提出有限选项，但不能自动落地；确认层只接受当前 action/revision 下的稳定候选 ID 与必要可读名称；`inspect_action()` 只从 Recording 领域已有事实判断五类资产是否匹配当前语义，不访问目标、不读取秘密正文、不持久化；编译层按当前全部事实重新生成内容寻址 Contract/Profile；展示层只消费 readiness/preview。

准备清单每项只使用 READY/AUTO/USER/BLOCKED。它通过 `ActionSafetySetupInspection` 读取 FLOW/RESOURCE/OBSERVATION/RECOVERY/EFFECT，不直接访问 Recording、FlowDraft 或 ActionSafetySetup Repository，也不调用安全准备 preview。唯一自动写动作是幂等创建缺失的非秘密 TestIdentity 记录，以及在全部前置项 READY 后复用 `CheckWorkflow.prepare` 构建当前配置；应用、权限或源码变化 blocker 出现时两者都停止。Observation、Recovery、Effect 即使只有一个候选，也必须由现有 Human GUI 确认事务落地。

准备页只用 `next_item_key` 找到顶层下一项并判断它是否为 AUTO，页面文案和路由直接读取顶层 `next_label/next_path`，不能回退到 item 自带路径。用户进入账号、流程或权限等详细页后，写入与本页重读完成，再刷新整个工作区并按返回快照继续；刷新失败时显示可恢复提示，不使用旧快照猜下一步。

状态变化类动作通常需要可执行 Recovery，且关键副作用必须有真实 Observer。缺少观察或恢复时保留明确 gap；能够运行的其他权限范围仍可提交，但不能把未覆盖范围冒充 PASS。TestIdentity 是当前执行代表，不写入 PermissionIntent；代表变化可以让生成配置失效，却不能改写用户已经确认的权限需求。源码理解、安全准备或 candidate 变化只让 `IntentImplementationBinding` 进入 NEEDS_REVIEW/UNRESOLVED；编译器只接受 ACTIVE latest + CURRENT，不得借重新准备删除、退休或重写人类 revision。

安全效果不能仅凭 HTTP method 或 `risk_hint` 自动确定。无法安全映射时保留 gap，不使用通用 `STATE_MUTATION` 兜底。Observation 的 KEY/SUPPORTING 与 required/corroborating 来自冻结 EffectBinding，不由页面文案决定。

## 不能破坏

- label 只服务展示，引用必须使用稳定 ID；候选、确认事实、PermissionIntent、Contract/Profile 和 Verification 不合并。
- 前端不复制可运行性、身份选择、效果映射或 stale 逻辑；这些都由后端确定性服务拥有。
- Recovery 只恢复当前业务副作用，不删除历史证据；测试环境全量 reset 是独立基础设施能力。
- 缺观察、缺代表、缺恢复或编译漂移形成 gap/不可运行事实，不自动改成 DENY、执行失败或安全结论。
- 编译器不调用 LLM，不执行目标请求，不读取秘密正文；secret 只以受控引用进入冻结执行边界。
- 已确认 action、Flow revision、资源、Observer、Recovery 或账号代表变化后，旧生成 Profile 即使仍在磁盘也不得提交。
- 静态安全资产是否齐备与登录态是否可用是两条独立事实；`inspect_action()` 不以 PREPARED 身份作为读取资产的前提，ProjectPreparation 再单独组合 TestIdentity 状态。

## 怎么验证

候选变化先测输入到候选的确定性和稳定 ID；确认变化测 revision、幂等与 stale；编译变化测 Contract/Profile 指纹、身份代表和 gap；展示变化再补 API/前端。不要为安全准备局部变化重复跑 Runner L4 或自动 L5。

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 test tests/backend/workflows/recording/test_safety_candidates.py tests/backend/workflows/recording/test_action_safety_setup.py tests/backend/workflows/security_setup tests/backend/workflows/test_project_readiness.py
```

若真实路径与示例命令不同，以当前测试目录和 `docs/llms.txt` 路由为准，先缩小到修改模块。

## 失败先查哪里

页面候选为空先查 Flow 是否已完成审阅、action/revision 是否一致，再查候选映射；不要在前端硬造默认项。Preview 与准备页不一致先比较后端当前 authority fingerprint 和 stale 原因。能生成 Profile 却不能提交时检查 Contract ACTIVE、当前代表、Flow/Observer/Recovery 指纹是否漂移。Recovery 执行失败要保留 Target 主错误与 cleanup 事实，不直接改状态或清除历史。
