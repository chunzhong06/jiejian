# 修改安全准备

> 状态：CURRENT。适用于权限考题编译、动作技术准备绑定与现场检查。当前后端通过只读 Preparation API 和 Workspace 投影动作准备；完整材料仍须通过当前 CheckPlan 预览门禁，用户显式提交后才进入 CHECK。

## 这是什么

准备服务把正式 BusinessAction revision 和 Permission revisions 翻译成真实身份、动作演示、具体资源、业务结果证明和恢复方式。`ActionAssuranceContract` 与身份需求计划都是确定性派生结果，不持久化为另一套权限规则。DENY 没有合法 ALLOW control 时要求回到权限维护，不能猜测允许身份。

`PreparationService` 每次重读业务事实、账号状态和技术绑定，形成 `SATISFIED / NEEDS_USER / STALE / BLOCKED / NOT_REQUIRED`。材料齐备不等于检查可运行，更不等于 PASS。旧 ProjectPreparation、SecuritySetupCompiler 和 CheckPreview 是保留迁移资产，不能作为当前准备入口；ActionSafetySetup 已被四类动作技术绑定取代。

## 正常修改路线

先确定变化属于派生需求、候选提取、技术事实写入还是现场检查。GET `/api/projects/{project_id}/preparation` 直接调用唯一 `PreparationService.get`，不连接目标、浏览器、模型或写库。Workspace 在原业务边界优先级之后依次处理待审录制、身份、动作演示、具体资源、Effect 证明与恢复；待审录制优先于再次演示，同类按稳定动作/slot/effect 顺序选择，所有材料齐备后 primary_task 可为空。权限与业务结果来自已批准的正式 revision；候选只来自真实脱敏事件、请求模板与 Flow 资源位置。唯一且合法的解释可由确定性程序采用，歧义则保留待审，LLM 只能解释。

TARGET 最终化时发布不可变 Flow，再在同一数据库事务保存 Recording 完成态、ActionExecutionBinding 和当前 owner 的 ActionResourceBinding。一个动作可有多个 owner 的资源；重复最终化不能用旧录制覆盖后来已成立的绑定。Flow 已发布但数据库事务失败时只留下内容寻址的孤立文件，重试必须验证相同 hash。

OBSERVATION 在开始前绑定当前动作已有的 effect_id，只能从明确的观察录制形成 ActionEvidenceBinding。REGISTERED_OBSERVER 是已存在受控 descriptor 的窄引用，普通 UI 不暴露，不接受任意 URL、SQL 或脚本。RECOVERY 只为改变状态的动作形成恢复模板；只读动作的恢复直接为 NOT_REQUIRED，不创建假记录。

## 完整对照与只读计划

每条 DENY 的完整 protected effects 必须由同 Action/revision、同 owner Actor/revision 的单条 ALLOW 覆盖。只按 subject Actor/revision 是否改变排名，全部等价最佳候选保留；多个最佳候选通过 GUI 的 `POST /api/projects/{project_id}/preparation/allow-control` 选择。请求格式 1 仅包含 deny/selected ALLOW 的完整身份和 expected_selection_fingerprint，服务端在同一事务重读并保存技术绑定，不修改 Permission、Approval 或 policy_epoch。候选或 revision 漂移后旧选择不再生效。

`PermissionBoundaryStatus.allow_control_available` 只表示完整合法候选存在；技术选择、账号 distinct 和 Twin 缺口只由 Preparation 投影。Workspace 的 SELECT_ALLOW_CONTROL 紧随完整 ALLOW 缺口，先于账号准备。

`PreparationService.current_plan` 装配现场检查通过的绑定、身份和精确 descriptor 能力，调用 `core/check_plan.py` 纯编译器。全部 current Action 保留；每条 ALLOW 有完整回归，每条 DENY 与 resolved ALLOW 形成同 owner/resource/Flow/证明/恢复/source/config 的 Twin。超集 ALLOW 保留完整回归，并为 DENY 整组 effects 生成子集 control；相同 case 可以复用两个角色。

动作的执行、证明与恢复绑定记录采集来源的双身份，不把模板限定在该来源 owner。来源仍须通过当前性检查；参数化请求注入每个 case 冻结的资源，受控 observer 必须支持精确资源关联。不同 owner 的 case 分别保留其资源绑定和证明指纹，不能复用另一个 case 的观察结果。计划可构造不等于真实操作已成功：正常对照必须实际确认业务结果，恢复必须实际确认当前资源回到基线。

注册证明必须由注入的受控 reader 精确返回 descriptor/effect 的三态、closure 与资源关联能力；未装配返回 gap。录制 GET 只有资源形成语义且精确注入 CASE_RESOURCE_ID 才支持 HTTP_RESOURCE_PRESENCE，其他 GET 仅 supporting。`build_execution_request_v3` 在关键 gap 存在时 STATE_PRECONDITION；成功仅构造无秘密的格式 3 快照，不提交 CHECK Job 或生成认证会话。

## 来源与失效

四类绑定分别保存 subject_test_identity_id/subject_identity_fingerprint 和 resource_owner_test_identity_id/owner_identity_fingerprint；资源主键按 Action/revision/owner 分组，不要求 owner 等于 subject。四类绑定只持久化被确认的技术事实与指纹。现场检查核对业务 revision、语义和实现指纹、真实确认 endpoint、源码来源、账号、来源 Recording/Draft 与 Flow。账号重新登录不抹去技术来源；账号删除保留历史 ID，但旧绑定不能满足当前准备。业务 revision 变化后旧绑定保留历史，不能迁到新 revision 冒充 current。

新写入先验证动作、effect、账号和来源属于同一项目且 revision 精确；补录必须关联同动作、同版本、同 subject 与 owner 的已完成 TARGET。确认前源码、目标地址或实现漂移时失败关闭，不根据名称重新匹配。

## 不能破坏

- 前端不重算身份匹配、准备完成、stale 或唯一下一步；Workspace 是任务优先级真源。
- HTTP method、risk_hint、模型建议和页面状态不能创造或改变 BusinessEffect、Permission、Verdict。
- 缺身份、资源、观察或恢复只形成准备缺口，不冒充安全结论。
- 现场检查不连接目标、不恢复浏览器、不读取秘密正文、不写“READY=true”。
- Recovery 不删除历史证据；测试环境全量 reset 是独立设施，不能冒充动作恢复。
- 数据库增量升级保留正式业务数据，旧候选录制或安全数据非空时在 DDL 前拒绝；不猜映射、不重置数据库。

## 怎样验证

需求变化测确定性与身份约束；候选变化测唯一、歧义和无候选；绑定变化测原子写入、幂等、多 owner 和独立来源漂移；持久化变化再补增量升级与失败不变证据。按实际影响选择直接节点，不因局部修改机械重跑全量或真实 L5。
