# 修改结果与报告

> 状态：CURRENT。适用于 Verification 三态、Finding/Occurrence、ResultPresentation、History、`report.json`、HTML/SARIF/JUnit 投影和 Regression Gate。

## 结果系统解决什么问题

结果系统把已经发布的执行与观察事实分成三类交付：安全判定告诉用户本次是否证明了越权或安全；人类展示解释“为什么”；机器报告和 Gate 提供稳定、可比较的自动化输入。三类产物消费同一已发布事实，但各自职责不能混成第二套真源。

正式链路是：

```text
PermissionContract + CaseResult + Evidence
→ Verification: PASS / BLOCK / INCONCLUSIVE
→ Finding / Occurrence
→ AuthorizationContinuityAssessment（冻结 twin + confirmed/absent/unknown effects）
→ ExecutionTrace（冻结快照 + 已发布 Evidence 的只读路径）
→ BreakpointLocator（复用 Continuity + Trace）
→ ResultPresentation diagnosis（固定七项故事 + 已确认影响）
→ 可选 RepairContract（从已发布 BLOCK/Finding 确定性重建）
→ Base report.json v5
→ HTML / SARIF / JUnit
→ 可选 RegressionBaseline / GateResult / Gate report
→ HistoryView
```

BLOCK 与 INCONCLUSIVE 都是成功完成的安全判定，不是程序失败。执行失败、报告生成失败和 Gate 失败要保留自己的生命周期，不能覆盖 Verification。

## 先判断谁拥有语义

| 问题 | 权威来源 | 下游可以做什么 | 下游不能做什么 |
| --- | --- | --- | --- |
| 原本允许谁做什么 | PermissionContract | 引用 action、subject、resource 和 effect bindings | 从页面标签或 HTTP 路径重新推导权限 |
| 请求怎样回应 | CaseResult 的 HTTP outcome | 解释 ACCEPTED/DENIED/UNKNOWN | 把 403 直接说成安全、202 直接说成成功 |
| 真实资源发生什么 | 已发布 Evidence | 说明 CONFIRMED/ABSENT/不完整 | 用模型文本或未发布 progress 补事实 |
| PASS/BLOCK/INCONCLUSIVE | Verification | 原样传给 Finding、Presentation、Report | 由 GUI、CLI、Report、Gate 或 LLM 重算 |
| 问题跨 Run 的身份 | Finding fingerprint/Occurrence | 显示 NEW/EXISTING/RESOLVED 等变化 | 按标题或列表位置猜是同一问题 |
| 人类解释 | ResultPresentation | 组织业务语言、来源角色和恢复建议 | 创造机器报告中不存在的新安全事实 |
| 修复要求 | 已发布 BLOCK/Finding + 冻结请求/Evidence | 重建“必须消失、必须保留、不能改变” | 给出文件、函数、行号、补丁或改变原考题 |
| 修复复验 | 冻结 RepairVerificationContext + 后续已发布事实 | 给出独立三态 | 替代 PASS/BLOCK/INCONCLUSIVE 或修改 Finding |
| 机器报告 | `report.json` | 作为 HTML/SARIF/JUnit 唯一语义输入 | 从 HTML 或页面状态反向重建 JSON |
| 回归是否可接受 | Regression baseline + GateResult | 比较既有冻结输入 | 改写本次 Verification 或 Finding |

LLM 可以在受限辅助流程中解释或起草，但不能决定 Verdict、Finding、Gate、权限规则，也不能进入正式报告生成链。

## 理解三态 Verification

Verification 只根据既有事实给出：

```text
BLOCK        已有充分、可靠、相关事实证明禁止动作产生了受保护效果
PASS         对本次冻结范围，所有关键效果都以充分闭合的事实证明未发生
INCONCLUSIVE 关键事实不足、观察不可用、因果或闭合条件不满足
```

PASS 是全称条件，不是“没有看到明显问题”。一个关键来源不可用时，即使其他五个来源均未发现，也不能用数量表决成 PASS。BLOCK 可以由一个满足合同的关键效果事实成立；其他 supporting 来源不完整不会否定已经充分成立的关键事实。INCONCLUSIVE 不是把风险判为安全，也不是把程序标成失败。

HTTP 表面响应与真实状态必须分开。例如 Bob 都收到 403：如果后台任务和最终 ZIP 仍形成，结果是 BLOCK；如果关键来源完整闭合且均未形成副作用，结果是 PASS；如果业务已修复但关键 Blob 读取不可用，结果保持 INCONCLUSIVE。

修改 Verification 规则属于核心公共语义变化，必须先停止并由主线程裁决；不能为修复页面、Golden 或报告测试顺手改变 Case、fingerprint、aggregate 或 Schema。

## 修改 Finding 与 Occurrence

Finding 是对稳定安全问题的材料化结果，Occurrence 表示它在某次 Run 中的状态。稳定 identity 来自冻结规则、资源、动作和规范化事实，不来自中文标题、Evidence 列表顺序或本次数据库自增 ID。

修改时保持：

- BLOCK 形成或延续问题；PASS 只有在同一权限要求本次被充分覆盖时才能支持 RESOLVED；
- INCONCLUSIVE 不能把旧问题标成已解决；
- 未执行或本次不在冻结范围内的是 `NOT_COVERED`，不是 PASS 或 RESOLVED；
- 多 Case 聚合继续使用正式 aggregate 规则，页面不自行挑“最严重的一条”；
- Finding 只引用已经发布且属于当前 Run 的 Evidence refs。

如果 fingerprint 变化导致历史断裂，先确认是真实公共语义变化还是非语义字段、顺序或展示文案误入 hash。不要用迁移脚本强行合并两个未证明等价的问题。

## 修改 ResultPresentation

`ResultPresentation` 是唯一人类结果表达。每条 issue 应按业务问题组织：原本应该怎样、计划账号、可确认的实际身份、HTTP 怎样回应、真实资源发生什么、最终结论及原因。实际身份只能从完整 Trace 中可靠且一致的 `IDENTITY` 事件投影；缺失、冲突或 partial 时保持 UNAVAILABLE，不能用计划身份补齐。技术 ID、reason code、raw fact 和 occurrence metadata 留在高级信息。

结果与历史还必须从已提交 Run 的 `PermissionPolicySnapshot` 复制 `policy_epoch`、`policy_fingerprint` 和 `relevant_intents(intent_id/revision/intent_hash)`。普通页面只直接显示“本次检查依据权限版本 X”，其余字段进入高级信息；Builder 和 History 都不能读取 live Ledger 重新解释旧 Run。

`execution_traces` 为每个 Case/Action 提供一条只读实际路径。Builder 只能消费冻结 request snapshot 与已发布 Evidence；事件的 `kind` 只允许 ENTRY、IDENTITY、AUTHORIZATION、PERSISTENT_EFFECT、MESSAGE、DELEGATION、FINAL_EFFECT、RECOVERY，`semantic_key` 继续保留业务名。事件按显式父引用形成稳定 DAG，并保留 subject/actor、结构化动作与资源权限范围、权限来源/委托来源、decision、effect、来源和 Evidence refs；完整性只判断已发布来源与结构，不依赖某个 Sample 的固定 semantic key 清单。`complete=false` 时说明只能确认部分路径，不补未知下游。Trace 不进入 `aggregate_security_effect`、`evaluate_permission_case`、Finding、RunVerdict 或前端判断。

VULNERABLE DENY Case 可以携带 `diagnosis`。该 DTO 只复制被动 Locator 的授权连续性、六种断裂类型和 EXACT/RANGE/VIOLATION_ONLY 精度，按固定顺序给出“权限要求、实际身份、本不该发生的业务后果、合法授权来源、首个可证明断裂、后续扩大影响的行为、最终业务影响”。主断裂与后续放大器分开表达；Trace 缺少稳定节点时只说明违规存在，不虚构断裂类型或代码位置。GUI、CLI Human/Machine 与现有 MCP 结果工具共享同一 ResultPresentation；完整 Trace 默认折叠，消费者不得重算 Verdict、授权连续性、断裂类型、位置或精度，也不得从 `semantic_key` 推断业务结论。

`evidence_sources` 只翻译冻结 binding 与已发布 Evidence：

```text
role:
  required channel       → KEY
  corroborating channel  → SUPPORTING

status:
  完整、可靠、相关的 CONFIRMED → FOUND
  完整闭合的 ABSENT           → NOT_FOUND
  其余                         → UNAVAILABLE
```

角色不能按 Observer 类型硬编码。当前普通页面采用稳定阅读顺序：目标业务状态、只读数据库、结构化审计记录、后台任务、消息通道、最终对象/文件；顺序只服务阅读，不参与判定。

来源不要求状态一致。BLOCK 中 Owner API 或 Blob 可以是 KEY/FOUND，某些 SUPPORTING 来源也可能 FOUND 或 UNAVAILABLE；PASS 要求所有关键来源充分 NOT_FOUND，但 supporting 仍可能 UNAVAILABLE；INCONCLUSIVE 的关键来源通常至少一项 UNAVAILABLE。`evidence_refs` 必须确实指向该 Run 已发布 Evidence，不能创建仅供页面使用的虚构引用。

页面可以翻译为“关键来源/佐证来源”和“已发现/未发现/无法确认”，但不能按卡片数量、颜色或文案重算 Verdict。仅供结果页解释的来源摘要不会自动升级为 `report.json` 新字段。

## 修改 RepairContract 与独立复验

`RepairContract` 只能从已发布且完整的 BLOCK、唯一 Finding、冻结权限快照、ALLOW/DENY 孪生、关键 Evidence、授权连续性和断裂诊断确定性重建。它冻结原 Run/Finding、原 `policy_epoch`、目标和 ALLOW 权限身份、DENY 动作与资源关系、受保护效果、关键证据要求、孤儿后果、主断裂与放大器，并只向普通用户表达“必须消失、必须保留、不能改变”。合同和 Agent 输入都不得出现文件、行号、函数或补丁建议。

Agent 只可读取合同并在通用变化提交中回传权威引用；服务端必须重建并核对 fingerprint。后续继续走现有 change prepare/run 链，Run 冻结 `RepairVerificationContext`。任一原 `intent_id/revision/intent_hash` 变化都要求重新形成检查；纯实现重绑不改变权限语义时可以继续。删除受保护效果、降低原证据标准、遗漏原 DENY/ALLOW 对或破坏合法功能都不能得到 `VERIFIED`；增加证据要求属于加严，但原要求及绑定仍须保持。

修复复验只输出 `VERIFIED / NOT_VERIFIED / INCONCLUSIVE`，不创建第二套 Verdict。`VERIFIED` 同时要求原违规效果有充分证据证明消失、ALLOW 控制成功、原权限未改变且关键证据未降低。ResultPresentation、History、CLI 和 report.json 只投影该三态，不能据此改写 Finding 或 Gate。

## 修改 report.json 与格式投影

`report.json` 是机器报告的唯一语义真源。Base report v5 冻结本次 Run、Finding、Evidence refs、runtime、artifact summary、presentation diagnosis、权限策略快照摘要、可选修复复验和版本；Gate report 在不可变 Base report 之上引用 GateResult。两者的 semantic input、report id 和 canonical SHA 必须确定。Report package manifest 仍是独立格式 1，不能随 Report 根机械升级。

HTML、SARIF 与 JUnit 都从同一 `report.json` 确定性投影：

- HTML 为人类审阅，不增加隐藏事实；
- SARIF 映射正式 Finding、location 和 severity，不让工具默认值改 Verdict；
- JUnit 映射用例结果，但 BLOCK/INCONCLUSIVE 与运行失败的区别必须保留；
- 任一投影失败只标记报告生命周期失败，不修改 Report、Finding、Evidence、Verdict 或 Gate。

公共报告字段变化需要同时评估 reader、Schema、canonical/hash、历史兼容和四种输出。普通展示需求优先放在 ResultPresentation；没有独立机器消费者和版本必要性时，不要把页面字段塞进 `report.json`。

报告中仍禁止秘密、目标正文、普通数据库内部字段、progress 私有诊断和模型自由文本。所有 reason code、路径和引用都要经过公开格式校验。

## 修改 Regression Baseline 与 Gate

Baseline 只接受满足正式门禁的已发布 Run。required observer issues、artifact 状态、Finding snapshot 和版本一起形成稳定输入；corroborating baseline 不参与 baseline fingerprint 或 twin gate。

Gate 比较 Base report 与冻结 baseline，输出独立 `GateResult`。它可以说明回归门禁是否通过，但不能把本次 BLOCK 改成 PASS，也不能在 Observation 不完整时补安全结论。更换 baseline 是治理动作，需要显式 actor/reason/accepted time，不由自动重跑静默覆盖。

若 supporting 来源增加导致 baseline hash 漂移，先检查是否错误把 corroborating evidence 纳入 fingerprint。若 Gate 与 Base report 看起来冲突，分别展示“本次安全结果”和“回归门禁结果”，不要合并成单一颜色或状态。

## 修改 History

History 只消费正式 Finding/Occurrence 和 Run 时间，不重新扫描 Evidence。当前顺序按正式时间正序提供；前端如需倒序展示，应在明确 DTO 合同下处理，测试不能假定数据库默认顺序。

历史状态至少区分：

```text
NEW / EXISTING     问题首次出现或仍存在
RESOLVED           同一要求已充分覆盖且取得 PASS
INCONCLUSIVE       本次覆盖但关键证据不足
NOT_COVERED        本次没有覆盖该要求
```

`NOT_COVERED` 和 INCONCLUSIVE 都不能显示成“已解决”。跨 Run 比较要用稳定 fingerprint 和正式 publication 时间，不能用列表索引、报告生成时间或文件修改时间。

## 三态 Golden 怎样作为验收真源

协作空间 Golden 使用同一应用、项目、项目负责人 Alice、普通成员 Bob 和同一导出动作，只改变被测业务状态或关键观察可用性：

| 状态 | HTTP 表面 | 关键真实事实 | Verdict | 用户解释 |
| --- | --- | --- | --- | --- |
| 缺陷态 | Bob 收到 403 | 后台任务与最终 ZIP 仍形成 | BLOCK | 请求被拒绝，但真实对象已经存在 |
| 修复态 | Bob 收到 403 | 关键来源完整闭合且副作用未发生 | PASS | 本次范围内真实资源未变化 |
| 证据不足态 | Bob 收到 403 | 业务已修复，但关键 Blob 读取不可用 | INCONCLUSIVE | 无法确认最终产物，不代表安全 |

Golden 必须从公开 API 取得最终 Run、ResultPresentation、Evidence、Report 和 History，并验证六个来源 one-to-one 发布、角色和关键状态。它不读取 Runner progress、attempt 私有目录或生产内部对象，也不在测试里复制 Verification 聚合。

断言应只约束语义必要矩阵：关键来源必须满足对应 Verdict，supporting 来源只验证实际执行、发布和合法状态，不要求所有来源都 FOUND/NOT_FOUND。失败摘要应有界、可净化，并基于公开 run/job/result/evidence；定位完成后不留下临时内部诊断。

Evidence 读取还要区分两个正式层级：`GET /api/runs/{run_id}/evidence` 返回 `EvidenceIndexRecord` 列表，`GET /api/runs/{run_id}/evidence/{evidence_id}` 返回完整 Evidence 文档。六来源、角色、事实和状态检查使用完整文档。不同层级结构不相等是正常合同，不能据此修改 API，也不能恢复已经退出普通产品面的 CLI Evidence 命令。

## 常见失败怎样定位

- 页面看到 403 就显示“安全”：回查 ResultPresentation；HTTP outcome 与真实资源事实必须分开。
- supporting `UNAVAILABLE` 把 PASS 变 INCONCLUSIVE：检查 Verification 是否误把 corroborating 纳入 required gate。
- BLOCK 要求六个来源全部 FOUND：测试过度约束；只断言关键事实与来源发布，不制造全同状态矩阵。
- Evidence 数量正确但来源角色错：从 EffectBinding 的 required/corroborating channel 追到 presentation，不按类型补丁修正。
- Report JSON 正确但 HTML/SARIF/JUnit 改了结论：投影器产生了新语义；恢复为 report.json 的确定性映射。
- 报告失败后 Run Verdict 变化：生命周期耦合错误；报告失败不能回写 Verification。
- 历史把缺失记录显示为 RESOLVED：检查 `NOT_COVERED`、稳定 fingerprint 和 Run 顺序。
- Golden 反复因不同展示状态失败：先冻结三态权威矩阵，再扫描整份测试的同类断言，只约束语义必要项后重跑。
- hash 因 facts/reason codes 顺序漂移：在计算前按协议模型的规范化规则排序。

## 最终检查清单

结果与报告变化至少确认：

```text
Verification 仍只根据既有事实产生 PASS/BLOCK/INCONCLUSIVE
HTTP 表面、真实资源事实、生命周期和安全结论彼此分开
PASS 满足关键事实全称闭合，INCONCLUSIVE 没有被降格为安全
Finding/Occurrence fingerprint 稳定，NOT_COVERED 不会变 RESOLVED
ResultPresentation 角色来自冻结 binding，状态来自已发布 Evidence

evidence_refs 均指向当前 Run 的真实 publication
report.json v5 仍是机器语义真源，package manifest 保持格式 1，格式投影没有新增语义
Gate 不改变 Base report、Finding 或 Verdict，supporting 不进入 baseline fingerprint
三态 Golden 只使用公开边界且没有测试内部诊断债务
直接结果/报告测试、必要 schema/docs/frontend/L5 验证通过
秘密、目标正文、模型决定和普通数据库内部字段没有进入结果产物
```
