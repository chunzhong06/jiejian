# 答辩材料

## 问题

Vibe Coding 生成的 Web 应用可能只在前端或 HTTP 表象上拒绝越权操作，后端副作用却已发生。只看状态码、页面提示或 LLM 文本判断，无法证明安全意图真的落实。

## 核心创新

1. **安全意图到可执行 Contract**：把角色、资源和动作关系转成可版本化规则。
2. **关系变异**：在正常 Flow 上只交换身份、资源或敏感字段，保持差分可解释。
3. **多观察者副作用判定**：同时比较 HTTP 与 owner API 前后状态，识别“拒绝后仍生效”。
4. **Evidence 门禁**：结论带规则、观察、原因码和内容哈希，可回溯、可回归。
5. **可恢复隔离执行**：Job、租约、Fencing Token、Runner、staging、原子发布和 reconciliation 阻止旧进程与半写工件污染结果。

## 架构

CLI、回环 FastAPI 和 React GUI 复用同一个 `ApplicationContext`。Run 和 Recording 都提交持久 Job，由独立 Worker claim 并启动对应的隔离 Runner；主动目标流量不在 API、GUI 或 Worker 内发送。Verification Runner 生成 Evidence，Worker 重验 staging 和内容哈希后原子发布，再通过 UnitOfWork 写入 SQLite 完成态；CLI、API 和 GUI 只读取同一份已发布结果。

## 当前能力

- 阶段 0～5 及阶段 5 工程优化已完成，阶段 6/7 尚未开始。
- safe/vulnerable 所有权样例形成相反门禁结论。
- 缺少必要观察者时明确输出 `INCONCLUSIVE`。
- Runner V1、SQLite migration、Job 控制、进程隔离、录制、Contract 治理和发布恢复均有自动化测试。
- Recording 可以把经过目标范围控制和脱敏的浏览器事件编译为待审阅 Flow；Requirement 可以通过确定性来源或受限 LLM 生成不可信 Candidate，再经过统一治理形成 ACTIVE Contract。
- 真实秘密不进入协议、数据库、日志或 Evidence。

## 当前限制

- 受限 LLM Candidate 默认离线；模型不能激活 Contract、执行目标流量或决定最终 Verdict。
- 显式 YAML Contract 仍是兼容入口；Recording 生成的 Flow 和所有候选规则仍需经过人工审阅或治理门禁。
- 阶段 6 的统一 Reporting/GatePolicy 与 HTML、SARIF、JUnit 等多格式报告尚未实现。
- 阶段 7 的正式评测集、跨框架覆盖和量化对比尚未开始。
- 当前验证重点是本机授权样例，不代表已经得到大规模准确率或召回率结论。
