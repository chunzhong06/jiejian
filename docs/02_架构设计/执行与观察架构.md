# 执行与观察架构

> 状态：CURRENT。当前适用范围：Job 控制面、Worker、隔离 Runner、ExecutionRouter、Web HTTP 执行和 Observer。

## 职责

说明从持久 Job 到隔离执行、目标请求、真实副作用观察和结果回收的边界；解释租约、fencing、取消、重试、关联、完整性和预算。

## 非职责

- 不定义 PermissionContract、Verification Verdict 或 Report 的业务规则。
- 不复制 JSON Schema 字段表。
- 不把未来目标适配器、MCP 入口或本地命令执行写成当前能力。
- 不允许 API/GUI 绕过 Worker 直接发高风险请求。

## 真源

执行模型真源是 `product/backend/workflows`、Worker/Runner 实现、`product/protocols/runner.py`、`execution_request.py`、`observer.py` 及其 Schema。

## 目的

真实表达控制面和高风险副作用之间的进程与安全隔离。

## 组件与边界

- Job 持有可恢复的执行意图、状态、尝试、租约和 fencing token。
- Worker 负责 claim、lease、fencing、cancel、retry、恢复、结果校验和 publication。
- `PersistedExecutionRequest` 是 Runner 的冻结输入，不重新读取可变 Profile 或 Contract。
- Runner 在隔离进程中执行受预算约束的目标流量，并产生受限结果和证据。
- `ExecutionRouter` 只选择已注册 Target adapter；当前只有 `WEB` 的 `HttpExecutionAdapter`。
- `WebTargetDefinition` 持有明确的 `WebTargetScope` 和 reset path；scope 检查 origin、host、port、重定向、私网授权、请求数、响应字节和超时预算。
- `ActionExecutionBinding` 持有 method、relative path template、无秘密 JSON body、accepted/denied statuses 和 resource injection；Core Action 不持有这些 HTTP 字段。
- Observer 按 phase 采集副作用或状态事实，使用 correlation、causality、completeness、reliability 和 budget 约束观察。
- Recording 回放必须先经过 Recording 工作流和安全重验证，再复用同一执行边界。

## 关键数据流

```text
Job → lease/fencing → Worker
  → PersistedExecutionRequest
  → 隔离 Runner
  → ExecutionRouter
  → WEB HttpExecutionAdapter
  → Observer phases
  → ExecutionFact / ObservationFact / Evidence
  → staging → Worker 校验 → publication
```

## 关键不变量

- 只有持有有效 lease 和 fencing token 的 Worker 能完成当前尝试。
- Supervisor 已为等待态 Job 建立启动责任后，若 Worker 在 claim 前不可恢复退出，只能通过 `job_id + waiting state + no lease` 的原子条件将 Job 及关联目标结束为 FAILED；条件失配时接受最新数据库状态，绝不覆盖已 claim 的 RUNNING Job。
- 旧 token、过期 lease、重复 completion 和孤儿 staging 不得覆盖已发布结果。
- Router 对未知 TargetType fail closed；当前不提供 Process 或 MCP 目标执行入口。
- HTTP scope、重定向、私网、请求/响应字节、并发和时间预算在 adapter 边界强制执行。
- Observer 的缺失、不完整、冲突或超预算结果不能被解释为安全通过。
- API/GUI 只能提交、观察和读取，不直接操作目标流量。

adapter 在 Web 边界完成 scope guard、binding 渲染、预算、脱敏和 HTTP 状态到 `ExecutionOutcome` 的映射，但不决定 Permission Verdict。

## 失败语义

输入解析、租约、fencing、预算、目标范围、adapter、观察关联、协议校验或清理失败时，执行停止或进入明确失败状态；claim 前的 Worker bootstrap 失败记录 `JOB_FAILED / WORKER_FATAL`，不消耗或伪造 attempt/fencing token。无法形成完整观察时向 Verification 提供 INCONCLUSIVE 证据，而不是伪造成功。

Worker 的 stdout/stderr 写入 `VarDir/logs/workers/<job_id>.log`，每次启动前按固定大小轮换并只保留有限备份；即使结构化 logging 尚未初始化，bootstrap traceback 也必须可定位。Worker 结构化日志同时进入主日志，并经过已知秘密脱敏。

## 安全约束

Runner 只获得完成当前请求所需的最小环境和秘密引用。日志、异常、事件、观察和结果统一脱敏。清理失败必须阻止可能污染后续用例的继续执行。

目标请求离开 adapter 边界前生成有界、脱敏的 input/output hash；失败输出使用确定性空输出 hash。

## 兼容与版本

当前执行产品只实现 Web + HTTP。机器 `schema_version`/`protocol_version` 按实际协议保留；字段和解析规则以 Schema 和协议源码为准。旧开发执行请求和结果不兼容读取。
