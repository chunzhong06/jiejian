# 产品入口与控制面架构

> 状态：CURRENT。当前适用范围：Windows 启动、首次使用、Web GUI、CLI、CI、loopback API 和 Worker 控制面。

## 职责

说明用户或 CI 如何进入产品、如何建立项目和权限规则、如何提交和观察检查，以及入口如何与高风险执行隔离。

## 非职责

- 不直接执行目标请求，不定义 Runner 字段或 Verification 规则。
- 不把页面展示状态当作安全结论。
- 不把 CLI_APPLICATION、MCP_AGENT、MCP ingress 或本地命令执行写成当前产品入口。
- 不复制启动脚本的全部实现细节或前端组件细节。

## 真源

入口真源是根 `README.md`、`start.cmd`、启动脚本、`product/backend/api`、`product/backend/cli`、`product/frontend`、ApplicationCore 和相关测试。

## 目的

真实区分产品使用入口、控制面和目标执行边界。

## 组件与边界

- `start.cmd` 是源码仓库的一键产品入口：准备或复用项目专用 Conda `jiejian_env`，由受控 uv 按 `uv.lock` frozen 同步并 editable 指向当前仓库；普通启动不安装或运行 Wheel。
- `scripts/dev.ps1` 是源码运行环境的唯一准备入口，提供 bootstrap、sync、update、prepare、start、cli、test、frontend-test、schema、shell 和独立可选的 package；只有 update 可以修改 `uv.lock`，只有 `schema -Update` 可以更新签入的公共 Schema，package 不参与普通启动。`dev.ps1 start` 只薄转发到 `start.ps1 -Mode Gui`，不自行准备后直接调用 `serve`。
- 前端源码输入在排除明确生成物后同时驱动指纹和 `var/runtime/build/frontend-workspace` 镜像；pnpm install、TypeScript/Vite build 和 Vitest 只在该工作区运行。前端构建固定输出到 `var/runtime/frontend`，只有产物缺失或输入/工具链指纹变化时才准备受控 Node/pnpm 并构建，后续启动直接复用。
- Web GUI 提供工作台、应用接入、测试账号、业务流程、权限规则、开始检查、检查结果、历史变化和设置能力；流程录制的内部术语继续存在，但普通用户入口统一称为“业务流程”。
- 模型服务是全局可选控制面，不属于项目、Runner 或 Verification。普通设置只管理 AI 辅助开关、默认供应商、临时 API Key、动态模型、推理强度和连接状态；多 profile、OpenAI-compatible、Base URL、环境变量引用与预算限制只进入高级设置。OpenAI、DeepSeek 和 Gemini 分别使用自己的正式模型目录与调用语义，未知模型不推测推理档位。
- DeepSeek 的连接探针和普通文本调用使用 Chat Completions；当前动态目录中的 `deepseek-v4-flash` 受限结构化调用使用官方 Responses API `json_schema`。Responses 的 reasoning 与最终正文共享 token 上限，因此适配器在不放宽响应字节硬限的前提下使用有界推理预算；只读取最终 `output_text` 并丢弃 reasoning。其余 DeepSeek 模型的 JSON Object 结果仍须整体通过相同本地白名单，失败只进入短退避，不能放宽验证或伪造 AI 推荐。
- 临时模型发现和已保存 profile 刷新都是显式写请求：前者只在单次请求内使用表单 Key，后者从共享 SecretStore 解析精确引用。GET、页面读取和启动不连接供应商；保存、测试、失败或关闭设置后，前端立即清空 Key。模型服务不可用时，确定性接入、权限准备、执行、观察和 Verification 仍完整工作。
- `GuidanceSnapshot` 从 ProjectReadiness、CheckPreview、活动任务和可信结果确定性生成有限下一步、稳定 option ID、服务端路由与事实指纹；`ErrorDiagnosis` 从稳定错误码、Runner 阶段、原因与 cleanup issue 生成恢复入口。二者均为只读投影，不调用模型、不创建 CheckPlan，也不改变权限预期、生命周期或安全结论。
- 工作台的 assistant GET 只重算 Guidance 并读取可删除缓存，返回 `DISABLED`、`REFRESH_NEEDED`、`GENERATING`、`READY` 或 `BACKOFF`；只有前端收到 `REFRESH_NEEDED` 后发出的明确 POST 才能连接默认模型 profile。同一项目、模板和事实指纹只生成一次，失败后等待事实变化或用户明确重试。AI 只能在系统选项白名单中排序或解释，页面先显示“界鉴确定”，真正的模型内容统一标记紫色 `[AI辅助]`。
- CLI 同时提供面向普通用户的引导工作台、熟练用户命令和 CI 自动化入口；Human、JSON、CI 与内部日志互不混用。
- API 是固定 `127.0.0.1` 的资源、任务、事件和结果控制面，负责严格解析、授权、ApplicationCore 调用和脱敏错误映射。所有 HTTP 请求先匹配实际 `Host`；GUI 根页面取得只属于当前服务进程的 HttpOnly、SameSite=Strict control session Cookie，全部 `/api` 请求验证该会话，`POST/PUT/PATCH/DELETE` 再要求 `Origin` 与实际界鉴 origin 完全一致。代理头不能改变授权 Host。
- API 内部路径统一为 `/api`；SSE 使用持久事件序号恢复，客户端断开后停止数据库轮询和等待。
- Onboarding 的基础目录识别只允许目录选择和受限配置元数据读取；不执行目标命令、不联网、不读取普通源码正文或秘密。用户确认本地应用地址后，源码理解必须经过第二次单独授权，并在独立预算内只读分析。
- GUI、CLI 和 API 复用 ApplicationCore 下的应用服务；Worker 使用独立 WorkerContainer，Worker/Runner 才能进入高风险执行链。
- “运行环境”页与 CLI 复用同一缓存维护服务，提供按需缓存状态、按预算清理、清空可重建缓存和修复运行时；数据重置不进入缓存入口。完整缓存统计和预算维护只由用户查看状态或显式 prune 触发，不属于 readiness 或普通 startup maintenance；启动后的有界孤儿/日志维护失败只进入诊断，不反向撤销已经成立的 ready。

## 关键数据流

```text
start.cmd
  → loopback 服务
  → GUI / CLI / CI
  → API 或 CLI 调用 ApplicationCore
  → Project / Contract / Profile / Job
  → Worker / Runner 执行
  → GUI / CLI / Report 读取已发布事实
```

新用户的普通接入主路径是：选择应用目录 → 确认应用已运行 → 系统从结构化配置、公开接口描述、显式启动端口和已识别框架默认端口中有界发现 IPv4 loopback 地址 → 用户确认并授权规范化后的 `127.0.0.1` 地址 → 用户单独授权源码只读分析 → 系统确定性提出带结构证据的角色与业务动作候选 → 用户确认、否定、重命名或补充 → 为已确认角色准备测试账号 → 下一步进入业务流程。`localhost` 只有实际包含 `127.0.0.1` 解析结果时才可规范化；仅有 `::1` 时明确提示当前 Web 执行不支持，而不是先接入再在 Profile 阶段失败。应用连接在完整 `WebExecutionProfile` 形成前可以是 DRAFT；旧 Profile 注册入口只保留为明确的高级能力。

`ProjectReadiness` 是从 Project、ApplicationUnderstanding、TestIdentity、Flow、测试资源/观察/恢复、PermissionIntent、ExecutionProfile、Contract、Run 和 Recording 权威事实计算的只读投影，供工作台、导航和接入页共同使用。它按每个已确认 action 分开显示应确认的权限组要求、已确认要求、当前可执行代表、代表缺口、可运行范围和剩余缺口，不持久化，不形成 CheckPlan 或新的安全真源；角色与动作候选也不形成 ALLOW/DENY 或漏洞结论。`CheckPreview` 从同一批当前事实投影普通用户能理解的动作、权限组、资源关系、预期和覆盖缺口；至少一个 ALLOW/DENY 差分范围完整时可以运行，其他缺口继续明确显示且不能被冒充为已覆盖 PASS。提交时只允许使用确定性 Compiler 当前生成并登记的唯一有效 Profile，Profile 标识不进入普通页面选择。已有完整高级 Profile 的项目继续从既有事实推导等价 readiness，不要求重新接入。浏览器本地状态只保存上次选择的项目与页面；endpoint、候选确认、Run 和 Recording 均从后端权威事实恢复。

Guidance 只把上述实时事实收敛成普通用户下一步，不是新的持久化进度。当前 scope 可运行时，“开始检查当前可运行范围”始终是确定性主动作，剩余 coverage gap 只作为可选补充；尚不可运行时只暴露最高阻断层。语义事实未变化时，页面刷新、切换菜单或 Run polling 不改变 Guidance 指纹，也不能触发新的 provider 调用。

测试账号是绑定当前已确认角色、endpoint 与 ApplicationUnderstanding revision 的项目资产，不是 Contract Subject、`WebExecutionIdentity` 或运行时 Cookie jar。用户在独立 headed BrowserContext 中自行登录，只有点击“这个账号已经登录，可以保存测试状态”后，身份准备进程才提取当前 target host 最多 32 个 Cookie，或当前 target origin 的单一 Bearer；两者同时出现或认证状态无法安全归约时转到高级身份配置。密码、localStorage、完整 `storage_state` 和其他站点状态不保存，登录阶段不生成 Recording 事件。

接入完成后的产品路径继续进入测试账号、业务流程、权限规则、开始检查和检查结果。结果页必须分别展示执行生命周期、Evidence、Verification Verdict 和 GateResult。

“开始检查”先展示当前可检查动作、检查用例、ALLOW/DENY 对照和未覆盖权限要求；可运行范围与剩余缺口可以同时存在，不能因为局部缺口禁用已经完整的当前范围。运行中页面只从 Job 生命周期和 Runner 非权威旁路事件展示“准备检查环境、验证正常允许的操作、尝试不应允许的操作、确认真实资源结果、恢复测试数据”，没有权威 completed/total 时不得估算百分比。旁路不可用只降级过程展示，不能改变检查结果。

### Windows 启动交互

- 启动准备保持六个有序阶段及其缓存、诊断、迁移、Chromium 和前端构建语义；每个任务只有一个主结果节点，版本、缓存状态和 revision 作为详情。准备完成后，第一层显示“图形界面 / 命令行 / 仅完成环境准备”，命令行第二层显示“引导模式（推荐） / 普通命令行 / 返回”。两层都把“↑ ↓ 选择    Enter 确认”固定显示在选项下方，方向键只重画选项行；RawUI 不可靠时一次性降级为带编号操作说明的选择。
- `RuntimePaths` 把 `VarDir` 固定分成 `data`、`runtime`、`cache`、`logs`、`temp` 和 `test`。数据库、Job、项目、Evidence、报告和工件检查只进入 `data`；可重建工具链、浏览器、前端工作区、最终网页与锁进入 `runtime`；pnpm store、Vite 等内容缓存进入 `cache`。旧根部布局不迁移、不双读。`product/frontend` 永远只保留 Git 管理的源码与配置；官方 prepare 即使命中指纹也精确清除旧设计遗留的 `node_modules`、`dist` 和 `tsconfig.tsbuildinfo`。
- 启动器在选择 Python 后必须清除继承的 `PYTHONHOME/PYTHONPATH`、启用 `PYTHONNOUSERSITE`，并核对实际解释器、环境前缀、`sys.path` 与关键依赖来源。主进程把已确认的解释器身份传给 Worker，Worker 启动前再次核对；任一来源漂移都停止运行并展示解释器、Node、pnpm、Playwright、前端依赖和恢复建议。Playwright 浏览器固定进入 `VarDir/runtime/playwright`，不能静默复用用户目录缓存。
- 图形界面继续进入 `serve --open`。引导模式只读取 ApplicationCore 的真实项目与结果事实；普通命令行进入仅对当前子进程生效的 PowerShell，直接调用已经解析的 Python 绝对路径并继承已确认的 `VarDir`。Node/pnpm 仅在需要重建前端时临时使用；退出后不得留下永久 `PATH`、PowerShell profile 或系统环境修改。
- readiness 的唯一真源是 Python 对 `/ready` 的精确响应校验：HTTP 200、根版本 1 且 `status=ready`。软等待阈值只产生一次“仍在准备”事件并继续等待，不能被解释为服务已启动或浏览器失败；serve 在 ready 前退出则产生独立启动失败事件。只有 ready 成立后才尝试打开系统浏览器，并分别报告“网页已打开”或“服务已 ready、浏览器未打开”。PowerShell 只展示 Python 产生的稳定状态事件，不自行猜测 readiness。
- 服务 ready 后启动动画立即结束，终端明确提示网页退出入口与 `Ctrl+C`，并继续持有服务生命周期。GUI 的“退出界鉴”复用当前 control session 与精确同源 Origin 触发同一 shutdown 链，不保留静态魔法控制头；正常退出依次停止 Worker、受控 Runner/浏览器和 ApplicationCore。系统浏览器页面属于用户进程，不被强制关闭，页面只提示服务已停止后可关闭。
- 创建 ApplicationCore、运行一致性恢复、结果最终化和 Worker 启动属于 ready 前关键路径；只检查缓存根直接临时项、过期 temp/test 顶层项和有界日志保留的 startup maintenance 在关键路径成功后由受控后台任务执行。完整 pnpm/uv 等缓存统计和预算 prune 仅按需执行。任务引用由应用生命周期持有，关闭时明确等待；维护失败记录耗时与错误但不关闭已可用服务。启动日志分别记录 run reconciliation、result finalization、worker start、ready total、startup maintenance 和 browser open 耗时。
- 自动化调用必须显式选择 GUI、CLI 或 prepare 模式；直接调用 `scripts/start.ps1` 时保持可组合的退出码并立即返回。`start.cmd` 对 PowerShell 的任意非零退出统一保留原始退出码，并在阶段、错误码、主错误、日志和恢复建议输出后等待用户关闭窗口；该兜底也覆盖参数解析和模块加载失败。

### CLI 引导与输出通道

- 引导首页只使用应用、身份、权限规则、业务流程、开始检查和检查结果等产品词。它从 Project、Contract、Execution、Recording 和已发布结果读取状态，不保存独立 Guide Progress，也不重新实现业务规则。
- 官方 `samples/web` 通过正常 GUI 接入或公开 CLI 使用同一个 Target 的 fixed、vulnerable、inconclusive 变体；产品不保存 Sample Target、预期结论或专用状态。真实应用的复杂权限矩阵、关系图和大量流程编辑继续进入现有图形界面。
- Human stdout 只呈现结论、关键事实和下一步，默认隐藏内部 ID、原因代码与复杂结构；`--verbose` 才显示有界技术详情。`--json` stdout 只包含一个机器对象，CI 保持严格机器接口。脱敏结构化日志写入 `VarDir/logs/jiejian.log`，普通 CLI 命令不把 INFO 日志混入 stderr。

### 流程录制产品闭环

普通 Recording 从当前 ApplicationUnderstanding 的一个已确认业务动作和一个已准备 TestIdentity 开始，不要求用户先创建或选择 `WebExecutionProfile`。服务端读取动作、endpoint 与非秘密身份元数据，把 TestIdentity 的精确 SecretStore 引用投影为本次录制专用环境引用；Recording Runner 在独立有头 BrowserContext 中恢复 Cookie 或 Bearer，秘密正文不进入请求快照、数据库、API 或 Flow。高级 Profile 入口只可复用同一 Recording application service 和同一 FlowDraft/Flow 编译链。

`STARTING` 表示浏览器准备至等待明确开始的持久生命周期，`RECORDING` 只在开始采集后进入；更细的准备、等待、采集和停止阶段由 attempt 控制事实投影，不扩展持久状态枚举。开始与停止由 API/ApplicationCore 写入当前 attempt 的有界无秘密控制标记，Worker/Runner 消费标记并保持 TargetScope、事件预算、网络预算、脱敏和清理边界。

Worker 在 claim 前发生确定性启动失败时，尚处于 `CREATED` 的 Recording 可直接进入 `FAILED`；该路径保留 `started_at_us` 为空，不伪造 `STARTING`、attempt 或 fencing token 事实。

审阅页以动作卡片和步骤卡片为主，系统只从已录制请求的路径、query、JSON body 或先前响应推荐 TARGET、动态变量和资源位置；推荐不自动生效。用户必须确认唯一 TARGET 与一个有限资源位置，最终 Flow 绑定 action，并只保留 TARGET 及其必要 SETUP，通过 `CASE_SUBJECT` 和 `CASE_RESOURCE_ID` 延迟注入差分主体与资源。Flow 不保存 alternate identity/resource、ALLOW/DENY、Observer 或 reset 默认。普通完成页展示动作名、TARGET method/path 和录制账号，不暴露 Flow JSON；生成的动作 Flow 后续仍进入唯一 ExecutionWorkflow、Evidence、Verification 和结果发布链。

Flow 保存后，普通页面继续以中文卡片分别确认“测试资源是什么、怎样独立确认真实结果、怎样恢复测试现场、真正需要防止的影响”。页面只允许选择当前 Recording 生成的有限候选和填写可读资源名称/类型，不接受 URL、脚本、任意 JSONPath 或秘密。候选只有用户确认后才成为事实；缺观察保留覆盖缺口，状态变更缺恢复时明确禁止自动执行，系统无法安全映射 SecurityEffect 时不得用 `STATE_MUTATION` 兜底。

普通“权限规则”页面从已确认权限组、TestResource 所有者权限组和 action Flow 形成中文权限组×动作关系矩阵，用户只确认允许、拒绝或暂不确认。确认不要求当下已经存在同组第二账号；TestIdentity 只在编译和预览时作为 OWNS、同组其他账号或其他权限组的临时执行代表。`PermissionIntent` 是普通安全需求真源；确定性编译器据此生成并治理 Contract，再把当前 Flow、身份、Observer 和 Recovery 生成内容寻址内部 Profile。普通用户不编辑 Contract JSON、不选择 Profile path，技术细节只保留在高级面板。CLI 只扩展现有引导，不建立第二套向导，也不要求普通用户手写 Runner JSON。

### 结果与权限解释

- 检查结果先回答“谁对什么执行了什么、规则期望什么、表面请求怎样、真实对象是否变化、为何形成该结论”，再展开安全意图、执行事实、观察事实和确定性结论；EvidenceTimeline 位于解释之后，内部标识默认收进高级信息。
- 首屏固定汇总本次检查、符合预期、权限问题、证据不足和未覆盖权限要求。PASS 必须说明只覆盖本次实际范围且不代表绝对安全；BLOCK 卡片固定解释预期、表面结果、真实结果、结论和原因，HTTP/页面显示拒绝但可信观察确认资源变化时仍明确判为权限问题；INCONCLUSIVE 说明既不代表安全也不代表已确认漏洞，并从确定性观察缺口给出“完善真实结果确认方式”的入口。
- 生命周期、结果完整性、Observer 配置、Schema、reason code、运行 ID 和证据原文默认进入高级信息或“查看证据”；只有 Job/Run 确实失败时显示执行错误。失败说明优先使用 ErrorDiagnosis 的结构化标题、短说明、恢复路由和 cleanup warning，不能把 BLOCK 或 INCONCLUSIVE 渲染成程序错误。
- 状态化关系差分结果必须同时说明请求表面、安全效果、ALLOW 控制、基线完整性、时间闭合和最终结论；workflow/twin/effect 指纹只在高级信息展示。
- PASS、BLOCK 和 INCONCLUSIVE 使用同一信息层级。尤其“请求表面被拒绝但真实资源已改变”必须直接显示为越权事实，不能由状态码替代真实观察。
- 用户可见结果只使用已发布执行快照、Evidence、Finding 和 Verification 的确定性投影；展示读模型可以补充可读标签和因果说明，但不得改变 Finding 身份、Occurrence Verdict、Verification Verdict 或 GateResult。
- 模型辅助不得进入结果真源；错误解释也必须先由 ErrorDiagnosis 给出确定性阶段、原因和恢复入口，模型至多解释已允许的系统选项。
- 权限矩阵使用可筛选热力表表达身份、角色、动作和资源，稳定区分 ALLOW、DENY、未声明与冲突，并支持单元格详情。关系看板的全局模式只展示身份、资源和 OWNS、SAME_TENANT、MEMBER_OF 等业务关系，角色作为身份属性而非独立节点；聚焦具体身份后才过滤相关关系并加入该身份自己的权限边。看板使用确定性的行式布局和响应式纵向布局，不依赖无限画布的缩放或平移；中文含义与原始标识分层展示，状态与关系不能只依赖颜色。
- GUI 与 CLI 的任务文案、按钮、状态和业务含义默认使用中文。品牌、命令、文件格式、代码、协议字段、路径及需要复制或对照的机器值保留原文；已知业务枚举使用“中文含义（原值）”展示，不能通过修改协议数据实现翻译。技术原值集中放在次要文字、高级信息或 `--verbose` 中。

## 关键不变量

- API、GUI 和 CLI 不直接创建 Engine、UnitOfWork、RequestStore 或 Dispatcher。
- API/GUI 不直接向目标发高风险请求。
- `127.0.0.1` 控制面与目标执行进程隔离；监听 loopback 不能替代 Host、会话和写请求 Origin 校验。
- 用户可见状态不替代机器结果；INCONCLUSIVE 不得显示为安全通过，HTTP 拒绝也不得替代真实状态观察。
- 启动失败、浏览器未打开、运行环境不可用和检查无法开始都应给出可恢复、脱敏的提示。
- 普通用户错误固定展示失败阶段、原因、任务标识、日志位置和下一步，并提供可复制文本；内部堆栈只进入有界脱敏日志。
- AI 关闭、未配置或失败不能阻断确定性主流程；模型不得创建路由、角色、动作、权限规则、恢复方式或执行命令。

## 失败语义

启动准备、浏览器、数据库、前端、API 输入、项目识别、Contract/Profile、目标地址或运行环境失败时，入口停止当前动作并保留可诊断日志。控制面断开不等于执行成功或失败；事件序号用于恢复读取。

## 安全约束

默认只监听 `127.0.0.1`。控制会话令牌使用 256-bit 随机源且只驻留当前服务内存与 HttpOnly Cookie，不写数据库、日志、报告或项目；Onboarding 的识别预算、目标范围、身份、写操作、reset、重定向、私网和请求预算必须显式确认或由执行边界校验。共享 SecretStore 只允许严格命名空间下的精确引用操作；测试账号的 Cookie/Token 正文只进入 Windows Credential Manager，API、数据库、项目文件、协议、日志、Evidence 和报告均不出现正文或可枚举秘密。

Serve 把本次实际、已规范化的控制面 origin 注入 ApplicationCore，并只通过固定最小环境传播到 Worker/Runner。应用地址确认在网络探测和持久化前拒绝该 origin；Web Target Guard 在目标请求边界再次拒绝，防止历史冻结配置或绕过控制面的输入让界鉴检查自身。CLI 未启动 Serve 时没有保留 origin，不使用固定端口猜测控制面地址。

## 兼容与版本

当前产品入口只服务 Web Target。CLI 的产品命令以实际 help 和启动输出为准；公共 JSON/Schema 版本不是产品代际。生产协议与当前使用路径都不保留未实现的 CLI_APPLICATION、MCP_AGENT 或 MCP 占位。旧启动模式、旧参数位置和旧路由 alias 不兼容保留。
