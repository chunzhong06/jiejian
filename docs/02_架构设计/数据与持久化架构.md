# 数据与持久化架构

> 状态：CURRENT。当前适用范围：SQLite、migration、Storage、事务、公共身份、工件发布、报告和恢复。

## 职责

说明持久实体如何建立身份和事务边界，如何从 staging 发布不可变事实，以及数据库、文件、日志、缓存、秘密和恢复之间的边界。

## 非职责

- 不定义完整 JSON Schema 或 Runner 字段。
- 不把数据库生命周期状态当作 Verification Verdict 或 GateResult。
- 不提供旧开发数据库、旧 Profile/Run/Report 或旧 wire format 的猜测式迁移。
- 不替代执行与观察 Architecture 的进程和预算语义。

## 真源

数据库真源是 `product/backend/migrations`；Storage、Unit of Work、Repository 和发布代码是运行真源；公共跨进程模型位于 `product/protocols`。

## 目的

真实表达“什么可以提交、什么必须先发布、什么发布后不可变”。

## 组件与边界

- SQLite 保存 Project、Contract、WebExecutionProfile、Job/Run、事件、Evidence 索引、Finding/Occurrence、结果派生状态、报告索引、Baseline、Gate 和相关治理实体。
- Storage 按垂直聚合提供 Repository 与 Unit of Work；ApplicationCore 负责组合和事务编排。
- Alembic 管理结构；当前空库从 `0001_initial.py` 建立完整基线。
- 当前持久实体包括 projects、runs、jobs、job_events、evidence_index、recordings、flow_draft_revisions、requirements、contract_candidates、contract_versions、llm_profiles、execution_profiles、findings、finding_occurrences、run_finalizations、regression_baselines 和 gate_results。
- Runner 先写受限 staging；Worker 校验关联 ID、fencing、大小、脱敏、路径和 hash 后原子 publication。
- Run publication 只保存 RunnerResult 与 Evidence；唯一 `ResultFinalizer` 在 publication 后幂等物化 Finding/Occurrence 和基础报告，派生失败以独立状态重试而不修改 Verdict。
- 独立 ReportStore publication 中的 `report.json` 是报告语义真源；HTML、SARIF、JUnit 是确定性投影。基础报告不依赖 Gate，后续 Gate 产生独立不可变版本。
- `RuntimePaths` 将 `var/data`、`runtime`、`cache`、`logs`、`temp` 和 `test` 物理分离；产品事实只进入 `data`，不属于源码或 Git。
- 可选 Wheel 复用 `var/runtime/frontend`，由 Hatch 在构建时映射为包内 `product/frontend/dist`，并包含 backend、protocols/Schema、配置、前端静态资源、migration 和 entry point；不包含 `node_modules`、tests、samples 或本地 `var` 布局。该路径不参与普通源码启动，也不向源码树回写 dist。

## 关键数据流

```text
ApplicationCore
  → UoW/Repository 建立身份与冻结请求
  → Worker/Runner staging
  → 协议、关联、完整性和安全校验
  → manifest/hash/Run publication → 数据库完成 Verdict
  → ResultFinalizer → Finding/Occurrence → 基础 Report publication
  → 可选 Baseline/Gate → Gate Report publication
  → GET、CLI、GUI 只读查询
```

数据库完成态只能引用已经校验并成功发布的事实。数据库提交失败而文件已发布时，由 reconciliation 幂等补齐；文件不完整或 hash 不符时不得标记完成。

## 关键不变量

- Project、ContractVersion、WebExecutionProfile、Run、Job、Evidence、Finding、Baseline 和 Gate 身份可追溯且不混用。
- 生命周期状态、Verification Verdict 和 GateResult 分离保存。
- ACTIVE ContractVersion 和执行快照不可原地改写；已发布 Evidence 不可变。
- publication manifest、内容 hash 和语义 hash 必须可验证。
- Evidence 以内容寻址 ID 和运行内工件路径唯一；`case_id` 是关联字段而不是唯一身份，同一 Case 可为不同孪生上下文发布多条 Evidence。
- Worker 不执行 migration；运行进程不绕过 Storage 和事务边界。
- waiting Job 的 bootstrap 失败只能由 Storage 条件 SQL 在 `PENDING/RETRY_WAIT + no lease` 仍成立时转为 FAILED；Job、Run/Recording 终态和 `JOB_FAILED` 事件在同一 Unit of Work 提交。
- 报告只能消费已发布事实，不能反向修改 Verdict 或 Evidence。
- Finding/Occurrence 和报告的派生状态不进入 RunLifecycle；GET 接口不得物化、修复或改变任何持久事实。
- 缓存维护和 runtime repair 不得删除 `var/data`；数据重置是独立危险操作，不能与 cache clean 复用。
- `cache clean` 只清理 `var/cache`，不得删除前端安装视图或最终网页；损坏的 `var/runtime/build/frontend-workspace` 由 `runtime repair` 清理，并在源码变化、最终网页缺失或强制准备等确需构建时重建，普通 prepare 仍可复用健康的最终网页。删除整个 `var` 是从零重建仓库本地运行态，不负责删除全局项目 Conda 环境。

## 失败语义

未知 migration revision、结构签名不匹配、协议版本不支持、身份关联错误、hash 不一致、路径越界、秘密泄露、预算超限或 publication 不完整均 fail closed。旧开发数据库要求停止并重建 `var`，不删除未知数据、不猜测迁移。

## 安全约束

秘密只保存受控引用或最小环境注入所需的临时值；秘密值不得进入数据库公共 JSON、协议、Evidence、日志或报告。运行产物、缓存和凭据不得写入源码目录。

## 兼容与版本

Schema 版本和 migration revision 是不同边界。公共 Schema 版本按机器格式处理；数据库只接受当前唯一 `0001_initial` 与结构签名。旧 `var` 布局、旧数据库和旧报告路径不迁移、不双读，也不保留兼容提示分支。
