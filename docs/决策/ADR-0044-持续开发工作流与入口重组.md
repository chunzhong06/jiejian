# ADR-0044：持续开发工作流与入口重组

> 状态：已接受。以 2026-10-01 的轻量伴随验证定位为有效决策；下文原始提议只作历史。当前行为以产品工作流、入口与导航及协议为准，版本验收状态由本轮验证报告单独记录。

## 2026-10-01 定位修订

用户接受轻量伴随验证定位，并授权落实。原提议中以开发任务、接单、结束为中心的前端方案退役；后台任务/上下文/交付和回执继续用于精确追溯，新增一次登记接口，不再构成日常人工前置。现行行为见产品工作流与导航；下文旧表仅作设计历史，不应恢复到产品。

沿用 R3 结果页设计语言：减少默认内容，保持页头、表格和详情的一致尺度。参考 VS Code Testing 的就近验证角色、Linear 2026-03-12 的界面降噪设计，以及 Apple Design Awards 2025 Play 对复杂专业操作的组织方式。参考只支持具体取舍，不代表界鉴已获奖或应模仿其业务模型。

参考：https://code.visualstudio.com/docs/debugtest/testing 、https://linear.app/now/behind-the-latest-design-refresh 、https://developer.apple.com/design/awards/2025/ 。本轮不实现原生悬浮窗、IDE 插件或聊天代理。

## 需要优先收敛的结构



以下是当前实现的局部问题。整体目标见下文“持续开发工作流的模块重组提议”，不能把局部替换折叠控件当成完整改造。

| 优先事项 | 当前实现 | 后续调整目标 |
| --- | --- | --- |
| 找不到修复入口 | 已有独立 Agent 协作、工作台精确主任务、结果页直达 | 保持原问题 → 任务 → 修改 → 独立复验的同一上下文 |
| 必须操作藏在说明里 | 手工补充、首次手工草稿、部分代码核对仍在折叠内 | 改为清晰次级按钮；复杂表单进入独立工作面 |
| 证据展开层级过多 | 观察依据内部还有来源折叠 | 合并成同一证据详情的分组，保留选中事实与返回位置 |
| 连接管理弹窗叠加 | 管理连接 Modal 可以再进入凭据确认 Modal | 管理操作回到连接页，弹窗只保留最后短确认 |
| 原题对照多处出现 | 结果页与修复页分别提供完整对照 | 结果页保留摘要，Agent 修复详情承载完整工作 |
| 旧项目历史不明显 | 环境操作记录折叠内进入 | 在环境页提供带摘要的明示入口 |
| 状态摘要可能被误解 | 导航的部分区域提示仍复用边界/准备状态 | 后续按模块真实事实表达待办，连接状态不表示修复状态 |

界鉴采用四个稳定主模块，子页通常保持两至三个；对象记录与任务步骤留在模块内。重要信息通过摘要和状态让人看到，完整细节通过明确入口让人找到，不靠增加一级导航解决所有层级问题。

设计依据：Carbon 将产品导航与系统操作分开，并限制侧栏的嵌套深度；界鉴据此采用稳定模块与页内子入口。[UI shell left panel](https://carbondesignsystem.com/components/UI-shell-left-panel/usage/)。Carbon 的创建流程按复杂度和上下文需求区分完整页面、侧面板和短模态框；界鉴将这一原则用于选择任务工作面的承载形式，而非机械复制其创建流程。[Create flows](https://carbondesignsystem.com/community/patterns/create-flows/)。

实现定位：产品壳与全局导航在 `product/frontend/src/app/`；具体工作面在 `product/frontend/src/features/`；公开任务定位由 `product/backend/workflows/workspace/service.py` 提供。修改方法与验证入口见[修改前端](../开发/能力/修改前端.md)。

## 持续开发工作流的模块重组提议

> 以下为待审设计，不表示当前已实现。原有四模块和上文入口表仍是实现现状。重组可以替换现有导航、页面、折叠和抽屉；保留的是业务事实与安全职责，而非旧布局。

### 产品主线

围绕一个持续开发的应用，保存人确认的权限约定，在每次开发前交给 Agent，在真实修改后重新验证。修复是开发任务的一种；应用接入是首次准备；一次 PASS 是一个确定代码状态下的结果，不是项目结束。

主线为：接入应用并建立业务权限 → 开始一项功能开发、重构或修复任务 → 读取本次基线与必须保留的要求 → Agent 修改代码并登记交付 → 界鉴核对真实变化与材料适用性 → 独立验证 → 处理问题或确认本次交付 → 开始下一项任务。

用户可以直接在 Codex 提需求，由 Agent 通过授权的 MCP 接入同一任务，不要求在界鉴再填一遍。界鉴也提供发起任务入口，但“已复制”“Agent 已读取任务”“变化已登记”“验证通过”必须各有真实依据。普通聊天文本、连接状态和文件保存不等于任务已接收。

### 建议一级模块

| 模块 | 用户问题 | 二级内容 | 不承担的内容 |
| --- | --- | --- | --- |
| 工作台 | 应用现在是什么状态，轮到谁做什么？ | 当前任务、代码与最近验证的对应、待确认事项、最近活动 | 不内嵌全部编辑器，不只展示一次检查结果 |
| 开发协作 | 本次让 Agent 做什么，实际改了什么？ | 开发任务、待核对交付；连接与授权作为模块工具入口 | 不把修复作为唯一入口，不伪造 Agent 正在修改 |
| 业务与权限 | 谁能对谁的什么资源做什么？ | 权限规则、业务动作、业务角色；对象详情含受保护结果与代码关联 | 不混入测试账号、实例维护和机器结论 |
| 验证中心 | 用什么材料、检查什么、现在能否执行？ | 当前验证、可复用材料；按具体任务展示变化后的待复核项 | 不重复建设历史列表，不凭影响分析静默缩减完整考题 |
| 检查历史 | 过去哪个代码状态得到什么结果？ | 默认全部检查、精确结果、证据、关联开发任务与修改 | 不承担新任务派发，不默认隐藏在旧筛选中 |

辅助区稳定保留“应用与环境”和系统状态。应用切换器只切换应用及接入新应用；官方示例条件、停止和重置归环境管理。AI 辅助与主题是工具设置，不占主导航。侧栏不增加三级树，二级内容只在所属模块出现。

五个模块分别对应全局、开发、要求、执行、历史，不是一条必须逐页点击的流水线。工作台主任务携带 task、change、run 等精确引用，直接进入当前需要的工作面。

### 工作台的具体构成

1. 顶部固定显示应用名称与应用环境入口；轻量状态行分别说明代码状态、权限版本、最近验证对应范围。不能合成一个“应用安全”的绿色标签。
2. 第一屏主体只有当前任务工作面：本次目标、当前可信状态、为何需要处理、一个主操作。右侧窄摘要给出当前基线与所涉业务，不放另一组竞争主按钮。
3. 下方是待处理清单：需要用户确认、等待 Agent 交付、待准备或验证。相同任务在此列出摘要，点击回到唯一任务详情。
4. 再下方是紧凑的项目活动流：需求确认、实际修改登记、运行结果、修复复验。这是既有事实的只读汇总，不新增第二套完成状态。
5. 当前没有任务时，主操作是“开始新的开发任务”，并展示既有权限和最近验证范围；不显示“流程全部完成”的终点。

只对真实活动任务展示进度。等待 Agent 时说明等待什么回执以及最后更新时间；未同步时保留旧状态并标记，不显示假进度或以连接状态推断正在工作。

### 开发任务工作面

任务列表按进行中、需要处理、已收口组织；首版每个应用只允许一个绑定当前工作区的活动开发任务，避免无法区分不同任务的源码修改。已存在多个变化批次时按真实关联展示，不能按提交时间或 Agent 名称自动归因。

任务详情由三部分构成：

| 位置 | 内容 | 操作 |
| --- | --- | --- |
| 顶部 | 任务目标、当前状态、唯一下一步 | 继续当前任务、暂停或放弃；不会混入连接设置表单 |
| 主工作区 | 需求与约束 / 实际修改 / 验证与交付，作为平级视图 | 核对要求、查看真实差异、确认执行范围、阅读结果 |
| 上下文摘要 | 应用、起始代码指纹、权限版本、正常业务要求、关联原题 | 明确链接进入完整规则或证据，不用嵌套折叠展开另一个编辑器 |

“复制给 Agent 的任务”放在任务目标下；只有复制事实时显示尚未发送。Agent 经 MCP 读取准确任务并形成回执后，才能显示已读取。用户仍在 Codex 中与 Agent 对话，界鉴不另外造一个聊天客户端。

修改后明确并排展示 Agent 的说明与界鉴核对的真实变化。正常开发任务也必须给出验证结果，不能只在发现漏洞后才进入界鉴。关闭任务是工作流动作，安全结论仍只来自 Verification。

### 结果后的分支

| 已形成事实 | 当前应显示什么 | 下一步 |
| --- | --- | --- |
| PASS | 本次已验证的规则、代码、环境与范围 | 本次交付可收口；继续下一次开发 |
| BLOCK | 原规则、实际后果和证据能证明的断裂 | 当前任务内形成修复尝试，沿用原题；不要求用户到历史中找派发入口 |
| INCONCLUSIVE | 哪项身份、执行、观察或恢复事实不足 | 补齐对应材料后再验证；不把未知自动交给 Agent 当漏洞修复 |
| 执行失败/中断 | 运行状态和可恢复位置 | 恢复或重新执行，不伪装成安全结论 |
| 代码或权限已变化 | 旧结果的历史范围及当前未验证部分 | 核对新变化，必要时由人批准权限提案，再按当前合同验证 |

验证中心与检查历史打开同一个 Run 结果工作面。结果页按“结论与适用范围 → 人的规则和实际后果 → 因果事实 → 所选证据”组织；完整来源、字段和技术引用进入同一个证据详情，不在折叠内部继续叠折叠。桌面使用就地证据栏，窄屏只保留一层抽屉。

### 小入口的统一归属

| 内容性质 | 新承载形式 | 对应入口 |
| --- | --- | --- |
| 高频独立任务 | 明确按钮进入完整工作面 | 新建开发任务、手工建立权限、准备材料、原题修复 |
| 模块内平级对象 | 页内导航加列表/详情 | 权限规则、动作、角色；开发任务与交付 |
| 必须关注的阻碍 | 摘要常显，附准确解决入口 | 代码关联失效、缺少证明、权限待确认、实例状态未知 |
| 证据与来源 | 当前事实旁的单层详情 | 因果节点、观察来源、完整证据引用 |
| 辅助输入/解释 | 表单附近工具按钮，局部展开 | 自然语言辅助、录制解释、结果解释 |
| 低频技术资料 | 命名清楚的单层折叠 | hash、原始公开证据、完整源码引用、诊断码 |
| 管理与危险操作 | 专属管理页，操作前短确认 | 连接凭据、逐应用授权、实例重置、移除应用 |

所有详情有固定返回路径。进入新模块采用该模块默认视图；从其详情返回保留列表筛选和位置。刷新按钮只是兜底，读取新状态和任务推进必须自动发生；自动更新不能覆盖正在编辑的输入或抢走焦点。

### 后端所需的最小补充

当前已有 SourceChange、ProjectRepair、Check/ResultStory、权限版本、源码身份和材料恢复。它们可以承载真实变化、问题与复验，但当前 MCP 的变化提交还没有稳定的“本次开发任务”引用。仅给 `/changes` 改名不足以形成上述主线。

| 能力 | 设计要求 | 已有能力如何复用 |
| --- | --- | --- |
| 开发任务根记录 | 稳定任务 ID、应用、目标、任务类型、业务范围、起始代码/权限引用、修订与明确的生命周期 | 任务只组织工作，不重复存储安全结论；不保存聊天全文或秘密 |
| 开工上下文 | 可核对的源码指纹、权限版本、必须保留的正常业务、已知问题与检查范围 | 引用现有正式边界及已发布事实；没有可信 PASS 时明确说明 |
| MCP 接入 | 在用户授权下创建或关联任务、读取开工上下文、交付时带任务 ID；都有幂等及项目归属检查 | 复用现有 MCP 授权与变化扫描，不要求用户重复登记 |
| 交付关联 | 一个任务可以有多次交付和修复尝试，每次关联准确 change/run/reference | Agent 说明与真实 diff 分离；未知回执先回读，不重复写入 |
| 工作台投影 | 聚合活动任务、源码对应、权限待确认、材料缺口、独立验证事实 | 唯一 PrimaryTask 仍由后端确定；不在前端重建状态机 |
| 任务收口 | 明确区分放弃、暂停、交付待核对与当前要求验证通过 | 修复仍需原题判断；旧 PASS 不随新代码自动延续 |

这些是拟议合同，实施前要冻结输入输出、持久化与迁移边界。任务类型只区分功能开发、重构、修复等必要用途，不引入 Sprint、估时、多人排期或通用项目管理平台。

没有开工前任务记录的代码变化仍允许接入，但应标记为事后登记，不能虚构历史基线、Agent 已读取约束或任务创建时间。真实 Git 提交、工作区指纹与实际运行实例分别保留，不能相互替代。

### 官方示例怎样体现持续开发

在同一个运行中的示例项目里完成至少两项连续开发任务：先确认并修复已有导出权限问题；再让真实 Codex 对合法业务做一次功能改进或重构，沿用原权限，登记实际修改并重新验证。第二次不必强行制造漏洞，也不能预设一定 PASS；展示实际形成的结论及适用范围。

检查结束、修复结束和下一次开发都不会重建项目。此前约定的“每次启动全新官方实例从零开始”保持成立：关闭后重新启动或显式重置才建立新的同步导出项目，旧项目归档并保留历史。正在运行的一次示例会话支持多次真实迭代；这与实例重启策略是两个层面。

预设异步优化/修复属于明确标记来源的开发演练，观察条件是独立环境支线，二者不能冒充真实 Agent 交付。竞赛中要展示真实 Codex 会话、实际修改、MCP 回执和独立检查。用户在界鉴发起需求时可以复制任务；自动唤起或投递到外部 Codex 的能力必须单独实现并验证，不能用按钮文案宣称已送达。

### 视觉与交互参考如何应用

| 参考 | 经官方资料确认的特点 | 界鉴采用的设计判断 |
| --- | --- | --- |
| Linear 的团队主页 | 主页汇集资源和团队工作入口 | 工作台提供项目全局与准确分流，具体任务留在模块工作面 |
| Things 3（Apple Design Award 获奖） | 聚焦当前事项、项目内分组、可选字段按需出现 | 主任务有清楚焦点；用分组而非卡片堆砌组织内容；辅助字段后置 |
| Crouton（2024 Apple Design Award 交互类） | 以清晰界面与逐步操作支持真实任务 | 把开发、交付、验证的下一动作做得明确，不让用户反复找菜单 |
| Carbon 导航与 Tabs | 稳定层级、平级内容使用页签；页签不承载渐进任务 | 模块导航稳定；审阅/确认采用任务步骤，不伪装成任意切换页签 |

参考出处：[Linear 团队主页](https://linear.app/docs/default-team-pages)、[Things 的设计与交互](https://culturedcode.com/things/features/)、[Things 获奖记录](https://culturedcode.com/things/blog/2017/06/back-from-wwdc/)、[Apple 2024 设计奖](https://www.apple.com/newsroom/2024/06/apple-announces-winners-of-the-2024-apple-design-awards/)、[Carbon Tabs](https://carbondesignsystem.com/components/tabs/usage/)。以上用于提炼组织和交互方式，不表示已逐个实测这些产品，也不以获奖身份替代界鉴自己的操作验证。

视觉上采用安静的中性色工作区、稳定的文本轴线和有限的表面层级。列表、任务、表单和证据分别有明确版式；一个视口一个主操作，次级操作成组且间距一致。修复说明不重复“已保存”，容器内部保持统一边距，中文按钮可换行；状态除颜色外必须有明确文字。亮暗主题、键盘和窄屏共享同一内容结构。

### 设计成立的验收条件

- 用户接入后能开始普通开发任务，不必先发现漏洞。
- 同一应用可连续完成两项真实开发任务，无需重新接入、批准未变化的权限或重新准备仍适用的材料。
- 从工作台可以明确看出当前任务、待谁处理、当前代码是否被最近结果覆盖。
- 从 Codex 发起的需求与界鉴任务可以关联，交付经 MCP 登记，无需手工重复填写。
- 原题修复与功能开发共用工作流，BLOCK、INCONCLUSIVE 和运行失败有不同下一步。
- 必须处理的事项不会藏进折叠区；没有抽屉套抽屉或管理弹窗再套管理弹窗。
- 列表进入默认无筛选、详情返回保留上下文；新状态可自动出现，输入不会被刷新覆盖。
- 收口一次任务不删除规则、材料和历史，也不宣布整个应用永久安全。
