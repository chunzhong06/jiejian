# 安全意图与验证架构

> 状态：CURRENT。当前适用范围：1.1.1 Business Boundary 持续维护、Permission v2，以及保留执行结果链的安全不变量。

## 职责

说明安全意图如何被审阅、编译为覆盖计划，如何与真实执行事实和观察事实关联，以及如何形成 Finding、Baseline、Gate 和 Report。

## 非职责

- 不执行目标请求，不定义 Worker/Runner 调度细节。
- 不让模型生成安全意图、权限契约或安全结论。
- 不定义协议 JSON 的完整字段表。
- 不把生命周期状态、Verdict 和 GateResult 合并为一个状态。

## 真源

领域代码位于 `product/backend/core`，公共模型和 Schema 位于 `product/protocols`。

## 目的

真实区分“想验证什么”“观察到了什么”“能否形成结论”和“是否通过交付门禁”。

## 1.1.1 当前真源

`BusinessActorRevision`、`BusinessActionRevision` 及其 Effect catalog 定义稳定业务边界；`PermissionIntentRevision` 只引用这些稳定 revision。维护草稿完整保留 current stable IDs/revisions，前端只提交 desired state，服务端确定 `REFERENCE / APPEND_REVISION / CREATE`、权限沿用或追加、实现重绑及停用。不可变 `BoundaryProposalBundle` 经固定 `LOCAL_GUI` Human Approval 后，在同一事务中形成全部 revision、binding、Decision 与新的 `policy_epoch`。

完整新 Compiler/Check/Runner 主链尚未重新接入当前 GUI。以下执行、证据、Breakpoint 和结果规则继续约束保留代码与已发布事实，但不能作为恢复旧 Permission writer、兼容表或 dual write 的理由。

## 组件与边界

- `TestResource`、`ObservationBinding`、`RecoveryBinding` 和 `SecurityEffectConfirmation` 是普通录制后由用户分别确认的前置事实；它们不构成权限意图或安全结论，直到后续确定性 Compiler 将当前事实编译进唯一 Contract/Profile 链之前都不能进入 Runner。
- `PermissionIntentRevision` 是 Human GUI 明确批准的长期 ALLOW/DENY 安全需求真源；它按稳定 `intent_id` 追加 ACTIVE/RETIRED revision，并以项目 `policy_epoch` 标记批准事务。revision 引用稳定 Actor/Action revision、关系、预期和受保护 effect IDs，不绑定 Candidate、TestIdentity、资源实例、endpoint、会话、HTTP、秘密、Observer 或 Runner 细节。
- `ActorImplementationBinding` 与 `ActionImplementationBinding` 分别映射当前业务 revision 到 Candidate；源码变化只能影响绑定状态，不能删除或改写人类业务 revision。没有 Binding row 表示用户从未建立代码映射，不强制形成重绑任务；已有 Binding 的证据消失或漂移才实时投影为 `MISSING / STALE / AMBIGUOUS`。
- `BoundaryProposalBundle` 冻结完整 Actor、Action、Effect、Permission 与来源快照。服务端批准事务校验 proposal fingerprint、来源 freshness、唯一 Decision 和 revision 引用，失败时不留下部分正式事实。
- 保留的 `SecuritySetupCompiler` 与 `CheckPreview` 当前没有接入 Permission v2 产品主链；不得以旧 `IntentImplementationBinding`、PermissionDraft 或权限矩阵作为兼容输入。
- `SourceRevisionSnapshot`、`ChangeManifest`、`SourceChangeSet` 与 `ChangeImpactAssessment` 保存受控重分析形成的版本、Agent 有界声明、服务端真实 diff 和逐权限影响。Agent 的 claimed paths 只作线索；源码正文、diff、Git 信息和命令输出不进入该聚合。
- `SourceRevalidationInspection` 是已保存变化相对当前源码、ACTIVE revision 与 CURRENT binding 的唯一只读核对；`RevalidationPlan` 只从 READY inspection 形成。直接相关权限至少进入必需重验集合；映射待审、无基线、源码漂移或策略漂移都关闭执行。`ProjectRevalidation` 再统一组合准备度和可信结果。当前 Runner 仍执行完整 Coverage，不按变化评估裁剪用例。
- `PermissionContract`/`ContractVersion` 是唯一可执行安全意图；Action 通过 `effect_ids` 引用 Security Effect Manifest，只有 ACTIVE 版本可进入执行。
- `Coverage` 和 `PermissionMutationPlan` 只从契约编译有界用例、关系和 required observations；`DifferentialExperimentPlan` 在覆盖之后建立 ALLOW 控制、DENY 变体和唯一变化说明。
- `WebExecutionSnapshot` 与 `PersistedExecutionRequest` 固定当前 Web Contract、计划、bindings、运行预算，以及提交时的 `PermissionPolicySnapshot(project_id, policy_epoch, policy_fingerprint, entries)`；变化重验还冻结 `ChangeVerificationContext(change_id, impact_fingerprint, required_intent_ids, source_fingerprint)`。Runner/Evidence 不接收文件清单，后续 live Ledger 或源码变化不能改写已提交 Run。
- `ExecutionFact` 表示请求表面事实；`ObservationFact` 以 `effect_id` 绑定具体观察与业务效果，`SecurityEffectFact` 按 manifest 效果聚合权威性、完整性、可靠性、基线和时间闭合。EffectProjector 只解释冻结业务投影，不用整个状态摘要猜测效果。
- `Evidence` 保存不可变 Case/孪生快照、执行与效果事实、观察完整性和有界脱敏证据。
- `AuthorizationContinuityAssessment` 是孤儿后果的唯一纯判断：它只消费冻结 `PermissionContract`、单个 DENY `PermissionTwin` 和已形成的 `SecurityEffectFact`，结果只允许 `INTACT / ORPHAN_EFFECT_CONFIRMED / UNKNOWN`。它不读取 Trace、live Ledger、当前源码或目标现场，也不是第四 Verdict。
- `BreakpointLocator` 是 publication 后的被动核心分析器：它复用 Continuity 已确认的孤儿效果，再消费冻结 ALLOW/DENY `ExecutionTrace` 和 Evidence 引用定位权限断裂。Trace 缺失只能把精度降到 RANGE/VIOLATION_ONLY，不能推翻外部权威 Observer 已确认的孤儿后果；它不提交 Job、不读取当前目标或实时权限意图，也不改变 Verdict、Finding、Gate 或 Report。
- `ResultPresentation` 把授权连续性、唯一 primary、后续 amplifier 和当前 DENY Trace 内的已确认影响锥确定性投影为固定七项业务故事，并从已提交 Run 的冻结请求复制权限版本、相关 intents 与可选变化重验摘要；它不读取 live Ledger 改写旧结果，也不重算类型、位置或精度。1.1.1 当前 Workspace 不接回旧 INCONCLUSIVE 恢复或结果路由。
- `Verification` 根据规则和证据形成 Verdict；publication 后由幂等 ResultFinalizer 物化 `Finding`/Occurrence 和基础 `Report`；`Baseline` 表示历史比较，`Gate` 是可选交付门禁并产生独立 Gate 报告。报告只汇总已发布语义事实。
- ownership 和 permissions 使用同一 Permission → Runner → Evidence → Verification → Results 链；复杂关系不建立第二套安全结论路径。

## Canonical 与 Hash 边界审计

所有语义 hash 都使用 UTF-8、键排序、紧凑分隔符并拒绝 NaN；相同字节规则不代表相同领域语义。最终代码按下表保留独立函数，禁止合并为万能 canonical 工具：

| 领域函数 | 输入、排序与排除 | 版本与非 JSON | 稳定身份消费者 | 决定 |
| --- | --- | --- | --- | --- |
| `permission_model_sha256` | Permission/Plan/Differential 的 Pydantic、`StrEnum`、Mapping、序列；排除只由调用方显式投影 | 模型中的 `schema_version` 参与；非 JSON/NaN 拒绝 | Contract、Case、Plan、Differential、行为指纹与 finding pre-identity | 保留在纯 Verification Core；不依赖协议或基础设施 |
| `permission_intent_sha256` 与 SecuritySetup authority fingerprint | 前者只含 effective state、三类业务显示名、关系、期望和受保护效果，明确排除 ID、revision、epoch、approval、candidate、运行与时间；后者纳入当前 policy snapshot 与可执行事实并排除编译输出 | 关系事实无独立根版本；非 JSON/NaN 拒绝 | revision 语义身份、Generated Contract/Profile 身份与 stale 判定 | 换审批人不改变语义 hash；换实现 binding 或账号代表会改变生成配置；秘密正文永不参与 |
| `web_execution_profile_sha256`、执行请求 canonical bytes、`canonical_runner_sha256` | 仅接受各自当前 Web Profile、Persisted Request 或 Runner 文档；完整排序并执行秘密/大小检查 | 当前 wire 版本参与；未知模型、秘密、超预算或非 JSON 拒绝 | Profile、Request、RunnerResult 传输完整性 | 各自保留，因为允许类型、秘密规则和大小预算不同 |
| `observer_canonical_sha256` | Observer BaseModel 或已归一 JSON；状态先做深度、键数、字节和非 JSON 约束 | Observer wire/state 版本参与 | normalized state、source、trace 与观察关联 hash | 保留在 Observer 协议，具体 Adapter 只消费它 |
| `_evidence_semantic_sha256` | Evidence 语义 payload；明确排除 `evidence_id/evidence_hash`，并稳定排序 observations/outcomes | Evidence `schema_version` 参与；非 JSON/NaN 拒绝 | Evidence ID 与 evidence_hash | 私有于 Runner 协议，不能替换完整 Runner 文档 hash |
| Finding stable key 与 `_finding_snapshot_sha256` | FindingIdentity 明确排除自身 `schema_version`；派生快照按已排序 Finding/Occurrence 视图计算 | 快照视图显式带版本；非 JSON/NaN 拒绝 | Finding ID、run finalization 的 finding snapshot | 两者用途不同，分别保留明确名称 |
| `gate_canonical_sha256` | Baseline、GatePolicy、GateFacts 与显式 ID 元组；无隐式排除 | `policy_version` 和模型版本参与；非 JSON/NaN 拒绝 | Baseline ID、Gate input hash、GateResult ID | 保留在 Gate Core，不复用 Permission hash 名称 |
| `report_canonical_sha256` 与语义输入函数 | Report semantic payload 明确排除 `canonical_sha256`；BASE/GATE 输入字段分别固定 | Report/规则版本参与；非 JSON/NaN 拒绝 | BASE/GATE report ID 与 canonical hash | 保留在 Report 协议；Artifact summary 与 Gate 输入使用具名函数 |
| publication、Artifact、Web exchange 的具名 hash | 完整 manifest、原始文件字节或已归一 Web 输入/输出 | 各自格式/预算负责校验 | publication、artifact、ExecutionFact input/output 完整性 | 属于传输/文件完整性，不冒充安全语义 canonical |

稳定身份回归固定 Profile、Contract、Plan、Differential、Request、Evidence、Finding、BASE/GATE Report 与三态 Verdict；重命名函数不得改变任何输入 payload 或字节。

## 关键数据流

```text
Human GUI 批准 BoundaryProposal 并推进 policy_epoch
  → BusinessActor/Action revisions + Actor/Action bindings + PermissionIntentRevision

保留但尚未接回的执行链：
  → Permission v2 适配后的确定性 SecuritySetupCompiler（后续版本）
  → PermissionContract
  → 当前唯一 Generated Profile + CheckPreview
  → 用户确认提交
  → Coverage / PermissionMutationPlan
  → DifferentialExperimentPlan（ALLOW 控制 / DENY 变体）
  → 冻结执行快照
  → ExecutionFact + ObservationFact + SecurityEffectFact
  → Evidence
  → Verification
  → Run publication
  → AuthorizationContinuityAssessment（冻结 twin + effect facts，三态纯判断）
  → BreakpointLocator（复用 Continuity + Trace，只读定位）
  → ResultPresentation diagnosis（固定七项故事 + 已确认影响锥）
  → Finding / Occurrence / 可选 RepairContract / Base report.json v5
  → 可选 Baseline / Gate / Gate Report
```

代码变化沿同一执行链进入，不建立第二套 Verification：

```text
Agent ChangeManifest → 服务端源码快照与真实 diff
  → ChangeImpactAssessment → RevalidationPlan
  → Human GUI 处理待审 binding
  → 当前完整 Compiler / Coverage
  → 冻结 ChangeVerificationContext → 现有 Runner / Evidence / Verification
```

修复型变化不建立第二套执行器：服务端从原 BLOCK/Finding 重建唯一 RepairContract，Agent 只回传权威引用；通用变化链冻结 `RepairVerificationContext`，再由现有 Runner/Evidence 形成独立的 `VERIFIED / NOT_VERIFIED / INCONCLUSIVE`。该三态不替代 Verification Verdict；改变原权限、删除受保护效果、降低证据或破坏 ALLOW 控制都不能把修复判为 VERIFIED。

DENY 变体出现确定性 ACCEPTED 或任一权威、完整、可靠、相关的禁止效果 CONFIRMED 时进入 BLOCK。PASS 必须同时满足请求被拒绝、全部禁止效果可靠 ABSENT、时间闭合、ALLOW 控制有效和基线一致；其余为 INCONCLUSIVE。辅助观察失败不能抹去已经确认的越权效果。

## 关键不变量

- Human GUI 的服务端批准事务是改变 PermissionIntent 语义与正式实现映射的唯一入口。CLI、MCP、Machine、AI、Compiler、Check Prepare、Run 和 Recording 只能读取、准备或提出不生效 proposal/草稿，不能修改 ALLOW/DENY、退休规则、批准 binding 或推进 policy epoch。
- 变化声明不能携带权限、Case、Effect 或 Profile 选择。`NO_DIRECT_EVIDENCE` 只表示当前未发现与已知实现证据直接相交的变化，不代表安全；变化重验不得删除 ALLOW 控制、DENY 变体或其他当前 Coverage。
- 普通“开始检查”提交只消费当前 Compiler 生成的唯一有效 Profile；页面只展示 CheckPreview，不接受 Profile 标识或路径作为普通用户选择。coverage gap 阻止把未覆盖范围冒充 PASS，但不被改写成执行失败。
- 被引用的 role/action 或 source、endpoint、Flow、资源、观察、恢复、安全效果发生变化时，人类 revision 仍保留，只有 implementation binding 降级；账号代表或会话变化形成实时执行 gap。任一权威输入变化都使旧 Generated Contract/Profile 不可继续提交，不能通过隐藏或删除规则缩小检查范围。
- `risk_hint`、HTTP method、响应或观察候选只能推荐 SecurityEffect；只有用户确认的当前效果事实才能进入后续编译，无法安全映射时必须保留 coverage gap，不能默认使用 `STATE_MUTATION`。
- ACTIVE ContractVersion 不原地修改；执行使用绑定版本和冻结快照。
- `ExecutionFact` 不携带 HTTP method、path、body 或 URL；HTTP 细节留在 Web binding 和受限观察中。
- ALLOW/DENY 孪生除显式身份、关系、上下文或 workflow state 外必须保持 workflow、target、非身份输入、逻辑资源、初始业务状态、effect manifest、observer bindings 和 normalization 一致；秘密字节不参与指纹。
- 基线只由 EXACT_RESTORE 或版本化 NORMALIZED_EQUIVALENCE 证明；reset 调用本身不是基线证据。
- BLOCK 使用存在性证据，PASS 使用全称证据；时间闭合 OPEN/UNKNOWN、基线无效或 ALLOW 控制无效都不能 PASS。
- Evidence 发布后不可变，Finding/Gate/Report 不反改原始 Verdict；证据不足后的准备修复和重新检查只能形成新 Run，不允许追加、修订或重开旧 Run 的观察窗口。
- Breakpoint 只对 DENY Case 中权威 `CONFIRMED` 的效果工作；首批类型固定为 AUTHORIZATION_MISSING/LATE/BYPASS、IDENTITY_SUBSTITUTION、AUTHORITY_EXPANSION 和 COMPENSATION_MASKING。每个 Case 只有一个最早可证明 primary，后续异常只记为 amplifier；事件对齐只使用 action、逻辑 resource、通用 kind、effect identity、父角色关系和同业务 `semantic_key` 辅助项，event/task ID、时间戳、HTTP 状态和列表位置不参与对齐。
- Authorization Continuity 只有 `INTACT / ORPHAN_EFFECT_CONFIRMED / UNKNOWN`。DENY 的受保护效果一旦由权威 `SecurityEffectFact.CONFIRMED` 证明，就不能被缺失 Trace 或表面拒绝改写；`INTACT` 必须由全部受保护效果的闭合、可靠、相关、基线有效 `ABSENT` 事实证明。
- Breakpoint 精度只允许 EXACT、RANGE、VIOLATION_ONLY。Trace partial、候选并发歧义或缺少稳定前界时必须降级，不能以 confidence 百分比或当前现场回读填补证据；结果中的全部事件引用必须属于对应 DENY Trace。
- `VIOLATION_ONLY` 在 Trace 无法支持具体类型时允许 `breakpoint_type = null`；这表示孤儿后果已确认但主断裂当前不可定位，不得用默认类型填空。`EXACT` 与 `RANGE` 不允许空类型。
- 结果故事顺序固定为权限要求、实际身份、本不该发生的业务后果、合法授权来源、首个可证明主断裂、后续 amplifier、最终业务影响。影响锥只沿当前已发布 Trace 的 child edge 向下游展开，并且只呈现 Locator 已确认的事件；不能按时间、列表位置或相似文案补边。
- RANGE 与 VIOLATION_ONLY 必须保留稳定降级文案。模型说明只可消费 `breakpoint_type`、`precision`、`minimal_witness`、`confirmed_impacts` 四项白名单事实，不能改变断裂类型、位置、精度或影响集合。
- Finding/Occurrence 和基础报告在 publication 后自动、幂等地形成；派生失败可重试但不能回滚 publication，GET 保持只读。
- 没有 Baseline 或 Gate 也必须存在基础报告；后来形成的 Gate 报告是独立不可变版本，不能覆盖基础报告。
- Verification Verdict、Job/Run 生命周期和 GateResult 分开保存。
- 模型可以在权限草稿入口为当前有限 option 提出不生效的 ALLOW/DENY 建议；其他入口只能排序或解释有限事实。模型不得批准权限、生成正式 PermissionIntent、恢复方式或执行命令，也不得决定 Contract 状态、Verdict、Finding 或 Gate。
- 产品结果读模型只能从已发布快照、ExecutionFact、ObservationFact、Evidence、Finding 和 Verification 确定性投影可读标签与解释，不得重写 Finding 身份、Occurrence Verdict、Verification Verdict 或 GateResult。
- `ResultPresentation` 可以把当前 Action 的实际 Observer 来源投影为 KEY/SUPPORTING 与 FOUND/NOT_FOUND/UNAVAILABLE；角色来自冻结 EffectBinding，状态来自对应 Outcome 和 ObservationFact，任何展示状态都不能反向影响 Verification、Finding、Gate 或 Report 机器真源。

## 失败语义

候选冲突、契约不完整、覆盖缺口、孪生不唯一、指纹漂移、基线无效、时间未闭合、观察缺失或事实 UNKNOWN 时拒绝给出安全通过，并保留可解释的限制原因。验证失败与执行生命周期失败分别记录，不能用 Job 完成态替代安全 Verdict。最新结果为 INCONCLUSIVE 时，控制面只依据当前权限考题、统一重验和准备投影指向 `/permissions`、`/preparation` 或 `/validation`；它不调用 Observer、Runner 或 Verification。

## 安全约束

权限规则、目标范围、身份、动作和 required observation 必须可追溯到同一执行快照。秘密值不进入 Contract、协议、Evidence、日志或报告。结果中的原始观察必须有界并脱敏。

## 兼容与版本

Schema/protocol 版本只描述机器格式；不代表产品代际。未知字段、结构签名、指纹或证据关联不满足要求时严格失败，不按旧开发格式猜测读取。
