# 应用接入与检查主流程

> 状态：CURRENT。当前适用范围：Web 应用接入、测试账号、业务流程、权限准备、检查预览、运行进度与结果解释。

## 职责

说明普通用户从一个本地 Web 应用进入界鉴，到形成确定性权限检查结果的唯一主路径；明确每一步的权威事实、用户确认和安全边界。Windows 启动、CLI、API 会话和本地维护见[产品入口与控制面](./产品入口与控制面.md)。

## 普通用户主路径

```text
选择应用目录
→ 确认应用已运行并授权 loopback 地址
→ 单独授权只读源码分析
→ 审阅角色与业务动作候选
→ 准备测试账号
→ 录制并审阅业务流程
→ 确认测试资源、观察、恢复和安全效果
→ 确认权限规则
→ 预览并开始当前可运行检查
→ 阅读结果、证据与历史变化
```

应用接入只剩 ApplicationUnderstanding 流程。普通用户不注册、选择或上传执行 Profile；后端可以继续保存由当前权威事实确定性生成的内部执行配置，并通过只读高级信息解释它。

## 应用接入与候选确认

基础目录识别只允许目录选择和受限配置元数据读取，不执行目标命令、不联网、不读取普通源码正文或秘密。系统从结构化配置、公开接口描述、显式启动端口和已识别框架默认端口中有界发现 IPv4 loopback 地址；用户确认并授权规范化后的 `127.0.0.1` 地址后，才可以单独授权源码只读分析。`localhost` 只有实际包含 `127.0.0.1` 解析结果时才可规范化；仅有 `::1` 时明确提示当前 Web 执行不支持。

ApplicationUnderstanding 确定性提出带来源证据的角色与业务动作候选。用户可以确认、否定、重命名或补充；候选本身不形成 ALLOW/DENY、PermissionIntent、Finding 或 Verdict。来自多种结构来源的同一 canonical 身份合并 Evidence 和 confidence，展示名称不参与 canonical 身份分裂。

## Readiness 与确定性引导

`ProjectReadiness` 从 Project、ApplicationUnderstanding、TestIdentity、Flow、测试资源/观察/恢复、PermissionIntent、内部执行配置、Contract、Run 和 Recording 权威事实计算，只读供工作台、导航和接入页使用。它按每个已确认 action 分开显示权限组要求、当前可执行代表、代表缺口、可运行范围和剩余缺口；不持久化，不形成 CheckPlan 或新的安全真源。

`CheckPreview` 从同一批当前事实投影动作、权限组、资源关系、预期和覆盖缺口。至少一个 ALLOW/DENY 差分范围完整时可以运行，其他缺口继续明确显示且不能冒充为已覆盖 PASS。提交只消费确定性 Compiler 当前生成并登记的唯一有效执行配置，内部标识和路径不进入普通页面选择。

Guidance 只把实时事实收敛为普通用户下一步。当前 scope 可运行时，“开始检查当前可运行范围”始终是确定性主动作；剩余 coverage gap 只是可选补充。尚不可运行时只暴露最高阻断层。事实未变化时，刷新、切换菜单或 Run polling 不改变 Guidance 指纹。

AI 辅助位于这条确定性主路径的理解层，共有下一步、候选审阅、账号准备、录制审阅、权限复核、观察与恢复、检查预览、结果和错误九类固定 surface。每类输入都由服务端从对应正式 View 构造，只包含当前实体 ID 与有界短事实；客户端不能提交任意 prompt 或 facts。页面挂载和 GET 只冷读缓存，只有用户点击紫色 `[AI辅助]` 按钮后才允许 POST 调用模型。输出最多三条短纯文本，只能引用当前实体并使用该 surface 允许的 kind；模型不能修改候选、TARGET、权限预期、scope、Verdict 或恢复入口。

浏览器本地状态只保存上次选择的项目与页面；endpoint、候选确认、Run 和 Recording 都从后端权威事实恢复。

## 测试账号

测试账号绑定当前已确认角色、endpoint 与 ApplicationUnderstanding revision，是“用哪个测试角色准备会话”的项目资产，不是 Contract Subject、`WebExecutionIdentity` 或运行时 Cookie jar。

用户在独立 headed BrowserContext 中自行登录。只有点击“这个账号已经登录，可以保存测试状态”后，身份准备进程才提取当前 target host 最多 32 个 Cookie，或当前 target origin 的单一 Bearer；两者同时出现或认证状态不能安全归约时转入高级身份配置。密码、localStorage、完整 `storage_state` 和其他站点状态不保存，登录阶段不生成 Recording 事件。秘密正文只进入受控 SecretStore，普通 API、数据库、项目文件、日志、Evidence 和报告均不出现正文或可枚举引用。

## 业务流程录制与安全准备

普通 Recording 从一个已确认业务动作和一个已准备 TestIdentity 开始，不要求用户创建或选择内部执行配置。服务端读取动作、endpoint 与非秘密身份元数据，把精确 SecretStore 引用投影为本次录制专用环境引用；Recording Runner 在独立有头 BrowserContext 中恢复认证，秘密正文不进入请求快照、数据库、API 或 Flow。

`STARTING` 表示浏览器准备至等待明确开始的持久生命周期，`RECORDING` 只在开始采集后进入。更细的准备、等待、采集和停止阶段由 attempt 控制事实投影，不扩展持久状态枚举。开始与停止由 API/ApplicationCore 写入当前 attempt 的有界无秘密控制标记，Worker/Runner 消费标记并保持 TargetScope、事件预算、网络预算、脱敏和清理边界。Worker 在 claim 前确定性失败时，尚处于 `CREATED` 的 Recording 可以直接进入 `FAILED`，不伪造 `STARTING`、attempt 或 fencing token。

审阅页以动作卡片和步骤卡片为主。系统只从已录制请求的路径、query、JSON body 或先前响应推荐 TARGET、动态变量和资源位置，推荐不自动生效。用户确认唯一 TARGET 和有限资源位置；最终 Flow 绑定 action，并只保留 TARGET 与必要 SETUP，通过 `CASE_SUBJECT` 和 `CASE_RESOURCE_ID` 延迟注入差分主体与资源。Flow 不保存 alternate identity/resource、ALLOW/DENY、Observer 或 reset 默认。

Flow 保存后，用户分别确认测试资源、怎样独立观察真实结果、怎样恢复测试现场以及真正需要防止的安全效果。页面只允许当前 Recording 生成的有限候选和可读资源名称/类型，不接受 URL、脚本、任意 JSONPath 或秘密。候选只有确认后才成为事实；缺少观察保留 coverage gap，状态变更缺恢复时禁止自动执行，无法安全映射 SecurityEffect 时不得用 `STATE_MUTATION` 兜底。

权限规则页从已确认权限组、TestResource 所有者权限组和 action Flow 形成中文权限组×动作矩阵，用户只确认允许、拒绝或暂不确认。`PermissionIntent` 是普通安全需求真源；确定性编译器据此生成并治理 Contract，再从当前 Flow、身份、Observer 和 Recovery 生成内容寻址内部执行配置。账号代表只在编译和预览时选择，不写入 PermissionIntent。普通用户不编辑 Contract JSON、不选择内部文件路径，技术事实进入高级信息。

## 检查运行与结果解释

“开始检查”先展示当前可检查动作、检查用例、ALLOW/DENY 对照和未覆盖要求。可运行范围与剩余缺口可以同时存在，不能因为局部缺口禁用已经完整的范围。

运行中只根据 Job 生命周期和 Runner 非权威旁路事件展示“准备检查环境、验证正常允许的操作、尝试不应允许的操作、确认真实资源结果、恢复测试数据”。没有权威 completed/total 时不得估算百分比；旁路不可用只降级过程展示，不能改变检查结果。

结果页先回答“谁对什么执行了什么、规则期望什么、请求表面怎样、真实对象是否变化、为何形成该结论”，再展开安全意图、执行事实、观察事实和确定性结论。首屏汇总本次检查、符合预期、权限问题、证据不足和未覆盖要求：

- `PASS` 说明只覆盖本次实际范围，不代表绝对安全；
- `BLOCK` 解释预期、请求表面、真实结果、结论和原因；即使 HTTP 或页面显示拒绝，可信观察确认资源变化时仍判为权限问题；
- `INCONCLUSIVE` 既不代表安全，也不代表已确认漏洞，并给出完善真实结果确认方式的入口。

生命周期、结果完整性、Observer 配置、Schema、reason code、运行 ID 和证据原文默认进入高级信息或“查看证据”。只有 Job/Run 确实失败时显示执行错误；ErrorDiagnosis 提供确定性标题、短说明、恢复路由和 cleanup warning，不能把 `BLOCK` 或 `INCONCLUSIVE` 渲染成程序错误。

PASS、BLOCK 和 INCONCLUSIVE 使用同一信息层级。用户可见结果只使用已发布执行快照、Evidence、Finding 和 Verification 的确定性投影；展示读模型可以补充可读标签和因果说明，不能改变 Finding 身份、Occurrence Verdict、Verification Verdict 或 GateResult。AI 只能解释既有确定性事实，不进入结果真源。

## 关键不变量

- GUI、CLI 与 API 复用 ApplicationCore，不建立第二套接入、权限或执行向导。
- API/GUI 不直接向目标发高风险请求；实际目标操作进入 Worker 和隔离 Runner。
- 候选、用户确认、PermissionIntent、Contract、内部执行配置、Evidence 和 Verdict 各自保留边界。
- 用户可见状态不替代机器结果；INCONCLUSIVE 不显示为安全通过，HTTP 拒绝不替代真实状态观察。
- AI 关闭、未配置或失败不阻断确定性主流程；模型不得创建路由、角色、动作、权限规则、恢复方式或执行命令。
