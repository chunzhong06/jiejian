# 应用接入与检查主流程

> 状态：CURRENT。当前适用范围：Web 应用接入、测试账号、业务流程、权限准备、检查预览、运行进度与结果解释。

## 职责

说明普通用户从一个本地 Web 应用进入界鉴，到形成确定性权限检查结果的唯一主路径；明确每一步的权威事实、用户确认和安全边界。Windows 启动、CLI、API 会话和本地维护见[产品入口与控制面](./产品入口与控制面.md)。

## 普通用户主路径

```text
选择应用目录
→ 确认应用已运行并授权 loopback 地址
→ 单独授权只读源码分析
→ 审阅角色与业务动作候选
→ 准备测试账号
→ 录制并审阅业务流程
→ 确认业务资源、真实结果、独立观察和恢复方式
→ 确认权限规则
→ 预览并开始当前可运行检查
→ 阅读结果、证据与历史变化
```

应用接入只剩 ApplicationUnderstanding 流程。普通用户不注册、选择或上传执行 Profile；后端继续保存由当前权威事实确定性生成的内部执行输入。技术格式只进入 Machine 输出、证据、报告和开发文档。

## 应用接入与候选确认

基础目录识别只允许目录选择和受限配置元数据读取，不执行目标命令、不联网、不读取普通源码正文或秘密。系统从结构化配置、公开接口描述、显式启动端口和已识别框架默认端口中有界发现 IPv4 loopback 地址；用户确认并授权规范化后的 `127.0.0.1` 地址后，才可以单独授权源码只读分析。`localhost` 只有实际包含 `127.0.0.1` 解析结果时才可规范化；仅有 `::1` 时明确提示当前 Web 执行不支持。

ApplicationUnderstanding 确定性提出带来源证据的角色与业务动作候选。用户可以确认、否定、重命名或补充；候选本身不形成 ALLOW/DENY、PermissionIntent、Finding 或 Verdict。来自多种结构来源的同一 canonical 身份合并 Evidence 和 confidence，展示名称不参与 canonical 身份分裂。

## Readiness 与确定性引导

`ProjectPreparation` 从 ApplicationUnderstanding、PermissionIntent、SourceChange、TestIdentity、Flow、安全资产检查结果和当前生成配置实时投影准备清单。Recording 领域的 `ActionSafetySetupService.inspect_action()` 统一判断 Flow、资源、观察、恢复和受保护效果是否缺失或陈旧；准备聚合器不直接读取这些存储，也不另算候选和 stale。每项只有 READY、AUTO、USER、BLOCKED 四态；AUTO 只允许创建缺失的非秘密 TestIdentity 记录，或在其他前置项全部 READY 后复用正式编译链生成当前配置。它不能登录、生成 Recording、确认候选、改写权限规则或提交 Run，任何应用、权限或源码变化外部阻塞都先停止自动动作。

`ProjectReadiness` 消费这份结构化准备投影，并结合 Project、Contract、Run 和 Recording 权威事实计算工作台、导航和接入页状态。它按每个已确认 action 分开显示权限组要求、当前可执行代表、可运行范围和剩余缺口；`ProjectPreparation` 与 `ProjectReadiness` 都不持久化，不形成 CheckPlan 或新的安全真源。

`SourceChangeService.inspect_revalidation()` 是源码、权限版本和实现映射是否仍可重验的唯一只读判定；`ProjectRevalidationService` 再按固定顺序组合最新变化、准备度和可信结果，形成 NO_CHANGE、REVIEW_REQUIRED、PREPARATION_REQUIRED、READY、VERIFIED 或 STALE。ProjectPreparation、ProjectReadiness、Guidance、ProductStatus、变化页和验证入口都消费这份统一状态，不比较摘要计数或 change ID 另算一套结论。

`CheckPreview` 从同一批当前事实投影动作、权限组、资源关系、预期和覆盖缺口。至少一个 ALLOW/DENY 差分范围完整时可以运行，其他缺口继续明确显示且不能冒充为已覆盖 PASS。提交只消费确定性 Compiler 当前生成并登记的唯一有效执行配置，内部标识和路径不进入普通页面选择。

Guidance 只把实时事实收敛为普通用户下一步。当前 scope 可运行时，“开始检查当前可运行范围”始终是确定性主动作；剩余 coverage gap 只是可选补充。尚不可运行时只暴露最高阻断层。事实未变化时，刷新、切换菜单或 Run polling 不改变 Guidance 指纹。

AI 辅助位于这条确定性主路径的理解层，共有下一步、候选审阅、账号准备、录制审阅、观察与恢复、检查预览、结果和错误八类固定 surface。每类输入都由服务端从对应正式 View 构造，只包含当前实体 ID 与有界短事实；客户端不能提交任意 prompt 或 facts。页面挂载和 GET 只冷读缓存，只有用户点击紫色 `[AI辅助]` 按钮后才允许 POST 调用模型。输出最多三条短纯文本，只能引用当前实体并使用该 surface 允许的 kind；模型不能修改候选、TARGET、权限预期、scope、Verdict 或恢复入口。

权限页另有显式的自然语言草稿入口。用户输入只在当前 POST 中使用，模型只能引用服务端从当前矩阵生成的 opaque option ID，并附 ALLOW/DENY 建议和原文精确引文；返回结果只是待审草稿，不持久化、不自动应用。模型不可用时用户继续直接操作矩阵，正式 revision 仍只由 Human Approval 形成。

浏览器本地状态只保存上次选择的项目与页面；endpoint、候选确认、Run 和 Recording 都从后端权威事实恢复。

Agent 完成代码修改后，不重建权限规则。它通过 MCP 提交变化原因和可选路径线索，服务端在既有源码只读授权内重新分析项目，以前后快照形成真实增删改，再关联当前权限实现证据。路径线索不能决定影响或检查范围。没有可比较基线、实现映射待审、源码再次变化或权限版本漂移时，检查停止并回到权限页；Agent 只能提出 rebind proposal，仍由用户批准正式映射。

## 测试账号

测试账号绑定当前已确认角色、endpoint 与 ApplicationUnderstanding revision，是“用哪个测试角色准备会话”的项目资产，不是 Contract Subject、`WebExecutionIdentity` 或运行时 Cookie jar。

用户在独立 headed BrowserContext 中自行登录。只有点击“这个账号已经登录，可以保存测试状态”后，身份准备进程才提取当前 target host 最多 32 个 Cookie，或当前 target origin 的单一 Bearer；两者同时出现或认证状态不能安全归约时进入明确的失败诊断，不让普通用户处理内部认证统计。密码、localStorage、完整 `storage_state` 和其他站点状态不保存，登录阶段不生成 Recording 事件。秘密正文只进入受控 SecretStore，普通 API、数据库、项目文件、日志、Evidence 和报告均不出现正文或可枚举引用。

## 业务流程录制与安全准备

普通 Recording 从一个已确认业务动作和一个已准备 TestIdentity 开始，不要求用户创建或选择内部执行配置。服务端读取动作、endpoint 与非秘密身份元数据，把精确 SecretStore 引用投影为本次录制专用环境引用；Recording Runner 在独立有头 BrowserContext 中恢复认证，秘密正文不进入请求快照、数据库、API 或 Flow。

`STARTING` 表示浏览器准备至等待明确开始的持久生命周期，`RECORDING` 只在开始采集后进入。更细的准备、等待、采集和停止阶段由 attempt 控制事实投影，不扩展持久状态枚举。开始与停止由 API/ApplicationCore 写入当前 attempt 的有界无秘密控制标记，Worker/Runner 消费标记并保持 TargetScope、事件预算、网络预算、脱敏和清理边界。Worker 在 claim 前确定性失败时，尚处于 `CREATED` 的 Recording 可以直接进入 `FAILED`，不伪造 `STARTING`、attempt 或 fencing token。

界鉴根据录制顺序自动整理 UI 上下文、目标请求、业务资源和动态变量。唯一且可执行的解释直接采用；只有出现多个同级业务解释时，页面才让用户在业务动作、有限资源值或来源步骤之间选择。HTTP method、path 位置、JSONPath、step ID 和 candidate ID 仍保留在内部编译事实中，不进入普通审阅。最终 Flow 绑定 action，并通过 `CASE_SUBJECT` 和 `CASE_RESOURCE_ID` 延迟注入差分主体与资源；它不保存 alternate identity/resource、ALLOW/DENY、Observer 或 reset 默认。

Flow 保存后，Recording 只回答四件事：这次操作影响什么业务资源、真实发生了什么、怎样独立确认、怎样恢复现场。唯一候选由后端自动采用，真正有歧义时才显示业务选择。缺独立观察或恢复方式时，用户在同一业务动作和测试账号下补录 `OBSERVATION` 或 `RECOVERY`；补录不创建新业务 Flow、PermissionIntent 或 ALLOW/DENY。只读动作由后端确定不需要恢复，状态变更缺恢复时仍禁止自动执行。安全效果和权限含义只由 Human Approval 管理，Recording 不形成第二个审批入口。

安全资产检查只读取已经保存的 Recording、FlowDraft、ActionSafetySetup 和当前非秘密身份元数据，按当前 action、Flow revision 与资产语义判断五类资产是 CURRENT、MISSING 还是 STALE。它不会连接目标应用、恢复登录状态、读取秘密正文或写入确认事实；登录是否准备好由 TestIdentity 单独负责。

权限规则页从已确认权限组、TestResource 所有者权限组和 action Flow 形成中文权限组×动作矩阵，用户只确认允许、拒绝或暂不确认。选择新值后先在 Modal 核对当前要求、目标要求、受保护业务后果和 `policy_epoch` 影响，只有点击“确认权限变更”才写入；重新确认同一语义只更新实现映射，不推进 epoch。Agent 的语义或 rebind 建议进入“Agent 建议等待确认”，批准和拒绝均由 Human GUI 调用服务端正式事务，前端不构造 revision。每次真实语义变化由服务端 Human GUI 事务追加 `PermissionIntentRevision` 并推进项目 `policy_epoch`；当前 candidate 映射位于独立 binding，源码重分析或安全准备变化只让 binding 待复核，不删除人的规则。CLI、MCP、Machine、AI、Compiler、Check Prepare、Run 和 Recording 都不是审批人。确定性编译器只消费 ACTIVE latest + CURRENT binding，生成 Contract 和内容寻址内部执行配置；提交时再冻结权限策略快照。普通用户不编辑 Contract JSON、不选择内部文件路径。

## 检查运行与结果解释

“开始检查”先展示当前可检查动作、检查用例、ALLOW/DENY 对照和未覆盖要求。可运行范围与剩余缺口可以同时存在，不能因为局部缺口禁用已经完整的范围。代码变化重验继续执行当前完整 ACTIVE/CURRENT Coverage；变化评估标出的权限只是最低必需重验集合，不允许 Agent 用它缩小检查范围。

运行中只根据 Job 生命周期和 Runner 非权威旁路事件展示“准备检查环境、验证正常允许的操作、尝试不应允许的操作、确认真实资源结果、恢复测试数据”。没有权威 completed/total 时不得估算百分比；旁路不可用只降级过程展示，不能改变检查结果。

结果页先回答“谁对什么执行了什么、规则期望什么、请求表面怎样、真实对象是否变化、为何形成该结论”，并显示“本次检查依据权限版本 X”；代码变化重验还显示本次重验标记与必需权限数量。该版本、变化上下文和相关 intent revision 全部来自 Run 提交时的冻结快照，不读取 live Ledger 重写历史，也不向普通页面暴露路径或指纹。随后再展开安全意图、执行事实、观察事实和确定性结论。首屏汇总本次检查、符合预期、权限问题、证据不足和未覆盖要求：

- `PASS` 说明只覆盖本次实际范围，不代表绝对安全；
- `BLOCK` 解释预期、请求表面、真实结果、结论和原因；即使 HTTP 或页面显示拒绝，可信观察确认资源变化时仍判为权限问题；
- `INCONCLUSIVE` 既不代表安全，也不代表已确认漏洞。旧结论和旧证据永久保留；后端只针对最新一次证据不足结果，把冻结的 `(intent_id, revision, intent_hash)` 与当前权限考题逐项核对，再根据重验状态和准备度给出权限规则、测试准备或重新检查入口。重新检查只会创建新的 Run，不会补写旧 Evidence 或修改旧 Verdict。

生命周期、结果完整性、Observer 配置、Schema、reason code、运行 ID 和证据原文只进入 Machine 输出、证据、报告或开发文档；普通页面使用明确的“查看证据”入口，不设置通用“高级”收纳区。只有 Job/Run 确实失败时显示执行错误；ErrorDiagnosis 提供确定性标题、短说明、恢复路由和 cleanup warning，不能把 `BLOCK` 或 `INCONCLUSIVE` 渲染成程序错误。

PASS、BLOCK 和 INCONCLUSIVE 使用同一信息层级。用户可见结果只使用已发布执行快照、Evidence、Finding 和 Verification 的确定性投影；展示读模型可以补充可读标签和因果说明，不能改变 Finding 身份、Occurrence Verdict、Verification Verdict 或 GateResult。AI 只能解释既有确定性事实，不进入结果真源。

## 关键不变量

- GUI、CLI 与 API 复用 ApplicationCore，不建立第二套接入、权限或执行向导。
- API/GUI 不直接向目标发高风险请求；实际目标操作进入 Worker 和隔离 Runner。
- 候选、Human Approval、PermissionIntentRevision、IntentImplementationBinding、Contract、内部执行配置、运行权限快照、Evidence 和 Verdict 各自保留边界。
- 用户可见状态不替代机器结果；INCONCLUSIVE 不显示为安全通过，HTTP 拒绝不替代真实状态观察。
- 已发布 Evidence 和旧 Run 只读不可变；任何补充观察、准备修复或重新检查都形成当前事实和新的 Run，不存在事后补写证据窗口。
- AI 关闭、未配置或失败不阻断确定性主流程；模型只能整理人主动输入的待审权限草稿，不能创建路由、角色、动作或正式权限规则，也不能生成恢复方式或执行命令。
