# 应用接入与检查主流程

> 状态：CURRENT。当前适用范围：Web 应用接入、业务边界持续维护、动作级工作区、权限确认与后端动作准备；保留执行子系统的边界说明。

## 职责

说明普通用户从一个本地 Web 应用进入界鉴，到形成稳定业务边界与 Permission v2 的当前主路径；明确每一步的权威事实、用户确认和安全边界。完整新检查执行主链尚未重新接入。Windows 启动、CLI、API 会话和本地维护见[产品入口与控制面](./产品入口与控制面.md)。

## 普通用户主路径

```text
选择应用目录
→ 确认应用已运行并授权 loopback 地址
→ 单独授权只读源码分析
→ 将角色与动作 Candidate 作为建议
→ 编辑 BusinessActor、BusinessAction 与真实业务 Effect
→ 编辑 ALLOW / DENY 与资源关系
→ 生成不可变 Boundary Proposal
→ 查看完整摘要并由本机 GUI 明确批准
→ 刷新后读取动作级 Workspace 与唯一 PrimaryTask
→ 业务或源码事实变化时，从完整 current 边界提交 desired state
→ 服务端规划 revision、权限沿用/更新、停用与实现重绑
→ 再次审阅不可变 Proposal 并由本机 GUI 明确批准
```

权限确认不要求先准备 TestIdentity、Flow、Observer 或执行配置。手工 Actor/Action 可以不引用 Candidate；批准后业务语义仍为正式 ACTIVE，代码绑定明确为 `MISSING`。`/tests` 由 PreparationPage 显示当前权限考题、真实身份、动作演示、具体资源、结果证明和恢复方式；它消费同一 Workspace 与 Preparation 事实，不提供 Check/Run。`/changes` 继续不可用，不得接回旧权限写链。

## 应用接入与候选确认

基础目录识别只允许目录选择和受限配置元数据读取，不执行目标命令、不联网、不读取普通源码正文或秘密。系统从结构化配置、公开接口描述、显式启动端口和已识别框架默认端口中有界发现 IPv4 loopback 地址；用户确认并授权规范化后的 `127.0.0.1` 地址后，才可以单独授权源码只读分析。`localhost` 只有实际包含 `127.0.0.1` 解析结果时才可规范化；仅有 `::1` 时明确提示当前 Web 执行不支持。

ApplicationUnderstanding 确定性提出带来源证据的角色与业务动作 Candidate。非 stale 的 HIGH/MEDIUM 仅作为 UI 预选建议，LOW 不自动预选；用户可以排除、重命名、明确合并或手工补充。Candidate 不形成 BusinessActor、BusinessAction、ALLOW/DENY、PermissionIntent、Finding 或 Verdict，只能进入独立 implementation binding。

## WorkspaceView 与确定性引导

当前 `WorkspaceService` 只读组合 Project、ApplicationUnderstanding、正式 Business Boundary、Permission、pending Proposal、实时 implementation inspection 与 PreparationView。它先处理连接、源码授权/分析、待审提案、建立边界、权限复核、ALLOW 对照与主体/动作实现，再依次处理 REVIEW_RECORDING、PREPARE_TEST_IDENTITY、DEMONSTRATE_ACTION、PREPARE_ACTION_RESOURCE、COMPLETE_EFFECT_EVIDENCE、COMPLETE_RECOVERY。每次只发布一个带精确 action revision、slot、identity、recording 或 effect 上下文的 `PrimaryTask`；准备任务路径为 `/tests`，材料齐备可返回 None，仍不表示 CHECK 可用。相同事实产生稳定 task ID/fingerprint；前端不按列表顺序、文案或旧 Readiness 另算主任务。

## 权限考题与动作准备真源

`core/assurance.py` 从当前正式 Action 与 Permission revisions 现场编译只读 `ActionAssuranceContract`。它冻结业务身份、权限 hash、ALLOW 对照、受保护 Effect、身份位置与资源所有者需求，不含账号实例或技术绑定；业务 revision 改变合同，技术材料改变 inspection。缺少覆盖 DENY Effect 的合法 ALLOW 时返回 `ALLOW_CONTROL_REQUIRED`，Workspace 先引导回权限维护。历史非法资源关系保留原文并返回 `PERMISSION_RELATION_REVIEW_REQUIRED`。

身份规划按 Actor revision 合并必须相同的位置，再按必须不同约束分配账号；组件不超过 12 时精确分配，超过时按固定顺序保守分配，并公开 EXACT/CONSERVATIVE。每个资源所有者位置同时形成具体资源需求。账号精确匹配 Actor revision，PREPARED 优先，然后按创建时间、identity ID 排序；NEEDS_REVIEW 不能填补可执行身份。

`workflows/preparation/PreparationService` 每次读取正式边界、非秘密账号视图和技术检查端口，分开投影身份、动作执行、资源、业务结果证明及恢复方式。缺失的技术材料只能是 NEEDS_USER；只读 Action 的恢复为 NOT_REQUIRED。ApplicationCore 已装配四类技术绑定检查，并由 GET `/api/projects/{project_id}/preparation` 直接投影；`preparation_complete` 只说明材料齐备，不创建 Run，也不形成安全结论。旧 `validation_contract_complete` 占位已从后端权限状态删除。

## 保留的旧检查与准备模块

`ProjectPreparation / ProjectReadiness / ProjectRevalidation / ProjectRepair / ResultPresentation` 是保留的迁移资产，不是当前 ApplicationCore 与 Workspace 的事实来源；旧 ActionSafetySetup 已由动作技术绑定取代。不得依据旧矩阵、prepare-safe 或历史页面接回第二条准备链。检查编译、运行和结果入口未装配。当前三类 Assistant 与权限草稿入口见[修改模型服务](../02_开发指南/任务/修改模型服务.md)，不依赖这些旧模块。
## 不作为权限前置的测试账号

测试账号绑定正式 BusinessActor 的稳定 ID 与 revision，是“用哪个业务主体准备会话”的项目资产，不是角色 Candidate、Contract Subject、`WebExecutionIdentity` 或运行时 Cookie jar。账号或登录状态都不是 业务边界维护与权限审批前置。

用户在独立 headed BrowserContext 中自行登录。只有点击“这个账号已经登录，可以保存测试状态”后，身份准备进程才提取当前 target host 最多 32 个 Cookie，或当前 target origin 的单一 Bearer；两者同时出现或认证状态不能安全归约时进入明确的失败诊断，不让普通用户处理内部认证统计。密码、localStorage、完整 `storage_state` 和其他站点状态不保存，登录阶段不生成 Recording 事件。秘密正文只进入受控 SecretStore，普通 API、数据库、项目文件、日志、Evidence 和报告均不出现正文或可枚举引用。

测试账号页只保留一个可见刷新入口。创建、删除、准备成功以及 PREPARED 轮询命中后，页面先重读账号列表，再刷新整个项目工作区；只有这次刷新返回后，底部“继续准备”才按最新准备投影续接。轮询中的普通 tick 不触发工作区刷新。

## 不作为权限前置的录制与动作准备

普通 Recording 从一个已确认业务动作和一个已准备 TestIdentity 开始，不要求用户创建或选择内部执行配置。服务端读取动作、endpoint 与非秘密身份元数据，把精确 SecretStore 引用投影为本次录制专用环境引用；Recording Runner 在独立有头 BrowserContext 中恢复认证，秘密正文不进入请求快照、数据库、API 或 Flow。

`STARTING` 表示浏览器准备至等待明确开始的持久生命周期，`RECORDING` 只在开始采集后进入。更细的准备、等待、采集和停止阶段由 attempt 控制事实投影，不扩展持久状态枚举。开始与停止由 API/ApplicationCore 写入当前 attempt 的有界无秘密控制标记，Worker/Runner 消费标记并保持 TargetScope、事件预算、网络预算、脱敏和清理边界。Worker 在 claim 前确定性失败时，尚处于 `CREATED` 的 Recording 可以直接进入 `FAILED`，不伪造 `STARTING`、attempt 或 fencing token。

界鉴根据录制顺序自动整理 UI 上下文、目标请求、业务资源和动态变量。唯一且可执行的解释直接采用；只有出现多个同级业务解释时，页面才让用户在业务动作、有限资源值或来源步骤之间选择。HTTP method、path 位置、JSONPath、step ID 和 candidate ID 仍保留在内部编译事实中，不进入普通审阅。最终 Flow 绑定 action，并通过 `CASE_SUBJECT` 和 `CASE_RESOURCE_ID` 延迟注入差分主体与资源；它不保存 alternate identity/resource、ALLOW/DENY、Observer 或 reset 默认。

Flow 保存后，Recording 只回答四件事：这次操作影响什么业务资源、真实发生了什么、怎样独立确认、怎样恢复现场。唯一候选由后端自动采用，真正有歧义时才显示业务选择。缺独立观察或恢复方式时，用户在同一业务动作和测试账号下补录 `OBSERVATION` 或 `RECOVERY`；补录不创建新业务 Flow、PermissionIntent 或 ALLOW/DENY。只读动作由后端确定不需要恢复，状态变更缺恢复时仍禁止自动执行。安全效果和权限含义只由 Human Approval 管理，Recording 不形成第二个审批入口。

技术绑定检查读取当前正式 Action/implementation、非秘密账号状态、Recording/Draft 和 Flow 指纹，现场判断执行、资源、效果证明与恢复是否匹配。四类绑定只保存来源事实，不持久化 CURRENT/STALE；账号删除保留历史但准备失效，重新登录不能抹去原技术来源。

业务流程页在最终 Flow 或安全准备事实写入成功后，先重读本页事实，再刷新项目工作区并开放“继续准备”；Recording 生命周期轮询本身不刷新整个工作区，避免把每个进度 tick 变成全局状态请求。

当前权限写入不由旧矩阵 cell 驱动。用户在首次或维护 Boundary Proposal 中确认 Actor、Action、Effect catalog、资源关系和 ALLOW/DENY；维护前端只提交完整 desired state，服务端依据 stable IDs/revisions 与当前指纹确定 write mode。批准事务追加必要业务 revision、Permission v2、implementation binding、Decision 和 `policy_epoch`；CLI、MCP、Machine、AI、Compiler、Check Prepare、Run 和 Recording 都不是审批人。

权限确认沿正式 Boundary maintenance Proposal 与 LOCAL_GUI Approval，旧矩阵 cell、can_confirm 与 prepare-safe 不是当前消费合同。权限、身份或录制写入成功后的展示必须先重读局部事实，再刷新 Workspace；下一步只使用服务端最新 PrimaryTask，不保存第二套完成状态。

## 保留但尚未接回的检查运行与结果解释

“开始检查”先展示当前可检查动作、检查用例、ALLOW/DENY 对照和未覆盖要求。可运行范围与剩余缺口可以同时存在，不能因为局部缺口禁用已经完整的范围。代码变化重验继续执行当前完整 ACTIVE/CURRENT Coverage；变化评估标出的权限只是最低必需重验集合，不允许 Agent 用它缩小检查范围。

运行中只根据 Job 生命周期和 Runner 非权威旁路事件展示“准备检查环境、验证正常允许的操作、尝试不应允许的操作、确认真实资源结果、恢复测试数据”。没有权威 completed/total 时不得估算百分比；旁路不可用只降级过程展示，不能改变检查结果。

结果页先回答“谁对什么执行了什么、规则期望什么、请求表面怎样、真实对象是否变化、为何形成该结论”，并显示“本次检查依据权限版本 X”；代码变化重验还显示本次重验标记与必需权限数量。该版本、变化上下文和相关 intent revision 全部来自 Run 提交时的冻结快照，不读取 live Ledger 重写历史，也不向普通页面暴露路径或指纹。随后再展开安全意图、执行事实、观察事实和确定性结论。首屏汇总本次检查、符合预期、权限问题、证据不足和未覆盖要求：

- `PASS` 说明只覆盖本次实际范围，不代表绝对安全；
- `BLOCK` 解释预期、请求表面、真实结果、结论和原因；即使 HTTP 或页面显示拒绝，可信观察确认资源变化时仍判为权限问题；
- `INCONCLUSIVE` 既不代表安全，也不代表已确认漏洞。旧结论和旧证据永久保留；后端只针对最新一次证据不足结果，把冻结的 `(intent_id, revision, intent_hash)` 与当前权限考题逐项核对，再根据重验状态和准备度给出权限规则、测试准备或重新检查入口。重新检查只会创建新的 Run，不会补写旧 Evidence 或修改旧 Verdict。

结果页还直接显示当前 `ProjectRepair`。等待 Agent、变化已提交、可独立复验、复验通过、未通过、证据不足和失效都使用服务端投影；按钮只导航到服务端给出的现有区域，不新增“发送给 Agent”或“确认修复”动作。进入验证页时，正式修复的关联 change ID 优先，其次才是普通 `ProjectRevalidation=READY` 的 change ID。

生命周期、结果完整性、Observer 配置、Schema、reason code、运行 ID 和证据原文只进入 Machine 输出、证据、报告或开发文档；普通页面使用明确的“查看证据”入口，不设置通用“高级”收纳区。只有 Job/Run 确实失败时显示执行错误；ErrorDiagnosis 提供确定性标题、短说明、恢复路由和 cleanup warning，不能把 `BLOCK` 或 `INCONCLUSIVE` 渲染成程序错误。

PASS、BLOCK 和 INCONCLUSIVE 使用同一信息层级。用户可见结果只使用已发布执行快照、Evidence、Finding 和 Verification 的确定性投影；展示读模型可以补充可读标签和因果说明，不能改变 Finding 身份、Occurrence Verdict、Verification Verdict 或 GateResult。AI 只能解释既有确定性事实，不进入结果真源。

## 关键不变量

- GUI、CLI 与 API 复用 ApplicationCore，不建立第二套接入、权限或执行向导。
- API/GUI 不直接向目标发高风险请求；实际目标操作进入 Worker 和隔离 Runner。
- Candidate、BusinessActor/Action、BoundaryProposal、Human Approval、PermissionIntentRevision、implementation binding、执行快照、Evidence 和 Verdict 各自保留边界。
- 用户可见状态不替代机器结果；INCONCLUSIVE 不显示为安全通过，HTTP 拒绝不替代真实状态观察。
- 已发布 Evidence 和旧 Run 只读不可变；任何补充观察、准备修复或重新检查都形成当前事实和新的 Run，不存在事后补写证据窗口。
- AI 关闭、未配置或失败不阻断确定性主流程；模型只能整理人主动输入的待审权限草稿，不能创建路由、角色、动作或正式权限规则，也不能生成恢复方式或执行命令。
