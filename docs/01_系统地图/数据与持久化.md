# 数据与持久化架构

> 状态：CURRENT。当前适用范围：SQLite、migration、Storage、事务、公共身份、工件发布、报告和恢复。

## 职责

说明持久实体如何建立身份和事务边界，如何从 staging 发布不可变事实，以及数据库、文件、日志、缓存、秘密和恢复之间的边界。

## 非职责

- 不定义完整 JSON Schema 或 Runner 字段。
- 不把数据库生命周期状态当作 Verification Verdict 或 GateResult。
- 不提供旧开发数据库、旧 Profile/Run/Report 或旧 wire format 的猜测式迁移。
- 不替代执行与观察系统地图的进程和预算语义。

## 真源

数据库真源是 `product/backend/migrations`；Storage、Unit of Work、Repository 和发布代码是运行真源；公共跨进程模型位于 `product/protocols`。

## 目的

真实表达“什么可以提交、什么必须先发布、什么发布后不可变”。

## 组件与边界

- SQLite 保存 Project、Contract、WebExecutionProfile、Job/Run、事件、Evidence 索引、Finding/Occurrence、结果派生状态、报告索引、Baseline、Gate 和相关治理实体。
- Storage 按垂直聚合提供 Repository 与 Unit of Work；ApplicationCore 负责组合和事务编排。
- Alembic 管理结构；Web V1 只有 `0001_web_v1.py` 一个数据库基线，它从空库显式建立当前全部表、索引和约束，不在 migration 运行时调用当前 ORM metadata 代建结构。
- 当前持久实体包括 projects、application_understanding、test_identities、test_identity_cookies、test_resources、observation_bindings、recovery_bindings、security_effect_confirmations、permission_intents、runs、jobs、job_events、evidence_index、recordings、flow_draft_revisions、requirements、contract_candidates、contract_versions、llm_profiles、ai_assistance_settings、execution_profiles、findings、finding_occurrences、run_finalizations、regression_baselines 和 gate_results。
- `application_understanding` 是项目级应用连接与理解事实：保存受控 source root、用户已确认的 IPv4 loopback endpoint、源码分析授权与 fingerprint、角色/动作候选及用户决策和 revision。它是 SQLite 关系字段集合，不是独立 JSON 根文档，因此不保存 `schema_version`；候选 JSON 也只是记录内部片段，ProjectReadiness 不入库。
- `test_identities` 保存项目、已确认角色、endpoint/revision 绑定、可读标签、支持的认证方式和准备时间；`test_identity_cookies` 只保存有限 Cookie 元数据与逐项 `secret_ref`。Cookie/Token 正文只存在于共享 SecretStore 的 Windows Credential Manager 实现中，不把 TestIdentity 伪装成独立 JSON 根。
- `test_resources` 保存由一次已完成 Recording 和已确认 Flow 建立的逻辑测试资源、有限实际 ID、所有者 TestIdentity、OWNS 关系、资源位置及 source/endpoint/understanding/Flow 指纹；`observation_bindings`、`recovery_bindings` 与 `security_effect_confirmations` 分别保存用户确认的独立读取、恢复方式和安全影响。它们是可事务替换的关系事实，不是跨进程根文档，候选本身不入库。
- `permission_intents` 保存用户确认的动作、主体权限组、资源所有者权限组、关系与 ALLOW/DENY，不绑定具体测试账号、资源实例、endpoint、会话或源码 revision。Readiness 与 CheckPreview 仍为实时只读投影，不增加持久表。
- `llm_profiles` 只保存 provider、model、可空推理强度、预算、SecretStore 引用和其他非秘密连接配置；`ai_assistance_settings` 是全局单行设置，只保存开关、默认 profile 名称和更新时间。API Key 正文不进入 SQLite，profile 与设置在同一 Unit of Work 提交，Credential Manager 写入失败或数据库失败通过显式补偿保持一致。
- 普通模式生成的 WebExecutionProfile 以内容 hash 命名并写入 `var/data/projects/<project_id>/execution/generated/`；文件不可原地改写，SQLite 的 `execution_profiles` 继续只保存登记元数据。旧文件可保留为审计历史，但只有当前权威输入对应的 Profile 可构造或提交请求。
- Runner 先写受限 staging；Worker 校验关联 ID、fencing、大小、脱敏、路径和 hash 后原子 publication。
- Run publication 只保存 RunnerResult 与 Evidence；唯一 `ResultFinalizer` 在 publication 后幂等物化 Finding/Occurrence 和基础报告，派生失败以独立状态重试而不修改 Verdict。
- 独立 ReportStore publication 中的 `report.json` 是报告语义真源；HTML、SARIF、JUnit 是确定性投影。基础报告不依赖 Gate，后续 Gate 产生独立不可变版本。
- `RuntimePaths` 将 `var/data`、`runtime`、`cache`、`logs`、`temp` 和 `test` 物理分离；产品事实只进入 `data`，不属于源码或 Git。
- `var/cache/assistant/` 只保存已经重新通过本地模板与 option 白名单校验的模型推荐，或同一事实指纹的短失败退避；缓存按项目、模板和稳定事实指纹隔离，可删除、可重建，不进入 SQLite、Run、Evidence、Finding 或 Report。缓存禁止 raw prompt、供应商原始响应、隐藏思考和秘密。
- 可选 Wheel 复用 `var/runtime/frontend`，由 Hatch 在构建时映射为包内 `product/frontend/dist`，并包含 backend、protocols/Schema、配置、前端静态资源、migration 和 entry point；不包含 `node_modules`、tests、samples 或本地 `var` 布局。该路径不参与普通源码启动，也不向源码树回写 dist。

## 关键数据流

```text
ApplicationCore
  → UoW/Repository 建立身份与冻结请求
  → Worker/Runner staging
  → 协议、关联、完整性和安全校验
  → manifest/hash/Run publication → 数据库完成 Verdict
  → ResultFinalizer → Finding/Occurrence → 基础 Report publication
  → 可选 Baseline/Gate → Gate Report publication
  → GET、CLI、GUI 只读查询
```

数据库完成态只能引用已经校验并成功发布的事实。数据库提交失败而文件已发布时，由 reconciliation 幂等补齐；文件不完整或 hash 不符时不得标记完成。

## 关键不变量

- Project、ContractVersion、WebExecutionProfile、Run、Job、Evidence、Finding、Baseline 和 Gate 身份可追溯且不混用。
- ApplicationUnderstanding 的 endpoint 必须由用户确认；源码重分析按稳定 key 合并，不能静默删除用户确认或手工添加的角色/动作。
- TestIdentity 只在角色仍为已确认、endpoint/fingerprint 未漂移且全部精确秘密引用可读取时为 PREPARED；漂移或秘密缺失只形成 NEEDS_REVIEW。重置和删除必须先精确删除秘密，删除失败时保留数据库元数据以便重试。
- TestResource 的实际 ID 只允许有限标识，拒绝 URL、路径、脚本、疑似秘密和超长值；用户主文案与后续报告使用逻辑资源名，实际 ID 只作为受限执行事实。
- Action、Recording、Flow、source、endpoint、understanding revision 或资源值任一漂移时，旧资源/观察/恢复/影响聚合不再是当前可执行事实。写操作缺少用户确认的恢复方式时保持 coverage gap，不能进入自动执行。
- PermissionIntent 只在所引用动作、主体权限组和资源所有者权限组仍为当前确认事实时为 CURRENT。测试账号缺失、登录状态过期或同组执行代表替换只形成实时 coverage gap 或新的生成配置，不要求重写权限确认；确定性编译输入变化仍产生新 Contract 版本和新内容寻址 Profile，不能覆盖旧资产或静默继续提交。
- 生命周期状态、Verification Verdict 和 GateResult 分离保存。
- ACTIVE ContractVersion 和执行快照不可原地改写；已发布 Evidence 不可变。
- publication manifest、内容 hash 和语义 hash 必须可验证。
- Evidence 以内容寻址 ID 和运行内工件路径唯一；`case_id` 是关联字段而不是唯一身份，同一 Case 可为不同孪生上下文发布多条 Evidence。
- Worker 不执行 migration；运行进程不绕过 Storage 和事务边界。
- waiting Job 的 bootstrap 失败只能由 Storage 条件 SQL 在 `PENDING/RETRY_WAIT + no lease` 仍成立时转为 FAILED；Job、Run/Recording 终态和 `JOB_FAILED` 事件在同一 Unit of Work 提交。
- 报告只能消费已发布事实，不能反向修改 Verdict 或 Evidence。
- Finding/Occurrence 和报告的派生状态不进入 RunLifecycle；GET 接口不得物化、修复或改变任何持久事实。
- 缓存维护和 runtime repair 不得删除 `var/data`；数据重置是独立危险操作，不能与 cache clean 复用。
- AI 辅助缓存命中不能绕过本地严格 parser；未知 option、字段、模板版本或超预算内容一律按未命中处理。
- `jiejian system cache clean --confirm` 只清理可重建缓存，不得删除产品数据；损坏的运行时由 `jiejian system runtime repair --confirm` 显式修复，并在源码变化、最终网页缺失或强制准备等确需构建时重建，普通 prepare 仍可复用健康的最终网页。删除整个 `var` 是从零重建仓库本地运行态，不负责删除全局项目 Conda 环境。

## 失败语义

未知或旧 migration revision、结构签名不匹配、协议版本不支持、身份关联错误、hash 不一致、路径越界、秘密泄露、预算超限或 publication 不完整均 fail closed。非空数据库只接受精确 `0001_web_v1` revision 及当前表、列和索引关系；其他开发数据库停止并要求备份后重建 `var`，不删除未知数据、不猜测迁移。

## 安全约束

秘密只保存受控引用或最小环境注入所需的临时值；秘密值不得进入数据库公共 JSON、协议、Evidence、日志或报告。运行产物、缓存和凭据不得写入源码目录。

## 兼容与版本

Schema 版本和 migration revision 是不同边界。公共 Schema 版本按机器格式处理；数据库只接受唯一 `0001_web_v1` revision 与当前 head 结构签名。旧开发数据库、旧 `var` 布局和旧报告路径不迁移、不双读，也不保留猜测式兼容分支；显式删除数据库后由 ApplicationCore 从 Web V1 基线重建。
