# 工程设计规范

> 状态：CURRENT。适用范围：界鉴当前 Web V1 的代码组织、模块边界、公共格式、安全工程、产品呈现和长期可维护性。

## 1. 本规范负责什么

本文只回答“系统应该怎样设计”。它不规定线程怎么交接、不重复测试命令、不解释沙箱 ACL，也不承担具体模块的逐文件导航。

任务恢复与验收见[任务执行与恢复](./任务执行与恢复.md)，委派见[执行线程协作](./执行线程协作.md)；测试入口与 L1～L5 见[验证与测试](./验证与测试.md)；工作区、沙箱和 Git 权限见[工作区与权限](./工作区与权限.md)；文档如何组织见[知识与文档治理](./知识与文档治理.md)。

## 2. 系统形态与依赖方向

界鉴是模块化单体。GUI、CLI、API 和 Worker 共享 `ApplicationCore` 与应用工作流；高风险目标执行只能经持久 Job、Worker 和隔离 Runner。

当前稳定责任如下：

| 区域 | 责任 |
| --- | --- |
| `product/backend/core` | 领域模型、纯规则、Verification、权限和结果语义 |
| `product/backend/workflows` | ApplicationCore 使用的应用编排和跨模块工作流 |
| `product/backend/infra` | Storage、Repository、事务、队列、发布和外部基础设施 |
| `product/backend/api` | FastAPI transport、资源、任务、事件和结果读取 |
| `product/backend/cli` | CLI 参数、调用共享工作流、等待、取消和展示 |
| `product/backend/migrations` | Alembic 数据库结构与迁移真源 |
| `product/protocols` | 跨进程公共模型、canonical、hash、解析和 JSON Schema |
| `product/frontend` | Web GUI 的用户任务、状态投影和交互；不直接执行目标，也不重算安全结论 |
| `scripts` | Windows 启动、开发准备、构建和运行环境编排 |

`ApplicationContainer` 是 GUI、CLI、API 的完整组合根，`ApplicationCore` 是能力门面；Worker 使用独立完整的 `WorkerContainer`。领域纯逻辑不得依赖 FastAPI、SQLAlchemy、Playwright 或具体 LLM SDK；协议模型不得反向依赖具体 transport。

跨模块共享的是明确公共能力和协议，不共享“方便拿到”的内部对象。一个模块需要另一个模块的信息时，优先通过已经存在的应用服务、公共 DTO 或稳定接口取得，不从别人的内部 Repository、React state 或数据库表旁路读取。

## 3. 当前产品与执行边界

当前唯一生产 Target 是 `TargetType.WEB`。生产协议不保留未实现的 CLI Target、MCP Agent 或 Process adapter；`/mcp` 是复用现有 ApplicationCore 的本地控制 ingress，不是 Target，也不能扩展为任意目标执行。未来 Target 需要真实实现和独立验收后再加入。

安全主链保持唯一：

```text
安全意图
→ PermissionContract / PermissionIntent
→ Coverage 与执行计划
→ Worker / Runner / TargetRuntime
→ ExecutionFact / ObservationFact / SecurityEffectFact
→ Evidence
→ Verification
→ Run publication
→ Finding / History
→ ResultPresentation / Report
→ 可选 Baseline / Gate / Gate Report
```

具体数据流由系统地图和协议参考解释，本文不复制实现步骤。

权限意图只表达“谁对什么资源做什么应该允许或拒绝”；Web method/path、身份注入、资源定位和 Observer 细节属于执行绑定与观察边界。Verification 只根据已形成事实给出安全结论，不反向执行目标、补造证据或依赖前端展示。

## 4. 唯一真源与公共格式

同一类事实只保留一个权威真源。前端、报告、CLI 和 AI 辅助可以投影或解释，但不能各自维护第二套权限规则、Verdict、History、Readiness 或 Report truth。

- 公共机器字段以 `product/protocols/schemas`、协议模型和注册表为真源。
- 可独立持久化、跨进程或对外交换且有独立 reader 的根文档才携带 `schema_version`；嵌套 DTO 不重复制造版本边界。
- canonical 序列化、hash 输入、身份关联、大小预算、秘密边界和严格解析必须稳定、可复现。
- Repository 从数据库恢复严格领域模型时，必须显式重建数据库不会自动恢复的 enum、tuple、嵌套模型等领域类型；不能把 SQLite/JSON 返回值直接当成领域对象。
- migration 是数据库结构变化的唯一入口。代码不得静默改表，也不得绕过 migration。
- 当前 Web V1 不为早期开发数据库、旧 Profile/Run/Evidence/Report 或旧 wire format 保留猜测式兼容读取。格式不匹配时明确失败，不建立长期 alias、fallback 或隐藏兼容层。

长期兼容只为已经发布或存在真实外部消费者的接口服务；开发期内部路径、route 和 DTO 没有真实兼容义务时，优先一次收敛到唯一当前形式。

## 5. 安全与副作用边界

- LLM 只能提出候选、排序或解释，不能决定 Verification Verdict、Finding、Gate，也不能自动激活权限规则。
- 秘密只通过受控引用和最小运行时注入；秘密值不得进入普通协议、Evidence、日志、异常、报告、源码或 Git。
- API/GUI 不直接发起高风险目标请求；目标范围、重定向、网络授权、预算、超时、脱敏和清理由执行边界负责。
- 已发布 Evidence 不可变；生命周期、Verification Verdict、Finding/Gate 等不同事实分别保存，不互相改写。
- `INCONCLUSIVE` 表示证据不足，不能解释成“安全”或“未发现问题”。
- display-only 的进度、诊断、统计、动画和 UI 投影只能读取权威事实或使用独立展示资源，不能消耗正式序号、ID、预算、重试、随机源、lease/fencing、canonical/hash 输入或 Verdict 状态。
- 用户看到终态后，页面状态最终必须重新收敛到后端权威事实，不能长期保留“Run 已结束但 Readiness 仍显示运行中”一类陈旧组合。
- `var/` 保存运行数据库、日志、缓存、临时 staging、审计和构建产物，不属于源码或提交内容。

## 6. 模块、抽象与文件设计

模块按真实业务、安全、协议、事务、进程或用户任务边界组织。新增抽象必须解决已经存在的问题，不为“未来可能会有第二个实现”预建空壳。

推荐判断顺序是：

```text
先确认职责是否真的独立
→ 再确认是否有稳定调用边界或独立失败/清理语义
→ 最后才决定是否拆文件、抽函数或增加接口
```

共享 helper 只有在真实复用或独立边界价值明确时才存在。不要为了满足函数数量、文件行数或目录整齐建立薄 wrapper、Manager、Coordinator、Service 壳。

代码规模只作为职责审查提示，不作为 CI 硬指标。文件明显同时承载多个演进方向、一个函数同时负责多种副作用，或修改一个小需求必须反复跨越无关代码时，应优先按职责拆分；反之，不为达到目标行数机械拆小文件。

声称代码“未接线”或“死代码”前必须从真实生产入口、registry、composition root 和框架注册核对。确认没有生产消费者、框架发现、当前需求或独立测试价值后再删除，不凭文件位置或单次 `rg` 结果猜测。

## 7. 用户可见产品设计

普通前端按“用户要完成的任务”组织，不按后端模块、DTO 字段或内部状态机组织。用户页面首先回答：

```text
这一步要完成什么
现在是什么状态
用户当前需要做什么
完成后发生什么
出现问题怎样恢复
```

后端返回的字段不能直接决定页面信息结构。普通页面应把事实组织成人能理解的故事或任务，例如“权限要求 → 应用回答 → 实际结果 → 结论”，而不是把 `subject/action/resource/relation/...` 原样排成字段表。完整字段、内部 ID、Reason Code、Observer、Profile、Schema 等进入高级详情或技术证据。

用户可见流程由后端权威事实驱动。前端可以决定名称、顺序、视觉和交互，但不能通过本地计数或临时 state 猜某个业务阶段已经完成；需要跨页面共享的步骤完成事实应由现有 Readiness/Presentation 等权威投影提供，不另建第二套前端真源。

同一任务区域优先只有一个明确主操作。只读“刷新状态”和会产生副作用的“重新登录 / 重新录制 / 重新准备 / 再次检查”等动作必须在命名和行为上分开，不能用模糊的“刷新”或“重新开始”隐藏副作用。

产品语言保持专业、自然、克制、容易理解。普通层使用用户需要理解的权限组、测试账号、业务流程、检查结果、证据不足等概念；内部工程术语只在高级详情中出现。

视觉和布局为信息服务：减少无意义的 Card 套 Card、重复边框和装饰性状态块；颜色主要承担主操作、状态、警告和来源，不用视觉效果代替文字语义。用户应始终能够发现安全退出等关键全局操作。

可访问性属于产品语义，不是视觉完成后的附加检查。替换组件或布局时必须保持或改善 accessible role/name、selected、disabled、loading、focus、键盘行为以及错误、警告、成功和终态语义。
