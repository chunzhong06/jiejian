# 知识与文档治理规范

> 状态：CURRENT。适用范围：`docs/` 五层开发知识、根入口、生成参考、CURRENT/历史分离、写作质量和同步责任。

## 1. 本规范负责什么

本文回答“知识应该放在哪里、读者怎样最快找到它、人工文档怎样写得清楚、代码变化后谁负责同步”。它不承担阶段任务管理，也不复制代码参考、测试命令或系统实现。

## 2. 知识入口与真源分层

界鉴只有一套 CURRENT 开发知识，不建立新旧两套入口。

| 位置 | 主要读者 | 负责什么 |
| --- | --- | --- |
| `AGENTS.md` | Codex | 行动门禁、全局硬边界和停止条件 |
| 根 `README.md` | 普通用户 / GitHub | 产品是什么、怎样开始使用 |
| `docs/llms.txt` | Codex | 唯一任务知识路由，说明不同工作必须读取哪些边界 |
| `docs/README.md` | 人类开发者 | 开发知识总入口和阅读方式 |
| `01_系统地图` | 开发者 / AI | 系统怎样协作、事实怎样流动、跨模块边界 |
| `02_开发指南/任务` | 开发者 / AI | 一类真实工作怎样完成 |
| `02_开发指南/模块` | 开发者 / AI | 稳定模块负责什么、从哪里进入 |
| `03_参考手册/代码` | 开发者 / AI | 工具生成的当前代码结构 |
| `03_参考手册/协议` | 开发者 / AI | 机器协议语义；字段仍由代码/Schema负责 |
| `04_工程约束` | 开发者 / AI | 协作、设计、验证、工作区和知识治理规则 |
| `05_设计依据` | 开发者 / AI | 为什么做出长期决策、仍约束当前实现的 ADR 和可迁移实验结论 |

Migration 是数据库结构变化真源；代码、测试、Schema 和实际运行事实最终决定“系统现在是什么”。

阶段提示词、问题账本、竞赛推进、临时调查和未来路线不进入 CURRENT Docs。具体执行任务名称、卡片编号、完成记录、版本施工顺序和“将在某版本接入”等过程信息，也不得写入源码注释或产品文案。运行交接材料保存在仓库外指定交接包或未跟踪的 `var/` 运行目录；调查默认保存在 `var/audit/<task>/`。只有主线程确认以后仍应遵守的结论，才写入上述长期知识。产品版本真源、公共协议版本和数据库 revision 保留各自的实际兼容语义。

## 3. 去重复与 CURRENT 原则

同一事实只维护一个详细真源。其他入口需要提及时只保留一句摘要和链接。

- 系统地图解释跨模块事实流，不复制逐文件签名和 ADR 历史。
- 任务指南解释“怎样完成工作”，不再写一遍整个系统架构。
- 模块参考解释职责、非职责和修改入口，不写成第二份任务教程。
- 自动代码参考描述公开符号、签名、import、PowerShell function 等“代码现在是什么”；人工 Docs 不复制这些清单。
- 协议参考解释目的、消费者、生命周期、失败/安全语义和版本；字段类型、required 规则仍以 Schema 为准。
- ADR 解释决策、理由、取舍和影响，不复制当前系统地图。
- 便宜且局部的实现细节留在代码附近。

CURRENT 文档只描述当前真实实现或仍约束当前实现的长期边界。已经被新 CURRENT 知识完整吸收的阶段过程和已取代说明从默认工作树删除，需要追溯时使用 Git。已取代/废弃/拒绝 ADR 不进入默认必读路由。

发现 Docs 与代码/测试/Schema/migration 冲突时，先标明冲突，核权威事实，再决定修代码还是修文档；不能让文档反向“补出”不存在的产品能力。

## 4. 文档写作目标：先让人会用，再让人深入

界鉴的开发文档优先学习成熟产品文档的任务式组织方式：读者先明白“这是什么、我能用它做什么、怎样完成第一次真实操作”，需要精确细节时再进入 Reference。

高频或跨模块 Guide 推荐按读者思路组织：

```text
这是什么 / 什么时候需要
→ 常见任务或快速入口
→ 我想修改什么，应该去哪里
→ 正常操作路线
→ 关键边界与不能做什么
→ 一个或少量真实示例
→ 怎样验证
→ 失败时先查哪里
→ 进一步参考
```

这不是固定标题模板。简单任务可以只有几段；复杂任务也不因为“完整”而复制所有源码。判断标准是：第一次进入项目的人不需要读完整模块源码，就能找到正确位置、理解主要边界、完成常见修改并知道怎样验证。

写作优先使用用户或开发者正在做的事情作为标题，例如“增加一个开发命令”“修改 Windows 启动显示”，少用内部类名作为导航标题。必要工程术语可以准确保留，但第一次出现时应让读者理解其作用。

Guide 中的例子必须来自真实当前能力，可复制命令和路径必须真实存在。不要写伪代码式“未来会支持”的 Quick Start，也不要为了好看伪造成功输出。

## 5. 系统地图、模块参考和 Reference

系统地图至少要让读者回答：这部分负责什么、不负责什么、权威事实来自哪里、关键组件怎样协作、哪些不变量不能破坏、失败时怎样表现、与哪些真源相连。只有确实相关的兼容、安全、版本内容才写，不要求机械凑齐固定十二个标题。

模块参考至少说明：职责、非职责、稳定入口、主要子域、常见“我想改什么 → 去哪里”、相关自动参考和直接验证。模块参考不逐文件复制函数列表。

协议参考至少说明：目的、生产者/消费者、生命周期、失败与安全语义、版本/Schema 真源和相关代码。机器字段表不手抄。

ADR 状态只使用 `提议 / 已接受 / 已取代 / 已废弃 / 已拒绝`。默认路由只进入仍约束当前实现的内容。

实验文档只保留问题、固定条件、观察、结果、结论、限制和可迁移影响；实验成功不等于生产能力已经实现。

## 6. 创建、更新、移动和删除

创建新文档前先确认已有唯一知识位置无法清楚承载该内容。只有存在独立读者、稳定职责或长期演进边界时才新增文件；不要因为一次阶段任务产生新永久目录。

修改代码、协议、Schema、migration、模块职责或安全边界后，主线程负责判断哪些人工 Docs 需要同步。执行线程提供当前代码事实和验证证据，不自行裁决长期文档表述。

人工维护的 `AGENTS`、README、任务指南、模块参考、工程约束、设计依据和协议解释由主线程直接编写、修改和验收。机器生成代码参考和 Schema 索引由确定性工具维护；人工不得手改生成区来掩盖漂移。

删除或移动文档前确认内容已迁移、Git 能追溯历史、没有必要消费者，并搜索旧路径引用。不要建立长期 redirect/wrapper 文档维持旧路径。

技术文档使用相对链接，标题使用稳定能力或任务名称，不使用阶段编号当作长期能力名。CURRENT 页面顶部应说明状态和适用范围；只有需要明确机器/事实真源时再额外写真源，不为模板机械增加字段。

## 7. 人类与 AI 的最小上下文路线

Codex 按 `docs/llms.txt` 的唯一任务路由读取所需知识；本文不再维护另一套开工清单。已读且仍有效的内容继续复用。

人类：

```text
README.md
→ docs/README.md
→ 当前任务 Guide
→ 需要时进入模块、系统地图和 Reference
```

已有 Docs 能定位模块时，不把“先全仓搜索、逐文件读懂后再设计”当作默认工作方式。若一次真实任务仍需要打开大量无关源码才能判断入口，优先检查任务 Guide、模块参考或 `llms.txt` 是否缺少路由，而不是把这种低效率固化成常态。

## 8. 文档验收

人工文档更新后至少检查：

```text
内容与当前代码/测试/Schema/migration 一致
没有第二个详细真源
链接与路由有效
旧路径消费者已经处理
普通 Guide 能直接定位常见修改
自动代码参考没有漂移
没有把阶段计划或未实现能力写成 CURRENT
```

`docs -Update` 只负责确定性生成内容；它不能证明人工说明写得清楚，也不能替代主线程对 Guide 可用性和产品知识准确性的验收。

高价值 Guide 的“快速找到修改位置”或职责等价表格必须通过确定性路径门禁。门禁只解析表格中用代码格式明确声明的静态仓库路径，允许目录和文件；动态 `var/` 运行路径、通配符、命令、示例值、类名和仅用于解释的短文件名不进入检查。被识别的路径必须在当前仓库真实存在；发现失效路径时修正文档或真实实现，禁止为了让门禁通过新建没有职责的占位目录。
