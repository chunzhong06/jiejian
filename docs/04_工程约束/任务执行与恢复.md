# 任务执行与恢复规范

> 状态：CURRENT。适用范围：普通任务与版本任务的执行、上下文恢复、提交和验收。

## 1. 普通任务与版本任务

普通任务采用“明确范围 → 修改 → 必要验证 → 交付”。局部修复、文档更新或单模块工作不强制创建执行卡、机器状态、人类账本或恢复提交；是否提交服从用户授权。验证依据放在现有对话或任务说明中即可。

用户明确指定版本目标、连续卡片或正式接受流程时，执行下面的完整恢复与验收事务。协作任务即使范围小也要明确写入权和交接；不能借轻流程跳过公共语义、安全边界或用户指定的验证。

### 权威顺序

当前用户的明确指令优先级最高。完整版本或任务提示词是范围、目标、禁令和最终验收真源；执行卡只切出当前自然子任务，不能扩大或缩减完整范围。机器状态只记录当前卡、写入者、基线、已接受提交和下一门禁；人类账本记录问题、裁决、说明和验收证据；CURRENT Docs、代码、测试、Schema 和 migration 分别说明长期约束与当前运行事实。

用户只提供背景、状态或交接材料而没有要求交付时，不自行调查、设计、实施、测试或委派。进入明确任务后才按根 `AGENTS.md` 和 `docs/llms.txt` 加载最少必要知识。

首次进入完整任务时读取完整提示词，只按语义标题边界读取账本顶部、当前卡和指定章节，并核对当前 `HEAD`、分支、working tree、最近接受点与机器状态。不得用固定行数、固定字节数或先全文读取再截断来猜范围；要求命中停止标题但没有命中时立即停止并报告。

## 2. 恢复与连续执行

新对话、上下文压缩、明显中断或用户要求继续时，恢复以下事实后再设计、写入或委派：

```text
最新用户指令和当前交付物
→ 当前 HEAD、分支和 working tree
→ 最近接受提交、账本和机器状态
→ docs/llms.txt 当前路由
→ 完整任务提示词和当前执行卡
```

旧聊天、摘要、提交名和旧路径只帮助定位，不能单独证明任务已完成、授权仍有效或工作树未变化。完整提示词始终是范围真源，不能被局部卡片或恢复摘要替代。

同一完整任务明确要求连续执行多张卡时，可以在首次入场建立连续信任窗口。上一卡只有完成“diff 审计 → 最小充分验证 → commit → SHA → machine state/账本 → working tree 核对”的接受事务，下一卡才可直接信任 `accepted_sha`；上下文压缩本身不要求重复整套入场审计。用户声明外部改动、出现未知写入者、接受事务不完整、Git 写操作失败或即将改写历史时，才重建相应边界。

任务机器状态与人类账本必须分开。职责等价的 `var/audit/<task>/stage-state.json` 不扩展成第二份问题历史，也不得通过正则解析 Markdown 账本推断机器推进状态。

## 3. 调查、设计与实施边界

复杂任务可以先做范围明确的只读调查，但调查材料默认写入 `var/audit/<task>/`，不进入 Git。只有经主线程裁决、后续仍须遵守的结论才写入 CURRENT Docs。

明显跨模块的任务在实施前形成模块实施图：

```text
每个模块要改变什么
→ 模块之间交换什么
→ 哪些公共语义不能改变
→ 实施先后关系
→ 每个模块怎样直接验证
→ 哪些工作由主线程完成，哪些允许交给执行线程
```

外部设计稿、旧聊天摘要、旧完成报告和历史提交都只是输入，采用前必须用当前仓库和 CURRENT Docs 复核。发现文档与代码实质冲突时明确说明并裁决应修改哪一方，不能静默选择。

## 4. 上下文与知识使用

知识加载遵循 `docs/llms.txt` 的唯一任务路由。已读且仍在上下文、未发生变化的正文继续复用；恢复时核对 Git、授权和接受事实，不机械重新读取整套文档。缺失完整范围或发生实质变更时，回读对应真源。

主线程把稳定设计、模块职责和开发入口写回唯一 CURRENT Docs。自动代码参考只描述“代码现在是什么”，人工文档解释“为什么这样、从哪里改、不能破坏什么、怎样验证”，两者不得互相复制。调查、diff、日志和测试输出限定到受影响路径；输出过大时缩小范围，不用重复全仓读取补偿截断。

## 5. 验证、真实体验与副作用

验证范围由当前任务提示词、受影响模块和 [验证与测试](./验证与测试.md) 共同决定。先跑直接测试和代表性闭环，再按风险决定是否升级；同一代码状态不重复完整 L4。测试只有真实收集并执行才构成证据，`0 collected`、路径不存在或收集前失败均不算通过。

预计耗时的多阶段流程必须有稳定、用户可见的阶段边界。进入阶段时刷新状态；能提供权威进度时有界输出，不能提供时说明当前阶段、可能的静默区间和停止条件。失败报告保留最后完成阶段和第一主错误，cleanup/回滚另列，不伪造百分比。

真实终端、浏览器、GUI、用户流程、视觉质量、焦点和键盘行为的最终体验由主线程验收。执行线程可以提供事实和直接测试，不能替代最终产品判断。

commit、push、reset、update-ref、删除、数据库写入、凭据写入和真实外部调用返回不明确时，先回读权威状态，不重复执行同一副作用来试探结果。真实付费、限额或产生外部影响的调用必须位于用户授权范围内。

## 6. 返工、提交与验收

一个自然子任务允许必要局部修复。主线程与执行线程对同一根因均以首次失败建立事实，再最多进行两次有证据的局部修正验证；两次后仍未解决则停止试错，收敛根因和方案。执行线程可以落实已经接受的跨模块实施图；出现超出该设计的跨模块协调、架构、安全、公共格式或范围扩大的问题时才升级。UI 等用户直接可见内容始终由主线程设计并实现，详细边界以[执行线程协作](./执行线程协作.md)为准。

验收只覆盖完整任务提示词和已接受任务明确列出的能力。范围外问题记录影响与后续建议；只有它直接否定当前任务成立时才重新划分边界。自然子任务可以建立恢复提交，最终是否 squash 或重写为一个版本提交只服从当前提示词和用户指令。

版本任务中自然子任务的正式接受是一次事务：最终 diff 审计和最小充分验证通过后提交，取得权威 SHA，再一次更新机器状态与人类账本并核对 working tree。任一步失败都不标记 `ACCEPTED`，也不重复建立“准备提交、已经提交、等待接受”多套恢复点。

正式接受前确认：

```text
完整任务范围逐项核对
问题账本和机器状态已更新
需要的人工 Docs 已同步
生成参考无漂移
直接验证充分，要求的 L5 已完成
Git/working tree 与完成报告一致
一次性执行线程已回收
没有混入下一版本或范围外工作
```

完整任务要求连续推进时，单卡接受不是停工点；否则任务或版本接受后立即停止，等待用户决定下一步。

## 7. 当前竞赛作品的版本规则

界鉴目前是持续完善中的竞赛作品，尚未对外发布稳定兼容承诺。产品使用连续功能版本：一个版本可以同时做产品减法、体验修复、内部重构和新增能力，只要完整提示词明确冻结范围并在版本结束时整体验收。不能因为历史版本中存在旧入口、旧字段或旧兼容层就自动保留它们。

产品版本、公共 Schema/protocol 版本、数据库 revision 和 Contract 业务版本彼此独立，不能机械同步。对外任务、文档和最终提交使用明确版本与能力命名；卡片只作为复杂版本内部的恢复边界，不作为新的产品代际。
