# 验证与测试规范

> 状态：CURRENT。适用范围：界鉴代码、协议、脚本、前端、文档和真实运行体验的验证合同。

## 1. 本规范负责什么

本文只回答“怎样证明一次修改成立”。它负责正式测试入口、模块范围、L1～L5、失败处理和提交前验证；不决定模块应该怎样设计，也不规定线程怎样委派。

## 2. 正式验证入口

Python 语法检查必须同时设置 `PYTHONDONTWRITEBYTECODE=1` 并使用 `python -B`，优先 `ast.parse`，不得在源码目录生成 `__pycache__` 或 `.pyc`。

pytest 的正式入口是：

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 test ...
```

裸 `python -m pytest`、PATH 中的 pytest 或“只激活 Conda 后直接跑”的结果不作为正式证据，因为它们不保证界鉴要求的项目根、用户包隔离、运行模式和主子进程身份。

前端 Vitest 的正式入口是：

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 frontend-test ...
```

后端 `test` 的追加路径以仓库根为坐标；`frontend-test` 的追加路径以 `product/frontend` 前端工作区为坐标。文档、help 和实现必须保持一致。

文档和 Schema 使用：

```powershell
.\scripts\dev.ps1 docs
.\scripts\dev.ps1 schema
```

默认只检查漂移；只有显式支持的 `-Update` 才允许更新签入的生成内容。

同一工作树的 `dev.ps1` 调用共享准备锁，必须串行执行；前一调用退出并释放锁后再启动下一调用。准备锁阻塞属于验证尚未执行，不记为测试断言失败。

## 3. 运行环境与安装视图证明

修改 Python package topology、`pyproject.toml` 包发现、editable 安装、开发同步、Worker/Runner import root 或发布安装方式时，必须离开仓库根和源码父目录，使用正式解释器验证对应公共包可以从安装视图导入。仓库根内导入成功不能替代仓库外证明。

测试若启动 Worker、Runner、Observer 或其他真实 Python 子进程，fixture 必须从正式父环境复制完整身份，再叠加当前用例授权的秘密。只有专门验证“缺失身份应被拒绝”的负向测试可以故意构造不完整环境。

前端依赖、pnpm store、Vite cache、测试 workspace 和 production build 只进入受控 `var/` 路径。生产 TS/TSX 变化除 Vitest 外，按风险补 TypeScript/production build；修改前端输入同步、构建或打包边界后，确认源码树没有 `node_modules`、`dist` 或 `*.tsbuildinfo`。

Windows PowerShell 5.1 需要读取中文的启动 `.ps1` 保持项目规定的 UTF-8 BOM；`.cmd/.bat` 保持既有 ASCII/无 BOM 边界。只有真正触及这些脚本时才验证字节约束。

## 4. 模块范围 × 验证程度

验证范围由两个独立维度决定：

```text
验证合同 = 受影响模块 × L1～L4 程度 + 是否需要 L5
```

模块按真实生产责任选择，例如 `core`、`workflows`、`infra`、`api`、`cli`、`protocols`、`scripts`、`frontend`、`architecture`，真正跨能力域时才使用 `e2e`。

- **L1 最小验证**：边界明确的局部修改。运行必要语法/类型检查、`git diff --check` 和少量直接测试。
- **L2 模块验证**：一个生产模块内的完整能力。先跑新增/失败项，再跑该模块集合。
- **L3 集成验证**：跨多个生产责任。验证相关模块、边界协议和一个或少量代表性闭环。
- **L4 全量回归**：公共协议、canonical/hash、Verification、ApplicationCore、Worker/Runner 公共生命周期、Storage schema/migration、大规模共享基础设施或阶段最终稳定树。阶段最终树通常只执行一次，同一代码/测试状态不重复。
- **L5 真实动态验收**：统一由 `dev.ps1 sample-test` 证明真实终端、PowerShell、浏览器/GUI、Worker/Runner 子进程、真实 Target/Observer、Credential Manager、数据库、端口与竞态。L5 是独立维度，不表示测试集合更大。

`essential` 只是稳定的重要回归集合，不等于 L1。L4 已包含它时，同一代码状态不先跑 `essential` 再立即跑全量。

## 5. 按改动明确验证依据

局部、边界清楚的修改用一句话说明受影响行为、直接验证和充分性即可，不要求新增合同文件。只改人工文档时检查内容、链接和适用生成漂移；功能修改验证改变后的行为。公共协议、安全、持久化、跨模块修改和正式版本仍须明确：

```text
受影响模块
当前需要 L1 / L2 / L3 / L4 中哪一级
是否需要 L5
为什么当前证据足够
什么新证据出现时才升级
```

人工整理的多文件、多节点 pytest/Vitest 清单或阶段测试矩阵，在真正执行前先确认路径和显式节点存在、坐标系正确。`0 collected`、路径不存在、节点不存在或收集失败不构成产品通过或失败证据。

验证按证据逐级扩大。执行线程不得因“保险”自行超过 handoff 给定的验证上限；真实影响变大时停止并把升级理由交给主线程。

最近一次 L4 必须绑定明确 HEAD 和 working-tree 状态。之后只有文档、注释或无行为文案变化时，不机械重复产品全量。L4 失败后先修失败项和直接邻域，只有共享核心被再次改变才重新决定是否需要第二次 L4。

## 6. 自动 L5 与展示验收

自动 L5 与竞赛验证共用唯一 `sample-test` family。无参数是 Official Sample 完整 L5：

```powershell
.\scripts\dev.ps1 sample-test
```

其余公共 suite 固定为：

```text
sample-test validation   = 完整验证 Case × 1
sample-test competition  = 完整验证 Case × 3
sample-test all          = official + validation
```

这些 suite 不建立第二个 L5 主命令。第二验证应用和 private oracle 只属于 tests / competition validation，不得进入普通产品 Sample 导航。当前 Worker 仅有 RECORDING 能力，完整检查与 Official Sample runtime 未接回，因此不运行 official、validation、competition 或 Portable；录制与退出验证按已装配能力执行，不能将 Worker running 解读为检查可用。

它必须从真实 `start.cmd` 启动隔离实例，并覆盖技术上可自动判定的启动、Recording、真实页面业务动作、Verification、Evidence、Report、History 和资源退出。不得再维护“sample-test 通过后还需运行另一套技术 L5”的双重入口。

人工检查只称为“展示验收 / Visual Acceptance”。它负责评委视角下的视觉、窗口体验、演示节奏、文案和交互，不重做自动 L5 已能确定的技术事实，也不新增人工 L5 命令。

产生真实副作用前先做一次只读 preflight，覆盖本轮真正依赖的：

```text
起始业务状态
运行身份与必要凭据
依赖、端口和外部服务
当前进程/控制会话
写入范围
后续步骤需要的状态
退出、清理或恢复条件
```

缺少必要条件时先停止，不先启动一半系统再逐项发现问题。

L5 结果必须绑定本轮实例、控制会话和起始状态；旧进程、旧页面、旧数据库状态或前一次结果不能作为本轮证据。

真实终端、浏览器、GUI 和用户流程中的技术闭环由自动 L5 验证；视觉层级、焦点体验、演示节奏和最终产品观感由主线程或用户做展示验收。用户可见 UI/UX 改动使用项目受控 Playwright 验证目标视口，单元测试和构建不能替代视觉与交互证据；至少覆盖受影响的桌面和窄屏布局、没有意外横向滚动或操作遮挡，并核对 accessible role/name、selected、disabled、loading、focus、键盘行为和错误/成功/终态语义。具体尺寸和操作清单由当前任务指南或阶段合同决定，不在本规范写死。

本地 Web 产品的自动 L5 使用仓库受控浏览器和正式产品进程。官方 Sample 的 headed Chromium、Recording Process、Windows UI Automation、运行收据和审计目录等实现合同统一见[修改官方示例与整链验收](../02_开发指南/任务/修改官方示例与整链验收.md)，本规范只规定验证层级和证据要求。

Codex 内置浏览器或用户 Chrome 控制只在任务确实依赖已有登录态、扩展或用户浏览器会话时使用，不能替代上述可复现的正式 L5。浏览器控制工具初始化失败属于工具/环境故障；若当前验收不依赖外部会话，直接使用仓库受控 Playwright 完成本轮 L5，不为适配工具修改正确的产品代码。若依赖的会话无法由受控 Playwright取得，则停止并交给用户恢复会话条件。

启动、端口或进程树变化时必须证明：旧实例不冒充新实例、ready 事实来自本轮进程、浏览器打开失败不被混成后端启动失败、退出后本轮拥有的服务/Worker/浏览器资源被正确回收。

## 7. 失败处理

失败后先区分：

```text
产品逻辑
测试 / fixture
运行环境 / 工具
```

修复后的第一步只重跑失败项；通过后按修复真实影响补直接邻域。只有修复扩大了共享边界才提升验证等级。

不得为了让测试转绿而擅自提高安全预算、请求数、超时、大小限制或重试次数，不得放宽 fail-closed 条件，也不得用第二次运行成功、固定 sleep 或预建空产物掩盖真实竞态。

错误解释器、缺失依赖、框架/jsdom 限制、浏览器 locator、错误测试路径和陈旧 fixture 不算产品失败，也不能为了适配验证工具而修改正确生产行为。

重复失败的方案应记录根因和错误假设；具有长期价值的结论转化为测试、规则、ADR、任务指南或校验项。

高成本验证的重试预算按“同一首错”计算，不按测试命令计算。首个有效失败用于建立事实，不计入重试次数；完成由小到大的分析并冻结修复后，允许针对同一稳定错误码或同一根因最多重试两次。语义相同但包装、堆栈或表面文案变化的失败仍占用同一预算；两次重试后旧首错仍存在时必须停止，不能靠继续运行碰运气。

同一命令在越过旧失败点后暴露新的第一主错误，表示验证已经推进到新的问题层，旧首错的重试预算随之结束，新首错重新拥有“初次失败 + 最多两次重试”的独立预算。每个新首错仍需先从失败模块内部分析，必要时再沿真实调用链扩大；不得把“错误变了”当作无需分析即可连续重跑的理由。

快速单测按失败项和直接邻域迭代。`sample-test`、完整 E2E 或 Golden 每次运行只消费并报告第一个有效失败，先保留无秘密的失败证据并确认本轮资源收口，不在同一次运行中继续试探后续问题。之后先只读形成以下矩阵并冻结一次性修复方案，才可在对应首错的剩余预算内重试：

```text
失败发生在哪一层
权威预期来自哪里
允许修改什么
禁止修改什么
一次性修复怎样验证
```

已经通过的高成本验证绑定当时的 HEAD 与 working-tree 状态。后续修改没有触及该场景的生产行为、fixture、协议、依赖或运行入口时，不机械重复；触及行为依赖时再按真实影响决定重跑范围。

正式 E2E 的失败输出只保留公开、有界、无秘密的 run、job、result、evidence 和稳定错误摘要。attempt、progress、staging 或私有诊断只可在本轮临时定位时读取；定位结束必须删除测试和验收对这些内部路径、字段或文件的依赖，不能把临时诊断债务留作长期断言。

## 8. 外部调用与秘密

真实模型或其他计费、限额、配额或会产生外部影响的调用必须维护本轮调用账本，至少记录 provider、operation、attempted、succeeded/failed、用户授权上限和剩余次数。

账本不得保存 API Key、完整 prompt、完整响应正文、reasoning 或思维链。第一次真实调用失败后优先用 mock、fake transport、recorded response 或本地受控 transport 验证修复；再次产生真实调用前按当前协作和用户授权要求处理。

## 9. 提交前验证

每次实现至少确认：

- 设计与当前权威文档一致；如果真实实现改变了长期设计，主线程已经同步唯一 Docs 真源。
- 没有新增秘密泄露、越界网络访问或未受控运行产物。
- 状态转换、失败、取消和清理路径有与风险相称的证据。
- 公共协议、Schema、API 客户端和实现保持一致。
- 需要的生成参考无漂移。
- 需要的 L5 已绑定当前实例并完成清理。
- `git diff --check` 通过，working tree 和阶段报告一致。

源码附近注释是否符合项目要求由 `.agents/skills/jiejian-comments/SKILL.md` 负责；本规范不重复注释格式和密度规则。

## 10. 测试放置

测试按生产责任放在 `tests/backend/core`、`workflows`、`infra`、`api`、`cli`、`protocols`、`architecture`、`e2e` 和 `scripts`；前端测试与对应前端源码共置。跨边界测试按被验证行为的主要所有者放置。

跨多个域真正复用的稳定构造器才进入 `tests/fixtures/`，不要从另一个 `test_*.py` 导入通用 helper。新增测试文件保持可唯一定位；移动或重命名后先确认 collect 结果再把它写入正式测试清单。
