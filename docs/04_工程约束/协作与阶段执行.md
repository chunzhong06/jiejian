# 协作与阶段执行规范

> 状态：CURRENT。适用范围：阶段提示词、主线程设计与实施、执行线程委派、跨模块协作、阶段恢复和最终验收。

## 1. 权威顺序与阶段加载

当前用户的明确指令优先级最高。完整阶段提示词是当前阶段的范围、目标、禁令和最终验收真源；执行卡只负责切出当前自然子阶段，不能扩大或缩减完整阶段。阶段问题账本记录问题状态、恢复点和验收证据；CURRENT Docs 负责长期工程知识；代码、测试、Schema 和 migration 负责实际运行事实。

首次进入一个阶段时，主线程完整读取阶段提示词，只读取总账本顶部和当前阶段，并加载当前执行卡。后续推进默认只保留最新恢复点、当前卡和 `docs/llms.txt` 路由到的最少知识，不重复把完整阶段提示词、整个账本或已验收子阶段塞回上下文。发生新对话、上下文压缩、明显中断或用户要求“继续”时，再按根 `AGENTS.md` 恢复当前 HEAD、working tree、恢复点、完整阶段提示词和当前卡。

阶段机器状态与人类账本必须分开：职责等价的 `var/audit/<stage>/stage-state.json` 只保存当前卡、写入者、基线、已接受提交和下一门禁，供恢复时确定性读取；人类账本保存问题、裁决、说明和验收证据。不得通过正则解析 Markdown 账本推断机器推进状态，也不得把机器状态文件扩展成第二份问题历史。

账本、交接包或提示词明确限定“顶部 / 当前阶段 / 指定章节”时，必须按语义标题边界停止读取，不能用固定行数、固定字节数或“先全文读取再截断”代替范围控制。

一个阶段完成后立即停止。未经用户明确要求，不自动加载、设计或实施下一阶段。

同一完整阶段若明确要求连续执行多张卡，可以在首次入场建立连续阶段信任窗口。首次核对 HEAD、远端、working tree、阶段提示词与机器状态后，上一卡只有完成“diff → 最小充分验证 → commit → SHA → stage-state/账本 → clean tree”接受事务，下一卡才可直接信任 `accepted_sha`，不重复整套 Git/账本入场审计。只有用户声明外部改动、未知写入者、上一卡接受事务不完整、Git 写操作失败或即将改写历史时，才重建相应边界；上下文压缩本身不是重复审计理由。

## 2. 主线程与执行线程的职责

主线程负责需要整体判断的工作：架构与公共语义、跨模块方案、安全边界、人工文档、AGENTS、README、任务指南、模块参考、工程约束、设计依据、用户可见流程、前端视觉、信息层级、用户文案、复杂可视化、最终产品体验和 Git 接受。

用户可见前端的外观与体验原则上由主线程直接设计并直接实施。执行线程可以调查现状、查找消费者、运行测试、实现主线程已经冻结的后端接线或机械改动，但不得自行决定页面布局、视觉层级、产品语言、导航结构、交互方式或“后端字段应该怎样展示给用户”。

执行线程适合承接两类工作：

1. **只读调查**：查清真实文件、调用者、消费者、状态来源、测试、旧路径和风险，返回事实，不替主线程做最终产品或架构裁决。
2. **冻结后的工程实现**：实现主线程已经明确输入输出和边界的后端工作流、Runner/Worker/运行时、确定性 API/DTO、启动脚本底层控制、有界重构、批量接线和直接测试。

可委派任务进一步限制在六类白名单：只读盘点；已冻结路径/文件的机械移动与引用同步；参数完全冻结的 UI 机械应用；已有权威答案的重复性测试；确定性生成物、死链接或版本消费者同步；主线程已经完成根因分析并给出唯一修复方案的局部机械修复。架构、安全、公共语义、未知故障诊断、两种合理方案选择、人工文档正文和最终验收不在白名单。

本文中的“执行线程”“Luna 线程”和“委派任务”，除非用户明确授权内部子智能体，均指 Codex 侧边栏中用户可见、可直接打开并继续对话的正式任务。主线程必须优先复用用户指定的任务或 `threadId`；`spawn_agent` 等内部子智能体接口不属于本文所称执行线程，不得用来替代、隐藏或绕过正式任务。既有可见任务无法继续时，按本规范停止调度并报告，不能自行改用内部子智能体。

人工维护的 `AGENTS`、README、任务指南、模块参考、工程约束、设计依据和协议解释正文由主线程编写、修改和验收。执行线程只提供代码事实、实现报告和必要的源码附近注释。机器代码参考和 Schema 索引由确定性工具生成，不由任何线程自由改写。

## 3. 调查、设计与跨模块实施

复杂阶段开始时，主线程不必自己读取全部源码。可以先把范围清楚的只读调查交给既有执行线程，让它输出当前事实，例如页面/路由清单、函数所有权、API 消费者、状态来源、测试覆盖和可能冲突。

阶段性调查材料默认写入 `var/audit/<stage>/`，不进入 Git。它们回答“开始实施前仓库是什么样”，阶段结束后无需长期维护。只有经过主线程裁决、以后仍需要遵守的结论，才由主线程写入 CURRENT Docs。

明显跨模块的任务在实施前必须由主线程形成“模块实施图”。至少写清：

```text
每个模块要改变什么
→ 模块之间交换什么
→ 哪些公共语义不能改变
→ 实施先后关系
→ 每个模块怎样直接验证
→ 哪些部分由主线程直接实施，哪些可以委派
```

执行线程只实现实施图中已经冻结的模块内部工作。如果真实代码证明关键假设不成立，立即携带证据返回主线程，不自行补做新的跨模块设计。

外部设计稿、旧聊天摘要、旧完成报告和历史提交只作为输入。主线程必须以当前仓库和 CURRENT Docs 复核后再采用，不能把旧结论直接当作当前事实。

## 4. 单写入者与线程生命周期

同一工作树同一时间只保留一个主要写入者。需要并行时必须使用独立工作树，并提前划清 Git、目录和文件边界。

同一阶段或一组高度相关阶段默认复用已有长期执行线程；进入不同目录、前后端切换或自然子阶段变化本身不是新建线程理由。只有现有线程实际出现上下文遗漏、重复返工、质量下降、无法继续访问，或任务确实需要隔离/并行时，才新建执行线程。

协作状态固定为：

```text
READY → DISPATCHED → WAITING → RETURNED → AUDITING → ACCEPTED
```

这些状态只表达责任和接受边界，不要求为每次状态变化建立 Git 提交、标记或重复确认。一个自然子阶段只在形成可恢复实现时提交；`READY_FOR_COMMIT`、已提交待接受和账本已接受不应再成为三套互相等待的仪式。

- `READY`：主线程已经冻结本批目标、范围、验证和停止条件。
- `DISPATCHED`：交接已经发送，执行线程开始承担本批工作。
- `WAITING`：执行线程是共享工作树的主要写入者；主线程不并发修改、不提前实施下一批，也不连续主动轮询。
- `RETURNED`：执行线程返回完成报告或升级报告，只表示“有结果可审计”。
- `AUDITING`：主线程核对报告、Git/working tree、修改范围、测试和偏离。
- `ACCEPTED`：主线程确认本批成立并记录恢复点，才允许进入下一自然子阶段。

`stopped`、任务事件结束、存在 commit 或单项测试通过，都不等于 `ACCEPTED`。

主线程创建的一次性线程在报告回收并验收后必须归档；工具支持删除时继续删除。长期执行线程按阶段约定持续复用，在其负责的长期任务最终结束、报告和 Git 证据全部回收后再归档并尽可能删除。

委派正常交接使用“原生线程等待 + 文件交接”。运行材料固定放在 `var/coordination/<task-id>/`：`request.json` 是 dispatch 后不可修改的施工合同，只记录 task id、准确基线、允许和禁止范围、完成条件、测试要求与 handoff 路径；`report.md` 保存详细报告；`handoff.json` 是唯一正式完成或升级入口。执行线程先完整写入并 flush 同目录临时 report，再原子发布 `report.md`；随后完整写入并 flush `handoff.tmp`，再原子替换为 `handoff.json`。handoff 状态只允许 `DONE / FAILED / BLOCKED / NEEDS_DECISION`。一旦发布 handoff，执行线程立即释放共享 working tree 写入权并结束本轮执行。

主线程派发后最多调用一次原生 `wait_threads`，只用它等待线程事件，不用它传递正式报告。线程结束后无论消息投影是否为空，都直接读取 `handoff.json` 和 `report.md`；正常流程禁止通过 `read_thread`、rollout JSONL 或线程长文本恢复正式报告。一次等待返回时任务仍未完成，当前主线程轮次立即结束，不得再次等待、改用文件轮询或反复播报 PENDING。

下一次用户发消息、任务显式恢复或执行线程出现真实完成/升级事件时，用户最新消息优先。需要恢复当前委派时先检查 `handoff.json` 是否已经原子发布；存在则读取并进入主线程审计，不存在时最多做一次线程状态检查。禁止自动周期性检查、heartbeat、后台 watcher、`check-handoff` 状态层和无推进价值的等待播报。

既有执行线程找不到、无法唤醒或无法交接时，主线程停止调度并报告，不自行用另一个未授权线程替代。`handoff.json` 只表示责任返回，不等于 ACCEPTED；`DONE` 仍需独立核对真实 Git diff、允许范围和当前卡的最小充分测试，`NEEDS_DECISION` 则表示执行线程已停止写入并等待主线程裁决。

## 5. 执行线程交接格式

只有预计能减少主线程调查、实施与重复审计总工作量时才委派；把机械步骤交出去却要求主线程重新读取全部上下文、重复测试和重做实现，不构成有效减负。同一委派最多一次主要实现加一次针对验收反馈的返工，第二次非偶发偏离时停止委派并由主线程收敛唯一方案。

每次只交接一个边界完整、可独立验收的自然子阶段。首次 handoff 至少包含：

```text
当前恢复点
本批目标
必须完成
明确不做
允许修改范围
已冻结的接口 / 状态 / 视觉或行为合同
直接测试
验证上限
升级条件
完成报告格式
```

后续 handoff 只发送最新恢复点和增量约束，不重复稳定背景，也不把整份阶段账本和完整 Docs 塞入执行线程。

执行线程完成报告固定包含：

```text
变更摘要
修改文件
实际验证命令与结果
偏离原方案
未完成或待确认问题
```

“偏离原方案”和“待确认问题”没有内容时明确写“无”。

执行线程不得因顺手优化扩大范围，不修改无关模块、依赖、公共接口、用户自己的改动或其他阶段代码。需要改变架构、安全边界、公共 API/Schema、持久格式、核心状态机、UI/UX 设计或人工文档解释时，停止实施并返回主线程。

## 6. 上下文与知识使用

非平凡任务先从根 `AGENTS.md → docs/llms.txt` 进入当前任务指南、模块参考和必要工程约束。已有知识能够定位模块时，不用重新靠全仓搜索和逐文件阅读“重新理解系统”。

主线程负责把最终稳定的设计和模块职责写回唯一 CURRENT Docs；执行线程的调查报告和阶段过程不替代长期文档。改变模块职责、开发入口、跨模块边界或长期设计理由时，主线程按 [知识与文档治理](./知识与文档治理.md) 更新唯一知识位置。

自动代码参考只描述“代码现在是什么”，人工文档描述“为什么这样、从哪里改、不能破坏什么、怎样验证”。二者不得互相复制。

调查、diff、日志和测试输出应限定到受影响路径和必要上下文。结果过大时缩小范围，不用重复全仓读取补偿截断。

## 7. 验证、真实体验与副作用

主线程在委派前决定本批测试模块、验证程度、是否需要 L5 和何时升级。执行线程以直接相关测试和一个代表性闭环为默认上限，不因“保险”自行扩大到 L4。

预计超过短暂命令时间的多阶段流程必须设计稳定且用户可见的阶段边界。每次进入阶段立即刷新状态；能够提供权威进度时有界流式输出，不能提供时说明当前阶段、可能的静默区间和停止条件，不用模糊“仍在处理”或伪造百分比形成黑箱。失败报告必须保留最后完成阶段和第一主错误，cleanup/回滚进度另列；这一要求同时适用于启动、打包、迁移、测试、下载和委派工作。

真实终端、浏览器、GUI、用户流程、视觉质量、焦点/键盘行为和最终产品体验的 L5 由主线程亲自验收。执行线程可以运行辅助测试或提供事实，但不能代替最终用户体验判断。

测试结果只有在测试真实收集并执行时才构成证据；`0 collected`、路径不存在或收集前失败不算通过。具体 L1～L5、测试路径和仓库外 import 规则以 [验证与测试](./验证与测试.md) 为准。

commit、push、reset、update-ref、删除、数据库写入、凭据写入和真实外部 API 调用等副作用操作返回不明确时，先读取权威状态再决定是否继续，不重复执行同一写操作来试探第一次是否成功。真实付费、限额或会产生外部影响的调用遵守验证规范和用户明确授权。

## 8. 返工、范围与阶段验收

一个自然子阶段默认一次主要实现加必要局部修复；同一委派至多再接受一次有明确验收反馈的返工。再次出现非偶发返工、一次明确纠正后仍偏离、或开始反复尝试无法解释的方案时，执行线程停止探索，把根因和证据交回主线程。主线程先收敛唯一方案，再决定接管实现或重新划分边界。

阶段验收只验证当前完整阶段提示词和已接受任务明确列出的能力。发现范围外缺口时记录“影响 + 后续建议”，不在验收阶段顺手扩项；只有缺口直接否定当前阶段核心能力时才重新规划。

自然子阶段可以建立清楚的恢复提交，但执行线程不得自行 squash、force push 或重写已稳定历史。最终是否整理为一个阶段提交，以当前阶段提示词和用户指令为准。

自然子阶段正式接受采用一次收口事务：最终 diff 审计和最小充分验证通过后提交，取得权威 SHA，再一次更新机器阶段状态与人类账本并核对 working tree。任一步失败都不标记 `ACCEPTED`；不得在同一卡内重复建立“准备提交、已经提交、等待接受”三轮恢复点或确认往返。

正式接受一个阶段前，主线程必须确认：

```text
问题账本已更新
需要的人工 Docs 已由主线程同步
生成参考无漂移
直接验证充分
需要的 L5 已由主线程完成
Git/working tree 与完成报告一致
一次性线程已回收
没有把下一阶段工作混入当前阶段
```

阶段进入 `ACCEPTED` 后立即停止，等待用户决定下一阶段。

## 9. 1.0.0 后的版本与任务命名

Web V1 1.0.0 完成后，正式产品推进使用语义版本，不再用“阶段10.9”“阶段11”等编号作为产品版本或任务主名称。阶段/卡片仍可作为一次复杂实施内部的临时拆分，但对外目标、交付、文档和提交应围绕明确版本与能力命名。

- 仅修复兼容缺陷、文案或不改变能力边界的小改动，递增补丁号，例如 `1.0.1`。
- 增加重要且向后兼容的产品能力，递增次版本号，例如 `1.1.0`。
- 只有明确破坏兼容并重新定义主要产品边界的大重构，才进入 `2.0.0`。
- Schema/protocol 版本、数据库 revision、Contract 业务版本与产品语义版本各自独立，不能因产品版本变化机械同步。

每个版本仍可使用机器状态和人类账本管理多卡连续执行；同一连续信任窗口、严格委派白名单、用户可见执行线程和 request/report/handoff 原子交接规则继续有效。
