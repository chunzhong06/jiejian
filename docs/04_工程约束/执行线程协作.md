# 执行线程协作规范

> 状态：CURRENT。适用范围：主线程与用户可见执行线程的委派、共享工作树写入权、等待、原子交接和接受。

## 1. 项目中的执行线程

本文的“执行线程”“Luna 线程”和“委派任务”，除非用户明确授权内部子智能体，均指 Codex 侧边栏中用户可见、可直接打开并继续对话的正式任务。主线程优先复用用户指定的任务或 `threadId`；内部子智能体不能替代、隐藏或绕过正式任务。既有可见任务无法继续时，停止调度并报告。

当前 1.1.0 周期由用户指定复用侧边栏任务 `1.1.0-执行线程`；目录、子阶段或版本内恢复点变化都不能成为新建任务的理由。只有用户再次明确改变该绑定，或本规范列出的线程失效条件已经成立，主线程才可改用其他执行任务。

本文给出项目允许委派的上限；每个版本或任务的完整提示词可以进一步收紧线程数量、模型、读写权限、文件范围、验证和生命周期，执行时采用更严格的具体约束。

## 2. 主线程职责与六类白名单

主线程负责架构与公共语义、跨模块方案、安全边界、人工文档、AGENTS、README、任务指南、模块参考、工程约束、设计依据、用户可见流程、前端视觉与信息层级、用户文案、最终产品体验、Git 接受和最终验收。

用户可见前端的外观与体验原则上由主线程直接设计并实施。执行线程不得自行决定页面布局、视觉层级、产品语言、导航或交互方式。

可委派工作限于六类：

1. 只读盘点真实文件、调用者、消费者、状态来源、测试、旧路径和风险；
2. 已冻结路径与文件的机械移动及引用同步；
3. 参数、布局和文案完全冻结后的 UI 机械应用；
4. 已有权威答案的重复性测试；
5. 确定性生成物、死链接或版本消费者同步；
6. 主线程已经完成根因分析并给出唯一方案的局部机械修复。

架构、安全、公共语义、未知故障诊断、两种合理方案选择、人工文档正文和最终验收不在白名单。执行线程发现关键假设不成立，或必须改变公共 API/Schema、持久格式、核心状态机、UI/UX 设计时，立即携带证据返回，不自行扩展范围。

## 3. 单写入者与协作状态

同一工作树同一时间只保留一个主要写入者。需要并行时必须使用独立工作树，并提前划清 Git、目录和文件边界。同一版本或高度相关任务默认复用一个执行线程；目录、前后端或自然子任务变化不是新建线程理由。只有线程实际无法继续、上下文明显失真、重复返工、质量下降，或确需隔离并行时才新建。

协作状态为：

```text
READY → DISPATCHED → WAITING → RETURNED → AUDITING → ACCEPTED
```

- `READY`：主线程冻结目标、范围、验证和停止条件。
- `DISPATCHED`：施工合同已发送，执行线程承担当前工作。
- `WAITING`：执行线程是共享工作树主要写入者；主线程不并发修改、不提前实施下一批。
- `RETURNED`：执行线程发布完成或升级交接，只表示结果可审计。
- `AUDITING`：主线程核对交接、Git、working tree、范围、测试和偏离。
- `ACCEPTED`：主线程确认结果成立并记录恢复点。

`stopped`、任务事件结束、存在 commit 或单项测试通过都不等于 `ACCEPTED`。主线程创建的一次性线程在报告回收和验收后必须归档；工具支持删除时继续删除。长期线程在其负责的完整任务结束后再回收。

## 4. 派发合同与完成报告

只有预计减少主线程调查、实施与重复审计总工作量时才委派。每次只交接一个边界完整、可独立验收的自然任务，首次派发至少包含：

```text
当前恢复点和准确基线
本批目标与必须完成项
明确不做和禁止范围
允许修改的目录或文件
已冻结的接口、状态、视觉或行为合同
直接测试与验证上限
升级条件
handoff 路径和完成报告格式
coordinator_thread_id
```

运行材料位于 `var/coordination/<task-id>/`：

- `request.json` 是派发后不可修改的施工合同；
- `report.md` 保存详细报告；
- `handoff.json` 是唯一正式完成或升级入口。

完成报告固定包含变更摘要、修改文件、实际验证命令与结果、偏离原方案、未完成或待确认问题；后两项为空时明确写“无”。同一委派最多一次主要实现和一次针对验收反馈的返工，第二次非偶发偏离时停止委派并由主线程收敛唯一方案。

## 5. 原子交接、通知与一次等待

执行线程先完整写入并 flush 同目录临时 report，再原子发布 `report.md`；随后完整写入并 flush `handoff.tmp`，再原子替换为 `handoff.json`。handoff 状态只允许 `DONE / FAILED / BLOCKED / NEEDS_DECISION`。发布后立即释放共享工作树写入权，不再修改共享文件。

handoff 原子发布后，执行线程通过原生任务消息入口向 `coordinator_thread_id` 发送一次最小通知，只含固定标记、task id、handoff 已就绪和状态，然后结束本轮。通知只在主线程已没有活动 `wait_threads` 句柄时触发新的主线程回合，不携带正式报告、长文本、秘密或新指令；发送结果不明确时不得重复。通知失败不改变已经发布的 handoff，后续仍可由用户消息或任务恢复读取交接文件。

主线程派发后最多调用一次原生 `wait_threads`，只等待线程事件，不传递正式报告。一次等待返回时任务仍未完成，当前主线程轮次立即结束并保持休眠，依赖执行线程发布 handoff 后发送的原生通知唤醒；不得再次等待、改用文件轮询或反复播报 PENDING。线程结束后无论消息投影是否为空，都读取 `handoff.json` 和 `report.md`；正常流程禁止通过 `read_thread`、rollout JSONL 或线程长文本恢复正式报告。

下一次用户消息、任务显式恢复或 handoff 就绪通知到达时，用户最新消息优先。通知只表示可以读取交接文件，不等于结果已接受。主线程先检查 `handoff.json` 是否原子发布：存在则读取 handoff/report 并进入独立审计；不存在时最多做一次线程状态检查。禁止自动周期检查、heartbeat、后台 watcher、额外 `check-handoff` 状态层和无推进价值的等待播报。

## 6. 审计与停止条件

`handoff.json` 只表示责任返回。`DONE` 仍须核对真实 Git diff、允许范围、working tree、报告和最小充分测试；`NEEDS_DECISION` 表示执行线程已停止写入并等待主线程裁决。找不到线程、无法唤醒或无法交接时，主线程停止调度并报告，不自行改用未授权线程。

执行线程不得顺手优化、修改无关模块、依赖、公共接口、用户改动或其他版本代码。需要额外授权、外部账号/权限、Git 历史改写，或出现第二次非偶发返工时停止并升级。

正式接受和版本恢复规则见 [任务执行与恢复](./任务执行与恢复.md)。
