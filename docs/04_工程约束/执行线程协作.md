# 执行线程协作规范

> 状态：CURRENT。适用于主线程与用户可见执行任务的职责分工、派发、共享工作树、错误升级、交接和验收。

## 1. 角色与推理等级

主线程负责完整目标、设计决策、用户流程与前端实现、文档治理和最终接受；执行线程负责按已接受设计完成有界非前端实现、文档同步和验证。角色按责任划分，不以旧提示词中的模型称谓限制谁必须编写后端代码。用户最新指定的模型、推理等级和启用时间优先于历史合同。

| 角色 | 模型与推理等级 | 责任 |
| --- | --- | --- |
| 主线程 | GPT-6 Astra，`xhigh` | 架构、安全、公共语义、持久化与核心生命周期方案、用户流程及前端实现、文档治理决策、复杂问题分析、审计、Git 与最终验收 |
| 执行线程 | GPT-6 Astra，Light（`low`） | 已接受设计下的完整非前端实现、适配与迁移、测试/fixture、局部修正、冻结验证、生成及人工文档编写和修改 |

创建或派发时显式设置执行模型 `gpt-6-astra` 和推理等级 `low`，不能只在提示词里写 Light。用户另有明确配置或延后启用要求时按其执行；错误处理不自行提高推理等级或更换任务。

执行线程与主线程采用相同的局部修正预算：首次失败用于建立事实，对同一根因最多分析、修正并验证两次。局部问题可以在已授权文件和冻结语义内自行解决；明确跨模块、架构、安全或公共格式等复杂问题立即交由主线程裁决。错误处理不改变已核验的模型与推理配置。

## 2. 用户可见任务与版本绑定

本文的“执行线程”和“委派任务”均指 Codex 侧边栏中用户可见、可打开并继续对话的正式任务。内部子智能体只有用户另行明确授权时才可使用，不能替代或隐藏正式执行任务。

同一版本默认只复用一个执行任务；目录、前后端、卡片或自然子任务变化都不是新建理由。新版本开工时，按用户授权归档旧执行任务，再创建新的执行任务。具体任务名称、ID、版本安排和执行卡保存在运行交接材料中，不写入 CURRENT Docs 或源码。

用户明确要求替换时，先回收旧任务写入权、报告和当前状态，按指定名称重命名并归档，再创建新任务。把已完成项、未决事项、有效验证和当前合同交给新任务，不让新任务重做已接受工作。无替换授权而既有任务实际无法继续时，停止调度并报告。

## 3. 主线程保留的职责

以下工作由主线程直接裁决，执行线程的报告不能代替该裁决：

- 完整版本范围、架构、模块责任、公共接口与 Schema、数据库迁移方案、Worker/Runner 核心生命周期及安全语义。
- 权限、秘密、目标范围、预算、失败关闭、Verdict、Finding 和 Gate 等关键边界。
- 用户流程、导航、布局、视觉层级、产品语言与可访问性设计。
- AGENTS、README、任务指南、模块参考、工程约束、协议解释和设计依据的治理决策与长期边界；准确裁决形成后可委派编写和修改。
- 跨模块或局部证据不足的复杂故障诊断、涉及职责或公共语义的方案选择、范围扩大和验证等级调整。
- 最终产品启动与交互体验、Git 历史整理、提交接受、推送和版本验收。

UI、布局、样式、导航、交互、可访问性和产品文案由主线程亲自设计并实现，即使方案已经确定也不交给执行线程编写。人工文档是允许委派的例外：执行线程可以整理语言结构、同步已确定事实，不自行发明能力或改变长期边界；AGENTS 和工程规则必须按合同中的准确裁决修改。对应的冻结测试和构建命令可以委派执行，最终体验仍由主线程验收。

保留设计决策不意味着所有后端代码必须由主线程亲自编写。接口、状态转换、安全边界、持久化方案和权威预期已经接受后，其实现可以交给执行线程；主线程负责审计是否忠实落地。已设计清楚的跨文件或跨模块实施按同一合同执行，不因文件数量多就退回主线程。

主线程可以把裁决后的机械部分按下一节交给执行线程，但不能只给一个宽泛目标，让执行线程自行补齐架构、安全或交互选择。

## 4. 可委派的八类工作

1. **有界调查与影响盘点**：核对指定问题涉及的文件、调用者、消费者、状态来源和直接测试，返回证据与未确认项。
2. **已接受设计的后端实现**：按冻结的模块图、输入输出、算法、状态转换、失败语义和验收矩阵完成实现；可以覆盖多个文件或已经明确责任与顺序的模块。
3. **适配器、仓储与服务接线**：实现已经确定的内部投影、转换、存取和组合接线。涉及协议或迁移时，字段、约束、兼容与数据处理方案必须先由主线程接受，不由执行线程自行设计。
4. **机械迁移与引用同步**：按冻结的路径、字段映射和消费者清单移动文件、替换引用、清理被取代的内部实现并同步调用参数；前端与产品交互代码仍由主线程修改。
5. **明确预期的测试与 fixture**：按权威场景矩阵编写后端测试、共享 fixture 和受控验收脚本；不得从当前实现反推 expected，或通过跳过旧断言掩盖回归。
6. **局部分析与修复**：在已授权范围、冻结接口和既定预期内定位实现、测试或命令问题，同一根因首次失败后最多两次修正验证；超出已接受设计或涉及新的复杂决策时升级。
7. **冻结的验证与构建**：运行主线程确认过路径、节点、范围和预期的测试、检查与构建，返回真实结果；不自行扩大验证等级或真实外部调用。
8. **文档与生成一致性维护**：按已接受设计编写或修改人工文档、整理语言结构、同步已确定的实现事实，并按指定工具更新生成参考、Schema 和静态链接等机器生成物；不自行决定长期边界、发明能力或修改前端产品文案。AGENTS 与工程规则须有合同给出的准确裁决。

白名单不转移主线程的设计和验收责任。已经设计清楚的实现应按能够独立验收的完整工作包委派，不必机械拆成大量小任务。一次合同可包含有明确先后关系的实现、迁移和直接验证；只在设计缺口、写入权或验收边界确实不同处拆分。上一工作包交回并审计后才能派发下一份，避免主线程重复调查和过细调度。

只读盘点必须限定问题、路径和输出格式，不能扩展成全仓调查。测试补齐不得从当前实现反推 expected、降低断言、放宽安全预算或改变失败关闭条件。技术验收脚本可以由执行线程编写，真实产品体验和最终结论仍由主线程验收。

## 5. 派发前冻结施工合同

主线程先确认当前用户授权、完整提示词、当前执行卡、最近接受点和工作树，再写入不可变合同。每次派发至少包含：

```text
task_id 与 coordinator_thread_id
准确工作区、基线 SHA 和必要的冻结文件指纹
完整提示词路径、当前卡及允许读取的章节边界
执行任务 ID、适用工作流、模型和推理等级
本次白名单编号、目标与必须完成项
允许修改的文件、生成区和运行材料目录
输入输出、算法/状态、失败语义或 UI 行为合同
权威 expected、直接验证命令与验证上限
禁止范围、局部修正预算、立即升级条件和主线程需要裁决的事项
report.md 与 handoff.json 路径及发布要求
```

完整提示词始终是范围真源，局部合同不能缩减验收条件。阶段要求一次只加载当前卡时，执行线程同样不得提前读取后续卡片或账本章节。

运行材料统一位于 `var/coordination/<task-id>/`。`request.json` 派发后不可修改；用户追加要求或冻结输入发生变化时，先收回写入权，再以新 task id 保存增量合同并重新派发。旧请求、报告和首错证据保留，不能覆盖成“从未发生过失败”。

## 6. 单写入者与协作状态

同一工作树同一时间只保留一个主要写入者。确需并行写入时，须先取得相应授权，使用独立工作树并划清文件、Git 和验收边界。

```text
READY → DISPATCHED → WAITING → RETURNED → AUDITING → ACCEPTED
```

- `READY`：主线程已经冻结当前任务。
- `DISPATCHED`：合同已发送给指定执行任务。
- `WAITING`：执行线程持有本次共享工作树写入权；主线程不并发修改、不提前实施下一批。
- `RETURNED`：执行线程发布完成或升级交接并释放写入权。
- `AUDITING`：主线程读取正式交接，核对范围、差异、当前事实和验证证据。
- `ACCEPTED`：主线程确认当前任务成立并记录恢复点。

只读验证期间同样要保护冻结输入。主线程、用户或其他任务需要修改相关代码、测试或协作文档时，应先结束当前委派并回收写入权；发现冻结文件变化时，执行线程立即交回，不在未知输入上继续验证。

执行线程停止、存在 commit 或单项测试通过，都不等于主线程已经接受。多卡连续任务只有完成前一卡的正式接受事务，才可加载下一卡。

## 7. 局部修正与复杂问题升级

出现真实失败时，先在失败文件和直接调用处区分产品、测试/fixture、运行环境问题。原因与修复都能限制在合同允许范围内时，执行线程可以自行分析、修正并验证；不必仅因命令失败就交回主线程。先运行失败项，再补直接邻域，已有效且未受影响的验证继续保留。

同一根因的首次有效失败不计入修正预算，之后最多两次修正验证。每次必须先说明证据、错误假设、允许修改位置和验证方式，不允许无分析地重跑。表面报错变化但根因相同仍共用预算；越过旧失败点后出现独立的新根因，按新问题记录。两次后仍未解决则交回主线程，不通过改任务名、重新派发或提高推理等级重置预算。

以下任一事实出现时，停止相关施工并立即升级：

- 基线、冻结文件、路径、运行身份或必要前提与合同不符。
- 出现超出已接受模块图的跨模块协调、核心生命周期调整，或局部证据无法确定安全修复。
- 实现需要改变冻结接口、Schema、持久格式、核心状态、权限边界或用户流程。
- 出现未授权文件、未知写入者、外部账号或权限阻塞，或副作用结果不明确。
- 合同无法决定涉及架构、安全、持久化或用户流程的方案，或必须扩大文件与验证范围。

预期负向测试中已被正确接住的错误不算施工失败；合同明确要求记录的“无匹配结果”也不触发升级。已确认的权限阻塞和不明确的副作用不能用局部修正预算反复重试。

报告保留原始失败、每次局部分析结论、修改、验证命令、剩余次数和最终结果。需要升级时列出最后完成步骤、第一主错误、已产生的副作用、清理结果和待裁决事项。秘密、完整请求正文、源码全文和无关日志不得进入交接。

主线程收到升级后依据已有证据收敛方案，不要求执行线程重新做已完成的调查。副作用不明确时先回读权威事实；权限已确认受阻时按[工作区与权限](./工作区与权限.md)处理。主线程同样遵守最多两次局部修正验证的预算；复杂问题先完成设计裁决，再决定由谁实施。

## 8. 原子交接与一次等待

完成、失败或需要裁决都必须发布正式交接。执行线程先完整写入并 flush 同目录临时报告，再原子发布 `report.md`；随后完整写入并 flush `handoff.tmp`，再原子替换为 `handoff.json`。handoff 状态只允许 `DONE / FAILED / BLOCKED / NEEDS_DECISION`。

报告固定包含变更摘要、修改文件、实际验证命令与结果、偏离原方案、未完成或待确认问题、当前 Git/working-tree 事实。没有偏离或待确认问题时明确写“无”。报告发布后立即释放写入权，不再继续修改共享文件。

执行线程通过原生任务消息入口向 `coordinator_thread_id` 发送一次最小通知，只包含固定标记、task id、handoff 已就绪及状态，然后结束本轮。通知不承载正式报告或新指令；发送结果不明确时不得重复。原子 handoff 已发布但通知失败时，交接仍然有效，可在后续用户消息或任务恢复时读取。

主线程每次派发后最多调用一次原生 `wait_threads`，只等待任务事件。等待返回时尚未完成，则结束当前回合并保持休眠，依靠 handoff 就绪通知唤醒；不追加等待、文件轮询、heartbeat、后台 watcher 或 PENDING 播报。

新的用户消息、显式恢复或就绪通知到达时，优先处理用户最新指令。先检查正式 handoff：存在则读取 handoff/report 并进入审计；不存在时最多检查一次任务状态。任务结束后即使消息投影为空，也以交接文件为准；正常流程不通过 `read_thread`、rollout JSONL 或任务长文本重建正式报告。

## 9. 主线程接受与任务回收

`DONE` 只表示结果可供审计。主线程必须核对真实 diff、允许文件、冻结语义、working tree、正式报告及最小充分验证；必要时亲自进行用户流程和视觉验收。

阶段正式接受按[任务执行与恢复](./任务执行与恢复.md)完成事务：

```text
完整提示词逐项核对
→ diff 与 CURRENT 文档审计
→ 最小充分验证
→ 恢复提交并回读完整 SHA
→ 同步机器状态和问题账本
→ 核对 working tree
→ ACCEPTED
```

白名单扩大不改变阶段验证上限。同一代码状态不重复 L4，执行线程不得自行启动产品、运行 L5 或扩大真实外部调用；测试合同统一服从[验证与测试](./验证与测试.md)。

执行线程不提交、推送、整理 Git 历史或操作正式引用；这些由主线程按当前授权执行。需要 Git 历史改写时，主线程先建立 recovery ref 并验证目标 parent/tree/message。

主线程创建的一次性执行任务，在报告回收和接受后归档；工具支持且授权允许时继续删除。长期复用任务按用户明确的版本生命周期回收。版本完成后停止；下一版本只有取得开工授权后才处理任务归档与新建。
