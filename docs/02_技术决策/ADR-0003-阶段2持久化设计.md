# ADR-0003：阶段 2 持久化映射与事务边界

- 状态：已接受
- 日期：2026-08-09
- 适用阶段：2.1 及其后续持久化调用方

## 背景

阶段 2.0 已通过 ADR-0002 冻结公共 ID、UTC Unix 微秒时间、Job 租约字段、Run/Job/Verdict 矩阵和工件发布顺序。阶段 2.1 需要建立可迁移、可重启读取的 SQLite 存储边界，但不得提前实现 Worker 调度、Runner 子进程或工件发布。

阶段 0 的 UUID 领域模型与阶段 1 的同步 CLI 仍然存在。持久化层不能为同一对象再生成一套公共 ID，也不能让 SQLAlchemy 类型渗入领域、协议或执行引擎。

## 决定

### 1. 当前物理表范围

首版迁移只创建以下五张业务表，Alembic 自身另维护 `alembic_version`：

- `projects`：项目 slug、显示名、状态和创建/更新时间。
- `runs`：Run 公共 ID、Project 外键、契约版本引用、引擎版本、独立的 lifecycle/verdict 和时间。
- `jobs`：Job 公共 ID、Project/Run 外键、操作类型、状态及 ADR-0002 冻结的幂等、尝试、租约、fencing、取消和时间字段。
- `job_events`：以 `(job_id, sequence)` 为主键的连续追加事件，保存稳定事件类型、状态变化、发生时间和最大 4 KiB 的有限标量元数据。
- `evidence_index`：Evidence 内容寻址 ID、Run 外键、Case 引用、规范相对路径、SHA-256、字节数和创建时间。

不预建 Recording、TestCase、Finding、Plugin、API、GUI 或 reconciliation 等未来表。`case_id` 在本阶段是 Evidence 的有限关联值；待 TestCase 持久化进入获批阶段后再以向前迁移增加关系，不提前创建空表。

### 2. ID 与时间

- `projects.project_id` 直接使用项目 slug。
- `runs.run_id` 直接使用 `run_` 加 32 位小写 UUID hex。
- `jobs.job_id` 直接使用 `job_` 加 32 位小写 UUID hex。
- `evidence_index.evidence_id` 延续现有 `ev_` 内容哈希前缀形式，并由约束校验其与完整 SHA-256 的前缀一致。
- 数据库不使用自增键作为公共标识，也不提供 ID 生成器。
- 所有绝对时间字段均为非负 UTC Unix 微秒整数，名称以 `_at_us` 或 `_expires_at_us` 表意；值由调用方传入，storage 不读取系统时钟。

### 3. 分层与公开边界

SQLAlchemy typed declarative 映射只位于 `jiejian.storage.models`。`domain`、`protocols`、`engine` 和阶段 1 服务不得导入 SQLAlchemy。

具体 Repository 接收并返回冻结、严格、版本化的 Pydantic record，不返回 ORM row。`StorageUnitOfWork` 只公开五个具体 Repository 以及 `begin()`、`commit()`、`rollback()`、`close()`；调用方没有公开的 Session 访问口。当前只实现已被阶段 2.1 测试使用的新增和查询入口，不创建单实现通用仓储接口。

### 4. 事务语义

- 每个 UoW 显式开始一个 Session 事务。
- `commit()` 是唯一提交入口；上下文退出不会隐式提交。
- 异常退出、显式不提交或关闭活动事务时均回滚。
- Repository 在 flush 时尽早暴露外键、唯一和 CHECK 失败；数据库异常映射为固定 `JiejianError`，不回显 SQL、参数、数据库路径或原始异常文本。
- `job_events` 只提供连续序号的 `append`，重复或跳号稳定拒绝。

阶段 2.4 才会把工件 promote 与数据库完成态提交纳入一个业务工作单元；阶段 2.1 不实现发布或 reconciliation。

### 5. SQLite 连接规则

默认数据库路径为 `<var_dir>/jiejian.db`。SQLAlchemy 使用文件 SQLite 与 `NullPool`；应用引擎和 Alembic 引擎都为每个新连接设置：

- `PRAGMA foreign_keys=ON`
- `PRAGMA journal_mode=WAL`
- `PRAGMA busy_timeout=5000`

测试必须在真实新连接上读取这些值，并证明外键违规失败、未提交写入不会被另一会话视为已提交。

### 6. 迁移与回滚

生产建库和升级入口是签入的 Alembic 向前迁移，`create_all` 不能替代迁移。第一版 revision 为 `0001_stage2_storage`，重复升级到 head 必须幂等。

本项目不提供自动 downgrade。发布迁移前应备份数据库；需要回到旧版本时，从兼容备份恢复或创建旧版本新库并重新导入受支持数据。迁移失败不得通过删除 `alembic_version` 或手工跳过约束伪装成功。

### 7. 数据库与文件系统分工

数据库只保存可查询元数据、状态、索引和引用。Evidence 正文、响应体、报告及大型工件留在文件系统。Evidence 路径复用阶段 2.0 的 Windows 安全相对路径校验，单项索引大小上限为 1 GiB，大小写别名在同一 Run 中由 NOCASE 唯一约束拒绝。

Repository 写入前扫描调用方提供的非空已知秘密，覆盖对象键和所有字符串值，并拒绝内联凭据形式；稳定错误不包含秘密或字段位置。真实秘密不得进入事件元数据或 Evidence 索引。

## 结果

- 阶段 2.2 可以在同一 Schema 上实现幂等提交、claim、续租、取消和重试，无需改变公共 ID。
- WAL 改善读写并行，但 SQLite 仍是单写者；只有实测成为瓶颈后才评估 PostgreSQL。
- 数据库约束负责单行与关系不变量，Pydantic record 和 Repository 负责完整路径、秘密与有限 JSON 等应用边界。
- 本决定不改变阶段 1 CLI、RunService、判定结果或退出码。

## 未包含事项

本 ADR 不实现 Worker、claim/续租算法、持久队列、Runner、子进程秘密传递、工件 promote 或 reconciliation。这些仍分别属于阶段 2.2、2.3 和 2.4。
