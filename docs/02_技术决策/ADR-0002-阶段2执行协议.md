# ADR-0002：阶段 2 Worker/Runner 执行协议

- 状态：已接受
- 日期：2026-08-08
- 适用版本：V1
- 相关协议：`docs/03_协议定义/Runner执行协议V1.md`

## 背景

阶段 1 通过 CLI 在单进程内完成安全验证纵切，已经证明契约、变异、观察、证据和门禁判定能够闭环。阶段 2 要把同一判定迁移为持久化 Job，由 Worker 租约调度并在隔离 Runner 中执行。数据库、租约、进程和工件提交如果各自定义标识、时间、重试或结果语义，会产生重复运行、旧进程越权写入、基础设施失败被误报为安全结论，以及数据库完成态指向未发布工件等问题。

本 ADR 在任何数据库或进程实现之前冻结控制面与 Runner 的协议边界。

## 决策

### 1. 标识符与时间

- 项目公共 ID 延续阶段 1 slug：`^[a-z][a-z0-9_-]{0,63}$`。
- Run 公共 ID 为 `run_` 加 32 位小写 UUID hex。
- Job 公共 ID 为 `job_` 加 32 位小写 UUID hex。
- Evidence 延续内容寻址 ID；不把数据库自增键暴露为公共 ID。
- 阶段 0 的 UUID 领域模型保持不变。阶段 2.1 的持久化映射必须保存并复用既有公共 ID，不得为同一 Project、Run、Job 或 Evidence 再生成另一套公共 ID。
- 协议及后续数据库边界只使用 UTC Unix 微秒整数。绝对时间字段以 `_at_us` 结尾，延迟或租约截止字段以 `_after_us` 或 `_expires_at_us` 表意。
- 时间由调用方注入；本阶段不增加全局时钟、单例或时间基础设施。

### 2. Run、Job 与 Verdict

| 尝试结果 | Run lifecycle | Job state | Run verdict |
| --- | --- | --- | --- |
| SUCCESS | COMPLETED | SUCCEEDED | PASS、BLOCK 或 INCONCLUSIVE，必填 |
| SAFETY_STOPPED | SAFETY_STOPPED | SUCCEEDED | 无 |
| CANCELLED | CANCELLED | CANCELLED | 无 |
| RETRYABLE_ERROR | 保持当前非终态 | RETRY_WAIT | 无 |
| FATAL_ERROR | FAILED | FAILED | 无 |

INCONCLUSIVE 只表示执行已正常完成但证据不足、必要观察面不可用或规则不可判定。启动失败、协议损坏、租约冲突、工件损坏、持久化失败和未完成清理等基础设施问题不得写成 INCONCLUSIVE。

### 3. 幂等、租约与 fencing

- Job 创建持久化 `idempotency_key` 和 `request_hash`。幂等作用域为项目、操作类型和幂等键的组合。
- 相同作用域、相同幂等键和相同请求哈希返回既有 Job 与 Run；无论任务当前是否完成，都不创建重复对象。
- 相同作用域和幂等键对应不同请求哈希时返回稳定冲突 `JOB_IDEMPOTENCY_CONFLICT`。
- `attempt` 是已开始执行尝试的 1 基序号；待执行 Job 在数据库中从 0 开始，每次从 PENDING 或 RETRY_WAIT 成功 claim 并准备启动 Runner 时递增。
- `max_attempts` 是包含首次尝试在内的硬上限。达到上限后的可重试错误转为最终 FATAL_ERROR。
- `available_at_us` 是 Job 最早可 claim 的 UTC Unix 微秒时间。
- 每次 claim 产生一个该 Job 内单调递增、永不复用的正整数 `fencing_token`。续租不更换 token。
- Runner 结果、心跳、暂存工件和后续状态写入必须同时匹配 `job_id`、`lease_owner` 和 `fencing_token`。旧 token 的任何写入均拒绝。
- `lease_expires_at_us` 到期只表示 Worker 失去续租权，不证明旧 Runner 已退出。恢复流程必须先确认旧进程退出或完成清理，才能 claim 新尝试并产生新的目标副作用。
- `cancel_requested_at_us` 首次写入后不可清空；Runner 和 Worker 在安全点观察取消，但仍必须完成必要清理。

### 4. Runner 输入

- 一次 Runner 尝试接收一个完整 Run；不得为每个测试用例启动独立 Runner。重试可以在确认旧尝试退出并清理后为同一 Run 启动替代尝试，但同一时刻最多一个尝试有权产生目标副作用。
- Runner 输入使用 `RunnerInputV1`，`schema_version` 固定为字符串 `"1"`，模型 `extra=forbid`、`frozen=True`。
- 输入包含 `run_id`、`job_id`、`attempt`、`lease_owner`、`fencing_token`、`created_at_us`、执行预算和不可变项目执行快照。
- 项目执行快照直接嵌入阶段 1 的 `TargetScope`、`Identity`、`ResourceDefinition`、`Flow` 和 `SecurityContract` 内容，并携带项目 slug、名称、观察器开关和 mutation seed。
- 快照独立重验阶段 1 的 ID、RuleKind、ACTIVE 契约和 Flow 所需规则不变量，不信任上游曾经完成 YAML 校验。
- `ProjectDefinition.flow_path` 和 `contract_path` 不进入快照。Runner 不得重新读取可变 YAML。
- 身份只能携带 `env:NAME` 秘密引用。阶段 2.3 解析的真实凭据只能通过最小子进程环境传递，不得进入 argv、Runner 输入、日志、结果或持久快照。

### 5. Runner 结果

- Runner 结果使用 `RunnerResultV1`，携带与输入一致的 `job_id`、`lease_owner` 和 `fencing_token`，结果类型固定为 SUCCESS、SAFETY_STOPPED、CANCELLED、RETRYABLE_ERROR、FATAL_ERROR。
- 结果携带关联 ID、attempt、fencing token、完成时间、结果类型、Run lifecycle、Job state、可选 verdict、稳定 reason codes、清理结果、受限错误结构和暂存工件清单。
- 错误结构只包含稳定错误码和 retryable 布尔值，不携带任意自由文本，避免把秘密或不稳定诊断写入协议。
- 暂存工件记录规范相对 POSIX 路径、字节数和小写 SHA-256。绝对路径、盘符、反斜杠、空段、`.` 和 `..` 均拒绝。
- 工件路径同时拒绝 Windows ADS、保留设备名、尾随点或空格和大小写别名；单项及同一结果的总字节数均以 1 GiB 为硬上限。
- 结果模型验证本 ADR 的状态矩阵。矛盾组合在 Worker 读取前即作为协议错误拒绝。
- Runner 进程退出码不编码 PASS、BLOCK 或 INCONCLUSIVE。退出码 0 仅表示已经原子产生一个可供 Worker 校验的完整结果文件；64 表示输入或协议版本错误，70 表示启动或内部故障且没有可信结果，74 表示结果文件写入失败。Worker 始终重新解析结果并验证 fencing 与工件哈希。

### 6. 规范 JSON 与大小限制

- 协议 JSON 使用 UTF-8、键排序和紧凑分隔符，不带 BOM，不允许 NaN 或 Infinity。
- SHA-256 对规范 JSON 的原始 UTF-8 字节计算。
- 未知字段、未知 `schema_version` 和任意层级重复键均拒绝。
- 阶段 2.3 调用方必须通过 `known_secrets` 向序列化、哈希和解析边界提供当前尝试的非空真实秘密；对象键或字符串值包含任一秘密子串时固定拒绝且异常不回显位置或原值。
- Runner 输入在解析前限制为 1 MiB；Runner 结果在解析前限制为 4 MiB。
- Pydantic 生成的 JSON Schema 签入 `schemas/runner/`，测试必须证明签入版本与当前模型完全一致。

### 7. 工件与事务顺序

提交顺序固定为：

1. Runner 只向本次尝试 staging 目录写入结果和工件。
2. Worker 校验结果 Schema、关联 ID、attempt、lease owner、fencing token、相对路径、字节数和 SHA-256。
3. Worker 原子 promote staging 目录。
4. promote 成功后，Worker 才在同一 Unit of Work 中写 Run、Job、事件和 Evidence 索引完成态。

数据库不得在工件发布前标记 Run 或 Job 完成。promote 成功但数据库提交失败时保留已发布目录，由阶段 2.4 reconciliation 根据 manifest、fencing token 和数据库状态收敛。旧 fencing token 的结果永远不得 promote。

### 8. CLI 边界

本 ADR 替代 ADR-0001 中“CLI 默认通过进程内应用服务执行主动验证”的相关决定。ADR-0001 对 GUI、CLI、CI、REST API、TUI、桌面和 Docker 的产品入口定位继续有效。

阶段 2.3 完成后，CLI 可以提交 Job、等待、取消和展示结果，但所有目标流量只能由隔离 Runner 发出。阶段 2.0 不修改现有 CLI 和同步 RunService；迁移在 2.3 通过兼容测试一次完成。

## 结果

优点：

- 数据库、Worker 和 Runner 在实现前拥有同一可测试协议。
- fencing token 阻断过期 Worker 和旧 Runner 发布结果。
- 生命周期、任务状态和安全结论不再因进程退出码或基础设施错误混写。
- Runner 不接触可变 YAML，执行输入能够重放和审计。

代价：

- 阶段 2.1 至 2.4 必须严格遵循协议字段和事务顺序。
- Schema 变化需要新版本和迁移，不能原地放宽 V1。
- 恢复流程必须处理“租约过期但旧进程仍存活”和“promote 后提交失败”两个显式中间态。

## 迁移与回滚

- 阶段 2.0 只新增协议、Schema、测试和规范，不改变阶段 1 同步执行结果及 CLI 退出码。
- 阶段 2.1 的表结构直接使用本 ADR 的公共 ID、微秒时间和 Job 字段；不得先引入临时格式再迁移。
- 阶段 2.3 切换 CLI 前必须保留阶段 1 全部黄金测试，并增加 Worker/Runner 等价性测试。
- 若阶段 2.1 至 2.3 实现尚未发布，可通过移除新入口回滚到阶段 1 同步链路；已经持久化的 V1 协议文档不得按另一语义解释。
