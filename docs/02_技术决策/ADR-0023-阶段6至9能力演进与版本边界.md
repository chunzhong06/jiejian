# ADR-0023：阶段 6～9 能力演进与版本边界

- 状态：已接受（阶段 6、7.1 与 7.2 已实现并通过对应验收；阶段 8～9 待实现）
- 日期：2026-08-14
- 范围：复杂权限、多观察者、Finding/回归门禁、产物检查、统一报告、评测与作品化
- 依赖：[项目设计规范](../01_开发规范/项目设计规范.md)、[开发路线图](../04_开发记录/开发路线图.md)、[Runner 执行协议 V1](../03_协议定义/Runner执行协议V1.md)、[数据格式](../03_协议定义/数据格式.md)

## 背景

当前 V1 以 `RuleKind + FlowStep + Identity + ResourceDefinition` 表达所有权越权，并以 `http + owner_api` 观察面形成 Evidence。它已经覆盖阶段 0～5.6 的所有权验证，但不能在不堆叠特殊字段的情况下表达租户、部门、层级、工作流状态和多种观察源。当前 Results 中的 Finding 还是单次 Evidence 的只读投影，也没有显式回归基线、独立 GatePolicy、产物检查边界或多格式报告真源。

后续演进必须隐藏这些新增复杂度，同时保持 V1 历史 Run、协议、工件、数据库和当前 CLI/API 读取能力。不得原地扩充 Runner V1 或让 LLM、Worker、报告渲染器取得判定权。

## 决定

### 1. 实施顺序

后续能力固定按以下顺序实施，前一阶段通过里程碑验收后才进入下一阶段：

1. 阶段 6：复杂权限关系、可解释用例约简和多观察者验证。
2. 阶段 7：稳定 Finding、显式回归基线、GatePolicy 与 CI 门禁。
3. 阶段 8：受控产物检查、统一 JSON 报告和确定性多格式渲染。
4. 阶段 9：有真值评测集、量化实验和比赛作品化。

阶段编号不是新增用户业务阶段；GUI 仍只显示接入、录制、建约、测试、验证、报告。

### 2. 版本演进总则

- Runner V1、现有 `schema_version="1"` 输入、历史 Run 快照和已发布工件永久按 V1 读取，不在原字段上增加可选语义。
- 阶段 6 建立版本化输入适配器和一份规范化权限用例中间表示。V1 loader 与 V2 loader 都编译到同一 Verification 执行/判定核心，不建立第二套执行核心。
- 只有现有 V1 能完整表达的所有权用例可继续走 Runner V1；复杂关系或多观察者用例必须使用 Runner V2 和新的公共 Schema。协议版本由提交时固化到 Run 快照，禁止运行中升级。
- 新 Schema、数据库表/列和迁移只在对应阶段实现时签入。本 ADR 只冻结边界，不提前创建占位模型、入口或 migration。
- Results 按 `schema_version` 分派 reader。历史文件不重写；新 reader 必须先通过历史 Run、旧数据库和旧报告 fixture 的兼容测试。

### 3. 阶段 6：规范化权限意图

V2 权限意图由六个正交部分组成；Contract 以 `role_ids` 显式声明可引用角色，主体、动作、工作流状态和关系路径都必须引用已声明事实：

| 部分 | 语义 |
| --- | --- |
| subject | 身份或身份类，以及角色、部门、租户、管理级别等已声明属性 |
| action | 稳定业务动作 ID；HTTP method/path 只是执行绑定，不是权限语义本身 |
| resource | 资源类型、稳定选择器、owner、租户、部门、父资源和当前状态 |
| relation | subject 与 resource/其他 subject 的关系及可验证关系路径 |
| context | 工作流状态、请求上下文和适用条件；只接受确定性、可序列化表达 |
| expected | `ALLOW` 或 `DENY`，以及形成结论所必需的观察器集合 |

规则的关系路径是从规则主体出发、沿有向关系事实连续到规则资源的有限路径，不能跳接、重复边或以其他资源结束。非空 context 必须包含本规则资源，并与该资源的工作流、租户和部门事实一致；这些约束在产生规范化计划前确定拒绝。

`FlowStep` 继续描述可执行正常流程；权限意图引用动作与资源，编译器再把它绑定到 Flow。`RuleKind` 继续属于 V1，不向其中堆叠新枚举。V1 的三个规则确定性映射为 V2 所有权意图，并在编译结果中保留原 rule、step、identity、resource、seed 和 engine version，保证结果可追溯。

阶段 6 首版纳入：

- 多角色、部门成员关系和租户隔离；
- 资源所有权、直接父子层级、管理层级和工作流状态；
- 显式有限资源集合上的批量操作；
- 在输入给出的有限无环关系图上进行有界间接继承，结果记录完整关系路径和最大深度。

首版不纳入任意策略代码、运行时脚本、自动发现未知组织图、开放式自然语言条件或无限图遍历。缺少关系事实或关系图不完整时输出覆盖缺口或 `INCONCLUSIVE`，不得猜测关系或默认允许。

### 4. 阶段 6：确定性覆盖与约简

用例生成不计算角色 × 资源 × 动作 × 状态的全笛卡尔积。编译器按以下固定顺序生成：

1. 每条 `ALLOW` 意图至少一个合法基线；每条 `DENY` 意图至少一个越界用例。
2. 对每个受保护关系维度生成“最近的禁止邻居”，例如同租户其他 owner、其他租户同角色、相邻管理层级和前后工作流状态。
3. 只有契约显式声明交互或风险等级要求时，才增加确定性 pairwise 组合。
4. 相同动作、观察要求和预期结果下，被更具体用例完全覆盖的项按稳定规则消除。
5. 最后应用请求、用例、时间和观察字节预算；排序只由规范化内容、固定 seed 和 engine version 决定。

编译计划必须保存来源意图、变异维度、关系路径、保留/消除理由、预算使用量和覆盖清单。预算不足、必需维度未覆盖或关系事实不完整时，覆盖清单显式标记 gap；相关 Run 不能因用例被约简而得到 PASS。

LLM 可以提出权限意图候选或解释覆盖缺口，但不能激活意图、选择最终覆盖、执行流量或决定 Verdict。

阶段 6.1 已落地 `verification.permissions` 纯模型、严格交叉引用校验、规范 JSON/SHA-256、每条规则一用例的规范化计划和 V1 ownership 适配器；阶段 6.2 已落地 `verification.permission_coverage` 的确定性关系覆盖计划、最近禁止邻居、批量授权模式、预算/gap、语义去重和稳定 finding 前置身份，并签入 `permission-contract-v2.schema.json` 与 `permission-mutation-plan-v2.schema.json`。`samples/*_apps/permissions_v2/` 提供同一 Contract 的 fixed/vulnerable/inconclusive 本机 loopback 场景资产，但不接入 V1 `project.yaml`。这些模型和样例只表达、规划和验证意图，Runner V2 执行阶段另有独立输入/观察/工件边界；finding 前置身份不是阶段 7 最终 Finding ID。

### 5. 阶段 6：Observer V2

Observer V2 将当前 `http + owner_api` 扩展为版本化观察协议，不把特定观察器字段直接加入 Evidence。每个 `ObserverSpecV2` 至少冻结：

- observer ID、类型和目标引用；
- `before`、`after` 或 `eventual` 观察阶段；
- 起止窗口、最大等待和轮询间隔；
- case/请求/业务 correlation 与 causality 规则；
- required/optional、完整性要求和不可用处理；
- 请求/查询/行数/字节/时间预算；
- 最小 `secret_ref` 集合、脱敏策略和允许的观察范围。

每个 `ObservationEnvelopeV2` 至少保存 observer、窗口、采集时间、correlation、causality、before/after/delta、payload hash、provenance、完整性状态，以及 `AVAILABLE/PARTIAL/UNAVAILABLE/ERROR`。原始秘密、未脱敏凭据和无界原始日志不得进入 envelope。

观察运行位置固定如下：

| 类型 | 运行位置与限制 |
| --- | --- |
| HTTP、owner API | Runner V2 内，继续受 TargetScope、重定向、请求和响应预算约束 |
| 只读数据库 | Runner 隔离域内的固定 observer 子进程；只允许预注册查询模板、只读账号/事务、statement timeout、行数与字节上限 |
| 审计日志、异步任务 | 固定 observer 子进程通过受限只读 API/文件窗口轮询；必须用 case correlation 和有界 eventual window |
| 消息队列 | 只允许 broker 的只读检查/快照能力；不得消费、ack、提交 offset 或创建持久消费者；不支持时标记不可用 |
| 对象存储 | 只允许固定 bucket/prefix 的 list/head/有界 get；禁止 put/delete 和跨范围枚举 |

API 不运行观察器，Worker 不解释观察结果。Worker 只解析本次 observer 所需的最小 secret 集并监督 Runner；Runner V2 负责观察时序、预算、清理和协议输出；Verification 纯判定层消费已校验 envelope。观察目标使用独立 `ObserverScope`，不能借观察器放宽 TargetScope、SSRF 或扫描授权。

required observer 不可用、不完整、超时或无法建立因果关联时，相关用例必须是 `INCONCLUSIVE`；optional observer 缺失仍进入可解释覆盖清单。观察器失败不能隐式切换到其他数据源。

### 6. Runner V2、持久化和历史兼容

以下变化必须使用 Runner V2 和新机器 Schema：权限意图快照、关系事实/覆盖计划、ObserverSpec、ObservationEnvelope、V2 Evidence 和 V2 result。阶段 6 已冻结独立 `RunnerInputV2`、`EvidenceV2`、`RunnerResultV2` 模型、parser/canonical 函数和三份 Runner Schema；显式 subject/action/observer binding、按 requirement 映射 observer、按 resource×phase 的逐资源覆盖、OWNER_API binding 的非秘密 `owner_api_credential_ref`、仅允许 BEFORE/AFTER/EVENTUAL 的执行观察阶段、请求 failure_code 与 Evidence 内容寻址 ID、以及 required observer 不完整即 INCONCLUSIVE 的不变量由协议层保护。Runner V2 与 V1 使用明确不同的模型、Schema 和协议测试；正式 `python -m jiejian.runner` 入口已按 schema_version 分派并在 staging 生成 Evidence/Result 工件，Worker supervision、持久请求、staging 校验、原子 publication 和基础 V2 结果读取已复用既有生命周期接线。当前通过无秘密 `PermissionExecutionProfileV2`、0008 摘要表和共享 Application 服务生成/冻结 V2 请求，并由显式 `/api/v2` 与 `permission-run` CLI 调用；0008 不增加 jobs/runs 协议字段，不保存完整 Profile、计划、秘密或 observation 明细。测试页高级复杂权限入口、验证页 V2 Evidence 展示和无秘密样例正式入口与动态闭环已接线；阶段 7.1 Finding 与 7.2 Baseline/Gate 已接线，阶段 8 统一报告仍未接线。

阶段 6 的数据库迁移只保存需要治理或查询的 V2 Profile 非秘密摘要；0008 的 profile/project/source/contract/plan/engine 元数据不复制完整配置、计划、秘密或 observation 明细。不可变完整快照与工件仍由 request/publication 机制保存。阶段 7.1 已为 Finding、Occurrence 增加独立记录；7.2 再为 RegressionBaseline 和 GateResult 增加独立记录。任何迁移均只向前新增，不改写 V1 行；旧数据库升级链和 Alembic metadata 必须比较验证。

阶段 6 已实现独立的 Verification V2 纯判定叶：它消费已校验的内部请求/观察事实，按权限期望、逐资源副作用和批量原子语义产生 CaseVerdict 与稳定原因码；不依赖 Runner/Observer 适配器，由 Runner V2 通过显式事实投影调用。

阶段 6.3 已签入独立 Observer V2 spec/invocation/envelope/outcome Schema 与纯协议模型；owner_api 适配器在既有 `HttpExecutor` 边界内生成 V2 envelope，再由唯一显式投影恢复 V1 `Observation`。SQLite 观察由 Runner-side supervisor 启动隔离子进程，父边界只传无秘密 invocation 和 `database_secret_ref` 对应的单一环境变量；子进程只执行固定 `resource-state` 参数化查询，以 `mode=ro` 和 `query_only` 防写，并以严格 envelope 返回完整性、预算和错误状态。fixed/vulnerable 配对已用同一 HTTP 403、同一 correlation 和真实 BEFORE/AFTER SQLite envelope 证明“拒绝且无变化”与“拒绝但已变化”两类事实。它不改变 V1 Runner 输入/结果、历史 Evidence/工件或 Verdict；Runner V2、Worker/publication、Profile 后端入口和正式样例已在阶段 6 后续批次完成接线。

阶段 6.4 已新增 `STRUCTURED_AUDIT_LOG` 与 `ASYNC_TASK_STATUS` Observer V2 类型和 Runner-side 隔离子进程观察器，并补充三类本机异步因果样例的四面事实测试。审计 locator 只接受 `env:` 授权根引用、固定顶层 JSONL 文件名/轮转族、字段 allowlist 和独立扫描预算；异步 locator 只接受显式 IPv4 origin、固定 request-marker 路径、`env:` 只读凭据引用和独立轮询预算。两类观察均使用独立 wire DTO，旧 6.3 Observer DTO 和 canonical bytes/hash 不变。输出只保存有界状态摘要、扫描/轮询计数和相对 provenance；明确 case correlation 是唯一因果根，观察窗口超时与目标任务 `TIMED_OUT` 分开表达。缺失/冲突/部分读取、状态冲突和预算失败不得退化为时间或资源相似推断。Runner V2、Worker/publication、V2 Profile、API/CLI/GUI 和正式样例均已接线；Queue 与 Blob 观察在阶段 6.5 完成。

阶段 6.5A 已冻结 `AZURE_QUEUE_PEEK`/`AZURE_BLOB_OBJECT` Observer V2 locator、独立嵌套预算、loopback/公网 endpoint、`env:` SAS 引用、独立测试队列/container 和字段/prefix allowlist。Queue 仅允许 EVENTUAL Peek；Blob 仅允许 BEFORE/AFTER/EVENTUAL 的固定 container/prefix 观察。六份 Observer Schema 均由各自模型原生 `model_json_schema()` 签入；新增 Azure 分支导致共享 spec 定义在 audit/async invocation Schema 中机械扩展，不改变旧实例运行语义、canonical bytes/hash 或 V1 行为。Queue Peek 与 Blob Object 已在 Runner 隔离子进程中以固定 REST 版本实现，并通过本机 Azurite 动态验证；Runner V2 可调度这些 observer，Worker/publication 可接收 V2 工件。阶段 6 不提供 Queue/Blob 专属普通用户配置或动态黄金样例；调用仍经受控 Profile/协议入口，不影响适配器的正式性。

Job、attempt、lease、fencing、cancel、retry、recovery、staging 和原子 publication 不因协议升级改变。生命周期仍与 Case/Run Verdict 和后续 GateDecision 分开保存。

阶段 6 里程碑已完成：复杂权限、owner_api、只读 SQLite、结构化审计、异步任务、Azure Queue Peek 与 Azure Blob Object 均使用同一 Observer V2/Runner V2 事实链；fixed/vulnerable/inconclusive 三变体通过独立 Worker、隔离 Runner、staging 和 publication 得到 PASS/BLOCK/INCONCLUSIVE。阶段 7.1 Finding/Occurrence 与 7.2 回归门禁已随后实现；阶段 8 统一报告未实现。

### 7. 阶段 7.1：Finding、Occurrence 与 Evidence（已实现）

- Evidence 是某次 Run 中一个 case 的不可变确认事实，包含观察、Verdict、原因和内容 hash；它不承担跨 Run 身份。
- Finding 是跨 Run 稳定问题实体。稳定 key 由项目、权限意图/规则、subject 类、action、resource 类/关系和问题类别规范化计算，不包含 run ID、case ID、时间、随机值或实际秘密。
- FindingOccurrence 表示某个 Finding 在一次 Run 中的出现、消失、重现或状态变化，链接一至多个 Evidence，并保存当次严重度、实际对象和覆盖上下文。

现有 `results.findings()` 的 V1 Evidence 投影继续用于历史读取，但不是阶段 7 的稳定 Finding 真源。升级时使用新的 schema/version 路径，禁止把 V1 `evidence_id` 静默解释为稳定 finding ID。

实现边界：`0009_stage7_findings` 只新增 Finding 与 Occurrence 索引；V1/V2 publication 先由 `PublishedResultReader` 完整性校验，再由稳定 Results v2 查询物化。Occurrence 以 Evidence ID 引用不可变事实。

### 7.2 阶段 7：RegressionBaseline 与 GatePolicy（已实现）

`0010_stage7_gate` 新增 RegressionBaseline 与 GateResult 持久化。RegressionBaseline 是显式接受的版本化对象，记录 project、accepted run、Finding/Occurrence/Evidence 引用、覆盖清单、请求快照摘要、协议/engine 版本、接受人、时间和理由；只有 PublishedResultReader 验证通过且生命周期为 COMPLETED 的 Run 可被接受。“最近一次运行”不能自动成为基线，LLM 不能接受基线。

GatePolicy 是独立于 Verification Verdict 的确定性策略。默认规则为：

- 新 BLOCK、已修复 Finding 重现、覆盖退化：门禁失败；
- `INCONCLUSIVE`、required observer 缺失或不完整：门禁失败；
- Run/Runner/observer/publication 执行错误或安全停止：门禁错误，不伪装成 PASS；
- 无新增/重现问题、覆盖不退化且执行完整时才可通过。

GateResult 保存 policy version、baseline、run、输入 hash、逐条原因和最终 `PASS/BLOCK/ERROR`，相同不可变输入只读取同一持久结果。v2 API 提供基线接受、Gate 求值和结果读取；新 CLI 的 `baseline accept`、`gate evaluate`、`gate result` 与 API 共用同一应用服务，其中 Gate CLI 使用 PASS=0、BLOCK=1、ERROR=2，旧 `ci` 退出语义不变。本批不新增 GUI，也不改变 Runner/Observer/Verification/Evidence/publication。

### 9. 阶段 8：受控产物检查

产物检查是独立、预算化的 JobHandler 和隔离执行边界，不属于 API 进程，也不让扫描器任意遍历源码或主机文件系统。输入只能是显式 staging 后的构建产物根、规范 manifest、项目/工件 ID 和规则集版本；拒绝 symlink/reparse、路径逃逸和特殊文件。

首版只提供可复现的确定性检查：已知秘密精确匹配与受限模式、调试/开发配置、暴露的 Source Map、禁止发布的文件，以及对显式 lock/manifest 使用固定本地规则集的依赖版本检查。每项检查具有文件数、单文件大小、总字节、时间和结果数预算；不得在检查时联网更新规则或执行工件代码。

产物 Evidence 与运行时 Evidence 保持来源类型和执行边界分离，但可以通过阶段 7 的 Finding/Occurrence 统一进入门禁。

### 10. 阶段 8：统一报告真源

每个新 Run 的 `report.json` 是该 Run 的唯一语义报告真源，带明确 `schema_version`。HTML、SARIF 和 JUnit 是从经过 Schema 校验、脱敏和完整性验证的同一 JSON 纯渲染得到的派生工件；渲染器不得重新判定、补 Finding 或改变门禁结果。

历史 V1 `report.json` 原样保留并由 V1 reader 读取。新报告版本在实现时提供显式 reader 和兼容投影：现有 API/CLI 的稳定字段和退出语义继续可用，新字段通过版本化响应/参数暴露。不得重写历史报告，也不得让 HTML/SARIF/JUnit 成为反向事实来源。

### 11. 阶段 9：评测与作品化

评测集按版本冻结输入、真值、预期观察完整性和环境，至少覆盖 ownership、tenant、department、hierarchy、workflow、bulk、异步观察、观察器不可用和产物问题，并包含 safe/vulnerable/inconclusive 配对与修复回归。

正式实验报告 Finding 级 precision/recall/F1、误报率、`INCONCLUSIVE` 比例及原因、覆盖率、观察器可用率、请求/字节/耗时预算、恢复与清理结果、重复运行 hash 一致性。LLM 只报告候选接受率和人工确认成本，不能计入 Verdict 真值来源。

数据集分训练/调试与保留集；不能通过修改真值迁就实现。运行环境、规则集、engine/protocol/schema 版本和随机 seed 必须锁定，实验只访问授权本地目标。作品化只整理已经通过验收的安装、演示、报告、指标、限制和答辩材料，不把规划写成已实现。

## 永久边界

- 保持模块化单体与独立 Worker/Runner；API 不执行目标或观察流量。
- Verification 纯领域/判定层不依赖 FastAPI、SQLAlchemy、Playwright、供应商 SDK 或具体观察器。
- Worker 不实现 Verification 判定；Runner 隔离域继续承载目标和观察流量。
- 生命周期、Verification Verdict 和 GateDecision 是三类不同事实。
- LLM 永远只生成不可信候选或辅助解释。
- 所有秘密最小化解析并统一脱敏；协议、工件和报告只保存 `secret_ref` 或已脱敏事实。
- 旧 Run、数据库、Schema、协议和报告通过版本分派兼容，不做静默原地升级。

## 未采用方案

- 不扩充 Runner V1 可选字段：这会让同一版本出现多套语义并破坏严格 Schema。
- 不为每种权限关系增加一个 RuleKind：这会把关系、动作、上下文和预期结果重新耦合。
- 不穷举全部组合或让 LLM 选择测试：前者不可控，后者不可复现且越过信任边界。
- 不在 API 中直接查询数据库、队列或对象存储：这会绕过隔离、秘密、预算和清理边界。
- 不把单次 Evidence ID 当稳定 Finding ID，也不把最新 Run 自动作为回归基线。
- 不让每个报告渲染器各自组装结论；JSON 是唯一语义真源。
- 不允许产物扫描器接受任意源码路径、执行构建脚本或在线更新规则。

## 实施门禁

每一阶段开始前必须把本 ADR 的相应设计落实为协议/Schema、迁移说明和失败语义测试。任何需要改变永久边界、V1 读取语义、Job 恢复、原子 publication 或 LLM 信任边界的证据，必须停止实施并形成新的用户决策；不能借“兼容”建立两套长期业务核心。
