# ADR-0029：安全意图与契约治理边界

- 状态：已接受
- 日期：2026-08-19
- 适用范围：Requirement、Candidate、PermissionIntent、PermissionContract 和权限覆盖治理

## 背景

权限检查必须从可审阅的安全意图开始，而不能由目标请求、模型输出或执行结果反推规则。需求、候选、契约、覆盖计划和验证结论需要有清晰的可信边界。

## 决策

`Requirement` 保存待验证意图，`ContractCandidate` 只保存确定性分析建议。普通产品路径另以用户逐单元明确确认的 `PermissionIntent` 保存业务权限期望；它只引用动作、主体权限组、资源所有者权限组、关系和确认来源，不绑定 TestIdentity、资源实例、endpoint 或会话。确定性 SecuritySetupCompiler 在编译时为组级要求选择当前 PREPARED 账号代表，再将可执行投影编译为 `PermissionContract`/`ContractVersion`，后者仍是唯一可执行安全意图。只有 ACTIVE ContractVersion 可以生成 Coverage 和 PermissionMutationPlan，并进入执行请求。

确定性候选使用稳定 canonical、ID、指纹、排序和漂移报告；冲突、歧义、观察器不足和能力变化形成治理阻断。人工审阅是激活前门禁。模型不进入 Candidate 生成、Contract 激活或后续执行链。

普通用户只编辑 PermissionIntent，生成 Contract 仍经过现有治理状态机；高级用户可以直接治理 Contract，但同一普通规则不能同时在 Intent 与 Contract 两侧手工维护。被引用权限组或动作改变后旧 Intent 不再 CURRENT；账号缺失、过期、补充或替换只改变覆盖缺口与生成 Contract/Profile，不要求重新确认组级权限期望。

## 理由与取舍

把治理和执行分开可以保留候选来源、审阅和漂移历史，同时避免不可信输入进入 Runner。代价是激活和修订需要明确状态转换，且执行必须保存契约快照。

## 影响

ownership 和 permissions 使用同一 Permission → Runner → Evidence → Verification → Results 链。Coverage/MutationPlan 表达用例、关系和 required observations；HTTP 字段和具体 Observer 细节留在执行绑定与协议边界。

## 迁移与兼容

旧 Contract/Candidate 治理记录只按当前模型严格解析；历史 LLM 来源字段只为既有记录读取保留，当前治理入口拒绝新建 LLM Candidate，不通过旧开发格式猜测恢复。ACTIVE 版本不可原地修改，修订产生新版本并保留旧版本关系。
