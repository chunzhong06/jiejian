# 系统架构

## 当前形态

界鉴是模块化单体，使用一个 Python 包共享领域模型和安全验证规则；高风险主动验证通过独立 Worker 和隔离 Runner 形成进程边界。阶段 4 增加只绑定本机回环的 FastAPI 控制面和静态 React GUI。

## 层次

| 层次 | 当前职责 | 允许依赖 |
| --- | --- | --- |
| 入口层 | `cli.py` 解析输入、调用服务、序列化结果。 | runtime、worker、storage 的公开边界 |
| 应用控制层 | `worker/` 管理提交、Job、租约、Runner 监督、发布与恢复。 | domain、protocols、storage、errors |
| 执行层 | `runner/` 解析 RunnerInputV1 并调用共享 Verification。 | protocols、verification、errors |
| 验证层 | `verification/` 完成输入、授权、计划、HTTP、多观察者判定和 Evidence。 | domain、errors、redaction、httpx |
| 领域层 | `domain/` 保存纯模型、ID、生命周期、结论和状态机。 | Python/Pydantic 基础，不依赖执行与存储层 |
| 协议层 | `protocols/` 保存 Runner V1 可执行模型与严格 JSON 边界。 | domain、errors |
| 持久化层 | `storage/` 保存 SQLite、ORM、Repository、原子条件更新与 UnitOfWork。 | domain、有限协议约束、errors |
| 运行支持层 | `runtime/` 保存配置、doctor 和结构化日志。 | errors、redaction |

## 依赖方向

- `domain` 不导入 SQLAlchemy、Alembic、httpx 或 Typer。
- `protocols` 不依赖 runtime、storage、CLI 或 Verification 流水线。
- `storage` 不反向依赖 worker、verification 或 CLI。
- `verification` 不依赖数据库；只有 `verification/http.py` 具备目标 HTTP 能力。
- `worker` 不导入 `verification.http` 或 httpx；只有 Runner 能连接 RunnerInputV1 与 Verification 执行核心。
- CLI 和未来 API 都是调用者，不能复制判定规则或直接操作 ORM Session。

这些约束由[架构测试](../../tests/architecture/test_dependencies.py)检查，技术原因见[ADR-0004](../03_技术决策/ADR-0004-代码组织设计.md)。

## 进程边界

### CLI

当前产品入口。负责校验 YAML、提交 Job、启动或连接独立 Worker、等待终态和展示结果；不直接发目标请求。

### Worker

持有 Job 租约，生成 Fencing Token，启动 Runner，续租、取消、重试、校验 staging、原子发布工件并提交数据库完成态；不决定安全规则。

### Runner

一次进程执行一个完整 Run。它只接收不可变 RunnerInputV1，只写当前 attempt staging，不读取可变 YAML，不写数据库或最终发布目录。

### SQLite 与文件系统

SQLite 保存 Project、Run、Job、Job Event 和 Evidence Index。文件系统保存请求快照、Runner staging、Evidence 正文、报告、发布 manifest 和 quarantine。两者按“先发布文件，后提交数据库完成态”的顺序协作。

更短的解释见根部[架构说明](../架构说明.md)，完整数据顺序见[数据流](数据流.md)。
