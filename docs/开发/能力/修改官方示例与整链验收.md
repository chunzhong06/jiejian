## 固定业务与普通审批

冻结配方位于`product/backend/workflows/business_boundaries/official_recipe.py`：Alice项目负责人可以导出自己的完整交付ZIP；Bob普通协作成员不得导出Alice资源，但可以查看日常协作资料。两个Actor、两个Action、两个Effect和三条Permission保持明确。

只有真实活动 OfficialSampleExperience 且 project_id 精确匹配时，普通权限页才提供“使用已提供的权限提案”。用户显式采用后进入同一待审 Proposal 和普通 LOCAL_GUI Human Approval。启动仍需 consent，不能按项目名称识别 Sample；预置提案只是可选输入，不形成第二套审批或安全判断。未批准或边界不匹配时返回结构化待办，不安装材料或创建检查。

受控验收脚本只可在本轮新实例内核对完整固定配方后自动提交普通批准。未知提案、权限变化或与配方不符的内容必须拒绝；这属于已授权验收数据准备，不证明GUI批准交互已经通过。

## 准备材料

普通 Preparation 当前缺口提供“使用已提供的测试材料”；显式采用后重读 Preparation 和 Workspace，再由普通 `/tests` 的“开始检查”显式提交，材料齐备本身不创建 Run。OfficialScenarioInstaller调用正式Recording提交、JobAttempt、结果消费、Review/finalize和current Preparation绑定。固定无秘密事件不是现场浏览器录制，也不绕过事务写Storage。录制创建、claim、消费与持久完成共用原子事务；同key可读回恢复，不能重复消费已接受结果。普通Recording的Worker/独立进程/headed Chromium能力仍独立保留。

Alice/Bob使用正式TestIdentity与内存SessionSecretOverlay，秘密不落真实CredentialManager或公共工件。导出TARGET与RECOVERY分开录制，日常查看先取得具体资源再执行唯一TARGET，subject/owner/资源注入均精确绑定。源码变化后先读取公开 actor_bindings/action_bindings；存在非 CURRENT 绑定时，先经普通 maintenance 提案核对原有业务语义与权限，再由 Human Approval 复核实现，之后才准备材料。不通过先失败一次 prepare 探测页面流程，也不自动更改权限或 epoch；prepare 返回的结构化 pending 仍按真实失败处理。

## 六来源及真实因果

导出最终ZIP的AZURE_BLOB_OBJECT是唯一VERDICT_REQUIRED；审计是DIAGNOSIS_REQUIRED；Owner API、SQLite、Task和Queue是SUPPORTING。六来源都实际执行，任务完成和消息派发不能冒充ZIP效果。Owner使用Alice合法Cookie读取受保护资源；独立Bearer观察端点保留独立用途。

问题实现先真实enqueue，再authorize；Bob收到403后Worker仍可能形成ZIP。Worker在响应完成后继续，Trace保留派发、后置授权及Worker分支，archive节点才标最终effect_id。通用Locator据此形成AUTHORIZATION_LATE，HTTP拒绝不等于安全。

| 版本 | 真实变化 | 新检查事实 |
| --- | --- | --- |
| BASELINE | 先授权，再在请求线程内同步生成项目包；不派发队列 | 起始 NEW Run 由实际证据判断，满足原要求后为 PASS |
| VULNERABLE | enqueue在authorize前，决定性ZIP观察可用 | BLOCK / AUTHORIZATION_LATE |
| FIXED | authorize移至enqueue前，合法导出和日常查看保留 | 原题NEW Run PASS / Repair VERIFIED |

尚未选择应用时工作台提供示例启动。`/changes` 的 OfficialDevelopmentJourney 将同步起点、异步优化、检查问题和原题修复组织为同一开发演练。只有同源码、同权限的已发布起始 PASS 才能应用预设优化；FIXED 必须携带已发布 BLOCK 重建的 CurrentRepairReference。代码变更明确登记为“预设演示 · 本机用户”，不冒充本轮 Codex 的交付，也不创建 Run 或预制 Verdict。各次检查具有独立 run_id，旧包保持不变。

工作台在首次启动与旧实例已确认退出时共用简洁的“启动示例”入口；有历史时只补充保留提示。归档与从零准备的详细说明留在环境管理页及启动确认框。`EXITED` 不表示启动失败，也不表示用户忘记停止；未知所有权的启动门禁保持不变。

项目列表的 `official_sample` 从持久示例工作空间关联投影，不按名称识别，也不代表运行中。浏览器恢复选择时先共同读取项目列表和官方环境状态；示例仅在对应项目仍为 active/RUNNING 时自动恢复，停止、未知及状态读取失败时回到启动入口。手动选中旧示例只展示历史入口，不继续旧工作台待办。普通应用仍恢复选择，“应用地址已确认”只表示保存过的接入事实，不承诺当前实时可达。

`/environment` 的 OfficialSamplePanel 只管理实例，以及可选“证据不足”支线。`POST /observation` 只修改 Owner/ZIP 观察可用性，不修改源码、不登记代码变化、不降低证据标准。旧 EVIDENCE_LIMITED 请求转入同一观察操作，当前代码版本保持不变。恢复观察后仍须重新核对材料并执行新的检查。

`GET /development` 从普通 Reader 和 ProjectRepair 只读投影当前事实。源码偏离最后一次预设状态时标记 CUSTOM，预设优化或修复拒绝覆盖已有外部修改。实际 Codex 开发沿用普通 MCP 变化登记和独立检查，复制需求只表示文本已复制。预置录制材料根据明确的执行模式记录同步 200 或异步 202；API 进程仅静态解析执行模式，复杂源码改写要求用户自行录制，不执行应用代码。目标应用的授权行为以当前源码为准，观察条件不覆盖源码实现。

## 运行与退出

示例每次真正启动都从全新同步导出实现开始。先确认旧受控实例退出并归档旧项目，再建立新项目与 `var/runtime/workspaces/<workspace-id>/source` 下的新源码副本；在 `var/runtime/official-samples/<experience-id>` 创建独立的 state、descriptor、端口、进程树和秘密。旧权限、源码修改、登录状态与材料不带入新项目；新项目必须重新审阅权限并准备材料，不自动批准或开始检查。停止只收口自己拥有的实例、Registry 与会话秘密，旧项目在下次启动时归档；历史 publication 和旧源码记录保留。活动实例上的 start 不重复创建，明确 reset 则停止后按相同的全新同步导出实现流程启动。移除应用仍走普通项目生命周期。

实例所有权使用持久化的独立 Windows Job 身份核对；不能按 PID、同名进程或空闲端口推断退出。GET 状态只读，显式 reconcile 追加核对记录，不改写旧环境操作回执。确认旧受控树退出后才清理其临时实例目录并允许再次运行。缺少身份的旧记录、路径漂移、不可核验进程一律保留不确定状态；不自动接管或终止外部进程。当前跨进程安全恢复针对 Windows 受控 Job；不能确认身份的平台明确阻塞。Sample 只绑定 loopback，不调用真实云或付费接口。

材料配方的幂等键包含目标地址和运行实例，来源核验也包含受控实例标识；重复准备当前实例复用当前配方。新项目创建独立的身份记录并使用当前实例独立的秘密引用，保留 SecretStore 的旧所有权记录，不清除所有权约束来复用旧引用。确认进程归属不等于确认运行代码的 Git 身份。

活动CHECK必须先经正式取消和回收，不能在目标执行中切换版本或删除源码。业务恢复仅撤销本资源当前效果，保留Task/Audit/历史对象；全局reset不作为业务恢复。失败清理不得覆盖第一主错误或终止无关进程。

## 默认自动验收

唯一最终入口为`dev.ps1 sample-test`。非前端编排由`official.py`保留真实start.cmd、新var、source receipt、解释器身份、端口保护、受控浏览器HttpOnly会话、限时等待、failure.json与精确清理；`current_api.py`编排已冻结配方和公开API。

顺序固定为：启动隔离实例、确认权限与准备材料、同步起始检查、应用预设异步优化、问题检查、观察不足的新检查、原题修复与新检查、结果与历史证据核对、退出与资源清理。完整 sample-test 仅在任务约定需要最终产品验收时执行；普通修改使用直接测试。

每轮从精确change_id的check-preview取得计划指纹，向schema2 runs提交完整Plan。切换条件后若普通 Preparation 仍完整且 CheckPreview 可执行，则复用已有材料，不为 Sample 安装标记重复准备；未知回执先回读；GUI路径只定位本轮新Run用于收口，不再次POST；API专用编排若重取回执也只使用原idempotency_key，不能生成新key重复检查。仅在result_integrity=VALID后读取ResultStory/Evidence/repair-contracts；当前有界check-history、runs列表及精确run_id回读替代旧History，ProjectRepair替代旧Finding修复投影。普通 ResultStory、Evidence、Changes 和 Repair 是唯一分析路径，不保留 Sample 专用展示页；旧 Report/CLI/ResultPresentation 链不恢复，也不标成已验收。

`current_gui.py` 通过本轮受控浏览器实际操作界面，记录成功动作；`current_api.py` 只核对公开事实。技术 GUI 自动化覆盖：环境启动、普通权限页采用精确提案、核对原始对照、勾选核对声明后提交 Human Approval、按 Workspace 精确 task_id 在普通 Preparation 采用材料、普通 `/tests` 提交、四个已发布结果与退出。绑定失效先普通重绑后准备；READY_TO_VERIFY 原题必须实际经 `/changes` 点击“复验原题”，核对精确 change_id 后再开始检查，不重复登记版本切换已经形成的变化。问题结果从总览表按精确 Case 进入事实页，再打开必要证明对应的“已发布证据”同页 region，最多两次操作；核对证明要求、观察记录及本次 GET 的 Run/Case/Action/Evidence 引用。执行过程和定位证据另核对“在哪里看到、看到什么、因此支持什么、不能单独证明什么”四问；缺少对应证明必须失败，不能补假证据。原题下钻与定位证据同样保留真实操作记录。API核验支撑详细不变量，不能替代这些交互；截图也不是交互证据。driver的GUI接入点未全部通过时不报告最终验收成功。视觉验收另覆盖三视口、亮暗主题、焦点、遮挡和菜单。


真实 GUI 还核对问题版执行路径：按同 Case Story 选择路径并点击节点，DOM 父边逐项等于已发布 parent_event_ids；完整性、精度和证据文档归属保持。没有对应路径时失败，不补图。原题定位证据提前注册全部 GET，再点击一次并逐项核对 Run/Case/Evidence。历史页实际搜索问题 run_id、打开精确记录，返回保留输入和筛选。截图只记录实际准备、提交后可观察状态、三种结果、历史、证据与修复，不制造运行占位。

### 同实例 MCP 责任场景

正常 Official 流程在起始、问题、观察不足、修复四轮与历史验收后、退出前运行 `current_mcp.py`；没有第二入口，stop_after_setup 跳过完整检查与此场景。受控 SDK 客户端名为“界鉴验收客户端”，不调用用户 Coding Agent 或付费模型，不声称编写过修复代码。

先读取 MCP paired。已有用户级配对只经当前控制会话 reveal 后在内存复用，不重新 pair/rotate/forget；此前未配对才通过 `/tools` 的真实按钮创建，成功或失败后清理自己新建的配对并回读。凭据是 Windows 用户级资源，不随 var 隔离；token、headers、完整 SDK 异常和凭据响应不得进入日志、截图、报告、配置、剪贴板或持久环境。凭据/账户权限阻塞即停止，不替换 SecretStore 或切换身份重试。

通过 GUI 对唯一 Sample 项目选择并核对 READ/PREPARE/EXECUTE 回执。READ 登记变化与 PREPARE 提交检查各拒绝一次，以前后公开列表证明没有新增状态。默认使用 `jiejian_change_registration_preview` 和 `jiejian_change_register`，不创建或接收人工开发任务。PREPARE 只登记一次“受控验收核对当前修复源码，未修改文件”的声明，claimed_paths 为空，实际变化必须为零，来源包含本客户端；GUI 通过精确 change_id 展示记录及客户端来源，不自动打开本地登记表单。EXECUTE 只提交一次关联该 change_id 的完整普通检查，不携带原题修复引用，不用 HTTP 再提交，也不重发未知 SDK 回执；只回读新增 Run 供失败清理。

新增检查沿既有发布读取核对 PASS、两动作三 Case 与六来源。它是第五个普通 Run，不能标 VERIFIED，也不能混进原四轮列表；原四轮及原题 VERIFIED 关系保持，summary 单列 MCP 证据及实际总数 5。用户仍在筛选历史页时，后台完成不改变 URL 或输入；实际点击完成提示后进入该精确新 Run，返回仍保留原筛选。确认无活动 Run 后恢复 READ、清理自建配对，再沿既有退出与资源清理。GUI、历史、路径或 MCP 必需记录缺失不能报告验收通过。

validation/competition/all及Portable是保留工具，不属于当前默认闭环，不为默认验收失败追加另一套技术L5。局部开发只跑直接测试/stub；最终前端与公开能力就绪后才运行唯一完整sample-test。

## 环境操作回执与历史

start/stop/reset 接受可选 UUID operation_id；显式 ID 持久绑定一次操作，重复 ID 只回读，不再启停。已有活动实例上的新 start 保持该实例，停止后的 start 与明确 reset 均创建全新同步导出实现项目；省略 ID 仍表示一次显式新操作。版本切换接口不增加新执行行为，未知回执不得重发来探测。

体验状态区分 NOT_STARTED、STARTING、RUNNING、STOPPING、STOPPED、FAILED 和 UNKNOWN，并给出 history_project_id、last_error_code、operation_id、operation_state。安装 available 与生命周期分开。服务重启不复活进程，旧 PENDING 只读投影 UNKNOWN；停止确认后为 STOPPED，项目与源码继续保留。连接部分提交失败保留已创建项目索引，清理错误不覆盖首个错误码。

`GET /api/experience/official-sample/history` 从独立持久操作表列出真实记录，默认25、最多100条并返回 has_more；不扫描日志猜历史。测试 `tests/backend/workflows/test_environment_receipts.py` 使用 stub 进程所有者验证重放、重启与局部失败，不替代真实环境验收。

## 脚本所有权

`official.py` 只保留场景编排；`harness/state.py` 保存运行状态，`harness/receipt.py` 校验源码回执，`harness/lifecycle.py` 管准备、进程、端口与清理，`clients/http.py` 管 HTTP。`CurrentGui` 由共享 session 和 environment、boundaries、checks、history、mcp 动作组成；`reporting/diagnostics.py` 负责有界公开诊断。validation 下 models、runtime、evaluation、summary、suite 分责，不增加用户入口。
