# 修改工作台与唯一主任务

> 状态：CURRENT。说明当前能力的唯一所有者、修改位置、直接消费者与验证。

工作台回答“这个应用现在下一步做什么”。唯一主任务由后端Workspace选择；前端只呈现任务并携带精确引用。任务出现不表示操作已经执行，也不表示安全通过。

## 快速找到修改位置

| 要改什么 | 唯一位置 | 必须一起检查 |
| --- | --- | --- |
| 条件读取、编排顺序、需要时才求preview | `product/backend/workflows/workspace/service.py::WorkspaceService.get` | reading是否多读/漏读；CheckPreviewRequired分支；当前API DTO |
| 项目、检查、录制或交付事实读错 | `product/backend/workflows/workspace/reading.py::WorkspaceReader` | 原事实owner及其reader；不在Workspace复制业务判断 |
| 多个任务同时成立时选哪一个 | `product/backend/workflows/workspace/tasks.py` | boundary_task、PreparationTaskSelection、current_check_task、development_task各自输入与优先关系 |
| 标题、理由、route、task_id或journey | `product/backend/workflows/workspace/presentation.py` | task_view的指纹输入；前端精确引用、导航和可执行状态 |
| 跳转丢change/run/action引用 | `product/frontend/src/shared/navigation/taskDestination.ts` | ControlShell、页面上下文、返回准备后的检查关联 |
| 页面显示陈旧任务或任务不消失 | `product/frontend/src/app/state/useProjectWorkspace.ts` | 实际Workspace响应、旧请求覆盖、终态刷新；不能在前端另算优先级 |

## 对象怎样协作

`ApplicationCore` 创建Workspace及它需要的明确reader。`WorkspaceService.get`读取项目/应用理解和正式边界，先得到边界任务，再读取Preparation。边界尚需处理时不进入准备任务选择；只有相应分支需要时才计算检查preview。

检查reader提供活动检查、变化、修复和最近结果；development reader提供任务、交付、运行与精确验证关联。`tasks.py`依据传入事实选择任务，`presentation.py`生成展示和引用，最终返回 `WorkspaceView`。整个读取流程不持久化页面READY或PrimaryTask。

### 一处容易读错的优先关系

`development_task`不是把所有已有任务无条件保留：当正式边界无需关注、没有活动检查，而交付运行还未加载时，会选择加载该交付。这是现有明确分支。若已有准备任务跳往tests且没有change/run，它会保留该交付的change_id，避免准备返回后变成无关联的普通检查。

因此修改优先级必须读真实分支及测试，不能仅依据“权限→准备→检查”的概括文字自行重排。`CheckPreviewRequired`只是纯选择层请求补充所需事实的标识，不是持久任务状态。

## 修改边界

- `service.py`协调读什么与什么时候读；`reading.py`持有读取依赖；`tasks.py`不能接Repository或访问目标；`presentation.py`不能重判Verification。
- 准备齐备、检查可执行、运行已加载、检查结束和原题已修复分别取其权威服务；缺字段或reader失败不按成功补默认值。
- `project_id/action_id/change_id/run_id/repair`等引用保持精确；改task_id指纹须核对续接与前端陈旧响应行为。
- 只改任务文案时检查同类页面表达与相应组件；只有改变任务优先级或可执行性，才进入workflow相关测试。

## 最小验证与失败定位

| 改动/症状 | 直接测试或首查 |
| --- | --- |
| 准备任务次序 | `tests/backend/workflows/workspace/test_preparation_tasks.py` |
| 原题/变化/活动Run相互覆盖 | `tests/backend/workflows/workspace/test_repair_task.py` |
| 装配、reader或get返回事实 | `tests/backend/workflows/workspace/test_service.py`；变DTO再加 `tests/backend/api/test_workspace.py` |
| task引用、文字和journey | `tests/backend/workflows/workspace/test_task_presentation.py`、`test_journey.py`（同目录） |
| 点击后到了错误应用/旧Run | 后端Workspace精确引用→taskDestination→对应页面；按实际组件选择frontend-test |
| 完成操作后任务仍旧 | 先确认操作的持久回执与权威状态，再看Workspace响应，最后看前端读取时序 |

测试必须表达真实组合场景，例如“有交付且实例未加载”“准备返回仍关联同一变化”“活动检查不被交付任务盖掉”。不要仅把纯函数实现的分支逐字复制为预期。
