# 候选、提案与正式权限怎样协作

> 状态：CURRENT。正式规则只能由明确LOCAL_GUI决定事务形成；业务语义、实现绑定和执行材料各有生命周期。

## 正常链

1. 源码分析给出角色/动作实现线索；用户或原Agent提交规则候选，RuleCandidateService保存候选修订和回执。
2. GUI读取候选及当前边界，用户核对业务角色、动作、资源关系、ALLOW/DENY和受保护效果。propose形成普通不可变Proposal，候选没有因此生效。
3. BusinessBoundaryService读取当前业务revision和提案依据，LOCAL_GUI显式批准或放弃。批准事务核对并发、生成必要revision、implementation binding及Decision；出现权限revision变化时更新policy_epoch。
4. Preparation按正式Actor/Action/Permission、真实账号、资源和绑定派生缺口。缺账号或实现binding不能反过来撤销人的权限意图。
5. CheckService重新读取当前正式规则与材料，构建完整当前考题并冻结。Agent、LLM、Recording或结果GET均不能修改正式权限。

## 谁保存什么

| 对象 | 创建/维护者 | 消费者 | 禁止混用 |
| --- | --- | --- | --- |
| 识别Candidate | 应用理解/分析 | implementation inspection与绑定 | 不作为正式Permission身份 |
| RuleCandidate revision/receipt | RuleCandidateService | GUI审阅、候选转提案、MCP读取 | Agent说明不等于批准 |
| Proposal/Decision | 边界服务的提案与决定事务 | 审阅、正式revision追溯 | 展示/复制不能代替决定 |
| 业务revision和policy_epoch | LOCAL_GUI批准事务 | 准备、计划、变化与历史 | 纯实现重绑不冒充语义变化 |
| 技术binding | 用户确认材料与绑定工作流 | 实时inspection、冻结输入 | 账号更换不静默改业务revision |

## 失败与收口

旧候选basis、提案指纹或revision失配时拒绝写入；不能用“合并最新值”悄悄改变用户刚审阅的要求。决定失败保持事务原子性；同一提案不能重复形成不同决定。候选/操作响应未知先查原键与当前提案状态，不直接重发批准。

批准后读取失败与批准事务失败分开，不能因为页面没有刷新就重做决定。旧Permission与Decision保持历史，不能从当前角色名称反推旧Run使用的规则。
