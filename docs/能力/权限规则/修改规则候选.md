## 修改路线

先读context获得当前正式边界及不透明basis；save验证basis和精确候选修订，保存候选与操作回执；show按修订展示候选和沿用分析；GUI显式propose形成普通提案。之后由[规则与批准](修改规则与批准.md)的唯一决定事务处理，不在候选服务里推进policy_epoch。

范围核对工作面支持用户显式选中多项明确要求并统一确认时间；歧义逐项澄清，全部确认后显示汇总，再显式进入规则核对；未决或失效范围继续阻塞。完整原文、回看决定与候选管理收在辅助入口。规则核对页的“Agent 协助”和“读取候选”放在同一候选区标题栏。协助请求在该区就地展开，原Agent保存后由唯一的读取按钮更新候选；不在页头或展开区重复放读取入口。连接设置返回时保留当前项目和候选修订。

候选列表按当前/已归档分页，返回真实角色、动作、权限、例子计数和现场评估摘要；GUI使用include_preparation=false，不为列表读取计算材料库存。业务信息已保存不等于权限已生效；不完整候选提供补充请求，正式空边界也可先保存CREATE候选。

归档由LOCAL_GUI显式PUT候选visibility，使用候选revision与展示状态expected_version并发校验。rule_candidate_visibility独立保存archived/version，候选修订、提案和批准来源不变；存在任一未决定提案时禁止归档。归档后不可继续修改或转提案，先恢复再处理。写入响应不明时先回读，不自动重发。MCP没有归档或恢复能力。

普通应用首次建立权限时，先说明“Agent 整理 → 读取候选 → 人审阅批准”，人工草稿收在辅助展开项。官方示例明确标注随包提供的权限草稿；源码识别只提供角色与动作线索，不冒充 Agent 整理结果。权限页保留原表格，通过“全部规则／允许／禁止”筛选；按动作查看继续由业务动作视图承担。提案审阅保留原始与拟生效值，筛选仅改变展示，批准仍覆盖整份提案。

来源描述、客户端名称和Agent理由只用于审阅，不等同于认证或事实证明。自然语言模型草稿查[模型服务](../控制面/修改模型服务.md)，它同样不能代替正式批准。

Agent输入的公开Schema必须包含实际reader的条件约束：DATA_DISCLOSURE要求非空protected_projection，其他效果类型该字段为空。MCP候选报错只给Schema已声明的字段名、有限索引和固定规则说明，不回显输入值、未知字段名或原始异常正文。首次CREATE候选允许正式边界为空；保存不产生正式权限。

资源访问范围的授予、开放与撤回按STATE_MUTATION描述，相应动作标记state_changing；只有实际凭据的获取才用CREDENTIAL_ACCESS。文件交付和访问范围变化分别列为效果。“曾开放又撤回”在当前检查窗口、正确主体资源关联且独立记录完整时可核验，不能降为只检查最终状态，也不能据此承诺任意全历史约束。具体投影字段须从真实业务数据确认。

Agent新保存的候选根为格式4；经人工批量核对或补充依据关联后升级为格式5，后续修订保持格式5。格式5新增scope_references，不改变旧格式1～4的严格reader。候选包含要求来源、人的范围决定及覆盖关联，仍最多10处情境、每处2～4个业务选项。旧格式1/2/3按原reader读取。指纹由服务端根据原话、实体及有限权限替换生成；客户端只提交选项或纠正，不能提交“人已同意”的来源。原话摘录采用NFC与换行规范化后的文本及出现序号，不使用浏览器字符偏移。旧格式1继续严格读取，不补造选择。

不需要替换权限的问题使用“业务边界核对”：GUI 的 `boundary-decisions` 入口接受问题标识、指纹、当前 basis/revision、分类、判断依据及仍保留的实际要求。保存后升级候选根为格式3；后续 Agent 修订由服务端携带决定，输入不接受伪造的人工记录。原问题和限制文字保留，历史修订不改写，旧情境决定继续按原指纹读取。GUI写入沿用本机控制面授权，MCP只有读取和修订候选能力。

“不作为独立动作”仅适用于问题；“已由权限表达”还必须引用本候选现有权限项。这两项不能消除 unsupported_constraints。只有人确认限制确属 Agent 扩大或误解原要求，并写明依据和实际要求时，才结束该限制问题；不能将接受风险当作证明。真实业务规则、执行前提、证据或入口覆盖缺口以及暂不能确定均继续阻塞。409不是权限拒绝；当前窗口过程证据不是任意历史证明；合并动作不证明多个HTTP入口已经分别取证。

决定指纹绑定候选、问题原文、正式依据及候选原文/角色/动作/权限。仅补充例子或其他问题沿用决定；业务正文或正式依据修订后保守要求重新确认，旧依据和理由仍展示。当前不推断自然语言依赖来自动缩小失效范围。相同问题的重复项独立编号；不能删掉旧限制或把已核对问题转入另一入口隐藏。决定、候选新修订与 DECIDE 回执在同一事务保存，同键异文和旧修订拒绝；未知响应查原操作。

候选开始人工核对后，其中未决范围进入项目的 `boundary_review_gaps`；旧版已有情境决定同样纳入，未完成的情境不能被新入口遗漏。列表包含原问题及返回入口，查询包括归档候选，另建候选不清除旧缺口。检查预览和提交事务均重新核对该范围，真实缺口存在时不创建执行请求，不删除计划Case。本轮不支持部分检查，也不改变既有Run/冻结输入/安全结论格式；旧结果保留当时正式规则范围，不补写为已验证新增要求。真实技术与取证限制不能靠分类确认放行。对于已明确的当前窗口要求，可由人关联具体权限、TARGET入口及证明类型；关联后允许规则审阅，检查预览与提交事务仍逐项核验批准映射、当前Case、真实入口和证明来源。任意历史要求继续阻塞。

GUI的SELECT、CORRECT、DEFER分别保存选择、纠正、待定；明确说明不适用时用DISMISS保存原因。决定追加候选修订，仍由原提案批准才能更新正式权限。Agent不可静默删除未决情境；需要权限替换的旧文字问题先转成同名情境再核对，无需权限替换的问题直接进入业务边界核对。已解决情境移除后，新修订不继承该处人工同意；情境依据变化使原选择失效，冲突选择不能以最后点击覆盖。DECIDE使用独立回执命名空间，未知响应只查原键。

含义核对的未保存选择按候选、情境及指纹保留在当前编辑会话；切页或其他情境保存造成修订变化不清空输入，依据变化则重新选择。页面分别显示已保存数量和未保存修改，离开前保留编辑提醒，不在浏览器持久存储业务草稿。每处仍由人显式保存。批准后提供“继续当前工作”，由 Workspace 决定下一步，不把再次接入新应用作为续接入口。

权限缺少对应 examples 时返回 `PERMISSION_EXAMPLE_REQUIRED`、字段位置和具体权限项标识；合法对照也需要例子。该问题不等于业务含义未决定，不通过新增情境、删除权限或改写原始要求消除。复制补充请求保留这些具体标识。

旧问题修订先读context与不指定revision的show。每条旧unresolved_questions要么原样保留，要么在新情境question中逐字保留（含标点），先保存新修订再由人核对；不要求人在情境尚未保存时寻找确认入口。错误返回旧candidate/revision、全部未映射问题的有限索引、目标字段、精确匹配要求与审阅入口，不回显问题原文。context/show的revision_guidance说明同一流程。unsupported_constraints独立核对，情境选择不建立取证能力，也不消除真实的不支持条件；明确要求、Agent误加限制和证据缺口不能被编造成相反的业务选项。

情境摘录或出现序号不匹配、替换项越界、选项替换集合不一致及重复标识通过固定错误类型指出字段位置；MCP只读取受控整数索引，不输出原话、输入值或任意异常上下文。替换项必须复用候选正文的权限项标识，不因不同选项引用同一权限而判重复。

候选详情说明当前应交给Agent补充还是由人核对；“复制补充请求”携带旧问题原文、字段位置和服务端修订指引。初次深链读取指定修订，显式点击“读取候选”则读取最新头并更新页面引用，避免Agent保存新版本后仍停在旧记录。失败保留原修订与正式权限；人的选择仍须经过完整提案审阅与批准。

候选转提案时冻结内容hash和决定摘要。原批准事务取得写锁后重新核验候选头、basis及来源，再写正式权限和准确item→intent/revision/hash映射；沿用项也保留映射。规则详情与候选详情由此回查，不能用名称或时间推算来源。手工提案继续沿原批准，不伪造候选选择。

规则预览支持APPROVED、PROPOSAL、CANDIDATE三类精确来源；未决或过期候选没有覆盖答案。返回ALLOW、DENY、UNCOVERED、CONFLICT及命中引用，不产生Run或Verdict。GUI将其收在提案和规则详情的可选展开区；MCP只读工具为`jiejian_rule_preview`。

## 失败与验证

同键异文、旧basis、旧revision和边界并发变化均应拒绝，不覆盖新决定。响应未知按project/kind/operation_id查询；找不到回执不能证明未执行。重点核对保存后仍非正式、提案生成不等于批准、重复键幂等、影响预览没有写入。涉及格式再验证严格reader和Schema，涉及MCP再测授权；不为候选展示改动重跑检查执行。

完整事务关系见[批准协作](批准协作.md)。

## 范围先行与缺口处理

完整设计与兼容边界见[候选范围与缺口处理设计](候选范围与缺口处理设计.md)。Agent可批量同时保存权限与requirement_sources；信息不足时也可先保存范围，不强制两个往返。用户确认本轮范围后才可进入提案。merge=true支持同一候选分批合并；总预算100动作、200权限、1MiB，不能为数量合并检查入口。GUI通过scope-decisions确认来源含义与时间范围，通过coverage-links关联真实缺口。MCP仍无人的决定能力。

CHECK格式5冻结当轮范围，结果不继承后续修订；PLANNED仅表示规则可审阅，不表示检查就绪或通过。next_tasks和复制请求按实际处理者分流，已解决问题只作为约束沿用。

## 集中确认与补充依据

`scope-batch` 仅由本机 GUI 提交，逐项绑定要求指纹并统一校验 basis、候选修订与操作键；全部成功才追加一个修订和 DECIDE 回执，同键异文拒绝。来源的 USER 标记不代表人工同意：清单默认不选中，用户还须明确核对含义和时间范围。旧单项入口保留。

SUPPORTING 用于将重复说明或源码线索关联到已确认的 IN_SCOPE 要求。它保存原文、判断依据、关联标识及目标决定的语义指纹；不能指向未决、准备或排除项，不能绕过其自身关联权限的完整覆盖。目标的用途、含义、时间或原文变化使关联失效，单改说明理由不制造重复确认。Agent 输入不接受人工决定和关联；既有来源不能静默删除。真正独立的业务要求继续纳入或保留未决，不能以补充依据隐藏。

冻结检查范围只列独立要求，SUPPORTING 的完整记录仍通过精确候选及修订追溯。历史要求、技术能力和真实取证缺口继续阻塞。项目缺口按当前阶段报告：范围未解决时不叠加尚未发生的批准提醒；已有来源但范围未决时不同时重复报告缺少已确认来源。候选列表已展示的行承担处理入口，归档或分页之外的缺口仍保留摘要；检查页只展示紧凑阻塞提示，详情集中处理。
