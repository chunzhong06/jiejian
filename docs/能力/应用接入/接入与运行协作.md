# 应用接入与受控运行怎样协作

> 状态：CURRENT。沿一次接入/加载说明控制面、源码、运行实例和检查引用；不把代码识别或页面可达当成完整接入证明。

## 创建与调用

1. GUI经projects/application入口调用ApplicationUnderstandingService；服务通过受控目录发现建立或复用Project与理解记录。
2. 用户确认loopback地址并授权源码分析。分析器读取受控范围，产生角色/动作候选；审阅决定与理解revision保存，正式业务规则另外批准。
3. ApplicationCore创建两类RuntimeProvider：官方样例由OfficialSampleExperience管理；普通Node由NodeRuntimeSetup预览入口、端口、源码和依赖形式。
4. 用户明确启动普通Node，控制面保存冻结加载请求及Job。专用Runtime Worker取得租约和进程树所有权，校验固定源码后启动目标、发布启动回执。
5. 加载Job成功后Worker仍拥有目标。ProjectRuntimePorts向材料、开发交付、规则详情和CheckRuntimeBuilder提供当前实例引用；它们不能以原始端口替代实例身份。
6. 后续变化先登记真实源码。加载当前最新交付继续使用稳定operation_id，核对快照一致，再建立新运行引用。CHECK前后核验运行对应，历史Verdict不改写。

## 读写与边界

| 责任 | 读取 | 写入/交付 | 所有者 |
| --- | --- | --- | --- |
| 应用理解 | 授权源码、当前revision、用户决策 | 理解与候选、源码fingerprint | application_understanding |
| 运行准备 | 明确入口/端口、快照和依赖身份 | manifest、冻结加载请求、Job | runtime/setup、load_jobs |
| 启动执行 | 冻结请求、Node身份、进程树所有权 | 真实实例与load receipt | runtime专用Worker/process |
| 加载回执 | 原operation、交付和Job关联 | 已确认终态回执或UNKNOWN投影 | NodeRuntimeActivation |
| 检查对应 | 冻结实例、manifest、活进程与文件 | 输入引用及检查前后适用性 | runtime builder/Runner |

## 失败与收尾

- 目录或候选分析失败不形成正式权限；地址发现并发revision变化时拒绝旧确认覆盖。
- preview后源码改变、入口/依赖形式不受支持时不启动；副本生成成功不代表进程已就绪。
- 启动响应未知先查原Job/回执。控制会话已变且尚未确认终态时保留UNKNOWN，不能换键重启探测。
- 停止或关闭由真实所有者回收整棵受控树；遗留PID/端口不能单独证明所有权。
- 未托管外部应用保持受限支持；受控Node机制不是对抗恶意宿主/应用的完整安全沙箱。
