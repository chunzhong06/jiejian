# 代码组织

## 组织原则

路径应直接回答“这段代码负责什么”。当前 Python 包按 `application`、`projects`、`contracts`、`recording`、`verification`、`execution`、`storage`、`protocols`、`api`、`cli`、`runtime`、`results`、`worker` 和 `runner` 划分；能力叶模块是真实代码真源，package-root 不复制内部实现。

## 新文件判断

新增文件前依次判断：

1. 是否有当前生产调用、框架发现、安全边界或独立清理职责？没有则延后。
2. 是否属于现有模块的同一业务职责？若是，优先在原模块内聚实现。
3. 是否有不同调用者、独立失败方式或明确演进方向？若有，可以拆出完整子模块。
4. 是否只是转发、兼容旧路径或包装单一实现？若是，不创建。
5. 是否会造成反向依赖或循环？先调整边界，不用全局 `helpers.py` 掩盖。

## 源码文件头

- 具有独立业务、安全、协议、事务或编排职责的 Python 文件使用“模块名称、定位、职责、调用链”四项 `#` 信息卡。
- 已有信息卡时不再保留重复的模块级三引号说明；没有信息卡的简单模块使用一行 `#` 说明，不用模块 docstring 模拟文件标题。
- 函数和类 docstring 只在需要表达调用动作、非直观数据、返回契约或关键不变量时保留；显然实现不为视觉统一添加模板段落。
- TypeScript/TSX 的实际页面、状态管理和 API 边界使用内容相同的块注释信息卡；明显 JSX 与简单展示函数不逐行解释。
- PowerShell 在 `#Requires` 后使用 `#` 信息卡，CMD 保持 `@echo off` 为首条可执行语句并使用 `REM` 信息卡；长启动流程只用少量业务阶段标题。
- 纯包标记、migration、生成文件和固定机器资源按发现机制处理，不机械添加大型信息卡。

## 依赖 DAG

- `domain` 是纯底层，不依赖执行、存储或 UI。
- `protocols` 依赖纯领域模型和稳定错误。
- `verification` 依赖 domain，但不依赖 storage、worker 或 CLI。
- `storage` 不反向调用 worker 或 Verification。
- `recording` 可依赖 Execution 端口；`execution` 不反向依赖 recording。
- `worker` 只保留稳定 runtime 壳；通用 Job/Attempt、监督、发布与恢复由 `execution` 拥有，不导入目标 HTTP 能力。
- `runner` 是唯一把 RunnerInputV1 连接到 Verification 的进程边界。
- `cli/app.py` 是 CLI 组合入口，不保存领域规则或 ORM Session；正式安装入口仍为 `jiejian.cli:main`。

## 文档与辅助目录

- `docs` 按读者任务分为项目介绍、架构、开发规范、技术决策、协议、开发记录和竞赛资料。
- `tests` 按业务职责镜像生产边界。
- `samples/fixed_apps`、`samples/vulnerable_apps` 和 `samples/inconclusive_apps` 各自保存完整黄金 bundle，避免越出项目目录引用 Flow/Contract；Recording 与 Contract/Drift 演示复用 fixed bundle。
- `schemas/{runner,recording}` 只保存跨进程机器 Schema；`backend/src/jiejian/protocols` 保留可执行 Pydantic 协议模型，两者职责不同。Contract/API 内部模型、测试 fixture、样例 YAML 和数据库映射不得复制到 `schemas/`。

系统级职责见[模块地图](../模块地图.md)和[系统架构](../01_架构设计/系统架构.md)；测试、样例和 Schema 细节分别见各自资产 README。组织决策见[ADR 索引](../03_技术决策/README.md)中的 ADR-0004、ADR-0008、ADR-0017 和 ADR-0018。
