# 代码组织

## 组织原则

路径应直接回答“这段代码负责什么”。当前 Python 包按 `domain`、`runtime`、`verification`、`protocols`、`storage`、`worker`、`runner` 分层；根包只保留 CLI、稳定错误、脱敏和样例入口。

## 新文件判断

新增文件前依次判断：

1. 是否有当前生产调用、框架发现、安全边界或独立清理职责？没有则延后。
2. 是否属于现有模块的同一业务职责？若是，优先在原模块内聚实现。
3. 是否有不同调用者、独立失败方式或明确演进方向？若有，可以拆出完整子模块。
4. 是否只是转发、兼容旧路径或包装单一实现？若是，不创建。
5. 是否会造成反向依赖或循环？先调整边界，不用全局 `helpers.py` 掩盖。

## 依赖 DAG

- `domain` 是纯底层，不依赖执行、存储或 UI。
- `protocols` 依赖纯领域模型和稳定错误。
- `verification` 依赖 domain，但不依赖 storage、worker 或 CLI。
- `storage` 不反向调用 worker 或 Verification。
- `worker` 依赖 storage/protocols，但不导入目标 HTTP 能力。
- `runner` 是唯一把 RunnerInputV1 连接到 Verification 的进程边界。
- `cli.py` 组合入口，不保存领域规则或 ORM Session。

## 文档与辅助目录

- `docs` 按读者任务分为项目介绍、架构、开发规范、技术决策、协议、开发记录和竞赛资料。
- `tests` 按业务职责镜像生产边界。
- `samples/fixed_apps` 与 `samples/vulnerable_apps` 各自保存完整 bundle，避免越出项目目录引用 Flow/Contract。
- `schemas/runner` 只保存 Runner 机器 Schema；`backend/src/jiejian/protocols` 保留可执行 Pydantic 协议模型，两者职责不同。
