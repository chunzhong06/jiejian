# 检查与复验

检查用冻结输入比较正式要求与实际行为。开始前需要已审阅规则、当前材料以及可核对的运行代码；复验还需要准确原问题。

## 提交检查

1. 从权限或准备入口打开检查预览。
2. 核对动作、规则修订、账号、资源、证明范围和代码。
3. 有缺口时回到所属项补齐，再生成预览。
4. 确认后提交，保留本次检查记录，等待执行与发布完成。

预览保留未准备动作，不悄悄缩小范围。提交使用当前计划指纹和幂等键；输入变化后旧预览失效。断连后查原运行，不能换键重复提交来判断第一次是否成功。

## 选择检查范围

默认检查全部已批准规则，未准备内容仍列为缺口。需要核对部分改动时，切换到“选定规则”，勾选具体规则。系统在“必要正常对照”中单独保留应当成功的操作，不把它与可自由取消的选择混排。相邻预览说明实际执行场景、材料缺口及未检查数量；窄窗口依次呈现选择与预览。

选择、规则修订和必要对照进入本次冻结请求。补账号、操作或来源后，返回原预览继续；规则修订变化时重新选择，不能沿用旧摘要。原题复验按原问题、修改目标和正常对照执行，不提供缩小原题范围的选择。

局部报告保留“选定规则检查”和未检查数量。通过只适用于这次范围；未决要求和未检查规则继续保留，不由局部结果推断整份权限都符合要求。

展开“保存与沿用检查范围”，使用“记住当前选择”，下次可直接沿用，无须重新逐项勾选。保存全部规则时，下次核对当时的全部已批准规则；保存局部选择时，原规则修订必须仍有效。规则变化会提示重新选择，当前检查范围不会被悄悄替换。

保存范围不执行检查，不复制账号或证明，也不沿用历史就绪结论。有效材料由准备服务复用，提交前仍生成当前预览。保存结果未知时，“核对上次保存”查询同一请求的结果，刷新页面后也不重新生成另一份方案；移除保存项只影响快捷选择，保留当前选择与历史报告。

## 查看进度与取消

排队和运行描述生命周期。取消只是请求，需等待任务实际停止及清理；超时、程序错误和权限违规分别表达。最终结果完整性无效或发布未完成时，不能把磁盘上的任意文件当作正式报告。

## 阅读报告

先读结果概览。普通检查按结果分组；修复复验分别列出原权限问题与正常功能，以共同列比较修改前、本次复验。选择“查看依据”后，列表收为紧凑导航，相邻阅读区展示所选项的实际业务结果、账号、资源与判断记录。修改前的结果和原检查入口只在该项依据中按需展开，不在每个列表项重复一套操作。

需要进一步查证时切换操作经过或证明记录，最后核对本次适用范围。对应场景缺失、关系不明确或验收状态未成立时，保留具体缺口，不能由单项通过或模型说明推断修复已完成。

## 如何理解结论

一条权限要求说明谁能否对什么资源执行什么动作。一次检查把这条要求与真实身份、资源、操作和证明对应起来；只有事实足够时才给出安全判断。

例如，负责人可以取得自己的内部完整包，评审不能取得负责人的内部包，但可以查看公开预览。这不是一条“下载需要登录”就能表达的要求：要分别核对实际主体、资源所有者和受保护结果。

### 要求与实际主体

角色是业务身份定义，账号是实际登录主体。资源名称不能代替所有者关系，接口地址不能代替业务动作，响应成功不能代替业务效果。规则和材料都携带准确标识与修订，避免把相似名称当成同一对象。

### 三种结论

| 结论 | 成立条件 | 不能推导的内容 |
| --- | --- | --- |
| 符合规则 `PASS` | 本次范围内的可信事实支持要求 | 整个应用均安全 |
| 不符合规则 `BLOCK` | 已有可信事实与要求冲突 | 每个执行错误都是违规 |
| 证据不足 `INCONCLUSIVE` | 身份、关联、对照或证明等关键条件不完整 | 暂时没有问题或已经通过 |

禁止项需要证明相关业务效果没有发生。读取不到一条记录并不天然支持这个结论，还要确认观察完整、可靠、关联本次运行并已闭合。已成立的违规事实也不会因另一份材料缺失而消失。

### 怎样读证据

业务结果回答是否真的取得内容或改变业务状态；操作经过回答走到了哪一步；证明记录给出判断所用事实。执行路径经过了权限判断，不等于判断正确；接口返回成功，也不等于内部包已完整交付。

允许项要有对应的正向效果，禁止项要有可靠观察及正常对照。只有错误提示、空响应或缺少记录时，先核对身份、关联和观察范围，再决定能否形成结论。报告中的技术详情用于查证，不能取代业务含义。

### 三类状态

准备状态描述能否形成执行输入；生命周期描述任务运行到了哪里；安全结论描述事实是否符合要求。三者分别表达。准备齐全不是检查通过，取消不是不符合规则，程序异常也不是漏洞结论。

### 历史范围

报告保存当时的冻结输入与发布结果。规则、代码、账号、资源或读取范围改变后，旧报告仍只证明原来的范围。重新核对或复验应产生新的事实，不改写历史。

LLM 可以提出候选和解释已有记录。正式权限由人工审阅批准，安全结论由确定性验证形成。

## 复验一次修复

以下流程从已经发现的权限问题出发，核对一次修改能否解决原问题，同时保留正常访问。它适用于已有违规报告和可运行修改的项目。

### 复验前

先完成[首次检查](开始使用.md)，理解规则与实际结果的区别。准备一份不符合规则的报告、对应源码，以及修改后可核对的运行实例。官方示例可使用其漏洞与修复流程；自己的应用需要在授权范围内修改与加载代码。

### 1. 保留准确原题

1. 在报告中选择不符合规则的项目，阅读与要求冲突的业务结果。
2. 打开“处理权限问题”，进入这条问题的修复任务，原规则与检查依据会随任务保留。
3. 同时核对需要保留的正常功能，避免通过一律拒绝访问掩盖问题。

例如，评审不得取得内部完整包，但负责人仍应能取得自己的内部包。两项都属于复验需要关心的行为。

### 2. 登记并加载修改

1. 在开发工具中完成修改后，回到修复任务选择“登记已完成的修改”。
2. 注明影响的准确规则和原问题，核对修改范围。
3. 将对应实现加载到受控运行环境，检查运行回执与当前源码一致。

登记只保存修改声明和关联；加载只确认运行代码。二者都不能提前证明修复有效。写入回执不明确时先查询原操作。

### 3. 补齐受影响材料并复验

1. 在同一修复任务中查看受影响条件，只补齐变化的登录、操作、资源或证明；已有设置会保留。
2. 打开复验预览，确认仍引用原问题，正常对照在范围内。
3. 提交并等待新的检查完成，读取复验摘要和必要证据。报告和材料页保留“返回修复任务”，不必经代码变更档案寻找下一步。

完成时应能分别回答“原问题是否解决”和“正常功能是否保留”。没有精确原题、代码不对应或对照不完整时，保留明确缺口，不用一条“已修复”关闭问题。

原报告保持原样，新报告保存新的输入与事实。关系说明见[规则、问题与修改](维护权限规则.md#规则问题与修改)。

状态名与未知写入的恢复见[状态与回执](../参考/状态与回执.md)。实现与证据链见[结果读取与诊断](../工程/能力/结果读取与诊断.md)和[修改与原题复验](../工程/能力/修改与原题复验.md)。

## 多目标修复与开发协作

一批修改可以关联多个原问题。复验报告逐个给出原问题是否解决，并集中呈现正常功能与相关回归；只通过其中一项时，不将整批修改表述为修复成功。证明要求变化、场景未能唯一对应或证据缺失时，保留无法验收的原因。

从问题详情使用“交给 Agent 修复”，或从报告使用“交给 Agent 解读”。复制请求固定应用、报告和必要原题引用；Agent 通过现有连接读取结果、证据、问题历史和修改回执。复制不会发送消息，也不会自动运行检查或修改权限。正常功能与原问题一同保留在协作要求中。

本版在界鉴内阅读报告，通过现有连接向 Agent 提供事实，不提供离线 HTML、PDF 或独立证据包。
