# 准备检查材料

准备页按业务动作汇集执行与判断需要的材料。开始前需要已批准规则和可核对的运行实例；否则即使有录制或账号，也可能不属于当前检查。

检查的依据仍是已批准的权限规则。以“负责人能改自己的工单，成员不能改负责人的工单”为例：先准备可重复执行的修改操作、真实账号和测试工单，再由界鉴按规则组织不同操作人的场景，读取业务记录判断工单是否实际改变。操作设置向导负责准备步骤，接口文档只提供候选，不决定谁有权限。修改后的复验沿用原问题，并确认正常操作仍能完成。

## 从缺口开始

场景保存后，可在核对页选择“预览试运行”，调整本次账号和已有资源编号，核对目标、步骤、请求预算及恢复请求，再确认执行一次。HTTP接受不等于有权，拒绝也不能说明业务效果没有发生。准备好场景后，另行确认用于检查，再执行正式权限验证。

记录保留当时修订，可以查看冻结步骤或继续编辑新修订。提交回执不明时查询原操作；变更数据后恢复请求未明确时，先处理原记录的恢复请求，不重发原受检步骤。恢复反馈只说明请求结果，正式检查仍核对业务状态。创建后才取得编号的资源目前经正式检查及其恢复核验执行，试运行不会猜测恢复位置。

1. 打开“测试”，选择“准备缺口”及对应业务动作。
2. 在材料索引选择账号、录制、资源、证明或恢复。
3. 查看当前状态及用途，从该项的操作入口处理。
4. 更换已采用材料时先核对影响范围，再确认采用。

| 显示状态 | 含义 | 处理 |
| --- | --- | --- |
| 已就绪 | 当前绑定满足准备条件 | 保留，提交前仍会重核 |
| 待准备 | 缺少具名材料 | 补齐该项 |
| 需要重新核对 | 角色、来源或绑定已经变化 | 核对当前事实后采用 |
| 无法继续 | 有明确前置条件阻塞 | 先处理原因 |
| 不需要 | 业务契约不要求 | 无需人为制造材料 |

## 账号与资源

已有内容先核对，再决定是否修改。角色职责、操作说明和结果说明是选填补充；业务角色、操作资源、实际结果和访问要求仍需明确。系统不会根据选填说明自动批准权限。

同一应用的其他账号可沿用登录位置、身份查询地址和字段对应，不再逐个配置。当前账号已有配置时保持原值；新账号只带入技术设置，账号编号单独填写，跨角色时也要明确角色值。密码和会话不随模板复制。保存相同配置会保留已有核验；配置确有变化时重新核验。

打开已保存的操作流程，先查看账号、数据、执行步骤和恢复方式的摘要，确认后即可继续使用。需要变化时选择“调整账号或步骤”。相同流程再次采用不创建额外绑定；账号未登录、源码或目标发生变化时，页面仍会指出必须处理的条件。

结果判断依据复用已经选定的业务操作、结果、测试数据和数据库对应。只有存在多个候选时才要求选择；没有唯一依据时不会擅自取第一项。相同来源配置再次保存不增加修订。新的运行实例或会话仍需要新的来源核对，配置保留不代表旧证据继续有效。

账号代表真实登录主体，并关联角色修订。同一主体用于多个动作时可以复用，不按动作重复建立账号；不同主体或权限不能混为一个。页面展示状态、归属与用途，秘密只经受控存储引用使用。

打开独立登录浏览器，完成应用自身的登录后，返回界鉴选择“我已完成登录”。界鉴只保存这次目标所需的有限会话；关闭窗口不会被当作登录成功。离开页面后可从“进行中的任务”返回原登录，换浏览器会话也能找到服务端已接收的任务。

在左侧选择要准备的账号，右侧只处理这个账号。选择“开始登录”，在独立窗口完成应用自身的登录，再回到原位置保存。保存后可继续下一个账号，全部完成后返回材料清单。

“登录设置与管理”用于修改登录方式、检查已保存登录是否有效或重新登录。登录设置支持应用页面、访问令牌和账号密码接口；开发者提供查询当前账号的接口、编号和角色字段，界鉴据此确认实际登录的是谁。密码和令牌只在独立窗口输入。保存成功和身份匹配是不同事实；失效、账号不符、角色不符或查询失败分别显示，不以其他账号顶替原账号。

登录未完成时先取消并等待清理，再重新登录或删除账号。若保存与取消同时发生，以服务端最终回执为准；已保存的结果不会变成取消成功。临时资源清理失败时保留账号，在原任务重试清理，不另开多组窗口。

录制采集真实操作。采用前核对目标步骤、身份、资源位置及运行版本。资源要有确定所有者与类型，路径、查询和正文中的同一资源应保持一致。秘密参数使用受控变量，不写入普通录制内容。

## 设置操作步骤

通常先在应用里录制一次真实操作。需要串联多个请求或已有接口文档时，在操作材料中选择“接口方式设置”。此路径面向了解应用接口的开发者，不要求普通用户从空白请求表开始。

1. 选择已有流程、已确认的录制、OpenAPI 3.0/3.1 JSON 文档，或手动填写接口。导入只读取文档，不执行请求，也不使用文档中的服务器地址。
2. 确认准备操作的账号、数据所有者和用于测试的数据编号。
3. 按顺序设置步骤，标记真正要检查的那一步。参数可直接填写，也可来自前一步的返回字段。数据会改变时，填写检查后的恢复接口。
4. 核对操作摘要，先保存，再确认用于检查。保存草稿不替换当前操作；再次编辑后需要重新保存。旧版本和报告保留。

路径中的 `{case_resource_id}` 代表每次检查的数据编号。新建数据的操作可指定返回结果中新编号的位置。当前编辑器支持 JSON 对象正文，其他录制格式继续通过原录制使用；不能在编辑中静默转换格式。

## 证明与恢复

准备业务结果证明时，先选择要判断的结果，再选择用于判断的记录。随后依次确认允许读取的范围、检查能否正确读取、确认用于正式检查。文件须对应当前应用，Observer 须关联本次身份、资源与效果。未读取到记录不天然证明没有发生，还需可靠、完整且闭合的观察。

普通 SQLite 应用可直接“选择判断方式”：选择业务结果、测试资源、已声明的数据表和业务字段。已有判断方式可在“查看与调整设置”中调整。随后确认实际读取字段，检查账号和数据归属，再确认使用。此路径不要求 Agent 代填，不要求业务代码写专用事件。

改变数据的动作需要恢复方式；不需要恢复必须来自业务契约。恢复失败和原权限结论分别记录，不抹掉已成立的违规事实。

## 批量准备与完成标准

官方示例可使用批量准备。先查看计划，确认后等待原批次回执；失败时处理具体子操作，不重放结果未知的目标写入。完成后核对各动作的缺口已处理，再打开检查预览。

准备完成说明可以形成执行输入，不说明权限安全。运行环境、规则、角色或材料变化后，相关状态可能需要重新核对。

发生变化时，准备页列出受影响的材料、原因和使用它们的规则，仍适用的材料可以保留。同一实际账号重新登录不自动作废所有录制；换了实际主体、角色、资源归属或业务语义时，必须核对对应材料。沿用的是配置与模板，新检查仍重新执行完整范围并形成新证据。
## 为不同适用条件选择数据

同一业务操作通常复用一份流程和判断方式。仅当规则需要不同状态的数据时，才为具体规则另外选择测试数据。例如正常操作使用待处理工单，归档限制使用归档工单；无需为此重复登录、录制或编写整份流程。

“测试资源”中列出这类规则、当前数据编号和修改入口。选择绑定当前规则修订、资源所有者及基础材料；规则或基础数据变化后，系统要求重新对应，不会悄悄使用旧选择。

使用租户或资源状态条件时，结果判断方式还需要指定实际租户、状态字段，以及账号信息中的租户位置。已有数据库、表和字段配置继续复用。读取授权会列出正常数据及额外数据和所读字段，增加范围后须重新确认。

准备完成只说明可以执行核对。检查会在目标操作前重新读取实际身份和数据条件；选错状态、主体不符或字段缺失时，不执行该项目标操作，也不把这项算作通过。

## 从接口来源整理场景

“测试”按业务动作保存可维护流程。可以从已关联请求进入，也可以沿用已有流程、录制或手工请求。明确本人及资源所有者、资源位置、唯一受检步骤和必要恢复，再保存流程修订并确认使用。已保存草稿与已用于检查分别显示；源码、环境、业务动作或来源请求变化时需重新核对。

字段披露结果可以声明所有者独立 GET 查询、资源编号、所有者编号和业务数据位置。受保护字段来自已确认的业务结果定义。检查在 Runner 中比较真实实体，原始业务值不进入报告；失败或无法对应保留证据缺口。该方式不提供数据库提交历史。

登录配置区分人员与服务身份。除浏览器、Bearer 和账号密码接口外，支持同一目标内明确令牌端点的 OAuth2 client_credentials 与 refresh_token 更新；复杂交互授权由本人浏览器参与。密钥与刷新令牌在独立窗口输入，访问令牌沿原安全存储保存。执行前重新核验实际主体，失败后准备或更新会话再核验，不自动重放结果未知的受检写入。

动态防伪参数可由显式前置请求提取并注入后续请求；提取项与使用项必须声明为秘密、对应同一实际身份。它不执行导入集合中的脚本。
