# 维护权限规则

规则要能回答谁能否对什么资源执行什么动作。开始前应能解释业务角色、资源所有者以及动作完成后会产生什么结果。

## 整理业务要求

1. 在应用分析或业务整理入口核对角色和动作，合并确实属于同一业务含义的候选。
2. 明确资源范围，区分自己的资源、指定角色的资源以及公开内容。
3. 为动作定义可观察的业务结果，再把技术入口绑定到该动作。
4. 将已确认内容组成权限提案。

“评审不得取得项目负责人的内部完整包”包含可检查的对象关系；“下载接口需要鉴权”仍缺少主体与资源范围。技术路径用于绑定实现，不代替业务名称。

首次编写时，在“业务角色”“操作与结果”“访问规则”之间切换填写。切换分区保留草稿，旁边的权限预览随输入更新；待补充项可直接返回对应分区。预览只反映草稿，生成完整提案后仍需审阅和批准。

## 审阅权限变更

1. 查看提案中的新增、调整和沿用内容。
2. 核对每条要求的允许或禁止、资源归属及受保护结果。
3. 确认后批准；不采用时放弃提案。

批准成功产生正式版本。请求携带提案指纹，读取后发生变化时必须重新审阅。界面显示批准结果未知时查询这次批准，不另提交一份提案试探。放弃不激活其中要求。

## 查询与修改

权限表一行对应一条要求：先看谁可以或不得做什么及资源范围，再横向核对适用条件、检查情况和最近检查。同一角色在不同租户或数据状态下的要求分别成行，可按角色、操作、资源或条件查找，再进入该行查看准备、历史和待处理问题。允许或禁止是要求，符合或不符合是验证结果；二者不互相替代。

业务要求改变时走新的审阅。实现违反现有要求时保留原规则，关联原问题登记修改并复验。相似文案的新规则不能代替原问题关闭。批准后的下一步是[准备材料](准备检查材料.md)。

业务要求没有改变、只缺少实现定位时，进入“编辑权限要求”，展开“角色与操作对应”，为原角色或操作选择已有线索；需要复核的已有对应可以原样重新确认。没有可选线索时，先在“业务角色与操作”补充并确认，再返回编辑。填写理由后生成提案，核对角色、操作和权限沿用原版本，再批准对应变更。修改线索的显示名称本身不会更新正式对象的对应关系。

## 规则问题与修改

修复以权限规则为中心：先明确哪条业务要求被违反，再说明修改影响了什么，最后证明该问题解决且正常功能保留。

### 关系

```mermaid
flowchart LR
  A[正式规则及修订] --> B[冻结计划]
  B --> C[实际检查]
  C --> D[具体问题与证据]
  D --> E[关联规则的源码修改]
  E --> F[加载对应代码]
  F --> G[重核材料并复验]
  G --> H[原问题与正常功能的结果]
```

修改可以影响多条规则，同一规则也可以经历多次修改。真实 diff、运行代码和检查对象分别留有对应关系，不能用一个笼统的“已修复”代替。

权限规则表达持续存在的业务要求，检查记录表达一次范围内的事实，问题表达已经发现的冲突，源码修改表达为处理这些要求而发生的实现变化。它们不能合成一条覆盖历史的状态。

### 原题为何要准确

同样的业务名称可能指向不同版本。复验必须保留规则标识、修订、原检查、原用例及问题指纹，才能比较同一个问题。正常访问的对照用于防止通过一律拒绝请求掩盖漏洞。

例如，评审曾取得不应访问的内部包。修改后应证明评审无法再取得该包，同时负责人仍能取得自己的包、公开内容仍可访问。只证明第一项会遗漏误封正常业务的可能；只证明代码差异则两项都尚未回答。

### 判断的边界

源码登记只说明声明了哪些变化，加载回执只说明哪份代码在运行。新的执行事实才能回答实际行为。证据缺口、材料失效或代码不对应时保留待处理状态，不提前关闭问题。

界面把修复入口放在问题所属规则附近；独立修改记录供查阅整体交付。报告首先展示业务判断，技术追踪信息按需展开。

从报告到复验的实际步骤见[复验一次修复](检查与复验.md#复验一次修复)。

精确批准、范围与回执契约见[权限规则](../工程/能力/权限规则.md)。

## 跟踪问题的处理历史

规则详情保留首次发现、每次复验和问题再次出现的记录。只有准确关联原题、正常功能与证明要求的复验才能标记修复已验证；普通检查通过不会替代它。

同一未解决问题可能在多次检查中重复发现。修改明确关联其中一次原题，且判断标准与正常对照一致时，成功复验可以接回同一问题历史；首次发现仍保留。标准不同或没有明确关联的通过结果不能关闭原问题。

原问题已验证解决后，同一业务身份与可比证明条件下再次确认违规，会开始新一轮修复，并以这次违规作为新的原题。之前的原问题和成功记录仍可查阅。证明条件不同时显示新条件下发现违规，不声称是同一问题复发。运行中或中断的复验只描述任务状态，不生成安全结论。

登记本地修改时可选择多个权限或问题。规则详情和修改记录共用登记方式；选择范围用于表达修改目的，不会缩小完整检查要求。文件预览来自实际源码，丢失响应时查询原回执，也可明确使用相同请求重试。

问题处理使用独立、连续的修复工作面：从报告或规则中的问题进入，依次登记并载入修改、补齐受影响材料、核对原题复验范围和查看结果。当前阶段提供一个主要下一步，原问题证据和文件归档作为辅助入口。规则详情用于理解规则和查看历史，代码变更档案用于查阅交付，两者不再作为修复过程中的必经跳转。

## 规则的适用条件

默认规则使用已登录账号。需要区分未登录访问、同租户或跨租户、待处理或归档等状态时，在该规则中设置适用条件；没有这类要求时不必填写。

租户描述操作账号与资源所属租户的关系，不增加一个虚构业务角色。匿名访问不要求建立账号或登录，但仍须明确资源所有者。资源状态填写应用实际使用的有限值，例如 `open`、`archived`；它不等于界鉴的材料准备状态。

权限表、提案审阅、检查预览和报告使用同一份条件。条件互斥的允许和禁止规则可以同时存在，例如允许修改自己的待处理工单、禁止修改自己的归档工单；条件范围重叠时仍须处理相互冲突的要求。

条件变化属于业务要求变化，需要重新审阅批准。历史报告保留当时的条件；修改实现但不改变要求时，沿用原规则修订进行复验。
