# ADR-0005：阶段 2.2 持久化 Job 与 Worker 控制面

- 取代者：ADR-0031
- 当前阅读提示：本文保留历史决策；当前边界以 ../README.md 和相关 CURRENT 文档为准。

- 状态：已取代
- 日期：2026-08-09
- 适用范围：阶段 2.2
- 依赖：ADR-0002、ADR-0003；当前代码组织和安全边界见项目设计规范与 ADR-0017

## 背景

阶段 2.1 已建立 `projects`、`runs`、`jobs`、`job_events`、`evidence_index` 五表映射和 UnitOfWork，但没有定义 Job 的生产行为。ADR-0002 冻结了幂等、租约、fencing、取消和恢复原则，仍需把公开操作、事务边界、事件、错误与恢复证明收敛为可测试的控制面。

阶段 2.2 只管理持久化状态，不执行 Runner，不发送目标流量，也不消费成功结果或发布工件。

## 决策

### 1. 模块和依赖

- `worker/models.py` 保存严格冻结的控制 DTO、事件枚举、失败码、恢复证明和重试策略。
- `worker/queue.py` 为未来 API/CLI 提供幂等提交和请求取消。
- `worker/attempts.py` 为 Worker 执行循环提供 claim、续租和当前尝试完成操作。
- `worker/recovery.py` 为监督/恢复层提供过期租约扫描与恢复确认。
- `worker/events.py` 是三个服务共享的连续 Job Event 追加边界。
- `storage/job_control.py` 保存 SQLAlchemy 原子条件更新；ORM 行和 Session 不得越过 storage。
- worker 可以依赖 domain、errors、storage；不得依赖 CLI、verification 或目标 I/O 库。
- storage 不得反向依赖 worker、verification 或 CLI。

公开 DTO 的 `schema_version` 固定为字符串 `"1"`，Pydantic 使用 `extra=forbid`、`frozen=True`、严格类型和隐藏输入错误。所有绝对时间由调用方以 UTC Unix 微秒整数传入。

### 2. 公开操作

公开面按调用者拆为三个服务，不提供总 facade、兼容 wrapper 或 mixin：

| 调用者 | 服务 | 操作 | 输入与结果 |
| --- | --- | --- | --- |
| 未来 API/CLI | `JobQueue` | `submit` | `SubmitJob` → 明确 created/复用的 `JobSubmissionResult` |
| 未来 API/CLI | `JobQueue` | `request_cancellation` | `RequestCancellation` → 首次时间和完成标记 |
| Worker 执行循环 | `JobAttempts` | `claim` | `ClaimJob` → `ClaimedJob`；无指定候选时可为空 |
| Worker 执行循环 | `JobAttempts` | `renew_lease` | `RenewLease` → 更新后的 Job/Run |
| Worker 执行循环 | `JobAttempts` | `complete_cancellation` | `CompleteCancellation` → 清理后的双 CANCELLED |
| Worker 执行循环 | `JobAttempts` | `record_retryable_failure` | `RetryableFailure` → RETRY_WAIT 或双 FAILED |
| Worker 执行循环 | `JobAttempts` | `record_fatal_failure` | `FatalFailure` → 双 FAILED |
| 监督/恢复层 | `JobRecoveryService` | `list_recovery_candidates` | `RecoveryScan` → 只读过期 RUNNING 列表 |
| 监督/恢复层 | `JobRecoveryService` | `confirm_recovery` | `ConfirmRecovery` → RETRY_WAIT 或双 FAILED |

本阶段故意不提供 Job=SUCCEEDED 或 Run=COMPLETED 操作。成功结果必须在阶段 2.4 按“校验 staging、原子 promote、最后提交完成态”的顺序消费。

### 3. 幂等提交

幂等作用域是 `(project_id, operation_type, idempotency_key)`：

- 首次提交在一个 UnitOfWork 中创建 Run=QUEUED、Job=PENDING 和 sequence=1 的 `JOB_SUBMITTED`。
- 相同作用域与相同 `request_hash` 返回原 Job/Run，`created=false`，不追加事件。
- 相同作用域与不同哈希固定返回 `JOB_IDEMPOTENCY_CONFLICT`。
- 并发唯一约束竞争后，服务必须在新 UnitOfWork 中重新读取该作用域；只有读到相同哈希才复用，否则返回稳定冲突或持久化错误。
- Run/Job 公共 ID 可由调用方提供，缺省由应用服务生成 `run_<32 lowercase hex>`、`job_<32 lowercase hex>`；storage 不生成 ID。

### 4. Claim、attempt 与 fencing

可 claim 的 Job 必须同时满足：

- state 是 PENDING 或 RETRY_WAIT；
- `available_at_us <= now_us`；
- `cancel_requested_at_us` 为空；
- `attempt < max_attempts`；
- 没有 lease owner/expiry；
- 关联 Run 非终态且 verdict 为空。

指定下一候选时按 `(available_at_us, created_at_us, job_id)` 升序。claim 使用单条条件更新，不能先读后无条件写。成功时原子执行：

- Job 转 RUNNING；
- `attempt += 1`；
- `fencing_token += 1`，新 token 单调递增且不复用；
- 设置 owner、expiry、更新时间；
- 首次 claim 将 Run 从 QUEUED 推进到 PREFLIGHT；重试 claim 保持 Run 的现有非终态；
- 追加 `JOB_CLAIMED`。

RUNNING 即使租约已过期也不具备 claim 资格。租约过期只允许进入恢复审计。

### 5. 续租

续租必须同时匹配 `job_id`、`lease_owner`、`fencing_token`，且 Job=RUNNING、旧租约在 `now_us` 时仍有效。新截止时间必须晚于 `now_us`、晚于旧截止时间，且一次租期不超过 300 秒。

续租不改变 attempt 或 fencing token；更新与 `JOB_LEASE_RENEWED` 在同一 UnitOfWork。旧 owner/token、终态和过期租约固定拒绝，事件和数据库不得产生副作用。

### 6. 取消

`cancel_requested_at_us` 只在首次请求时写入，之后不可清空或改写：

| 当前 Job | 请求取消行为 |
| --- | --- |
| PENDING / RETRY_WAIT | 追加首次 `JOB_CANCEL_REQUESTED`，同一事务将 Job/Run 转 CANCELLED，再追加 `JOB_CANCELLED` |
| RUNNING | 只写首次取消时间并追加 `JOB_CANCEL_REQUESTED`，不提前写终态 |
| CANCELLED | 幂等返回原首次时间，不新增事件 |
| SUCCEEDED / FAILED | 返回 `JOB_TERMINAL_CONFLICT` |

RUNNING 的取消完成必须由当前有效 owner/token 调用 `complete_cancellation`，表示必要清理已经完成；随后同一事务写 Job/Run=CANCELLED、verdict 为空并追加 `JOB_CANCELLED`。过期租约不能完成取消，必须先恢复审计。

### 7. 重试和失败

可重试失败只能使用 `RetryableFailureCode`：`EXEC_REQUEST`、`EXEC_TIMEOUT`、`RUNNER_START_FAILED`、`WORKER_INTERRUPTED`。致命失败只能使用 `FatalFailureCode`：`PROTOCOL_INVALID`、`RUNNER_FATAL`、`CLEANUP_FAILED`、`WORKER_FATAL`。不接受自由文本错误正文。

当前有效 fenced 尝试的可重试失败：

- `attempt < max_attempts` 时，Job 转 RETRY_WAIT，清除 lease，Run 保持非终态且 verdict 为空，追加 `JOB_RETRY_SCHEDULED`；
- `attempt >= max_attempts` 时，Job/Run 转 FAILED，verdict 为空，追加 `JOB_FAILED`；
- 已请求取消的 RUNNING Job 不进入 RETRY_WAIT，应完成取消或按致命清理失败处理。

明确致命失败直接写 Job/Run=FAILED、verdict 为空和 `JOB_FAILED`。任何基础设施失败都不得写成 INCONCLUSIVE。

退避为有上限的整数指数退避：第 n 次已失败尝试的基础延迟为 `base_delay_us * 2^(n-1)`，先截断至 `max_delay_us`；注入的抖动值位于 `0..min(max_jitter_us, max_delay_us-base)`，总延迟不超过 `max_delay_us`。V1 默认 base=1 秒、上限=300 秒、最大抖动=0.25 秒；允许调用方注入策略和抖动源，禁止隐藏全局时钟或随机单例。

### 8. 过期租约恢复审计

`list_recovery_candidates` 只列出 `RUNNING AND lease_expires_at_us <= now_us`，按 `(lease_expires_at_us, created_at_us, job_id)` 排序；扫描不改变 state、attempt、token、lease 或事件。

`confirm_recovery` 必须匹配当前 owner/token，并携带下列稳定证明之一：

| proof_type | reason_code | 含义 |
| --- | --- | --- |
| EXECUTION_EXITED | PROCESS_EXIT_CONFIRMED | 监督方已确认旧执行退出 |
| CLEANUP_COMPLETED | CLEANUP_CONFIRMED | 恢复控制方已完成必要清理 |

operator 只能是 `WORKER_SUPERVISOR` 或 `RECOVERY_CONTROLLER`。证明、operator 和 reason code 写入有限事件元数据，不接受任意说明文字，也不复制 lease owner。

证明匹配后，未耗尽时进入 RETRY_WAIT 并计算下一 `available_at_us`；耗尽时进入双 FAILED。若先前已有取消请求，取消时间保持不变，恢复到 RETRY_WAIT 后不能 claim，可通过幂等取消请求完成双 CANCELLED。恢复后旧 token 因状态和 lease 条件不再匹配，续租、失败、取消完成和其他状态写入永久拒绝。

### 9. 事件与事务

事件类型固定为：

- `JOB_SUBMITTED`
- `JOB_CLAIMED`
- `JOB_LEASE_RENEWED`
- `JOB_CANCEL_REQUESTED`
- `JOB_CANCELLED`
- `JOB_RETRY_SCHEDULED`
- `JOB_FAILED`
- `JOB_RECOVERY_CONFIRMED`

每个操作的 Job 更新、Run 更新和事件追加都位于同一 UnitOfWork。事件 sequence 从 1 连续增加，只追加不修改。元数据只允许稳定有限标量；允许整数 `fencing_token`，禁止秘密、owner 原值、SQL、日志、数据库路径和外部异常正文。

### 10. 稳定错误

公开控制面至少使用：`JOB_NOT_FOUND`、`JOB_IDEMPOTENCY_CONFLICT`、`JOB_NOT_CLAIMABLE`、`JOB_LEASE_MISMATCH`、`JOB_LEASE_EXPIRED`、`JOB_RECOVERY_REQUIRED`、`JOB_CANCEL_CONFLICT`、`JOB_TERMINAL_CONFLICT`、`JOB_ATTEMPTS_EXHAUSTED`。策略、秘密、时间和持久化边界分别使用 `JOB_RETRY_POLICY_INVALID`、`JOB_SECRET`、`JOB_TIME_INVALID`、`JOB_PERSISTENCE`。

错误消息固定且脱敏，不携带 SQL、参数、数据库路径、秘密、lease owner、输入字段名或原始异常正文。

## 阶段交接边界

- 阶段 2.3 才实现 Runner 输入构建、子进程、最小秘密环境、进程终止和 CLI/CI 调度切换。
- 阶段 2.4 才实现成功结果消费、staging 校验、工件 promote、Evidence 完成态和 reconciliation。
- 阶段 2.2 不改变现有同步 CLI、RunService、Runner V1 Schema、五表 Schema 或 `0001_stage2_storage` revision。

## 后果

优点：并发领取由数据库条件更新仲裁；状态和事件原子；过期租约不会直接引发第二次目标副作用；失败与 INCONCLUSIVE 明确分离。

代价：SQLite 写入仍串行；恢复证明由未来监督/进程层产生，阶段 2.2 只校验和记录；成功链在阶段 2.4 前不可通过此服务完成。

## 回滚

本决策未改变物理 Schema。代码回滚可移除 `worker/` 和 `storage/job_control.py`，数据库仍保持阶段 2.1 可读；已写 Job/Event 数据按既有五表保留，不执行自动 downgrade 或历史事件改写。
