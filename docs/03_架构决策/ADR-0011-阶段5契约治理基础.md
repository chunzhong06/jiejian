# ADR-0011：阶段 5 契约治理基础

- 取代者：ADR-0029
- 当前阅读提示：本文保留历史决策；当前边界以 ../README.md 和相关 CURRENT 文档为准。

## 状态

已取代

## 背景

阶段 4 只把一个 ACTIVE YAML Contract 的路径与哈希绑定到 Project，并在持久执行请求中保存完整 `SecurityContract` 快照。阶段 5 需要继续支持显式需求、多来源候选、人工审阅和版本修订，但不能让不可信候选、数据库或未来 LLM 进入 Runner 的执行边界，也不能复制现有 `SecurityContract`/`ContractRule` 形成另一套判定正文。

## 决策

1. 新增冻结、严格且带 `schema_version=1` 的 `Requirement`、`ContractCandidate` 和 `ContractVersion` 公开模型。Requirement 与 Candidate 都保存项目归属、内容哈希来源定位、创建者和 UTC Unix 微秒时间；Candidate 始终是不可信输入，不具有 ACTIVE 状态。
2. `ContractVersion` 是控制面的治理聚合，正文直接保存现有 `SecurityContract` 快照，另存 Requirement/Candidate 引用、来源集合、审计轨迹和可空的上一版本号。Runner V1 仍只消费持久请求中的 `SecurityContract`，不读取治理表，也不改变 Evidence、Verdict 或 Oracle 语义。
3. 版本状态继续使用 `DRAFT → REVIEW → ACTIVE/REJECTED` 和 `ACTIVE → SUPERSEDED`。空规则、重复 Rule ID、非法转换和跨项目引用均被拒绝；只有显式进入 REVIEW 的版本可激活。ACTIVE 与 SUPERSEDED 不得原地修改正文。
4. ACTIVE 修订生成同一 Project/Contract 下 `version+1` 的新 DRAFT。激活新 REVIEW 时，应用服务在同一 `StorageUnitOfWork` 中先把旧 ACTIVE 改为 SUPERSEDED，再激活新版本；SQLite 部分唯一索引保证同一 Project/Contract 最多一个 ACTIVE。
5. Alembic `0004_stage5_contracts` 只新增 `requirements`、`contract_candidates`、`contract_versions` 三张表。既有迁移、Project 文件绑定、Run 的 Contract ID/Version、录制、Worker/Runner 协议和目标流量边界均不修改。
6. 所有治理记录进入数据库前复用统一敏感内容扫描，拒绝已知秘密、Bearer 和凭据赋值文本。来源只保存定位字符串与 SHA-256，不保存真实凭据或未脱敏正文。

## 影响与迁移

旧数据库从 `0003_stage4_control_plane` 向前升级后，原有 Project、Run、Job、Recording 和工件记录保持不变，新表初始为空。阶段 4 的 YAML Contract 绑定仍可继续运行；本子阶段不自动导入旧 YAML，也不把数据库 ACTIVE 版本自动绑定到现有项目路径。确定性需求解析、Flow/路由候选、冲突与漂移、API/CLI/GUI 入口及 LLM 适配器由后续子阶段接入统一治理服务。

## 回滚

数据库迁移不提供 downgrade。需要停用时停止调用契约治理服务，保留三张表及历史版本；现有 Runner V1、文件 Contract 和已发布运行仍可独立工作。恢复旧程序使用迁移前备份或新建旧版数据库，不删除治理记录。
