# ADR-0017：阶段 5-O3 能力优先架构迁移约束

## 背景

阶段 0–5 已形成可运行的模块化单体，但当前应用服务、录制、验证和 Worker 控制面仍按历史阶段逐步叠加。后续迁移需要让能力边界先于实现文件位置，并保持既有运行行为、公共协议和持久化格式不变。

本决策只冻结目标架构和迁移约束。阶段 5-O3 批次 1 不移动生产文件、不新增空能力目录、不删除旧导出，也不开始阶段 6/7。旧 `application`、`domain`、`worker` package-root 聚合导出在 5-O3 全阶段保留；兼容性删除与死代码清理由 5-O3A 审计后决定。

## 决策

### 1. 能力优先的目标结构

目标结构按能力组织，而不是按历史阶段或技术类型继续堆叠：

- `projects`：项目登记、来源完整性、目标授权和项目级运行上下文；不发起目标请求。
- `contracts`：Requirement、Candidate、Contract Version、审阅/激活/修订和契约来源治理；不绕过 Verification 的最终判定。
- `recording`：浏览器录制、事件脱敏、FlowDraft 审阅、回放和录制工件；只能通过授权的录制边界接触浏览器和目标。
- `verification`：Run 的输入、授权、变异、观察、判定和 Evidence 语义；保持领域规则与目标安全内核的独立性。
- `execution`：通用 Job/Attempt 执行、租约、取消、重试、监督和清理协议；不包含具体 Recording 逻辑，不反向依赖 `recording`。
- `results`：已发布结果、Evidence/报告读取、完整性校验和对外展示所需的派生视图；不重新执行验证或改变 verdict。
- `runtime`：配置、诊断、脱敏日志、进程级启动与关闭；不持有领域判定。

能力区之间的目标依赖方向为：

```text
application.context
        │  组合并注册能力实现
        ├── projects ──┐
        ├── contracts ─┤
        ├── recording ─┤
        ├── verification ──> execution protocol / JobHandler port
        ├── execution ──────> storage / protocols / runtime adapters
        ├── results ────────> published artifacts / read models
        └── runtime
```

这是目标依赖图，不代表本批已经完成目录迁移。目标能力尚未形成真实生产入口时，不预建空目录或零调用 wrapper。

### 2. `application.context` 是组合根

`application.context` 是 API、CLI、Worker 和未来 GUI 入口共享的组合根。它负责创建运行时配置、存储 UnitOfWork、能力服务、执行适配器和结果读取器，并把实现注册到端口；能力模块不自行发现全局单例，不在领域代码中创建框架或基础设施对象。

组合根可以依赖各能力区和基础设施适配器，但能力区不得反向导入 `application.context`。入口层只调用组合根暴露的应用服务，不复制契约治理、录制审阅、验证判定或结果完整性规则。

### 3. 稳定 Worker 进程边界

`product.backend.infra.runtime.worker_process` 永久保留为单任务 Worker 进程的稳定边界壳。其命令行入口、进程启动/退出语义和最小安全边界属于运行协议；内部 Handler 注册、监督实现和能力模块可以演进，但不得要求 CLI、API 或外部调度器改用新的进程模块路径。目标迁移完成后，runtime 壳只负责解析进程参数、建立组合根、选择已注册 Handler、执行一次任务并映射退出结果。

### 4. JobHandler 端口与两类真实实现

通用 `execution` 核心通过 `JobHandler` 端口消费“加载请求、执行一次尝试、确认结果/清理”的能力，不依赖具体业务模块。Verification Run 和 Recording 分别提供真实 Handler 实现，由 `application.context` 注册；Execution core 只依赖端口、公共 Job/Attempt 协议和必要的结果/清理 DTO，禁止反向依赖 `recording`。

批次 7 已建立 `JobHandler` 端口，批次 8 已将 Job/Attempt、监督、发布与恢复实现收拢到 `execution`，并由组合根惰性注册 Verification Run 与 Recording 两个真实 Handler。若发现需要改变公共协议、状态机或安全边界，必须先回到 Sol 更新 ADR。

### 5. 旧聚合导出与公开面

5-O3 保留当前 `product.backend.workflows`、`product.backend.core`、`product.backend.infra.runtime.worker_process` 的 package-root 聚合导出，以维持阶段 0–5 行为基线和现有调用方兼容。它们是暂时保留的兼容面，不是新增生产代码的推荐依赖面：

- 新生产代码必须从具体能力模块或稳定协议模块导入，例如 `product.backend.workflows.services`、`product.backend.core.lifecycle`、`product.backend.infra.runtime.job_requests`。
- 不新增旧路径 wrapper，不收缩或删除现有 `__all__`；5-O3A 先审计仓库和外部调用风险，再决定兼容导出的删除、收缩或迁移说明。
- `product.protocols`、`product.backend.infra.storage`、CLI 产品入口和 `product.backend.infra.runtime.worker_process` 继续作为稳定公共/进程边界；本 ADR 不改变 Runner V1、Recording 协议、数据库 Schema、migration 或结果格式。

批次 8 完成后，生产代码不再从 `product.backend.infra.runtime.worker_process` 聚合根导入；`product.backend.infra.runtime.worker_process/__init__.py` 仅保留既有兼容导出，内部实现位于 `execution` 叶模块。`product.backend.workflows` 和 `product.backend.core` 的 package-root 兼容面同样不作为新生产代码依赖。

### 6. 目录深度与展平审查

在 `product/backend` 或 `product/frontend/src` 之后，默认目录形态为“能力 → 子职责 → 专门分组”，文件父目录最多三层。三层是软上限，不是 LOC 指标或目录数量 KPI；目录可以因真实能力边界保持小文件和独立目录。

超过三层时，只有在安全隔离、稳定协议或版本边界、框架发现或资源定位、部署或运行隔离、独立演进子能力至少一项成立时才可保留，并须在项目设计规范中记录保留理由和可执行约束。单子目录链，以及只有一个普通生产文件且没有子目录、又没有独立边界的目录，默认为展平审查候选。

不得为了对称或缩短 import 创建空 package、薄 wrapper，或模板化的 `helpers`、`utils`、`controllers`、`services`、`repositories` 层。migration、生成文件、测试数据、固定协议资源和外部工具目录可以例外，但必须说明其发现机制或不能展平的原因。

批次 9 的 `results/` 当前只有 `published.py` 一个普通生产叶文件，但它承担跨 API 的已发布结果完整性读取和只读派生视图，具有独立演进边界，保留该目录不视为模板层或展平缺陷。`verification/models.py`、`results/published.py`、`runtime/worker_manager.py` 和 `runtime/serve_lock.py` 均在默认目录深度内。

已有目录超过软上限时不立即移动。先审计 public import、相对导入、wheel/sdist、框架发现、资源定位、测试/样例和外部消费者；兼容导出、删除和展平迁移候选交由 5-O3A 审查。

## 取代关系与迁移

此前代码组织决策中关于职责拆分、Domain 纯度、Verification DAG、Storage/Worker 安全边界和历史路径迁移的有效约束仍由本文和项目设计规范承接。本 ADR 记录 5-O3 阶段曾保留 package-root 聚合导出的迁移窗口，并禁止新代码依赖它们。

此前信息架构决策中已经完成的测试、样例和 Schema 路径重组继续有效；当前最小文档真源由 ADR-0021 重新冻结。本文只记录 5-O3 的生产 Python 能力边界和兼容窗口。

迁移顺序由后续批次单独验收：先冻结具体模块和端口，再迁移实现与组合根注册，最后由 5-O3A 审计兼容面和死代码。每批必须保持公共协议、持久化、生命周期状态与安全结论语义不变，并为失败恢复保留可回滚提交点。

批次 9 已完成 Verification 纯模型、Results 已发布只读读取能力和 Runtime 资源管理叶模块迁移。`ApplicationContext` 持有唯一 `PublishedResultReader` 实例并向 API 复用；`product.backend.infra.runtime.worker_process` 继续作为稳定进程壳。该批不引入 Reporting、GatePolicy、RegressionBaseline 或新报告格式。

## 后果

正面后果：能力边界、组合根和进程边界有单一说明；Execution 不需要知道 Recording；后续迁移可以逐批替换实现而不先破坏阶段 5 行为基线。

代价：短期同时存在目标能力命名、当前实现路径和兼容聚合导出；文档与架构测试必须明确区分“当前可执行约束”和“后续目标约束”。

## 验收与回滚

本批只验收 ADR、规范和架构测试的一致性；不修改生产实现、公共 Schema、migration、samples、前端或能力测试目录。若目标依赖被证明会改变公共行为、安全边界、持久化或核心状态机，停止后续迁移并回到本 ADR 重新决策。回滚只需恢复本 ADR、同步文档和新增架构测试，不涉及运行数据转换。
