# ADR-0029：安全意图与契约治理边界

- 状态：已接受
- 日期：2026-08-19
- 适用范围：Requirement、Candidate、PermissionContract 和权限覆盖治理

## 背景

权限检查必须从可审阅的安全意图开始，而不能由目标请求、LLM 输出或执行结果反推规则。需求、候选、契约、覆盖计划和验证结论需要有清晰的可信边界。

## 决策

`Requirement` 保存待验证意图，`ContractCandidate` 保存确定性或 LLM 建议，`PermissionContract`/`ContractVersion` 保存唯一可执行安全意图。只有 ACTIVE ContractVersion 可以生成 Coverage 和 PermissionMutationPlan，并进入执行请求。

确定性候选使用稳定 canonical、ID、指纹、排序和漂移报告；冲突、歧义、观察器不足和能力变化形成治理阻断。人工审阅是激活前门禁。LLM 只能产生带 provenance 的不可信候选，不决定 Verdict、Finding、Gate，也不能自动激活契约。

## 理由与取舍

把治理和执行分开可以保留候选来源、审阅和漂移历史，同时避免不可信输入进入 Runner。代价是激活和修订需要明确状态转换，且执行必须保存契约快照。

## 影响

ownership 和 permissions 使用同一 Permission → Runner → Evidence → Verification → Results 链。Coverage/MutationPlan 表达用例、关系和 required observations；HTTP 字段和具体 Observer 细节留在执行绑定与协议边界。

## 迁移与兼容

旧 Contract/Candidate 治理记录只按当前模型严格解析；不通过旧开发格式猜测恢复。ACTIVE 版本不可原地修改，修订产生新版本并保留旧版本关系。
