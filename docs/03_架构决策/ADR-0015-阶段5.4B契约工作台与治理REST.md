# ADR-0015：阶段 5.4B 契约工作台与治理 REST

- 取代者：ADR-0029、ADR-0035
- 当前阅读提示：本文保留历史决策；当前边界以 ../README.md 和相关 CURRENT 文档为准。

- 状态：已取代
- 日期：2026-08-11
- 范围：阶段 5.4B 应用工作台与本地 FastAPI 治理接口

## 背景

阶段 5.1–5.4A 已建立 Requirement、Candidate、ContractVersion、确定性分析、受限 LLM 候选和治理 ACTIVE 到新 Run 请求快照的链路，但 API 尚未提供共享的治理工作台入口。若路由自行编排持久化和状态转换，会绕过既有评估、项目隔离和 5.4A 绑定事务边界。

## 决策

1. 新增 `ContractWorkbench`，统一编排 ProjectControl、ContractGovernance、ContractAnalysis 和 LLMCandidateGeneration 服务。路由只负责严格请求解析、错误映射和 `model_dump(mode="json")` 输出。
2. 治理 REST 固定使用 `/api/v1/projects/{project_id}/contract-governance` 命名空间，并提供 Requirement、候选派生/LLM 候选、Contract Version 草稿/修订、审阅/拒绝/激活、assessment、diff、drift；`/api/v1/runs/{run_id}/contract` 复用历史 resolver。阶段 4 `/contracts` 文件接口不改变。
3. Requirement 创建请求只接收正文、标签和 actor；来源 locator/hash 由服务从规范化内容生成。Candidate 派生只接受显式 Requirement ID 和当前已校验 Flow，不开放任意文件、URL、源码或外部引用。
4. 确定性候选存在阻断 issue 时整批零持久化；无阻断时在一个 UoW 内按 Candidate ID 幂等复用。新建/修订 Contract 必须引用已存 Candidate，仍经统一 assessment 和治理状态机。
5. 默认 ApplicationContext 不配置 provider。LLM REST 仅接受显式 Requirement ID，受控 provider 失败返回脱敏稳定错误；LLM Candidate 不改变 Candidate→assessment→REVIEW/ACTIVE 门禁。

## 后果

- API、CLI 和 GUI 可以复用同一个工作台服务，避免三套治理编排。
- 工作台快照可同时展示项目绑定、Requirement、Candidate、版本和当前 Flow 派生摘要；结果仍为派生数据，不增加数据库表或迁移。
- 5.4B 不提供模型配置、任意路径或目标请求能力；CLI/GUI 的用户体验接入留给后续子阶段。

## 验证

`tests/backend/workflows/contracts/test_workbench_service.py` 和 `tests/backend/api/test_contract_workbench.py` 覆盖离线闭环、阻断零落盘、幂等、项目隔离、受控 provider、assessment/diff/drift/history，并回归旧控制面与 5.1–5.4A 测试。
