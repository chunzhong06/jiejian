# ADR-0020：阶段 5.6 LLM 配置、秘密存储与协议边界

- 取代者：ADR-0034
- 当前阅读提示：本文保留历史决策；当前边界以 ../README.md 和相关 CURRENT 文档为准。

状态：已取代
日期：2026-08-12
范围：阶段 5.6 批次 1–5；冻结并实现配置、秘密、出站、候选联调、启动准备与 GUI 外壳事实

## 背景

阶段 5.3–5.4 已建立默认离线的受限 LLM Candidate 生成服务。Requirement 必须由调用方显式选择，输入需要脱敏和有界，输出必须是严格 JSON，并继续进入 Candidate → assessment → REVIEW/ACTIVE 治理链。下一批需要支持多供应商 profile，但如果先实现请求发送再补配置和秘密边界，会把密钥、出站地址、重定向和模型输出混入现有执行安全边界。

本 ADR 不改写 ADR-0013 或 ADR-0019。ADR-0013 继续约束 Candidate 的不可信性质和既有生成 metadata；ADR-0019 继续约束 Windows 启动准备、缓存和秘密不被启动器覆盖。本 ADR 只增加阶段 5.6 的 profile 配置、秘密引用、供应商协议族和迁移契约。

## 决策

### 1. 配置事实真源与版本

非秘密 LLM profile 以 SQLite `llm_profiles` 表为持久化事实真源，由迁移 `0007_stage5_llm_profiles` 创建。配置模型和未来 API DTO 均使用 `schema_version="1"`、Pydantic 严格模式、`extra="forbid"` 和 `hide_input_in_errors=True`。表不保存明文秘密、DPAPI 密文、请求 prompt 或响应正文。

每个 profile 的字段冻结为：`profile_name`、`provider`、`model`、可选 `base_url`、`timeout_ms`、`max_input_bytes`、`max_output_bytes`、`max_budget_microusd`、`enabled`、`secret_ref`、`allow_local_http`、`created_at_us` 和 `updated_at_us`。profile 名是小写 slug；时间是 UTC Unix 微秒整数；更新时刻不得早于创建时刻。`enabled=false` 只表示该 profile 不可被后续显式选择，不表示自动切换到其他 profile。

0007 只向前迁移，不提供 downgrade。旧数据库升级后新增表为空，既有十张业务表、列语义、历史 Candidate、Run、Runner 和 Verdict 不变。需要恢复旧程序时使用迁移前备份或旧版本新数据库重建；不删除 profile 记录，也不回写旧表。

### 2. 供应商与适配器边界

`provider` 只允许 `openai`、`deepseek`、`gemini`、`openai_compatible`。OpenAI、DeepSeek 和 OpenAI-compatible 属于同一 OpenAI-compatible HTTP 传输协议族，但 profile 仍必须显式保存 provider；Gemini 使用独立传输边界。领域模型不依赖 SDK，当前实现只依赖标准库、Pydantic、SQLAlchemy 和已有 httpx。生产请求只由显式测试连接或显式 profile 候选生成触发；自动化测试使用 fake transport/fixture，不访问真实模型或收费网络。

离线 provider 始终可用。启动时不得访问模型、测试连接、探测 DNS、自动降级或隐式切换 profile。后续“测试连接”和“生成”均必须是调用方显式发起的一次有界请求；API/GUI 只负责配置入口，不改变六个用户可见阶段。

### 3. URL 与出站安全

`base_url` 只接受 `https`，默认拒绝 `http`；禁止 userinfo、query、fragment、空 host、控制字符、反斜杠和无效端口。规范化 scheme/host/port/path：scheme 和 host 小写，IDNA host 转 ASCII，IPv6 使用压缩格式，去除默认端口，路径按 POSIX 规范化并保留尾斜杠语义。

只有同一个 profile 同时满足 `allow_local_http=true` 且 URL host 是 `127.0.0.0/8`、`::1` 或其他明确的 IP loopback 地址时，才允许 `http`。该授权只属于 LLM provider profile，不得复用到 Runner、扫描 TargetScope、Recording 或其他目标 I/O。后续 httpx 客户端必须 `follow_redirects=false`；任何重定向均不得把凭据带到不同 host，跨 host 重定向必须拒绝。

### 4. 秘密引用与写入协议

`secret_ref` 是不透明引用，不是秘密值。环境变量引用只能匹配 `env:NAME`，其中 NAME 为大写字母、数字和下划线；本机 GUI 录入的秘密使用 Windows Credential Manager 泛型凭据，引用稳定为 `cred:jiejian/llm/<profile_name>`。实现边界使用 `CredWriteW`、`CredReadW`、`CredDeleteW` 的 ctypes 封装；不使用 DPAPI 密文文件、数据库 blob、JSON/TOML、localStorage 或源码保存秘密。

后续写入 DTO 允许一个 write-only `secret` 字段，必须隐藏输入错误、禁止 `model_dump` 序列化回显，并在响应中只返回 `secret_ref` 与 `secret_configured`。读取响应永远不返回密钥；日志、异常、审计、provenance 和报告也不得包含密钥。删除 secret 是显式动作，删除不存在的凭据保持幂等。

### 5. 错误与预算

供应商传输边界的 wire code 冻结为：`llm_auth_failed`、`llm_rate_limited`、`llm_timeout`、`llm_invalid_response`、`llm_budget_exceeded`、`llm_provider_unavailable`。这些 code 通过 `LLMWireErrorCode` 映射到现有 `JiejianError`/API `schema_version=1` 的 `error` envelope；不会创建第二种错误响应结构。既有离线治理错误 `LLM_PROVIDER_UNAVAILABLE` 和 Candidate 校验错误继续保留，只有真实 provider 传输层使用上述小写 wire code。

profile 的 timeout、输入/输出字节上限和单次预算是独立硬上限。超限在发送前或读取响应时终止并映射稳定错误；不得通过重试、自动换 profile 或无限增大预算绕过。请求和响应都不写入数据库或运行工件。

### 6. Provenance 与信任边界

现有 `LLMGenerationMetadata`（schema 1）继续服务于 ADR-0013 的 Candidate 记录。阶段 5.6 的生成 provenance 通过同一 `contract_candidates.llm_metadata_json` JSON 列向后兼容扩展落地，不新增表迁移：可选保存 `provenance_schema_version="2"`、provider/profile、model、adapter/version、prompt version、input/output SHA-256、UTC 开始时间、耗时、预算上限和可选估算费用；旧 Candidate 缺少这些字段时按 `None` 读取。它不保存密钥、secret_ref、未脱敏 prompt 或原始响应。

LLM 只能产生不可信 Candidate，不能产生 Verdict、PASS、BLOCK 或 INCONCLUSIVE，不能绕过 assessment、REVIEW、ACTIVE，也不能改变 Worker/Runner/Verification/Verdict 的状态机和安全结论。

## 分批迁移

批次 1 完成配置模型、秘密端口、API Schema 声明、provenance 版本、Storage ORM/Repository、0007 migration、ADR 与定向测试；批次 2 在不改变数据库格式的前提下完成 profile 应用服务、四类传输边界、显式测试连接 API 和脱敏错误映射。两批均不接入候选生成联调、GUI、启动器或视觉实现。

批次 3 已在本 ADR 冻结的 profile 和 secret 端口上实现候选生成 profile 选择与联调；批次 4 增加带指纹的启动准备快速路径、迁移 revision 检查和真实 `/ready` 门禁；批次 5 增加启动终端阶段展示、`/api/v1/system/status` 只读观察面、六阶段 GUI 外壳与响应式收口。后续批次不得改变离线默认、Candidate 治理链或让浏览器直接接触密钥。

## 当前实施状态

批次 2 已形成后端独立闭环：`LLMProfileRegistry` 编排 profile CRUD、秘密解析、Credential 补偿和显式单次连接测试；`adapters/openai_compatible.py` 与 `adapters/gemini.py` 负责协议构造/响应结构校验，`adapters/httpx_transport.py` 负责禁重定向、禁环境代理和响应字节上限；`api/routers/llm.py` 仅暴露版本化 profile 设置入口。批次 3 在此基础上增加 profile testing 状态/并发保护、显式 resolver 候选生成和模型服务设置 Drawer；`llm_candidates` 不自动选择 profile，Candidate 继续进入既有治理链。

批次 4 在 `start.cmd → scripts/start.ps1 → jiejian serve --open` 唯一入口上增加 `PrepareOnly`、`ForcePrepare`、原子准备状态、内容指纹快速路径、失效重做、数据库 migration revision 校验、启动失败恢复提示和 `/ready` 成功后才打开浏览器的门禁。批次 5 增加原创终端阶段展示、`/api/v1/system/status` 只读状态观察、真实 API/Worker/浏览器/LLM 状态 Tag、模型服务设置入口和窄屏外壳适配；六阶段名称与路由不变。

## 后果与回滚

正面后果是配置、秘密和 provider 传输可以独立演进，数据库永远不需要保存秘密，离线治理不依赖外部服务，且下一批有明确的出站和错误边界。代价是 profile 表需要向前迁移，Windows Credential Manager 需要 ctypes 平台适配，Gemini 不能复用 OpenAI-compatible 请求格式。

回滚本批实现时停用 profile Repository/API 入口并恢复旧程序或迁移前备份；不得执行自动 downgrade，不删除 `llm_profiles` 中可能已存在的配置，不修改既有 Candidate metadata 或执行数据。

## 验收证据

- `product/backend/infra/llm/config.py` 覆盖 strict/forbid/hide-input、provider 枚举、secret_ref 合法性、URL userinfo/HTTP/非回环拒绝和本机 HTTP 双重授权。
- `product/backend/infra/llm/secrets.py` 只暴露 Credential Manager 端口，不把秘密交给 Storage。
- `api/product/protocols/schemas/llm.py` 覆盖 write-only secret 不序列化、响应只含 secret_ref 和 configured 状态。
- `0007_stage5_llm_profiles` 覆盖旧数据库向前升级、仅新增非秘密结构和禁止 downgrade。
- 本批自动化测试使用 fake transport/fixture，不访问外网或模型服务；生产传输只由显式动作触发。
