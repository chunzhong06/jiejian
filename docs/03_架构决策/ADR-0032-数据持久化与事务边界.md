# ADR-0032：数据持久化与事务边界

- 状态：已接受
- 日期：2026-08-19
- 适用范围：SQLite、Storage、Unit of Work、Repository 和 migration

## 背景

领域模型、数据库、文件工件和跨进程协议有不同的生命周期。若让 SQLAlchemy 细节进入领域，或让数据库完成态先于工件发布，系统会产生无法恢复或无法解释的结果。

## 决策

SQLite 是当前本机持久化边界；Storage 通过垂直聚合、Repository 和 Unit of Work 提供事务操作。`product/backend/migrations` 是数据库结构真源，空库只从唯一 `0001_initial` 建立；当前 metadata 与 migration 必须保持零漂移。

Project、ContractVersion、ExecutionProfile、Job/Run、Evidence 索引、Finding、Baseline 和 Gate 使用稳定身份并分离生命周期、Verdict 和 GateResult。Evidence 以内容寻址的 `evidence_id` 为身份，并以运行内工件路径保持唯一；同一 Case 参与多个孪生对时允许产生多条内容不同、关联可追溯的 Evidence。Worker 不运行 migration，不绕过 Storage 或事务边界。

## 理由与取舍

集中事务和身份边界便于恢复、审计和测试；代价是跨数据库与文件的完成语义必须由 publication/reconciliation 协同完成，而不能依赖单一数据库事务。

## 影响

未知 revision、结构签名不匹配、公共格式不支持或身份关联错误时，系统在写入前 fail closed。`var/data` 保存数据库与产品事实，`runtime`、`cache`、`logs`、`temp`、`test` 分别保存可重建运行时、缓存、诊断、临时物和测试物，均不写入源码目录或 Git。

## 迁移与兼容

不兼容旧开发数据库、Profile、Run、Evidence、Report 或 wire format。未知数据库要求由用户明确重建 `var/data`，不提供 0002、兼容迁移或双读，也不自动删除未知数据。
