# 夹具与断言

夹具只建立测试所需的真实前置事实。业务断言留在用例中，使读者能看出输入、动作和预期；不要把判断藏在通用“成功流程”里。

## 按资源划分所有者

| 资源 | 所有者 | 建立与释放 |
| --- | --- | --- |
| 小型业务事实 | `tests/support/facts.py` | 构造严格模型需要的最少字段，返回新对象 |
| 内存秘密存储 | `tests/support/secrets.py` | 每次构造独立引用表；不访问系统凭据；失败注入由测试局部替身承担 |
| 核心与数据库 | `tests/conftest.py` 的 `core` | 每个用例独立目录、数据库和内存秘密存储，结束关闭核心 |
| 本地 HTTP 客户端 | `tests/contracts/conftest.py` | 独立 TestClient 与应用实例，不启动目标 Worker |
| 真实服务进程 | `tests/support/runtime_server.py` | 独立运行根、端口和进程；等待 ready；结束请求正常退出并核对退出码 |
| 官方业务场景 | `tests/support/official.py` | 记录本次项目、写操作标识和已完成阶段，不替测试决定 verdict |
| 浏览器 | `tests/runtime/conftest.py` | 每个场景独立 browser context；结束关闭浏览器，检查脚本错误 |

使用 yield 或上下文管理器使清理与资源获得相邻。后续夹具建立失败时，已启动服务仍需退出；测试失败不能跳过清理。只停止本夹具创建的进程，不按端口、进程名称或全局模式清理其他实例。

业务支持代码与测试分开，避免一个测试调用另一个测试。资源可以复用实现，状态和运行产物不能跨独立用例共享。纯逻辑用例不提前装配浏览器和整个服务。

同一协议的合法构造、非法输入和任务关联放在其所有者下。迁移图、初始化与事务归存储验证，任务目标及构造器归 Job 验证，依赖装配归组合根验证；不另建一组笼统的“当前契约”测试重复承载这些职责。合并文件仍按每个用例实际使用的资源分级，不能让文件中相邻的 SQLite 场景抬高纯逻辑检查的等级。

## 在恰当位置替换外部机制

确定性测试可以替换时钟、等待、秘密存储、网络端口或浏览器启动机制，以复现超时、取消及失败。判断模块必须接收实际格式的事实，不用 mock 直接返回预期的 PASS、BLOCK 或复验成功。

HTTP 边界使用实际路由和本地防护；存储测试使用真实 SQLite 事务；L4 使用实际 Worker、Runner 和独立官方目标。提高真实程度的代价是启动成本和环境依赖，因此只在需要证明该协作时使用。

## 断言可观察契约

- 正向：断言持久结果、输出关联及用户可见状态，而非仅断言没有异常。
- 拒绝：检查错误类别、状态未被写入以及资源仍可回收；拒绝一次未知操作不应留下半份正式状态。
- 权限：区分允许、禁止和证据缺口；保留正常功能对照，不能以统一拒绝掩盖越权。
- 写入：提交使用一次操作标识；回执未知先查询原操作，不重新提交来等待成功。
- 页面：优先角色、名称、焦点、展开状态和真实内容，避免 CSS 类名、布局像素或任意休眠作为业务条件。
- 机制：只有调用去重、取消所有权等明确契约，才断言调用次数或内部生命周期。

页面标题出现不代表业务事实已经加载。等待表格、材料索引或具体结果入口，再核对内容。截图可等待有限动效结束，但不能因此声称不存在字体闪换或悬停卡顿；这些问题需要相应的动态观察。

## 等待与回执

轮询使用单调时钟和明确截止时间，只轮询读取。成功与失败终态都应结束等待，随后分别断言。不要把失败状态当作“还没成功”一直等到超时。

记录阶段状态、耗时、用例标识和脱敏错误类别；密码、Cookie、Token、请求秘密和原始异常正文不得进入测试报告。参数化用例中的敏感参数不能直接作为公开标识。

## 审阅一个新用例

确认它能发现一个具体回归；失败时能区分产品、夹具和环境；独立运行与换序运行的结论一致；失败后资源能释放。如果已有用例能提供同样证据，扩展原用例或删掉重复，不为提高数量拆成多份。

## 区分业务约束与实现快照

| 检查对象 | 有价值的断言 | 容易失效的写法 |
| --- | --- | --- |
| 数据库升级 | 迁移图完整、唯一终点、业务行与引用保留、漂移拒绝时未写入 | 固定修订数量、全部文件名或复制一份当前 head |
| 事件与状态 | 关键状态转换被准确记录，失败时状态与事件一同回滚 | 只断言事件有若干条 |
| 分页和预算 | 每页不越预算，游标连续，无重复、遗漏或停滞 | 固定第几次调用结束、游标必须落在某个常量位置 |
| 结果与证据 | 必要业务问题可回答，来源指向正确封存字段，不跨项目、用例或运行 | 只数说明段落，依赖某一段永远排第一 |
| 工具与脚本 | 真正执行参数转交、退出码、环境恢复、解压和清理 | 统计源码片段出现次数、锁定变量名或函数排列 |
| 依赖与安全入口 | 核对真实依赖、命令树、授权及拒绝后的事实 | 通过禁止某段调用文字推断不存在权限旁路 |
| 测试组织 | 每个风险有所有者，相关范围可选，未知写入和迟到响应得到处理 | 固定验证步骤数量、下标或文件夹层数 |

固定值本身并非问题。协议版本、支持的历史输入、冻结字节、哈希、授权等级和明确资源上限仍需精确保护；由测试独立建立两条记录时，断言两条也合理。判断标准是：保持业务行为不变的一次内部重构，是否仍能通过；一个真实的错误结果，是否会被拒绝。预期不能只由被测函数计算后再与同一个函数比较。

替身替换外部机制，不替代本次要验证的判断。调用次数仅在防重复提交、禁止重放、资源释放等明确契约中使用；其余场景观察结果与副作用。已知合法输入能成功通过严格验证，是有效正例，但须与相应非法输入、关联错误或边界条件配合。

静态审计须核对扫描根和实际输入，扫描不到任何调用点时明确失败，不能把空集合当作安全证明。读取性约束应观察实际 HTTP 方法、参数和副作用；函数常量中没有写入动词，不能证明程序没有执行写入。脱敏预期独立列出需要保留和遮蔽的字段，不能由同一个脱敏函数生成答案再重复比较。

分级按用例实际触及的资源确定。内存事实属于 L2，真实 SQLite 事务属于 L3；启动 Worker、Runner、目标进程或浏览器才进入相应 L4 范围。不能因为夹具文件中还定义了浏览器工具，就把未使用该工具的测试整体标成 L4。

被替身替换的进程和网络不按真实进程或目标计级。本地文件、SQLite 和失败清理仍需按实际 I/O 验证；真实录制子进程和运行时协作保留显式 L4。恢复旧用例时清除已经不参与输入构造的 fixture 参数，不能为满足失效参数重新引入退役请求。

这些选择参考 [Google 对变更探测式测试的分析](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html)和 [Vitest 的实践指南](https://vitest.dev/guide/learn/testing-in-practice)：测试应保护行为与要求，并允许实现合理演进。
