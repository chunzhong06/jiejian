# 执行验证与排查失败

在仓库根执行，使用开发入口管理依赖、运行目录和报告。下面的命令均可直接复制；按实际改动选择其中一组，不需要全部执行。

## 查看并执行范围

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 verify --list
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 verify --area preparation --level L2
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 verify --area preparation --level L2 --run
```

第一条列出可选契约。第二条只展示具体命令，第三条按同一计划顺序执行，首个失败立即停止。范围可以重复指定，测试文件会合并去重。计划不代表已经验证；没有 `--area` 或 `--all` 时不会推测执行范围。

L1 对后端选定文件执行 AST 检查，对前端执行类型检查；范围自带的文档、Schema 与架构检查仍保留。等级更低时，高成本集成用例不会运行；需要它们的变更应主动选择 L3。

## 直接选择文件或用例

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 test tests/application/workspace/test_projection.py -q
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 frontend-test src/shared/lib/useRead.test.tsx
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 frontend-test --types-only
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 docs
```

pytest 支持文件、节点标识和 `-k` 进一步缩小范围。`frontend-test --types-only` 只运行类型检查，普通 `frontend-test` 先检查类型再执行所选 Vitest。AST 检查不导入目标代码；正式 Python 运行同时设置 `PYTHONDONTWRITEBYTECODE=1` 并使用 `-B`。

## 显式选择真实流程

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 sample-test official baseline
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 sample-test official repair
```

baseline 建立独立官方示例，批准规则、准备真实材料、完成一次检查并查看两套主题的关键页面。repair 独立建立基础状态，再引入原问题和修复，分别核对违规与复验结果。后者含自身基础阶段，不必为相同目的连续运行两个场景。

两者使用新运行根和本地官方目标，不接触日常项目。普通 `test` 收集到 runtime 用例会跳过，不能把跳过写成通过。需要可用的受控 Chromium、Node 和本地秘密存储；前置环境失败时先修复环境，不降低产品安全门禁。

### 相邻进程场景

部分适配器、Worker 和录制测试也需要实际进程，标为 `level4`。它们属于各自模块，不因存放在基础设施目录就默认运行。先选择具体文件或节点，再显式启用：

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 test tests/infrastructure/samples/test_web_sample.py --run-level4 -q
```

`verify` 的普通范围始终排除这些场景，即便等级上限为 L4，也不会额外执行全部进程测试。完整官方流程仍由上方 `sample-test` 选择；目录收集和未执行的场景不提供运行证据。

## 区分失败原因

| 观察 | 优先核对 | 处理 |
| --- | --- | --- |
| 依赖准备或浏览器启动失败，业务尚未执行 | 权限、锁文件、运行时和可执行文件 | 修复环境后重新执行原范围 |
| 严格 reader 拒绝夹具字段、页面定位无对应内容 | 当前契约、真实页面、夹具输入 | 契约已变则修正测试；否则调查产品回归 |
| 返回成功但状态、归属或拒绝边界错误 | 当前产品行为与可接受要求 | 修复产品，重跑失败项和直接邻域 |
| 写请求超时 | 操作标识对应的持久事实 | 查询原操作，避免重复写入 |
| 测试通过但进程未退出 | teardown、资源所有者、退出码 | 视为失败，先修复资源释放 |

首次失败保留错误类别和已完成阶段，最多进行有证据的局部修正；发现跨模块或安全契约问题时重新界定方案。不要通过删断言、扩大等待或恢复旧交互掩盖原因。

## 交付结果

说明改动风险、实际执行命令、通过与失败、环境修复以及未覆盖范围。结构化回执帮助定位本次执行，不能替代语义审阅；真实流程和人工审查也不替代确定性边界测试。
