# 应用与运行

本页面向维护者，说明能力协作、持久事实、拒绝边界和恢复方式。用户操作从[文档入口](../../README.md)选择；源码定位查[模块索引](../../参考/模块索引.md)。

## 使用普通应用

### 先确定要证明的结果

先与 Agent 说清楚“谁对谁的什么资源，可以或不可以做什么”，再选能代表业务结果的具体字段。例如，禁止普通成员把他人的对象状态改为某个受保护状态。界鉴必须同时检查正常允许的操作，不能靠拒绝所有请求得到通过。

只看 HTTP 403 或最终状态不够：应用可能已经发生变化，又把状态恢复了。任意 JSON 日志也可能漏记，不能因为字段齐全就被认定可靠。

### 通用记录方式的接入条件

当前完整证明适用于由界鉴受控启动的本地 Node ESM Web 应用。把需要验证的资源集合接入内建 `jiejian:records` 模块，由记录组件保存这些资源的真实数据和每一步状态变化。应用继续自己实现登录、权限判断和 HTTP 路由；界鉴不替应用批准操作。

这需要修改所选资源的读写方式。它不是给任意现有日志加几个字段，也不是数据库扫描器。没有接入组件的外部数据库、文件、队列和后台任务不在此证明范围内。Node 执行环境用于冻结加载方式和核对运行对应，不是对抗恶意应用代码的安全沙箱。

```javascript
import {openCollection} from 'jiejian:records'
const items = openCollection('work_items')

// 初始化不会覆盖已存在的数据或清空其历史；owner_id 创建后不可转移。
await items.seed('item-1', 'user-a', {phase: 'initial'})

// 在真实 HTTP 请求处理器中，根据已登录账号判断是否允许。
const item = await items.read('item-1')
await items.transact({
  resource_id: item.resource_id,
  subject_id: actualUser.id,
  expected_version: item.version,
  changes: allowed ? [{path: ['phase'], value: 'ready'}] : [],
})
// 必须 await 完成本次写入，再结束 HTTP 响应。
```

`transact` 只接受有限 JSON 字段赋值，不执行 SQL、脚本、回调或外部请求。每次事务至多 8 次赋值，一次请求至多 32 个事务。先改成 `ready` 再改回 `initial` 的两个变化都会被保留。版本不符会拒绝写入，避免把并发变化拼接成同一操作。

宿主把事务关联到真实 HTTP 请求，应用不能自行声明请求已经完成。响应结束后继续写入会被拒绝；没有等待写入、异常关闭或记录不完整时，不能证明“没有发生”。记录的持久日志由 Runtime Worker 独占，损坏或超过 128 MiB 上限会停止提供完整证明，不自动清空或修补。

不要把密码、Cookie、Token 或其他凭据放入资源数据。凭据只通过现有受控账号引用注入。

### 一次完整流程

### 让检查保留实际执行过程

业务结果证明和内部执行路径需要分别接入。只提供 HTTP 回应或最终业务状态，界鉴无法知道内部经过了哪些权限判断。受控 Node 应用可以在原有记录集合上使用与官方示例相同的通道：

```javascript
// 在同一真实请求中调用，父引用取上一条实际写入事件；只用公开 ID，不写入凭据或正文。
const entry = await items.trace(item.resource_id, {
  kind: 'ENTRY', semantic_key: 'request_received', parent_event_id: null,
  subject_id: actualUser.id, source_component: 'my_app', source_location: 'handler/entry',
})
const decision = await items.trace(item.resource_id, {
  kind: 'AUTHORIZATION', semantic_key: 'permission_checked', parent_event_id: entry.event_id,
  subject_id: actualUser.id, authorization_decision: allowed ? 'ALLOW' : 'DENY',
  source_component: 'my_app', source_location: 'handler/permission',
})
// 若真实事务已完成，再用其 operation_id 写 PERSISTENT_EFFECT/RECOVERY 事件。
// 响应结束前，写 MESSAGE / response_prepared，父引用为实际最后节点，并 await 完成。
```

每条事件必须属于当前请求和资源；提交事件必须引用真实事务，不能跨请求引用。每个资源请求最多 128 条事件。未接入、记录失败或未闭合时显示路径缺口，不生成示意链替代。采集调用应单独处理诊断错误，保留原业务返回；不要让诊断错误反过来改变应用的权限行为。

Agent 接入时应核对真实入口、账号识别、权限判断、提交与响应的位置。只有所接入的事件可展示，任意外部数据库、后台队列或第三方服务不会自动出现。来源读取范围和采用仍由人在界鉴确认。

源码整理可以先于应用启动。需要实际准备材料时，再核对运行方式、资源接入和本人确认事项：当前受控运行要求本地 Node ESM 静态模块及支持的依赖形式；检测到源码或页面能打开，都不代表完整证明已可用。官方数字展馆提供有界的示例材料，仍需核对权限与证明。

1. 选择应用源码目录，单独授权只读分析，审阅识别到的角色与业务动作。
2. 在原 Agent 中确定规则，通过 MCP 保存候选；到界鉴核对例子和完整变更，再确认正式权限。
3. 在“应用与环境”中核对入口文件、端口和读取范围，明确启动受控实例；准备实际测试账号，录制业务操作和必要恢复操作，审阅资源与账号的对应关系。
4. Agent 调用 `jiejian_preparation_context`，根据当前动作、账号、资源和输入合同填写证明来源，不猜随机 ID。
5. 在界鉴确认读取范围。预检查由独立 Worker/Runner 核对实际账号、角色、资源所有者、字段与记录组件，不在 API 请求内直接运行目标操作。
6. 预检查可用后，核对资源集合、受保护字段或状态，以及这次采用会替换什么。明确采用后，才能进入正式检查。
7. 检查完成后，在“Agent 协助”复制本轮请求，粘贴到原 Agent 对话。Agent 通过 MCP 读取该 run_id 的结果，再按 case_id/evidence_id 读取必要证明与事件，解释实际操作、观察、结论和缺口；也可直接查看界鉴原始结果。
8. BLOCK 时先核对修复要求及必须保留的正常业务；INCONCLUSIVE 时先补证；PASS 时明确验证范围。由人决定修改后，Agent 沿用任务上下文与修复引用，登记真实变化，核对运行与材料并按授权复验。对变化的运行实例、会话和来源重新核对，旧结果保持原样。

### 遇到准备问题时

材料页和 Agent 的 `jiejian_preparation_context` 共用当前准备建议。它列出可沿用的材料、具体缺口、原因、处理者和对应页面。全局顺序仍取工作台当前任务；只有已经轮到结果证明，才细分读取授权、预检查和采用，不越过规则确认、账号或录制。

Agent 应先重读上下文的 `basis_id` 和 `guidance`，再使用其中的动作修订、来源修订及预检查引用。`next_step` 是结构化的下一步，不再是一句固定提示。`NEEDS_REFRESH` 表示读取期间条件变化，应重新读取；未知失败原因只提示核对，不声称已经定位。候选建议没有授权效力，写操作仍核对当前权限和修订。

| 看到的情况 | 接下来做什么 |
| --- | --- |
| 测试账号与角色不符或缺登录状态 | 进入该动作的测试账号页核对；保留规则和其他有效材料 |
| 源码与受控实例未对应 | 先到应用环境核对运行，再预检查原配置 |
| 映射缺失或字段类型不符 | 让 Agent 按实际字段修正这一来源 |
| 尚未确认读取范围 | 由本人在 GUI 核对并确认；Agent 不能扩大范围 |
| 预检查运行中 | 查询原任务，不重复启动 |
| 预检查可用但尚未采用 | 本人核对影响并采用；此时尚未形成权限结论 |
| 写请求的回执未知 | 查询原操作标识，不能用新标识重复提交 |

### 自己体验时如何记录

建议先在概览启动官方示例，审阅权限、采用提供的材料、执行检查，再在“修改与验证”完成预设优化、发现问题和原题修复。随后选一个满足上述条件的本地应用，沿本页流程建立自己的检查。自动技术验收不能替代这次实际使用。

遇到问题只需记录：想完成什么、在哪一步、实际看到什么、期望什么，以及系统页的产品版本与页面资源状态；可以附截图。不要提供密码、Cookie 或 Token。耗时和重复输入次数未记录就留空，不根据测试总耗时推算。系统页可区分当前页面与服务资源一致、有更新、尚未确认；有更新时先保存编辑并等待检查结束，再明确刷新。

### Agent 应填写什么

| 配置 | 含义 |
| --- | --- |
| `source_kind` | `MANAGED_TRANSACTION_RECORDS` |
| `collection` | 应用实际通过 `openCollection` 使用的集合名 |
| `relative_path_template` | `/collections/集合名/{resource_id}`，这是逻辑来源位置，不是应用必须提供的接口 |
| `TRANSACTION_HISTORY_V1` | 核验资源状态变化；`state` 映射到 `data` 下的实际字段 |
| `RESOURCE_FIELDS_V1` | 核验有限 JSON 内容读取；受保护字段必须与已确认业务要求一致 |
| `identity_claims` | 受控账号引用、应用账号 ID、真实身份 GET 路径、账号字段路径和角色字段路径 |
| `target_resource_path` / `target_owner_path` / `target_data_path` | 内容读取时，目标响应中的资源、所有者和业务内容位置 |

资源标识和所有者固定映射为 `resource_id`、`owner_id`。身份接口、角色名、应用入口和业务状态值没有专用白名单。字段能读到只能证明配置可执行；用户还必须确认该字段确实代表要保护的业务结果。

Agent 可以保存候选、修正配置、在既有授权内预检查与正式执行；不能批准规则、采用来源、扩大读取范围或决定安全结论。写请求使用稳定操作标识，响应不明确时查询原回执，不用新键重复提交。

## 官方示例

### 默认Node展馆故事

首次权限草稿直接在普通候选整理工作面呈现为 Agent 回复，明确标注“示例模拟”，不声称真实 Agent 保存过候选。权限页与候选入口都可继续同一草稿，不经“其他入口”跳回示例页。展示版选择保留四张同级大卡；选择后在当前工作面打开普通完整 Proposal 审阅，仍需人的核对与批准，不自动写入正式权限。真实 Agent 已保存的候选仍按其原引用打开。

默认入口安装`samples/web/digital_gallery`的严格格式2清单。`OfficialSampleManager`只校验和复制这份Node源码，`NodeOfficialSampleExperience`编排普通接入、显式运行加载及材料入口；`NodeRuntimeSetup`、Runtime Worker与现有记录组件拥有目标和运行事实。`sample_workspaces.runtime_kind`明确区分NODE_ESM和旧PYTHON，同一项目不能被两个运行提供方同时认领。

人的展示版下载选择进入普通待审Proposal，随后仍由LOCAL_GUI批准。 同页提供允许下载、仅在线预览、这些都不是、暂不确定四个同级选项。后两项只引导自定义整理或暂缓，不按false解释，也不生成官方提案；自定义要求沿原草稿与人工审阅入口。三项动作是公开预览、公开展示版下载、内部完整包领取。内部包领取会为当前账号建立私有取用权限并交付实际ZIP；访问接口实际核对access_for与visibility。负责人允许这两项后果，评审禁止这两项后果；公开预览与已选择的展示版要求另行检查。合法对照与禁止路径覆盖同一组后果。

五个预设只改真实业务源码：正常起点、错误交付、独立提交开放后再撤回、正确修复、后续公开预览修改。每次修改经普通变化登记和受控加载，再使用原材料核对与完整检查。已发布结论只从关联本批change的Run读取；与历史同源码也不借旧PASS。源码偏离最后预设交付时进入普通开发，不覆盖外部修改。

“使用已提供的测试材料”一次建立并自动登录两个官方虚构账号，按需创建展馆资料，再导入录制、资源与证明来源候选。登录使用原身份准备管理器监督的独立进程：固定账号、已确认的本机地址、原有网络限制和 Windows SecretStore；通过实际登录响应与身份接口核对成功。已有可用账号、录制和资源复用，不重建；有自定义账号或尚未完成的手动登录时，明确提示处理。官方实例生成的 ZIP 和 PDF 通过普通参照输入服务一并导入，新来源直接填写参照引用；已存在的来源配置保持原样，缺文件时补充可选输入。重复准备复用相同文件。用户随后核对文件用途、读取范围、预检查和采用；示例安装不静默批准规则、授权读取或采用文件。业务文件仅在运行数据目录生成，不从源代码中的文件名或摘要推断交付成功。

账号已建立但未登录时，示例材料入口保持可用，并说明会自动登录和准备；原登录浏览器入口保留给手动处理。导入完成后回读准备事实和工作区，再展示证明核对任务。已有录制、资源、恢复和来源候选后，主操作进入具体证明核对；缺少来源时仍可导入候选。界面不将“已提供”解释为证明已获授权或所有材料已齐备。API 不直接执行浏览器；跨进程结果继续使用原账号准备合同，秘密不进入普通回执。超时收口原登录进程，返回有限错误，不重放未知写动作。

启动、重置和停止保留原操作键；查询不重放。Node加载仍使用持久Job和原回执，目标不在API进程启动。退出先取消本项目活动检查、等待回收并核对精确Node进程树，最后清理本项目临时登录状态；旧权限、源码和发布证据保留。新的应用接入仍从空白目录选择开始。

新实现与直接验证入口：`product/backend/application/examples/node_environment.py`、`gallery_recipe.py`、`gallery_materials.py`；`tests/application/examples/test_node_official_sample.py`覆盖真实五次实现、两次独立提交、原题VERIFIED和历史不改写。独立官方流程使用 `tests/support/official.py` 与 `tests/support/browser_review.py`；MCP授权和工具行为由对应接口契约单独验证。人工体验与真实开发Agent的使用成本另行记录，不能由脚本耗时推算。

### 运行与退出

“继续上次示例”使用当前未归档项目及原源码副本；只有“重新开始示例”或重置才创建新项目并归档旧项目。停止通过当前CHECK取消与受控运行所有者收口，保留原项目源码、权限和发布证据。继续时必须已确认旧实例退出，旧登录会话及实例相关证明重新核对。重复启动活动示例不创建第二实例。GET状态不启动目标；来源、实例身份不明时保持不确定，不按PID、端口或项目名称猜测所有权。Sample只绑定loopback，不使用真实云或付费接口。

### 环境操作回执与历史

start/stop/reset/resume 接受可选 UUID operation_id；显式 ID 持久绑定一次操作，重复 ID 只回读，不再启停。Node 的 start/reset/resume 先持久受理并返回202，后台完成接入；内部需要等待的调用者仍等待同一操作。已有活动实例上的新 start 保持该实例，停止后的 start 与明确 reset 创建新项目；resume 保留当前项目。省略 ID 表示一次显式新操作，未知回执不得用新键重发。

状态查询可携带 operation_id 精确回读，lightweight 省略完整材料投影及变化记录。阶段依次为核对旧实例、创建项目、提交加载、等待目标、核对连接、整理源码。进度记录各阶段起止时间，界面只显示从同一受理时间计算的总用时。前端确认后立即关闭对话框，以400ms串行读取活动操作；明确成功后才同步完整工作区，隐藏页暂停显示轮询。已结束的旧操作不能混入新项目字段。

工作线程活跃时 reconcile 只回读；服务中断后的未知步骤不自动重放。已有精确项目和受控运行记录时核对原实例，其余保留 UNKNOWN 供处理；这不是跨重启自动恢复整个启动流程。后台关闭先等待环境编排结束，再释放运行所有者和数据库。

体验状态区分 NOT_STARTED、STARTING、RUNNING、STOPPING、STOPPED、FAILED 和 UNKNOWN，并给出 history_project_id、last_error_code、operation_id、operation_state。安装 available 与生命周期分开。服务重启不复活进程，旧 PENDING 只读投影 UNKNOWN；停止确认后为 STOPPED，项目与源码继续保留。连接部分提交失败保留已创建项目索引，清理错误不覆盖首个错误码。

`GET /api/experience/official-sample/history` 从独立持久操作表列出真实记录，默认25、最多100条并返回 has_more；不扫描日志猜历史。测试 `tests/application/examples/test_environment_receipts.py` 使用 stub 进程所有者验证重放、重启与局部失败，不替代真实环境验收。

### 示例执行链与结果解读

示例材料通过 GUI 的“一键准备示例材料”集中确认与连续处理，不要求演示者逐个核对四个来源。配方更新当前资源绑定和相应文件候选；手工修改过的非配方内容必须另外核对。预设修改加载新进程后，旧进程内的 Cookie 会话失效，示例同步清除旧登录准备状态，随后由一键准备重新登录；测试不得额外登录来掩盖产品中的旧会话问题。

数字展馆在真实请求入口、身份识别、权限判断、事务完成和响应准备处写入 `records.trace`。事务事件引用实际 operation_id，撤回是独立恢复事件；没有把版本名或预期结论写成事件。Runner 通过普通已采用来源读取并封存，旧运行结果不会补写路径。现有示例实例需要重新加载修改后的源码并重新检查，才能得到新链条。

这与普通 Node 应用共用通道，见[使用普通应用](#使用普通应用)。示例的业务存储本来就依赖受控 `jiejian:records`；新增 Trace 不是让任意项目自动具备内部过程采集。诊断调用失败不改变业务响应，但界鉴会保留不完整说明。五个真实实现回归同时检查原有 PASS/BLOCK、实际事件发布及可读路径。

检查完成后使用界面的“Agent 协助”复制本轮请求。Agent 经 MCP 读取结果和证据，解释实验，再按用户决定修复与复验；界鉴不会仅因为复制了请求就显示“已发送”。

### 脚本所有权与诊断

`official.py` 只保留场景编排；`harness/state.py` 保存运行状态，`harness/receipt.py` 校验源码回执，`harness/lifecycle.py` 管准备、进程、端口与清理，`clients/http.py` 管 HTTP。`CurrentGui` 由共享 session 和 environment、boundaries、checks、history、mcp 动作组成；`reporting/diagnostics.py` 负责有界公开诊断。validation 下 models、runtime、evaluation、summary、suite 分责，不增加用户入口。

脚本直接测试分别检查 contracts、diagnostics、driver、environment、lifecycle、validation；`_support_sample_test.py` 只存无业务判断的准备与替身。失败记录保留 sample_test 根下的相对调用位置和首个错误，不发布绝对私人路径、响应秘密或完整 SDK 异常。

当前套件与证据范围见[环境与脚本](../开发.md)。算法矩阵的身份必须来自实际记录，恢复必须回读业务状态，进程清理另行核对。

## 应用与源码

### 源码整理与运行连接分开

选择目录只建立Project及理解记录，不自动探测地址。源码只读授权和扫描可以先于应用启动、地址确认；保留目录限制、授权、revision和扫描后并发核对。运行加载预览复用同一源码授权，不再使用单独绕过地址前置的标志。

GUI先整理源码及业务候选。“应用运行”将连接已有应用与由界鉴启动组织为两种编辑方式；选择方式本身不探测目标、不写入地址、不启动或停止进程。工作台在实际登录、录制、来源读取和正式检查前，仍使用各自的运行门禁；定位某个页面或表单不能代替访问和执行授权。

受控启动进行中由页面回读原操作和实例，不重复启动。启动完成只形成运行事实，页面以实例地址和管理操作替换旧启动确认；采用地址必须由用户明确选择“使用此应用”，共用地址确认事务。切回手工地址表单不改变进程归属，仍保留管理原实例的入口。停止只针对本项目的实例标识；运行事实、当前检查地址和源码对应关系分别负责自己的语义。

### 修改路线与协作

先区分识别错误、用户确认错误和当前实现失效。connect建立或复用项目；源码分析产生理解与候选，后续重分析按稳定key保留用户决策。正式角色/动作及权限由边界事务批准；分析器不能直接激活规则。 候选审阅中，新识别且未过期的权限组默认勾入本次审阅，明确排除的决定仍保留；低置信动作继续待审。默认勾选只影响本地草稿，必须核对完整摘要后保存，不能代替正式权限批准。源码理解变化还影响实现绑定inspection、材料来源和完整检查的指纹。

改解析器先测最小源文件fixture；改合并逻辑再核对同key候选、用户手工补充、源码删除和revision并发；改公开输入/输出时核对router与access消费者。详细读写和失败收口见[接入与运行协作](#接入与运行协作)。

### 失败先查哪里

- 候选消失：核对分析输出、稳定key与决策合并，不用名称猜测同一业务对象。
- 地址确认被拒绝：核对normalize_loopback_endpoint、保留控制面origin、当前revision与用户确认；不放开scope来绕过失败。
- 源码已经改动但页面仍显示旧材料：从当前source fingerprint、实现inspection和BindingSourceInspector追踪，不在页面强制READY。
- 页面可达但没有完整证明：核对普通应用支持条件，普通外部应用与受控Node运行的能力范围不同。

### 同目录复用与全新接入

`connection-preview` 只读取目录及同源项目，并返回项目状态快照。GUI 检出旧项目后要求选择 RESUME（明确指定原项目）或 NEW（独立空项目）；没有旧项目也使用带快照和固定操作键的 NEW，避免预览与提交间的并发变化被静默当作复用。旧 AUTO 调用只允许正常活动项目复用，不能自动恢复归档项目。

服务在写事务内重验快照。NEW 使用固定操作键形成项目标识，重复相同操作返回原结果；异文或目录不符拒绝。新项目不复制权限、候选、授权、凭据或材料。响应未知时前端只查询该项目与理解事实，不重发创建。源目录不再是项目唯一身份，同目录各项目通过 project_id 隔离。移除继续保留历史，恢复继续沿用原权限，二者必须对用户说明。

## 运行加载

### 正常路线

首次启动先预览受控源码、明确入口和端口，再以稳定operation_id明确授权执行。后续加载只能针对当前任务最新交付，实际源码必须与该交付快照一致；预览不是已启动。NodeRuntimeActivation在调用方事务中登记加载、持久Job和PENDING回执，查询按原operation_id关联当前Job/启动回执。

Runtime Worker独立启动并拥有目标进程树。加载Job成功仅说明启动事实已发布，Worker继续持有目标，直到目标退出或控制面收口。CHECK引用该实例，不能靠健康响应或源码相同认定运行对应。

默认官方Node样例和普通Node应用共用专用持久加载Job、Runtime Worker和记录来源；只有格式1 Python样例仍由原受控副本provider提供。工作空间的runtime_kind与持久加载归属共同确保ProjectRuntimePorts只选择一个所有者。完整格式与限制见[受控运行对应](#受控运行对应)，共同协作见[接入与运行](#接入与运行协作)。

### 未知与失败

- 响应未知：先查原回执及关联Job；不换键重新启动探测。
- 服务会话变化而操作仍未收口：UNKNOWN不表示失败已确认，更不授权重放。
- 源码与交付不同：先登记当前真实变化，不让运行加载替用户提交新的变化。
- scope、依赖形式、入口、进程所有权或manifest不满足：明确受限支持；不补造实例身份。
- 停止必须针对本项目的受控实例和进程树；不按进程名称清理用户其他服务。

## 受控运行对应

### 当前支持的提供方

| 提供方 | 谁启动和拥有进程 | 对应证据 | 支持边界 |
| --- | --- | --- | --- |
| OFFICIAL_SAMPLE | OfficialSampleExperience及受控Python进程树 | 授权源码副本、RuntimeLaunchManifest/Receipt、实际所有权及检查前后核验 | 明确顶层Python入口与已确认解释器；官方样例专属生命周期 |
| CONTROLLED_NODE_ESM | NodeRuntimeSetup提交RUNTIME_LOAD；专用Runtime Worker拥有Node目标树 | 固定模块/依赖身份、加载请求/Job、NodeRuntimeLoadReceipt、NodeRuntimeReference | 本地受支持ESM与依赖形式；通用记录组件只覆盖接入的资源，不自动覆盖外部系统 |
| 普通未托管外部应用 | 用户自行管理 | 已确认地址、授权源码扫描及可用材料 | 不自动获得受控运行对应或完整记录证明 |

ProjectRuntimePorts在组合根连接真实provider；不按项目名称猜测归属。应用识别、运行对应与业务证据分别核验。

### 输入、回执与reader

| 根/事实 | Writer | Reader及责任 |
| --- | --- | --- |
| RuntimeLaunchManifest | 受控Python副本构建者 | 独立target启动模块先核对解释器、目录、文件、入口和清单 |
| RuntimeLaunchReceipt | 已获进程树放行的启动模块 | 持有真实进程对象的控制者核对实例、清单和PID；回执在目标导入前形成，不证明应用就绪 |
| Node加载请求与manifest | NodeRuntimeSetup/load_jobs及受控工件构建 | runtime_process与node_owned核对实际模块、入口、解释器、来源和所有权 |
| NodeRuntimeLoadReceipt/Reference | 持有目标树的Runtime Worker | RuntimeLoadJobs与运行provider、检查前后校验；Job成功后进程继续持有目标 |
| RuntimeActivationReceipt及Node变体 | 对应加载服务 | 按原project/operation读取；必须匹配精确task/delivery/Job |
| CHECK runtime/result变体 | RuntimeBuilder与Runner | 严格parser及publication接受；历史reader不补造运行身份 |

准确版本由[注册与格式](../../参考/模块索引.md)提供。Python运行模型位于 `product/protocols/runtime/runtime_identity.py`，Node模型位于 `product/protocols/runtime/node_runtime.py`；CHECK reader位于 `product/protocols/checks/`。

### 文件与运行身份

Python源码副本冻结排序路径、字节数与内容指纹，不随工作区修改；业务数据和临时文件写独立运行目录。只有独立Target启动模块在核验后加入该副本导入路径，不允许API/Worker借此把仓库加入产品导入视图。

Node执行要求当前受支持的静态ESM模块和依赖形式，实际检查由 `product/backend/infrastructure/runtime/process/controlled/artifact.py` 等实现。运行引用还绑定真实进程树与实例。依赖配置指纹不证明任意第三方包、宿主或外部服务可信。

### 加载与恢复

首次运行先预览，再明确同意执行；新源码必须重新登记并明确加载。NodeRuntimeActivation只加载当前任务最新交付，实际源码需匹配快照。持久加载输入、Job与PENDING回执同事务形成；响应未知只查原操作。

运行回执查询不会重放启动。NodeRuntimeActivation._resolve可以依据精确Job已形成的终态，在事务内将PENDING操作回执收敛为终态；这是回执恢复，不能概括成所有GET都无任何持久更新。无法确认责任或控制会话已变化时保留UNKNOWN，不凭空补成功。

官方Python加载沿现有样例生命周期；全新样例启动创建独立项目。普通Node加载Job与长期实例拥有责任分开，不能因为Job完成就退出持有目标的Worker。停止、取消和服务关闭只能回收已确认归属的树。

### 检查适用性与局限

CHECK前核对冻结实例、进程所有权、启动清单和受控文件；无法确认时停止目标执行。检查后漂移保留已观察事实，运行适用性标为未确认，不能回写历史Verdict。精确交付关联通过development_check_runs，不能按时间或同源码推断。

这防止正常开发中的旧进程、入口混淆及修改未加载；不提供针对恶意宿主、进程内存篡改或文件修改后还原的可信执行证明。普通Node运行环境也不是任意恶意代码沙箱。

修改与直接验证查[运行加载指南](#运行加载)。Python副本的直接测试为 `tests/infrastructure/runtime/process/test_target_artifact.py`，普通加载为 `tests/infrastructure/runtime/jobs/targets/test_runtime_load_jobs.py` 和 `tests/application/runtime/test_node_runtime_activation.py`。

## 接入与运行协作

### 创建与调用

1. GUI经projects/application入口调用ApplicationUnderstandingService；服务通过受控目录发现建立或复用Project与理解记录。
2. 用户先授权只读源码分析；应用未启动、没有已确认地址时也能整理角色/动作候选。审阅决定与理解revision保存，正式业务规则另外批准。实际登录、录制和检查前再显式确认loopback地址；选择目录不自动探测地址。
3. ApplicationCore创建两类RuntimeProvider：官方样例由OfficialSampleExperience管理；普通Node由NodeRuntimeSetup预览入口、端口、源码和依赖形式。
4. 用户明确启动普通Node，控制面保存冻结加载请求及Job。专用Runtime Worker取得租约和进程树所有权，校验固定源码后启动目标、发布启动回执。
5. 加载Job成功后Worker仍拥有目标。ProjectRuntimePorts向材料、开发交付、规则详情和CheckRuntimeBuilder提供当前实例引用；它们不能以原始端口替代实例身份。
6. 后续变化先登记真实源码。加载当前最新交付继续使用稳定operation_id，核对快照一致，再建立新运行引用。CHECK前后核验运行对应，历史Verdict不改写。

### 读写与边界

| 责任 | 读取 | 写入/交付 | 所有者 |
| --- | --- | --- | --- |
| 应用理解 | 授权源码、当前revision、用户决策 | 理解与候选、源码fingerprint | application_understanding |
| 运行准备 | 明确入口/端口、快照和依赖身份 | manifest、冻结加载请求、Job | runtime/setup、load_jobs |
| 启动执行 | 冻结请求、Node身份、进程树所有权 | 真实实例与load receipt | runtime专用Worker/process |
| 加载回执 | 原operation、交付和Job关联 | 已确认终态回执或UNKNOWN投影 | NodeRuntimeActivation |
| 检查对应 | 冻结实例、manifest、活进程与文件 | 输入引用及检查前后适用性 | runtime builder/Runner |

### 失败与收尾

- 目录或候选分析失败不形成正式权限；地址发现并发revision变化时拒绝旧确认覆盖。
- preview后源码改变、入口/依赖形式不受支持时不启动；副本生成成功不代表进程已就绪。
- 启动响应未知先查原Job/回执。控制会话已变且尚未确认终态时保留UNKNOWN，不能换键重启探测。
- 停止或关闭由真实所有者回收整棵受控树；遗留PID/端口不能单独证明所有权。
- 未托管外部应用保持受限支持；受控Node机制不是对抗恶意宿主/应用的完整安全沙箱。
