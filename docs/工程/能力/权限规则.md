# 权限规则

本页面向维护者，说明能力协作、持久事实、拒绝边界和恢复方式。用户操作从[文档入口](../../README.md)选择；源码定位查[模块索引](../../参考/模块索引.md)。

## 规则与批准

### 这是什么

当前权限真源拆成稳定业务语义与当前代码定位：

```text
ApplicationUnderstanding Candidate
  → 仅用于发现和 implementation binding

BusinessActor + BusinessAction + Effect catalog
  → 人确认的稳定业务边界

PermissionIntentRevision
  → 谁对谁的资源执行什么动作，应 ALLOW 或 DENY，保护哪些 Effect
```

Candidate、测试账号、Flow、HTTP 绑定或某次 Run 都不能成为业务权限真源。只有本机 GUI 发起、服务端固定为 `LOCAL_GUI` 的 Proposal 决定事务可以改变正式语义；CLI、MCP、Machine、AI、Compiler、Worker 和 Runner 都不是审批人。

### 正式语义与技术选择

DENY 的整组 effects 必须有单条完整 ALLOW 覆盖，不能拼接半截权限。PermissionBoundaryStatus 只表达正式语义缺失、revision/relation 复核和完整 ALLOW 不存在；allow_control_available 表示完整候选存在，不表示技术选择或可运行性。等价候选选择、distinct 身份和 Twin 对齐缺口由 Preparation 负责。

GUI 技术选择通过严格格式 1 的 preparation/allow-control 入口提交当前有限候选身份与候选指纹；同事务校验后只替换 ActionAllowControlBinding。它不追加 Permission revision、Approval 或 policy_epoch，不向 CLI/MCP/AI 开放。

### Candidate 的责任

`preview_from_discovery()` 读取 ApplicationUnderstanding 的角色与动作 Candidate，只输出未 stale 且没有被用户明确 `REJECTED` 的候选。HIGH/MEDIUM 只可作为前端默认建议，LOW 只列出而不自动采用。多个 Candidate 合并为一个业务主体或动作必须由用户明确操作；名称相似不构成合并依据。

正式 Actor、Action、Effect 和 Permission 不保存 Candidate ID。Candidate ID 只进入 `ActorImplementationBinding` 或 `ActionImplementationBinding`；手工业务语义使用 `MISSING` binding，仍可 ACTIVE，页面必须同时说明“业务边界已确认”和“当前代码中还没有可靠定位”。

### Business Boundary revision

`BusinessActorRevision` 和 `BusinessActionRevision` 按稳定 ID 追加不可变 revision。Action revision 拥有完整 Effect catalog；Effect 表达真正业务结果，例如对象形成、状态变化或受保护数据披露，不能用 request、task、queue 或 worker 节点代替。

Permission v2 引用稳定 Actor/Action revision，语义包含资源关系、`ALLOW/DENY` 和受保护 effect IDs。`PermissionIntentRevision` 不包含 Candidate、TestIdentity、Flow、Observer、Profile 或运行信息。

普通 `BusinessBoundaryView` 只投影每个 intent_id 的 latest revision 中仍为 ACTIVE、且精确匹配当前 ACTIVE subject actor、resource owner actor、Action revision 与当前 Effect catalog 的权限。RETIRED、旧 Actor/Action revision 和失效 Effect 引用继续留在 history，但不进入当前权限计数或 Workbench 完成判断；当前 Action 没有有效权限时，页面区分“从未确认”与“历史权限需要按新 revision 重新确认”。本版不自动迁移旧权限。

### 编辑读取与提案原始对照

BusinessBoundaryService.editor在同一StorageUnitOfWork读取正式边界、候选预览、完整维护草稿与最多100条待审摘要；pending_has_more只说明还有未返回的待审记录。这个一致性边界限于应用持久事实，不把外部源码写入说成原子快照。

按ID读取Proposal时，review投影对Actor/Action/Permission逐项读取expected_current_revision；权限引用的主体、动作、效果名称也来自其精确历史修订。缺失历史标记UNAVAILABLE，不伪装成新增；current_state_changed只说明当前正式修订与提案基线不同，不改写before。权限更新/沿用摘要使用同一旧修订，当前实现定位另行核对；旧绑定没有独立历史时不构造旧绑定对照。GET不写草稿、Decision或policy_epoch。

### Proposal 与 Human Approval

新 Proposal 与批准事务必须校验资源关系：OWNS 和 SAME_ROLE_OTHER_ACCOUNT 的 subject/owner 必须是相同 Actor revision，OTHER_ROLE 必须是不同 Actor。不要把该校验放进历史 revision 的读取模型而使旧数据无法打开；历史不一致由 Assurance 合同阻断并要求复核。PermissionExpectation 与 BusinessEffectKind 的唯一真源是 `product/backend/domain/boundaries/semantics.py`；旧 Verification 只临时 re-export 同一枚举对象，持久字符串不变。

持续维护读取完整 current 边界，在浏览器内保存 desired state；客户端不指定 write mode。服务端根据稳定 ID、预期 revision 与 boundary state fingerprint 决定 `REFERENCE / APPEND_REVISION / CREATE`、权限沿用、停用和实现重绑。纯 rebind 不改变业务或 Permission revision，也不推进 policy_epoch。

编辑页只保存浏览器内草稿。用户点击“生成待审业务边界”后，服务端冻结 `BoundaryProposalBundle`、来源快照和 `proposal_fingerprint`；待审正文没有 PATCH 入口。返回修改以旧 Proposal 初始化新的本地草稿，最终创建新的 Proposal；放弃形成 `REJECTED` Decision。

批准请求只包含路径中的 `proposal_id`、预期 `proposal_fingerprint` 和原因。服务端重新校验 Proposal 未决定、指纹一致、来源没有漂移且没有 unresolved question，然后在同一 Unit of Work 中提交：

```text
BusinessActor / BusinessAction revisions
+ Actor / Action implementation bindings
+ PermissionIntent revisions
+ ProjectPolicyState
+ APPROVED Decision
```

任何一步失败都不允许留下部分正式事实。前端不能提交 `approved_by` 或审批渠道冒充其他主体。

### policy_epoch

`ProjectPolicyState.policy_epoch` 从 0 开始。批准事务只有实际写入一条或多条新的 `PermissionIntentRevision` 时才推进一次；同一 Proposal 中 carry-forward 三条权限也只推进一次。只有 Actor/Action/Effect revision 而没有权限 revision、纯 Candidate 重新绑定、相同语义重试或读取操作都不推进 epoch。批准事务必须从当前正式状态计算下一 epoch，并通过 revision、`boundary_state_fingerprint`、Proposal fingerprint 与唯一 Decision 约束拒绝并发旧写。

### 候选与Agent入口

候选上下文、保存、提案生成和回执见[规则候选](#规则候选)；连接认证和READ/PREPARE/EXECUTE见[MCP授权](控制面与授权.md)。两者均不能成为正式批准者。

### 官方 recipe 内部资产

`OfficialBoundaryRecipe` 是有限、公开的示例材料，只生成普通 Proposal command，不是业务 Core model，也不自动批准。真实活动 OfficialSampleExperience 可以把固定配方送入普通提案审阅，经 Human Approval 后由用户显式准备；普通项目没有 Sample 专用审批入口，不按项目名称识别 Sample，prepare 不自动创建 Run。

### 提案回看与关联停用

已决定提案保留历史深链，提供返回当前规则列表的独立入口并清除旧提案定位；任务导航只有审阅提案任务携带proposal_id。停用业务对象时，界面列出仍启用的关联权限，必须明确同意后才将这些权限一起加入同一草稿；最终仍经过完整提案批准。不能为了绕过录制或证据缺口停用仍需检查的动作。

## 规则候选

### 修改路线

先读context获得当前正式边界及不透明basis；save验证basis和精确候选修订，保存候选与操作回执；show按修订展示候选和沿用分析；GUI显式propose形成普通提案。之后由[规则与批准](#规则与批准)的唯一决定事务处理，不在候选服务里推进policy_epoch。

范围核对工作面支持用户显式选中多项明确要求并统一确认时间；歧义逐项澄清，全部确认后显示汇总，再显式进入规则核对；未决或失效范围继续阻塞。完整原文、回看决定与候选管理收在辅助入口。规则核对页的“Agent 协助”和“读取候选”放在同一候选区标题栏。协助请求在该区就地展开，原Agent保存后由唯一的读取按钮更新候选；不在页头或展开区重复放读取入口。连接设置返回时保留当前项目和候选修订。

候选列表按当前/已归档分页，返回真实角色、动作、权限、例子计数和现场评估摘要；GUI使用include_preparation=false，不为列表读取计算材料库存。业务信息已保存不等于权限已生效；不完整候选提供补充请求，正式空边界也可先保存CREATE候选。

归档由LOCAL_GUI显式PUT候选visibility，使用候选revision与展示状态expected_version并发校验。rule_candidate_visibility独立保存archived/version，候选修订、提案和批准来源不变；存在任一未决定提案时禁止归档。归档后不可继续修改或转提案，先恢复再处理。写入响应不明时先回读，不自动重发。MCP没有归档或恢复能力。

普通应用首次建立权限时，先说明“Agent 整理 → 读取候选 → 人审阅批准”，人工草稿收在辅助展开项。官方示例明确标注随包提供的权限草稿；源码识别只提供角色与动作线索，不冒充 Agent 整理结果。权限页保留原表格，通过“全部规则／允许／禁止”筛选；按动作查看继续由业务动作视图承担。提案审阅保留原始与拟生效值，筛选仅改变展示，批准仍覆盖整份提案。

来源描述、客户端名称和Agent理由只用于审阅，不等同于认证或事实证明。自然语言模型草稿查[模型服务](控制面与授权.md)，它同样不能代替正式批准。

Agent输入的公开Schema必须包含实际reader的条件约束：DATA_DISCLOSURE要求非空protected_projection，其他效果类型该字段为空。MCP候选报错只给Schema已声明的字段名、有限索引和固定规则说明，不回显输入值、未知字段名或原始异常正文。首次CREATE候选允许正式边界为空；保存不产生正式权限。

资源访问范围的授予、开放与撤回按STATE_MUTATION描述，相应动作标记state_changing；只有实际凭据的获取才用CREDENTIAL_ACCESS。文件交付和访问范围变化分别列为效果。“曾开放又撤回”在当前检查窗口、正确主体资源关联且独立记录完整时可核验，不能降为只检查最终状态，也不能据此承诺任意全历史约束。具体投影字段须从真实业务数据确认。

Agent新保存的候选根为格式6，旧格式1～5仍按各自严格reader读取。格式6在既有范围、补充依据和覆盖记录上增加纠正建议、辅助说明、人工确认的依赖范围及覆盖依赖指纹；不改写旧修订。仍最多10处情境、每处2～4个业务选项，根文档不超过1MiB。客户端不能提交“人已同意”的记录。原话摘录采用NFC与换行规范化后的文本及出现序号，不使用浏览器字符偏移。

不需要替换权限的问题使用“业务边界核对”：GUI 的 `boundary-decisions` 入口接受问题标识、指纹、当前 basis/revision、分类、判断依据及仍保留的实际要求。保存后升级候选根为格式3；后续 Agent 修订由服务端携带决定，输入不接受伪造的人工记录。原问题和限制文字保留，历史修订不改写，旧情境决定继续按原指纹读取。GUI写入沿用本机控制面授权，MCP只有读取和修订候选能力。

“不作为独立动作”仅适用于问题；“已由权限表达”还必须引用本候选现有权限项。这两项不能消除 unsupported_constraints。只有人确认限制确属 Agent 扩大或误解原要求，并写明依据和实际要求时，才结束该限制问题；不能将接受风险当作证明。真实业务规则、执行前提、证据或入口覆盖缺口以及暂不能确定均继续阻塞。409不是权限拒绝；当前窗口过程证据不是任意历史证明；合并动作不证明多个HTTP入口已经分别取证。

旧边界决定未记录依赖时仍绑定整份业务正文与正式依据，失效后明确说明需要一次核对。GUI核对可同时选择关联要求；服务器从要求推导权限、动作、角色及共享权限的其他要求，保存为该次人的决定范围。此后无关变更不使该决定失效，相关定义或范围变化仍失效；Agent只能建议关联，不能修改已确认范围。缺少完整定义时拒绝局部关联，不能猜测自然语言依赖。情境只有在旧修订可读、原决定指纹吻合、唯一摘录与选项相同、完整关联要求和相关实体相同时局部沿用；无法证明时重新确认。覆盖关联独立绑定目标权限、动作和角色定义。相同文字的问题按稳定标识区分；决定、候选新修订与DECIDE回执原子保存，未知响应查原键。

### Agent修正与人的核对

`next_tasks.handler`表示该项决定由谁作出，不是禁止Agent修其他草稿。明确的引用、正常对照、权限例子和用户已保存的纠正先由Agent处理；用户范围与真实歧义随后确认。界面先展示草稿修正交接，后续事项与已确认内容收进回看入口，所有阻塞仍由后端判定。

旧问题或旧限制必须保留原文；Agent在保存命令的`review_suggestions`提交原问题标识、当前指纹、纠正理由、保留要求及可选关联。服务端验证引用并绑定新修订依赖，GUI并列展示原问题与建议，由人显式确认。建议不改变人的决定、不自动解除限制，不用新建候选或归档消除缺口。用户确认真实规则/准备/证据/覆盖缺口后，原有补齐与检查门槛继续执行。

新的源码线索、技术前提和通用能力说明可放入保存命令的`supporting_notes`；它们不是独立权限要求。已有requirement_sources、旧问题和限制仍由原保护规则禁止静默删除，不能移入说明逃避核对。辅助说明按稳定note_id修订，撤回须保留原文并填写withdrawal_reason，历史修订保存提议者和原因。实际要求若遇到能力缺口，仍须明确记录在业务要求与限制中；来源标签不赋予Agent决定权限。

候选开始人工核对后，其中未决范围进入项目的 `boundary_review_gaps`；旧版已有情境决定同样纳入，未完成的情境不能被新入口遗漏。列表包含原问题及返回入口，查询包括归档候选，另建候选不清除旧缺口。检查预览和提交事务均重新核对该范围，真实缺口存在时不创建执行请求，不删除计划Case。本轮不支持部分检查，也不改变既有Run/冻结输入/安全结论格式；旧结果保留当时正式规则范围，不补写为已验证新增要求。真实技术与取证限制不能靠分类确认放行。对于已明确的当前窗口要求，可由人关联具体权限、TARGET入口及证明类型；关联后允许规则审阅，检查预览与提交事务仍逐项核验批准映射、当前Case、真实入口和证明来源。任意历史要求继续阻塞。

GUI的SELECT、CORRECT、DEFER分别保存选择、纠正、待定；明确说明不适用时用DISMISS保存原因。决定追加候选修订，仍由原提案批准才能更新正式权限。Agent不可静默删除未决情境；需要权限替换的旧文字问题先转成同名情境再核对，无需权限替换的问题直接进入业务边界核对。已解决情境移除后，新修订不继承该处人工同意；情境依据变化使原选择失效，冲突选择不能以最后点击覆盖。DECIDE使用独立回执命名空间，未知响应只查原键。

含义核对的未保存选择按候选、情境及指纹保留在当前编辑会话；切页或其他情境保存造成修订变化不清空输入，依据变化则重新选择。页面分别显示已保存数量和未保存修改，离开前保留编辑提醒，不在浏览器持久存储业务草稿。每处仍由人显式保存。批准后提供“继续当前工作”，由 Workspace 决定下一步，不把再次接入新应用作为续接入口。

权限缺少对应 examples 时返回 `PERMISSION_EXAMPLE_REQUIRED`、字段位置和具体权限项标识；合法对照也需要例子。该问题不等于业务含义未决定，不通过新增情境、删除权限或改写原始要求消除。复制补充请求保留这些具体标识。

旧问题修订先读context与不指定revision的show。每条旧unresolved_questions要么原样保留，要么在新情境question中逐字保留（含标点），先保存新修订再由人核对；不要求人在情境尚未保存时寻找确认入口。错误返回旧candidate/revision、全部未映射问题的有限索引、目标字段、精确匹配要求与审阅入口，不回显问题原文。context/show的revision_guidance说明同一流程。unsupported_constraints独立核对，情境选择不建立取证能力，也不消除真实的不支持条件；明确要求、Agent误加限制和证据缺口不能被编造成相反的业务选项。

情境摘录或出现序号不匹配、替换项越界、选项替换集合不一致及重复标识通过固定错误类型指出字段位置；MCP只读取受控整数索引，不输出原话、输入值或任意异常上下文。替换项必须复用候选正文的权限项标识，不因不同选项引用同一权限而判重复。

候选详情说明当前应交给Agent补充还是由人核对；“复制补充请求”携带旧问题原文、字段位置和服务端修订指引。初次深链读取指定修订，显式点击“读取候选”则读取最新头并更新页面引用，避免Agent保存新版本后仍停在旧记录。失败保留原修订与正式权限；人的选择仍须经过完整提案审阅与批准。

候选转提案时冻结内容hash和决定摘要。原批准事务取得写锁后重新核验候选头、basis及来源，再写正式权限和准确item→intent/revision/hash映射；沿用项也保留映射。规则详情与候选详情由此回查，不能用名称或时间推算来源。手工提案继续沿原批准，不伪造候选选择。

规则预览支持APPROVED、PROPOSAL、CANDIDATE三类精确来源；未决或过期候选没有覆盖答案。返回ALLOW、DENY、UNCOVERED、CONFLICT及命中引用，不产生Run或Verdict。GUI将其收在提案和规则详情的可选展开区；MCP只读工具为`jiejian_rule_preview`。

### 失败与验证

同键异文、旧basis、旧revision和边界并发变化均应拒绝，不覆盖新决定。响应未知按project/kind/operation_id查询；找不到回执不能证明未执行。重点核对保存后仍非正式、提案生成不等于批准、重复键幂等、影响预览没有写入。涉及格式再验证严格reader和Schema，涉及MCP再测授权；不为候选展示改动重跑检查执行。

完整事务关系见[批准协作](#批准协作)。

直接验证：`tests/contracts/http/boundaries/test_rule_candidate_decisions.py`、`tests/contracts/http/boundaries/test_candidate_boundary_reviews.py`、`tests/contracts/http/checks/test_checks.py`、`tests/domain/boundaries/test_rule_scenarios.py`与`tests/infrastructure/storage/test_workspace.py`。前端检查`BoundaryReview`、`RuleCandidatesPanel`、`RuleCoveragePreview`及提案/规则详情消费者。

### 范围先行与缺口处理

完整设计与兼容边界见[候选范围与缺口处理设计](#候选范围与缺口处理设计)。Agent可批量同时保存权限与requirement_sources；信息不足时也可先保存范围，不强制两个往返。用户确认本轮范围后才可进入提案。merge=true支持同一候选分批合并；总预算100动作、200权限、1MiB，不能为数量合并检查入口。GUI通过scope-decisions确认来源含义与时间范围，通过coverage-links关联真实缺口。MCP仍无人的决定能力。

CHECK格式5冻结当轮范围，结果不继承后续修订；PLANNED仅表示规则可审阅，不表示检查就绪或通过。next_tasks和复制请求按实际处理者分流，已解决问题只作为约束沿用。

### 集中确认与补充依据

范围决定绑定同一候选内的具体要求原话、来源和解释，不再绑定整份正式规则的依据号。其他规则修订或补齐权限映射不要求重做未改变的范围决定；原话或解释变化、未决定与暂缓项继续阻塞。旧格式决定用其保存时的依据号复算原指纹，历史记录不改写。此处只沿用人对业务要求的判断；候选保存、提案及批准仍核对当前正式依据与精确修订，不自动批准新增或改变的权限。

`scope-batch` 仅由本机 GUI 提交，逐项绑定要求指纹并统一校验 basis、候选修订与操作键；全部成功才追加一个修订和 DECIDE 回执，同键异文拒绝。来源的 USER 标记不代表人工同意：清单默认不选中，用户还须明确核对含义和时间范围。旧单项入口保留。

SUPPORTING 用于将重复说明或源码线索关联到已确认的 IN_SCOPE 要求。它保存原文、判断依据、关联标识及目标决定的语义指纹；不能指向未决、准备或排除项，不能绕过其自身关联权限的完整覆盖。目标的用途、含义、时间或原文变化使关联失效，单改说明理由不制造重复确认。Agent 输入不接受人工决定和关联；既有来源不能静默删除。真正独立的业务要求继续纳入或保留未决，不能以补充依据隐藏。

冻结检查范围只列独立要求，SUPPORTING 的完整记录仍通过精确候选及修订追溯。历史要求、技术能力和真实取证缺口继续阻塞。项目缺口按当前阶段报告：范围未解决时不叠加尚未发生的批准提醒；已有来源但范围未决时不同时重复报告缺少已确认来源。候选列表已展示的行承担处理入口，归档或分页之外的缺口仍保留摘要；检查页只展示紧凑阻塞提示，详情集中处理。

## 候选范围与缺口处理设计

### 要解决的问题

源码发现的接口、用户的业务要求和准备步骤曾混在同一候选。数量限制促使 Agent 合并接口；所有未决限制又统一阻止规则审阅，使明确的规则无法进入准备。改动保留原始要求、人的决定、正式批准和完整检查门禁，不将限制声明当作通过证明。

### 范围先行

Agent 通过原候选保存接口一起整理 requirement_sources 与权限；确实无法整理时可以先保存范围。每项记录稳定标识、标题、来源类别、依据原文、Agent解释及权限映射。USER只是来源声明，不当作已获人同意。明确的草稿错误先由Agent修正，真正未明确的业务含义再交给用户。

用户逐项确认纳入本轮、仅用于准备恢复、不属于本轮或暂不确定，记录实际要求、理由及检查窗口/历史/不涉及时间的范围。全部来源都确认为准备或不属本轮且没有权限时，仅记录范围，无需编造权限或生成空提案；这些记录仍会进入之后的范围快照。只有 GUI 可提交决定。权限及必要正常对照必须关联已确认的本轮要求；准备和排除项不能同时作为有效权限。不静默删除旧来源；纠正保留历史。权限映射补齐不使原话确认失效，原文、解释、来源或正式依据变化则重新确认。

新候选根为格式6；旧1～5保持独立reader。纠正建议、辅助说明及局部依赖的具体合同见修改规则候选。旧记录没有足够依赖证据时保守复核一次，不补造来源与人的同意。

### 分批保存与完整审阅

merge=true按稳定标识合并角色、动作、权限、来源与情境，未提交项保留；例子按权限标识替换，问题与限制去重并保留。原文改变需完整修订。根文档仍限制1MiB，最多100动作、200权限、400例子、100来源；超过预算明确拒绝，不裁切数据。所有批次在同一候选修订链上，最终只形成完整提案。正常对照、关系及引用校验始终保留，不再只在有情境时检查正常对照。

### 问题分工

next_tasks从当前问题产生USER、AGENT、CAPABILITY处理者。补充请求只要求处理当前问题，已解决决定作为约束附带。范围问题无需编造相反选项；材料问题不要求生成情境；未知写回执只查询原键。MCP仍无范围确认、正式批准和来源采用工具。

### 缺口进入检查准备的条件

真实准备、证明或覆盖缺口仍先经原业务边界核对保存。Agent可在coverage_suggestions预填已核对的权限、HTTP目标入口与证明类型；这些建议没有批准效力。用户另行确认该要求对应的候选权限、HTTP目标入口、需要业务结果证明还是过程记录，以及时间范围。关联绑定问题指纹和人工决定修订；原文、业务实体、权限或人工解释变化均使关联失效。

未列全的关联可先保存为DRAFT，继续阻塞。只有人明确确认关联清单完整，且当前窗口关联有效时才为PLANNED，只允许规则进入提案审阅，不等于条件满足；清单或时间修改后需重新确认完整性。HISTORY、未确认业务含义、缺少关联或失效关联继续阻止提案。真实业务规则仍需正确表达，不能用材料关联替代。

检查预览与提交事务从候选批准映射查找精确Permission修订/hash，与当前Case对应，并核对冻结配置中的TARGET请求方式和完整路径段。SETUP不计作覆盖；同一业务动作的两个接口分别列入关联，一份单TARGET录制不能同时满足两个不同路径。需要独立验证时应保留两个可独立准备的动作及相应正常对照，不用标题合并充当覆盖。

PROCESS_RECORD额外要求受保护状态变化效果具有匹配的受控事务记录来源；最终状态快照不能替代过程记录。原计划仍校验账号、资源关联、证明能力、恢复及合法对照，实际执行仍由Worker/Runner完成，最终结论由Verification形成。任意全历史能力未新增，不能将其降为当前窗口。

缺少映射、Case、TARGET或证明时继续阻塞；可准备的缺口提供材料入口。材料失效或正式规则修订变化后实时重新阻塞，没有手工“标为完成”开关。候选归档不隐藏缺口，继续同一候选链修订；本轮不提供跨候选自动承接或自然语言等价消除。

### 范围冻结与结果

CHECK请求新增格式5，保留既有完整计划算法及证据标准，额外冻结已批准候选修订、人的实际要求、范围分类、时间范围与精确权限引用。预览指纹包含范围快照；提交事务重核，不能以旧预览提交新范围。独立reader校验本轮要求确实关联执行Case，排除项不携带已检查权限。旧请求3/4和旧结果不补写新范围。

检查页展示已确认要求及准备/未纳入内容；结果页只读本轮冻结范围，明确未纳入项没有接受独立验证。保持完整检查，不新增删除缺失Case后的部分检查模式。

### 后续验收场景

- 新项目先保存范围，未经GUI确认的接口不得成为可审阅规则；MCP伪造人的决定被严格输入拒绝。
- 同一要求补合法对照，超过10条分批合入同一候选，不丢旧项、不新增相反业务选项。
- 修改原话、时间范围或正式依据时重新确认；补例子、补权限映射沿用仍有效的范围决定。
- 旧1/2/3记录、已有2/2情境决定、归档记录可读；未知回执不重复写，旧revision和同键异文被拒绝。
- 两个不同TARGET入口，遗漏其中之一或只在SETUP出现时阻塞；准备完整后允许提交，撤销来源或更改规则后再次阻塞。
- 当前过程要求需要过程记录；全历史要求仍阻塞；409不能作为权限拒绝。
- 提交前后范围变化、候选并发修订和原始要求遗漏不能绕过门禁；旧结果不继承新范围。
- 页面审阅覆盖范围待确认、已保存、需要重新确认、检查关联待准备、检查阻塞及历史范围摘要，包含窄屏。

## 批准协作

### 正常链

1. 源码分析给出角色/动作实现线索；用户或原Agent提交规则候选，RuleCandidateService保存候选修订和回执。
2. GUI读取候选及当前边界，用户核对业务角色、动作、资源关系、ALLOW/DENY和受保护效果。propose形成普通不可变Proposal，候选没有因此生效。
3. BusinessBoundaryService读取当前业务revision和提案依据，LOCAL_GUI显式批准或放弃。批准事务核对并发、生成必要revision、implementation binding及Decision；出现权限revision变化时更新policy_epoch。
4. Preparation按正式Actor/Action/Permission、真实账号、资源和绑定派生缺口。缺账号或实现binding不能反过来撤销人的权限意图。
5. CheckService重新读取当前正式规则与材料，构建完整当前考题并冻结。Agent、LLM、Recording或结果GET均不能修改正式权限。

### 谁保存什么

| 对象 | 创建/维护者 | 消费者 | 禁止混用 |
| --- | --- | --- | --- |
| 识别Candidate | 应用理解/分析 | implementation inspection与绑定 | 不作为正式Permission身份 |
| RuleCandidate revision/receipt | RuleCandidateService | GUI审阅、候选转提案、MCP读取 | Agent说明不等于批准 |
| Proposal/Decision | 边界服务的提案与决定事务 | 审阅、正式revision追溯 | 展示/复制不能代替决定 |
| 业务revision和policy_epoch | LOCAL_GUI批准事务 | 准备、计划、变化与历史 | 纯实现重绑不冒充语义变化 |
| 技术binding | 用户确认材料与绑定工作流 | 实时inspection、冻结输入 | 账号更换不静默改业务revision |

### 失败与收口

旧候选basis、提案指纹或revision失配时拒绝写入；不能用“合并最新值”悄悄改变用户刚审阅的要求。决定失败保持事务原子性；同一提案不能重复形成不同决定。候选/操作响应未知先查原键与当前提案状态，不直接重发批准。

批准后读取失败与批准事务失败分开，不能因为页面没有刷新就重做决定。旧Permission与Decision保持历史，不能从当前角色名称反推旧Run使用的规则。
