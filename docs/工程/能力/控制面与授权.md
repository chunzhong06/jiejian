# 控制面与授权

本页面向维护者，说明能力协作、持久事实、拒绝边界和恢复方式。用户操作从[文档入口](../../README.md)选择；源码定位查[模块索引](../../参考/模块索引.md)。

## API与装配

### 这是什么

控制面把 GUI、CLI、MCP 和自动化请求翻译为同一 ApplicationCore 调用，再把已形成的产品事实投影给用户。它负责 transport、严格输入、LocalControl/MCP 授权、错误映射、生命周期接线和输出格式，但不负责执行目标请求，也不在路由或工具里重新判断权限安全。

工作台的读取与主任务选择见[工作台指南](#工作台与任务)，MCP授权与工具见[MCP指南](#mcp与授权)。

### 正常修改路线

ApplicationCore 对无环依赖使用构造注入；变化/原题、运行提供方和交付关联使用具名连接方法，最后只检查生产所需连接，不执行回调。MCP 撤权回调在控制器构造时传入，证明准备的授权查询由控制面明确连接。连接整理不得改变原 UoW、关闭顺序或失败后保留资源的条件。

MCP 的工具注册入口仍为 `product/backend/interfaces/http/mcp/server.py`；`mcp/errors.py` 统一分级授权与净化错误，`mcp/transport.py` 处理 Bearer 和 ASGI 挂载，`mcp/views.py` 维护给 Agent 的有限事实投影。修改工具业务先核对原 workflow，不能在投影或传输模块执行事务。

先确定变化属于 transport 还是应用服务。只是新增查询或写入入口时，先在已有 workflow/application service 中确认唯一职责，再让 Router 完成 strict DTO 解析、调用和 envelope 映射。需要 GUI 与 CLI 同时展示的新事实，应先进入共享只读投影，再由两端分别做格式投影；不要先改页面或 CLI 字符串，再回填后端。

本地 API 固定绑定 IPv4 loopback。GUI 根页面取得当前服务进程的 HttpOnly、SameSite=Strict control session；所有 `/api` 请求验证 Host 与 session，写请求再验证精确 Origin。`X-Forwarded-*` 等代理头不能扩大授权。错误必须通过稳定 `ErrorCode`、有界 details 和 trace 映射；异常正文、环境变量和秘密值不能进入响应。

正式业务边界和权限写入只走普通business-boundaries Proposal approve/reject事务，LOCAL_GUI由服务端固定；自然语言permission-drafts只返回有限待审草稿，不写Proposal/Permission。修复、MCP、Runner和结果均不能成为审批者。

当前动作准备、TestIdentity、Recording与CHECK均经ApplicationCore。Job取消将CHECK交给同一CheckService.cancel，Recording仍按正式队列取消。SourceChange/Repair、check-preview及 HTTP 提交格式 2 的 runs 已装配（其持久冻结请求为 ExecutionRequest）；旧preparation writer、ProductStatus和旧结果链不回接。

MCP挂载同一个ApplicationCore，工具、会话、分级授权和恢复由[MCP与授权](#mcp与授权)集中说明。精确注册见[注册参考](../../参考/模块索引.md)。

Machine 输出是 CLI 的稳定自动化表面，成功 envelope 固定为 `schema_version/kind/status/data/next_actions/warnings`，失败增加有界 `error`。默认 Human 只给结论与下一步，只有显式 `--json` 才进入 Machine 模式；两种输出都来自同一产品事实。更完整的关系见控制面与 Machine 输出协议。

退出时HTTP连接排空最多等待5秒，防止Windows连接重置造成底层关闭通知遗漏而无限等待；期限仅覆盖传输层排空，随后仍沿原应用生命周期关闭Worker、运行实例、数据库和专用浏览器，不以强杀替代资源收口。

### 不能破坏

- API 与 CLI 不直接导入 Web adapter、Observer 或 Runner executor；目标流量不能在控制面进程产生。
- Router 不复制 workflow 事务，不自行写 Verdict、Finding、Gate、Readiness 或 ResultPresentation。
- API `schema_version` 描述机器 envelope；嵌套 DTO 不重复根版本，产品版本也不能冒充 Schema 版本。
- 同一 VarDir 只能有一个控制者。已有 GUI/CLI 持有 ServeLock 时，第二个入口必须在创建 ApplicationCore 前失败。
- GET 不产生供应商调用、目标请求或隐式写入；需要副作用的操作使用明确写端点和幂等/确认边界。
- `/health`、`/ready`、系统状态和业务状态各司其职；浏览器自动打开失败不能被解释为服务未 ready。
- MCP 是 Web 产品的控制入口，不是 `MCP_AGENT` Target；高风险动作仍通过共享 Worker/Runner，工具不能旁路检查主链。
- CLI、Machine 与 MCP 都不是权限审批人；不得增加直接修改 ALLOW/DENY、确认/拒绝正式实现映射或降低受保护效果的入口。
- MCP 的 claimed paths 只是有界线索；真实变化、影响分类和重验计划必须由 `SourceChangeService` 形成。读取投影只允许返回授权源码根下的 claimed/added/modified/removed 相对路径，不得返回绝对路径、hash、diff 或正文。

### 失败先查哪里

出现 403 先区分 Host、control session 和 Origin，不要立即放宽 LocalControl。GUI 与 CLI 不一致先比较它们读取的 workflow 投影是否相同，再检查 renderer；不要让两端互相抄输出。服务 ready 但页面打不开，先看 `/ready`、前端入口和浏览器打开诊断，不把三者合成一个错误。第二控制者错误先查 ServeLock 对应 VarDir 和真实持有者，禁止靠删除锁文件绕过仍存活的进程。

### 专属能力的入口合同

普通运行调用[运行加载](应用与运行.md)，补充材料调用[材料服务](材料与恢复.md)，证明预检查与采用调用[来源服务](证明来源.md)。Router只做严格解析、当前入口授权和输出转换；不能复制这些workflow事务。

## MCP与授权

### 协助入口与准确上下文

报告的“交给 Agent 解读”入口复制明确的项目、运行与可选用例引用，供用户带回开发工具；复制本身不发送消息、不创建任务，也不表明客户端已经读取。请求要求先读取指定报告和逐条证据，不使用“最近一次”替代当前记录。

候选与材料建议仍使用各自的有限上下文和严格保存协议。准备建议的依据标识与证明来源依据不同，不能互换；保存结果未知时查询原回执，规则批准、登录、读取范围与采用仍分别经过相应门禁。需要额外能力时，在开发工具中核对项目与授权范围。

### Agent 协作的完整顺序

MCP输入模型在调用业务服务前单独解析；只在该边界报告INPUT_INVALID及安全字段提示。业务服务内部ValidationError报告STORAGE_STATE和诊断编号，不回显异常正文或输入值。GUI内部校验错误同样与RequestValidationError分开，诊断保留产品版本、前端构建身份、受控项目/候选引用及trace_id。MCP的system_status从实际服务目录返回frontend_identity；无法核验时明确UNCONFIRMED。材料页据实际接口原因处理，不以权限为空推断读取失败。

| 阶段 | Agent 做什么 | 界鉴与用户如何接续 |
| --- | --- | --- |
| 权限约定 | 读取上下文，整理角色、动作和允许/禁止要求，保存候选 | 用户审阅完整变更并批准 |
| 材料准备 | 读取当前缺口，保存实际来源候选，在已有授权下执行可用的准备/预检查；不能只重复给出操作建议 | 官方示例使用固定配方一键准备；普通项目集中核对账号、资源、读取位置和文件，再由界鉴顺序检查并采用 |
| 检查执行 | 先 jiejian_check_preview 读取计划；取得 EXECUTE 授权后，携带 expected_plan_fingerprint 提交或查询指定检查 | 人决定是否执行，界鉴保存操作与独立证据 |
| 结果解读 | 读取该 run_id 的结果、索引和具体证据，解释结论与缺口 | 整轮和具体证据入口随当前视图切换，同屏不重复显示两个 Agent 入口 |
| 修复复验 | 读取修复要求；获修改授权后完成代码修改，登记真实差异并核对新实例 | 按原要求检查，保留正常业务对照，将复验结果继续交给 Agent 解读 |

准备页有一个整体协作入口。文件准备内嵌在该页时不再增加第二个入口；独立来源页的入口只处理当前材料。统一上下文使用 jiejian_agent_context，不再提供内置模型短解释。

### 结果交接的读取范围

报告在 `pages/checks/report/Report.tsx` 组织协助对话框。用户核对 MCP 连接后复制请求到原对话，解读既有记录只需要 READ。请求固定 project_id、run_id 及可选 case_id，不使用“最近一次”代替用户正在看的记录。复制成功仅表示剪贴板写入，不显示“已递交”或“Agent 已读取”。

Agent 先调用 `jiejian_result_show`，取得每项 evidence_refs、路径可用/完整状态和 review_url；再调用 `jiejian_evidence_show` 读取索引，以 record_ref 读取具体业务证明和 Trace。两步都核对项目与检查归属，使用同一已发布包。解释包括权限要求、实际账号与资源、执行、观察、结论与缺口，并给出可回看的引用。Trace 不取代独立业务证明。

BLOCK 沿 `jiejian_repair_show` 解释必须消除与保留的结果；INCONCLUSIVE 说明具体缺证；PASS 说明覆盖范围。讨论后获得用户修改授权，再使用已有 task/context、变化登记、运行加载、检查预览和复验流程。结果解读本身不提升权限、不修改应用、不批准业务规则或采用来源，也不自动提交下一轮。

### 三层授权边界

1. 长期配对凭据只保存在精确SecretStore引用，transport逐请求核对Bearer；连接会话ID不代表权限。
2. READ读取有限事实；PREPARE登记变化或候选；EXECUTE提交/取消当前完整检查及获授权的来源预检查。逐项目提升只属于当前控制会话，重启、暂停、旋转/删除凭据和关闭会清除提升。
3. 正式权限批准、证明读取范围、来源采用仍由GUI中人的决定形成。MCP提供context、candidate、preview及GUI去向，不能通过参数旁路人的决定。

精确工具名及注册位置查[注册与格式](../../参考/模块索引.md)。每个新工具先调用已有workflow能力，再处理严格参数、授权和有限输出；不在transport或views复制事务。

### 当前连接状态

`MCPAccessView.connection_state`拥有连接阶段：凭据准备、Bearer已认证和SDK已处理MCP请求各是不同事实。配置被复制或客户端声称保存成功，不能先显示连接成功；最近活动也不证明客户端此刻正在编码。

GUI 先点击“连接 Agent”，再选择 DSH、Codex、ZCode、TRAE、CodeBuddy Code 或 Qoder CLI。`AgentConnections` 为已安装客户端准备本机 stdio 配置，TRAE 使用官方安装链接并保留客户端确认。用户不复制凭据或修改配置；文件格式、配置档歧义、未安装和写入失败必须明确显示。当前客户端共享连接授权，不能宣称按客户端独立撤权。

连接器用绝对 Python 与脚本路径启动，逐请求从 SecretStore 读取原凭据，透明转交当前回环 HTTP MCP 服务；stdout 只写协议。端口和服务代次存入 Windows DPAPI 保护的运行文档，服务重启时刷新。客户端配置只含命令及受保护文档路径，不含凭据，也不依赖 DSH 会清除的敏感环境变量。

再次选择客户端先读取已有配置与回执，不因查看状态重新安装。连接器在每次请求前重读受保护文档，服务代次或地址变化时只重新建立必要的协议会话，再发送尚未提交的业务请求。完成 initialize 后，连接器空闲约5秒发送一次有界协议 ping；服务恢复后可自动重新握手，不依赖模型调用业务工具。stdin 由有界队列读取，探测和客户端请求在同一线程串行发送，内部探测响应不写入客户端 stdout。服务暂时停止或响应中断时保持 stdio 通道，不重放失败的业务请求。客户端已经停止或停用此服务时仍须由用户启用；连接器不会自行启动外部客户端。恢复连接不恢复项目临时提权。

`CONNECTED` 回执表示握手或协议探测已成功，不能冒充已读取工具；新服务代次清除工具计数。连接页约3秒回读状态，连接弹窗约2秒回读回执。配置完成、协议连接、工具读取与业务调用分别反馈，任何一步都不自动提升项目授权。统一 Agent 上下文在生成上下文指纹前先将内部模型转换成 JSON 值，避免规则或材料模型导致序列化异常。

`TOOLS_READ` 只表示客户端实际读取非空工具列表；`REQUEST_ACCEPTED` 表示客户端实际调用工具并取得协议结果，不代表该工具的业务操作成功。两种事实都不保证持续在线。Codex 等客户端首次加载配置的确认说明按客户端分别展示；不能把 DSH 的 profile 指引混入其他客户端。

DSH 写入所选配置档的 `cordis.patch.yml`，以 `insert` 挂载 MCP 插件；只写裸插件 id 不能证明插件已挂载。全局同名覆盖、共享插入块和未知配置格式均保留原文并报告冲突。JSON/TOML 仅替换界鉴条目；原配置以 DPAPI 备份。恢复接口只在当前完整文件仍与安装回执一致时恢复，避免覆盖后来改动。

ZCode 连接配置由对应适配器选择已支持的协议模式；配置不匹配时显示 `CONFIG_UPDATE_REQUIRED`。更新需要用户显式执行，状态读取不会写入配置。客户端的协议行为可能变化，应使用当前客户端和适配器的直接测试核验，不能把旧机器观察作为长期版本保证。

DSH 连接器对 `server/discover` 返回方法不存在，使客户端自动使用已实现的 `initialize` 请求/响应协议。当前桥不支持新版长期 `subscriptions/listen` 流，不能广告该能力后等待整个订阅响应结束。DSH 工具定义展开本地引用，将可证明互斥的 nullable 联合转成 `oneOf`；其不支持的标量约束写入说明，同时连接器保留完整原始 Schema，在每次调用前验证，服务端仍执行原业务和授权校验。未知或不能安全转换的定义拒绝交付，不删除校验来让工具注册通过。

新 DSH 配置保留插件生命周期并启用有界退避重试；已有自定义重试参数保留。旧的首次失败即退出策略由状态接口返回 `CONFIG_UPDATE_REQUIRED`，用户点击“更新连接配置”后沿用原凭据更新界鉴条目，并在 DSH 确认重载。状态查询本身不写配置。默认最多重试 10 次、间隔上限 30 秒；超过重试预算后需在 DSH 重载。已建立的连接遇到界鉴重启时重新握手，失败的业务调用不自动重放。

本机连接回执附带失败阶段和耗时；连接超时、响应超时、服务不可达、管道关闭、工具定义不兼容分别记录。阶段字段的默认值兼容同版本旧回执；它们不包含请求正文、凭据或第三方异常原文。

配置准备、等待客户端确认、连接器启动、实际读取工具是不同事实。只有连接器回执中的真实 `tools/list` 非空结果才能显示“客户端已读取工具”；空工具、认证拒绝、会话过期、服务不可达和受控凭据不可读分别说明。历史活动不保证持续在线。界面回执未知时只读状态，不重复写配置。客户端确认/重载与逐项目授权仍由用户决定；具体客户端安装联调证据另行记录。

### 失败先查哪里

- 认证失败：transport与SecretStore精确引用；日志/异常不可回显输入令牌。
- 工具能列出但操作被拒绝：当前项目及权限级别、客户端会话、实际工具required level。
- 保存或登记响应未知：回读原领域operation receipt；MCP净化输出不能改变幂等身份或自动重放。
- 撤权后预检查未结束：authority回调、proof job_authorized、持久取消和Runner清理分别核对。
- 字段泄漏或结果失真：先核对原reader，再查views/public_preparation；不把隐藏字段删改传播回内部权威模型。

### 验证与深入

授权变化覆盖READ/PREPARE/EXECUTE、错误项目、撤权、暂停、重启与输入额外字段拒绝；纯投影变化测字段边界和对应业务reader。改变传输会话才补SDK/ASGI直接集成，不调用真实付费模型。装配见[API与装配](#api与装配)，生命周期见[启动与退出协作](#启动与退出协作)，公开格式见[控制面协议](#控制面与machine输出契约)。

### 持久材料批次

jiejian_preparation_batch_plan与status为READ；cancel要求EXECUTE。GUI确认后由后台自动推进，不开放MCP批准入口。批次保存精确来源修订、配置摘要、依据和读取授权引用；未知步骤只查原回执，撤权或重启后回GUI重新核对。

## 工作台与任务

### 对象怎样协作

`ApplicationCore` 创建Workspace及它需要的明确reader。`WorkspaceService.get`读取项目/应用理解和正式边界，先得到边界任务，再读取Preparation。边界尚需处理时不进入准备任务选择；只有相应分支需要时才计算检查preview。

检查reader提供活动检查、变化、修复和最近结果；development reader提供任务、交付、运行与精确验证关联。`tasks.py`依据传入事实选择任务，`presentation.py`生成展示和引用，最终返回 `WorkspaceView`。整个读取流程不持久化页面READY或PrimaryTask。

### 一处容易读错的优先关系

`development_task`不是把所有已有任务无条件保留：当正式边界无需关注、没有活动检查，而交付运行还未加载时，会选择加载该交付。这是现有明确分支。若已有准备任务跳往tests且没有change/run，它会保留该交付的change_id，避免准备返回后变成无关联的普通检查。

因此修改优先级必须读真实分支及测试，不能仅依据“权限→准备→检查”的概括文字自行重排。`CheckPreviewRequired`只是纯选择层请求补充所需事实的标识，不是持久任务状态。

### 修改边界

- `service.py`协调读什么与什么时候读；`reading.py`持有读取依赖；`tasks.py`不能接Repository或访问目标；`presentation.py`不能重判Verification。
- 准备齐备、检查可执行、运行已加载、检查结束和原题已修复分别取其权威服务；缺字段或reader失败不按成功补默认值。
- `project_id/action_id/change_id/run_id/repair`等引用保持精确；改task_id指纹须核对续接与前端陈旧响应行为。
- 只改任务文案时检查同类页面表达与相应组件；只有改变任务优先级或可执行性，才进入workflow相关测试。

| 改动/症状 | 直接测试或首查 |
| --- | --- |
| 准备任务次序 | `tests/application/workspace/test_preparation_tasks.py` |
| 原题/变化/活动Run相互覆盖 | `tests/application/workspace/test_repair_task.py` |

## Agent上下文

### 当前入口

统一上下文由 `application/agent_access/workflow.py` 提供，HTTP为 `/api/projects/{project_id}/agent-context`，MCP为 `jiejian_agent_context`。规则、材料、录制、结果与修复使用精确项目和记录引用；页面复用 `协助对话框`。复制只表示请求已复制，不表示送达或处理完成。

材料批次由 `application/preparation/batches.py` 管理。用户在GUI确认固定清单；MCP只能读取计划、查询批次和在EXECUTE权限下停止批次。后台自动续行已批准步骤，无需Agent反复发送授权或采用命令。重启、撤回读取授权或依据变化后暂停后续步骤，回到GUI重新核对。

开始检查前先调用 `jiejian_check_preview`；`jiejian_check_run` 必须携带读到的 `expected_plan_fingerprint`。改变权限、源码或材料后旧指纹不能提交另一份检查。结果由界鉴形成，Agent只解释；修复仍须用户授权，不降低原规则。

### 修改边界

协作服务只交接有限事实。录制去除query、fragment、请求正文与资源实际路径值；结果固定到run/case。秘密不进入协作请求、普通数据库或日志。MCP不能代人批准规则、确认读取范围或扩大已确认材料计划。

详细授权见修改MCP与授权，材料步骤见[修改证明来源](证明来源.md)。

## 启动与退出协作

### 装配与调用

1. start.cmd及受控脚本准备环境与前端资源，serve先核对解释器、运行目录与单控制者锁，再创建ApplicationCore。
2. ApplicationCore显式创建UoW、业务服务和基础设施。无环依赖构造注入；运行provider、变化/原题、交付等使用具名连接，最终validate_connections只校验接线，不执行目标回调。
3. FastAPI挂载当前router及同实例MCP。GUI用本机control session/Origin，MCP用独立Bearer与逐项目权限，CLI只提供当前系统操作。所有业务写入进入对应workflow。
4. CHECK、RECORDING、PROOF_PREFLIGHT经通用Worker分支执行；Node运行加载由专用Runtime Worker持有目标；身份准备有独立受控浏览器进程。各自复用进程树和最小注入边界，不能混为一个任务生命周期。
5. Workspace、History、系统状态读取事实。只读系统状态不代表所有业务已接受，也不能由GUI本地状态替代后端事实。
6. 关闭按当前实现先确认受控录制、身份准备、Worker/运行监督等资源退出，再清理短期秘密与释放数据库资源。失败时保留责任与异常链，未确认进程退出前保留共享资源。

### 状态与所有权

| 资源 | 创建/所有者 | 读取/使用者 | 退出责任 |
| --- | --- | --- | --- |
| ServeLock与owner token | 当前serve进程 | Worker存活监督、第二实例检查 | 原持有者释放；旧文件不能证明锁仍有效 |
| UoW/Engine | ApplicationCore或WorkerContainer各自创建 | 本进程工作流/Repository | 各组合根确认依赖停止后close |
| MCP配对与项目提升 | agent_access与GUI决定 | transport及每个工具 | 暂停/撤权/重启/关闭清除临时提升 |
| 目标进程树 | 对应Supervisor/Worker | 当前执行者与恢复逻辑 | 只清理已证明归属的树，不接管用户进程 |
| 前端页面状态 | app/shared与具体feature | 用户交互 | 写后回读、陈旧响应隔离；不新增持久业务状态 |

### 失败路径

第二个控制者在创建核心服务前失败；不能共用同VarDir并行写。Worker bootstrap失败先核对是否已claim，采用对应条件事务。失去服务owner token触发持久取消并清理受控树。启动UI动画失败可以降低展示，不覆盖真实ready结果。维护预览、清理运行数据与用户数据重置是不同操作，不因为目录看起来临时就删除。

## 控制面与Machine输出契约

### 先理解：多个入口只有一套产品状态

界鉴可以从 GUI、CLI 或自动化脚本进入，但这些入口不能各自维护业务进度。当前 GUI 状态由 `WorkspaceService` 从 Project、ApplicationUnderstanding、正式 Business Boundary、Permission、pending Proposal、实时 implementation inspection 与 PreparationView 形成；当前检查与结果由 CheckService、严格发布 Reader 和 ResultStory 提供，SourceChange/ProjectRepair 负责真实变化与原题复验。

```text
ApplicationCore / Published facts
  → WorkspaceView / BusinessBoundaryView / ResultStory / ProjectRepair
  → loopback API envelope → GUI
  → CLI Human / Machine v1
  → MCP Streamable HTTP → 固定工具白名单
  → 当前 Evidence publication（只读已发布事实）
```

页面文案、终端颜色或 JSON 格式都不能反向改变事实。Report 是独立不可变交付物，也不由 CLI stdout 代替。

### WorkspaceView 与 GUI

使用独立 `WorkspaceView` 作为 GUI 唯一工作区 DTO。它包含当前项目与连接、Actor/Action 动作级视图、current Permission、实时 implementation inspection、四个长期区域，以及服务端按固定优先级选出的唯一 `PrimaryTask`。稳定 task ID 与 stale fingerprint 由服务端事实生成；前端不得重算优先级、binding currentness 或权限状态。

Business Boundary API 位于 `/api/projects/{project_id}/business-boundaries`。无正式边界时，`preview` 与首次 Proposal create 建立稳定 identity；已有边界后，普通 create 返回 `BOUNDARY_MAINTENANCE_REQUIRED`，客户端改用 `maintenance-draft` 和唯一 `maintenance-proposals` desired-state 写入口。客户端不提交 `write_mode`，服务端用 `boundary_state_fingerprint` 校验并发后自动形成 CREATE/REFERENCE/APPEND Proposal；Proposal 列表/读取/批准/拒绝继续复用，Approve body 只含预期 `proposal_fingerprint` 与 reason，审批身份和渠道固定为 `LOCAL_GUI`。没有 official recipe 普通路由、PATCH Proposal、旧 matrix cell writer 或自动 approve；应用候选决定不属于权限批准。current 响应只含精确匹配当前 ACTIVE Actor/Action revision 与 Effect catalog 的 latest ACTIVE Permission；历史 revision 仍由历史读取入口保存。

GUI 通过固定 loopback API 读取 envelope。当前工作区入口只有 `GET /api/projects/{project_id}/workspace`，旧 `/status` 返回 404。API 成功 envelope 使用根 `schema_version="1"` 与 `data`；异常由稳定 error code、trace 和有界 details 映射。API envelope 版本描述控制面机器格式，不是产品版本。

当前准备和权限由 PreparationService 与 BusinessBoundaryService 提供；旧 ProductStatus、Delivery 和 History 服务已移除，保留的旧准备/矩阵类型不构成当前写入口。

当前 GUI 与 projects API 不提供独立交付检查入口；Workspace 不产生交付结论。

### 应用候选批量决定

`PUT /api/projects/{project_id}/candidate-decisions` 复用 application-understanding 格式，命令根版本为 1，携带 understanding revision 和 1 至 256 个不重复候选决定。嵌套决定仅包含种类、候选引用、显示名称与决定，不另设版本。服务端先检查所有项，再在同一事务保存并只推进一次 revision；未知、重复、失效或非法候选使整批失败。MANUAL 候选不能转成系统 PROPOSED。成功后只更新理解与既有绑定刷新，不创建或批准权限。

回执不明先读当前理解，匹配新 revision 与全部决定才展示保存事实；旧 revision 不自动重放。Workspace journey 是嵌套只读位置投影，复用唯一 PrimaryTask，不建立任务表或新的裁判逻辑。首次存在有效待审候选且没有正式边界、未同时确认权限组和动作时，发布 REVIEW_APPLICATION_CANDIDATES。

### 当前 CHECK 历史与执行路径

`GET /api/projects/{project_id}/check-history` 只读当前 CHECK，保留原 `/runs` 列表契约。默认 limit 25、最大 50；query 最长 128，trim 后大小写不敏感的字面子串匹配 run_id 和已验证冻结动作名，可按 verdict/lifecycle 筛选。成对 cursor 使用 created_at_us 降序与 run_id 升序的严格 keyset，项目条件在 SQL 中限制；每次最多校验 250 条候选，返回最后实际扫描键之后的继续位置，只有后面仍有候选才提供 cursor。因此空 items 加非空 cursor 合法，不提供 total 或跨请求快照保证。INVALID 不使用数据库 Verdict、未知标签或上下文冒充已发布事实；NOT_PUBLISHED 原义保持。精确 DTO 由 `application/checks/reading/results.py` 和自动代码参考维护。

`ActionResultStory.execution_path` 是同 Case 的只读嵌套投影，不写回发布包，不携带 schema_version。没有非空 Trace 或多个 Trace 冲突时为 null；相同 Trace 保留一份完整拓扑图，partial/空 partial 的 complete/reasons 原样保持。全部最多 512 个节点与显式 parent_event_ids 逐项复制，不按时间补边；文档引用只包含实际承载该 Trace 的 CheckEvidence ID，保序去重，不混用事件的其他来源引用。节点不包含时间、凭据、authority scope、semantic_key 或原始正文；字段真源为 `application/checks/reading/story.py`。完整性错误仍传播，不能以空图吞错。

Workspace 的 active_check 只表示本项目最新 QUEUED/RUNNING，终态后为空不代表 PASS；source_change.submitted_by 直接复制登记来源。三个一级入口、会话保留、结果通知和局部证据区的详细消费职责见[交互与视觉](../前端/交互与动效.md)。这些读取不改变 PrimaryTask、修复合同或安全结论，也不恢复旧 History/Report writer。

### CLI Human 与 Machine

CLI 默认输出人类可读结果；`--json` 是唯一显式 Machine 模式。两种模式不会在同一个 stdout 中混写。`--var-dir` 只保留给源码启动、开发脚本和 Portable 的内部运行时接线，不出现在普通 help 或 README 中。

Human 先给结论、关键事实与下一步，隐藏内部 ID、reason code 和复杂结构。需要完整稳定结构时使用 Machine v1；诊断环境问题时使用 `system doctor`。Machine v1 成功对象固定包含：

```text
schema_version
kind
status
data
next_actions
warnings
```

失败对象使用 `kind=error` 并增加有界 `error`，其中保存稳定 `error_code`、trace、恢复建议和允许的结构化 details。Machine stdout 必须只有一个 JSON 对象；stderr 不混入 INFO、traceback 或人类提示。结构化脱敏日志单独进入当前 VarDir 的 logs。

CLI `--version` 直接输出 `product.backend.__version__` 并退出，它是产品版本查询，不使用 Machine envelope，也不创建 ApplicationCore。

CLI 与 Machine 输出是控制和投影通道，不是审批人。公开命令树不提供 PermissionIntent ALLOW/DENY 写入，也不提供角色/动作候选的确认、拒绝或手工创建；自动化只能准备既有事实、执行已冻结操作或读取结果。

普通命令当前只公开 `serve`、产品版本与 `system doctor/repair/clean`。`status`、`application`、`change`、`check`、`result` 和 `history` 在当前 暂不公开；Business Boundary 创建与 Proposal 决定只在 GUI/loopback Human API 完成，Agent 自动化不能取得审批能力。

### MCP Streamable HTTP 与工具输出

MCP精确挂载同一loopback FastAPI的/mcp，由官方SDK提供Streamable HTTP，不创建第二个ApplicationCore或端口。当前通用Worker支持CHECK、RECORDING、PROOF_PREFLIGHT，运行加载使用专用Worker，System/ready/MCP投影同一真实存活与能力事实；只有Worker running不能证明Plan可执行。长期Bearer只经精确SecretStore保存，启动恢复READ。

GUI 读取的 `MCPAccessView` 明确区分凭据与连接：`DISABLED → CREDENTIAL_READY → AUTHENTICATED → CONNECTED` 是正常建立过程，认证失败投影为 `CREDENTIAL_REJECTED`，人工暂停投影为 `PAUSED`。`last_authenticated_at_us` 只证明 Bearer 通过，`last_seen_at_us` 才代表 SDK 已成功处理的客户端活动；状态页面不能把凭据生成、配置复制或客户端自报当成连接成功。恢复、轮换、暂停和 shutdown 都清除旧活动与逐 Project 提升，避免上一客户端或上一 serve 冒充当前连接。

MCP工具按SDK返回structured content，不套API/CLI envelope；仅独立持久根有schema_version。当前提供有界事实、SourceChange和完整Check提交/取消，不开放Proposal决定、权限writer或任意执行。

长期配对只恢复READ，逐项目临时授权和人的确认边界见[MCP指南](#mcp与授权)。工具注册从[生成参考](../../参考/模块索引.md)查；未声明参数拒绝，不提供任意HTTP/shell、权限审批或自选检查范围。

### ResultStory 与 Evidence

当前 ResultStory 从严格发布 Reader 读取冻结请求、Case 结果、证据和 Breakpoint，组织权限要求、实际身份、表面响应、真实业务结果、定位和原题复验。它只解释已有事实，不重新运行 Verification，也不让模型补写结论或定位。

ExecutionTrace 提供同 Run 的派发、授权和真实业务效果因果；只有已确认禁止效果的 Case 才进入 Breakpoint，缺少中间来源只降低定位精度。原题要求从已发布 BLOCK 重建，复验状态读取精确关联的 NEW Run，不能用最新普通结果冒充修复。

API evidence index 只返回已发布索引；完整 Evidence detail 是另一资源，索引与文档不能逐字比较。独立报告格式和保留的 ResultPresentation 底层实现不接入当前检查入口。格式投影边界见[报告与格式投影协议](../协议与持久化.md)。

### LocalControl 与 ServeLock

loopback 不等于自动可信。API 先校验实际 Host；GUI 根页面取得当前服务进程签发的 HttpOnly、SameSite=Strict control session；全部 `/api` 请求要求该会话，写请求再要求 Origin 与控制面 origin 完全一致。MCP 使用独立 Bearer 与 SDK Host/Origin 防护。代理头不能改变授权 Host，测试 header 不能变成生产旁路。

GUI serve 与会创建 ApplicationCore 的 CLI 命令共享 `ServeLock`。同一 VarDir 已有控制者时，第二入口在创建 ApplicationCore 前返回 `WORKSPACE_ALREADY_CONTROLLED`。锁文件是所有权记录，不是 daemon 或 IPC；持有者仍存活时不能靠删除文件绕过，进程正常/异常退出后必须可重新获取。

### 状态、错误与长时过程

控制面显示的状态必须来源明确：当前 Workspace/PrimaryTask 是动作工作区事实，Job/Run 表示生命周期，Runner progress 是非权威展示旁路，ResultStory 只投影经校验的发布结果。Workspace 的活动检查与最近结果摘要必须来自当前 Reader，不能从进度推算安全结论。

发生错误时先保留第一主错误及 trace，再执行正式 cleanup。cleanup warning 单独展示，不覆盖 primary failure。安全 BLOCK/INCONCLUSIVE 不是控制面执行错误，不能被 ErrorRecovery 当作异常页面。

### 版本边界

### 普通来源准备工具

MCP EXECUTE 授权代次绑定每次预检查；降权、暂停、轮换、忘记和控制进程重启使旧任务失效。重新授权不会复活旧 Job。写操作按原操作标识回读；来源修订采用 CAS。

## 控制面与装配

### 当前入口

工作台唯一状态入口为 `/api/projects/{project_id}/workspace`。`WorkspaceService` 组合 Project、ApplicationUnderstanding、当前 Business Boundary、Permission、implementation inspection 与 PreparationView，输出动作级事实和唯一 `PrimaryTask`。`/permissions` 支持首次建立与 desired-state 持续维护，变更摘要由服务端生成。`AppShell` 在 `/tests` 装配 CurrentTestsPage，准备区域仍由 Preparation 消费唯一 Workspace task。材料写入后先刷新局部事实与 Workspace；服务端预览允许后，用户显式提交完整检查，再读取 ResultStory 与已发布证据。`/changes` 登记声明并展示真实源码差异、原题修复和精确复验入口。

### 组件与边界

- `start.cmd` 是源码仓库的一键产品入口：准备或复用项目专用 Conda `jiejian_env`，由受控 uv 按 `uv.lock` frozen 同步并 editable 指向当前仓库；普通启动不安装或运行 Wheel。
- `scripts/dev.ps1` 是源码运行环境的唯一准备入口，提供 bootstrap、sync、update、prepare、start、cli、test、frontend-test、schema、shell 和独立可选的 package；只有 update 可以修改 `uv.lock`，只有 `schema -Update` 可以更新签入的公共 Schema，package 不参与普通启动。`dev.ps1 start` 只薄转发到 `start.ps1 -Mode Gui`，不自行准备后直接调用 `serve`。
- 前端准备、Node/pnpm、构建缓存和开发工作区只属于源码开发环境，不属于产品控制面；完整规则见[修改开发环境](../开发.md)。
- Web GUI 以工作台为唯一主控入口，变化、权限、测试保留既有导航层级。权限区域承载业务边界写流程，检查准备区域承载身份登录与录制动作。首次建立后可从完整 current 边界调整 Actor、Action、Effect、Permission 与实现线索；前端不传 `write_mode`，服务端规划变更并冻结 Proposal，再由用户查看摘要并批准或拒绝。
- 当前确定性下一步由 `WorkspaceService`、动作准备 inspection 由 `PreparationService` 提供。旧 Guidance/ErrorDiagnosis 及八类旧 AI surface 为 dormant 算法，未注册旧 result/error API。当前三类受限 Assistant 只解释服务端短事实，不能改变准备要求、权限或技术绑定。
- CLI 当前只公开 `serve`、产品版本和系统诊断/维护；应用、变化、检查、结果、历史与 status 命令在当前 暂不公开。Human、Machine JSON 与内部日志互不混用。CLI 不提供 Business Boundary、PermissionIntent 或 Proposal 决定写入。
- API 是固定 `127.0.0.1` 的资源与控制面，负责严格解析、授权、ApplicationCore 调用和脱敏错误映射。所有 HTTP 请求先匹配实际 `Host`；GUI 根页面取得只属于当前服务进程的 HttpOnly、SameSite=Strict control session Cookie，全部 `/api` 请求验证该会话，写请求再要求 `Origin` 与实际界鉴 origin 完全一致。业务边界审批只接受路径中的 `proposal_id`、预期 `proposal_fingerprint` 和原因；审批主体与渠道由服务端固定为 `LOCAL_GUI`，并在同一事务中提交 revision、binding、permission、decision 与 epoch。
- 当前 ApplicationCore 不装配旧 `ProjectPreparationService`，也不注册 `/api/projects/{project_id}/preparation/prepare-safe`。不得重新接回 Candidate、Permission Matrix 或 ActionSafetySetup 链。当前 GET `/api/projects/{project_id}/preparation` 直接调用 `PreparationService.get`；动作级下一步只由 `WorkspaceService` 决定。
- 当前代码变化由 `application/changes/service.py` 的唯一inspection核对源码/权限/映射，ProjectRepair只读组合原题、精确变化与NEW Run；Workspace包含变化、修复和当前结果摘要，不重新计算安全结论或保存页面状态。
- 旧 ProjectRevalidation 与 Delivery Check 不属于当前产品入口；当前 ProjectRepair 只读原题合同和精确关联的已发布复验事实，不回接旧权限表。
- MCP 是同一 FastAPI 进程中精确挂载的 `/mcp` Streamable HTTP 控制入口，复用同一 ApplicationCore 与 shutdown 链，不监听第二个端口，也不单独装配 Worker。首次配对生成的独立 Bearer 只经 SecretStore 精确引用长期保存；以后启动自动恢复 READ。GUI Cookie 和模型 Key 均无效。当前 MCP 提供固定只读工具；GUI 对当前项目临时提升后，PREPARE 可登记变化声明，EXECUTE 可提交或取消完整检查。任何 level 都不能 approve/reject、直接修改权限预期、候选审批状态或自选重验范围。
- 当前 `ResultStory` 消费已发布结果与 Evidence，`ExecutionTrace` 为通用 Breakpoint 提供因果事实；二者不根据页面或事件顺序重算 Verdict。旧 ResultPresentation 不属于当前产品入口。
- API 内部路径统一为 `/api`。当前产品通过状态读取与取消接口管理 CHECK；独立 Job SSE 路由未挂载。其 reader 使用持久事件序号恢复，断开后停止轮询，不能据文件存在声明产品已经开放。
- 应用接入、源码分析、身份、Recording、权限准备和结果解释沿唯一主路径推进，详细边界见[应用接入与检查主流程](../../产品/检查与复验.md#如何理解结论)。
- GUI、CLI 和 API 复用 ApplicationCore。当前通用Worker装配CHECK、RECORDING、PROOF_PREFLIGHT；运行加载使用专用Worker，检查后端通过 preview/submit/status/result-story/evidence API 接入，目标请求进入独立 Runner；前端通过同一控制面提供显式检查、结果、变化登记与原题复验。
- “运行环境”页与 CLI 复用同一 `LocalMaintenanceService`。它按明确类别预览可回收的旧构建、下载与构建缓存、历史日志和运行临时文件；预览形成当前实例内短期有效的固定 `MaintenancePlan`，确认按固定计划和所选条目逐项执行，单项占用、变化或失败不会丢失其他结果。应用、权限配置、数据库、Evidence、报告、凭据、当前会话日志、活跃运行目录、进程锁、当前开发工具、测试活动目录和被引用的官方示例数据受保护。启动后的有界孤儿与日志保留维护失败只进入诊断，不反向撤销已经成立的 ready。

### 关键数据流

```text
start.cmd
  → loopback 服务
  → GUI / CLI / Machine / MCP
  → API、CLI 或 MCP 调用 ApplicationCore
  → Project / ApplicationUnderstanding / Business Boundary / Proposal
  → GUI形成人工业务决定；MCP按项目临时READ/PREPARE/EXECUTE读取事实、登记变化与提交完整检查，不能审批权限

CHECK 与 Recording Worker 均接入服务生命周期；当前 CheckResultReader/CheckStoryBuilder 只读已发布事实，不装配旧 Report/Repair writer。
```

应用接入、业务边界、身份、Recording、动作准备与当前 CHECK的边界统一见[应用接入与检查主流程](../../产品/检查与复验.md#如何理解结论)。控制面只暴露该主流程已有的 ApplicationCore 操作，不建立第二套业务或内部配置入口。

### Windows 启动交互

- 启动准备保持六个有序阶段及其缓存、诊断、迁移、Chromium 和前端构建语义。默认无参数启动在准备完成后直接进入 GUI，不等待方向键或 Enter 选择；`-Mode Cli` 与 `-Mode Prepare` 仍为显式入口。只有主动指定 `-Mode Interactive` 才显示模式菜单。
- `RuntimePaths` 只拥有当前产品 `VarDir` 的 `data`、`runtime`、`cache`、`logs`、`temp` 和 `test`。数据库、项目及保留的 Job/Evidence/报告事实进入 `data`；当前实例前端副本、官方体验与锁进入 `runtime`。Worker 路径由各自的受控Supervisor 使用，状态取本轮实际线程。普通产品缓存只保留 `cache/assistant`；源码开发依赖、工具和构建缓存全部位于 `var/development`，按本地存储计划的明确类别清理，始终保护当前在用构建和产品数据。
- 启动器必须核对受控解释器与关键依赖身份，来源漂移时停止并给出恢复建议；当前 CHECK/RECORDING Worker 与独立 Runner 必须继承同一受控身份。具体 Python、前端工具链和 Playwright 准备规则见[修改开发环境](../开发.md)。
- 图形界面继续进入 `serve --open`。工作台只展示 `WorkspaceView` 中的当前应用、连接状态、唯一 `PrimaryTask`、动作级权限/实现摘要和长期区域状态；不读取 dormant Run 或 Result 伪造最近结果，也不保存线性进度。普通命令行进入仅对当前子进程生效的 PowerShell，调用已解析的 Python 绝对路径并继承当前 `VarDir`。
- readiness 的唯一真源是 Python 对 `/ready` 的精确响应校验：HTTP 200、根版本 1 且 `status=ready`。软等待阈值只产生一次“仍在准备”事件并继续等待，不能被解释为服务已启动或浏览器失败；serve 在 ready 前退出则产生独立启动失败事件。只有 ready 成立后才尝试打开系统浏览器，并分别报告“网页已打开”或“服务已 ready、浏览器未打开”。PowerShell 只展示 Python 产生的稳定状态事件，不自行猜测 readiness。
- 服务 ready 后启动动画立即结束，终端明确提示网页退出入口与 `Ctrl+C`，并继续持有服务生命周期。GUI 的“退出界鉴”复用当前 control session 与精确同源 Origin 触发同一 shutdown 链，不保留静态魔法控制头；正常退出依次停止 Worker、受控 Runner/浏览器和 ApplicationCore。系统浏览器页面属于用户进程，不被强制关闭，页面只提示服务已停止后可关闭。
- ready 前装配 ApplicationCore、MCP/control及通用Worker、运行加载监督生命周期。/ready 不把配置或对象存在视为线程存活；后台维护失败只记录错误，不冒充 Worker 失败或成功。退出先有界停止受控任务和 Supervisor，任一独立进程停止失败时保留共享凭据、数据库和运行目录，确认停止后再释放共享资源。
- 自动化调用可显式指定 GUI、CLI 或 Prepare；省略模式时同样进入 GUI。直接调用 `scripts/start.ps1` 时保持可组合的退出码并立即返回。`start.cmd` 对 PowerShell 的任意非零退出统一保留原始退出码，并在阶段、错误码、主错误、日志和恢复建议输出后等待用户关闭窗口；该兜底也覆盖参数解析和模块加载失败。

### CLI Human / Machine 输出通道

- 当前 CLI 只公开 `serve`、产品版本和系统诊断/维护，没有 `status` 或工作台命令；Human/Machine 只投影这些已注册命令，不提供旧状态、检查、报告或历史命令。
- 官方环境入口使用普通 Project/BusinessBoundary/Recording/Preparation 与 CHECK 事实。环境面板仅启动、重置、停止或切换中性条件；项目精确匹配时，可在普通权限页采用已提供提案并 Human Approval，在普通 Preparation 采用材料。分析统一进入普通验证、ResultStory/Evidence、Changes/Repair，不能保存预期 Verdict 或 Sample 专属安全判断。
- Human stdout 只呈现结论、关键事实和下一步，不显示内部 ID、原因代码与复杂结构。完整稳定结构使用 `--json`；环境诊断使用 `system doctor`。Machine v1 成功固定为 `schema_version/kind/status/data/next_actions/warnings`，失败另含有界 `error`；stderr 不混入 JSON、INFO 或 traceback。脱敏结构化日志写入 `VarDir/logs/jiejian.log`。
- `serve` 与所有准备创建 ApplicationCore 的普通 CLI 命令复用同一 VarDir 系统锁；同一运行目录已有 GUI 或 CLI 控制者时返回 `WORKSPACE_ALREADY_CONTROLLED`，不会创建第二个 ApplicationCore，也不通过 daemon、IPC 或本机 HTTP 绕过。

### 当前业务边界主流程

当前主流程是接入应用、确认或持续维护业务边界，并从 WorkspaceView 获得动作级待办。普通权限、准备缺口、显式验证与已发布结果、变化登记及原题复验共享同一控制面；官方提供的提案/材料只是可选输入，不形成第二套审批或结果链。完整边界见[应用接入与检查主流程](../../产品/检查与复验.md#如何理解结论)。产品文案默认中文，机器字段和路径保留原文。

### 关键不变量

- API、GUI 和 CLI 不直接创建 Engine、UnitOfWork、RequestStore 或 Dispatcher。
- API/GUI 不直接向目标发高风险请求。
- `127.0.0.1` 控制面与目标执行进程隔离；监听 loopback 不能替代 Host、会话和写请求 Origin 校验。
- MCP Bearer 的 SecretStore 引用、逐 Project 临时提权和 SDK Host/Origin 防护不能由 GUI Cookie、Provider Key 或代理头替代；普通状态不能返回 Bearer 正文，工具白名单不能暴露秘密、源码、请求正文、完整日志、完整 Evidence、shell 或任意 HTTP。
- Agent 变化声明只能携带项目、原因与有界相对路径线索；控制面不得接受 Git 命令、文件正文、diff、权限 ID、Case ID、Effect ID 或 Profile 选择。变化感知的 prepare/run 只接受服务端已经形成的 `change_id`。
- 用户可见状态不替代机器结果；INCONCLUSIVE 不得显示为安全通过，HTTP 拒绝也不得替代真实状态观察。
- 启动失败、浏览器未打开、运行环境不可用和检查无法开始都应给出可恢复、脱敏的提示。
- 普通用户错误固定展示失败阶段、原因、任务标识、日志位置和下一步，并提供可复制文本；内部堆栈只进入有界脱敏日志。

### 失败语义

启动准备、浏览器、数据库、前端、API 输入、项目识别、Contract/Profile、目标地址或运行环境失败时，入口停止当前动作并保留可诊断日志。控制面断开不等于执行成功或失败；事件序号用于恢复读取。

### 安全约束

默认只监听 `127.0.0.1`。控制会话令牌使用 256-bit 随机源且只驻留当前服务内存与 HttpOnly Cookie；MCP 使用另一份至少 256-bit 的长期配对 Bearer，其正文只经 `cred:jiejian/mcp-control/pairing` 进入 SecretStore。两者不能互相替代，MCP Bearer 不写数据库、日志、报告或项目，普通 API 也不返回正文。Onboarding 的识别预算、目标范围、身份、写操作、reset、重定向、私网和请求预算必须显式确认或由执行边界校验。共享 SecretStore 只允许严格命名空间下的精确引用操作；测试账号的 Cookie/Token 正文只进入 Windows Credential Manager，API、数据库、项目文件、协议、日志、Evidence 和报告均不出现正文或可枚举秘密。

Serve 把本次实际、已规范化的控制面 origin 注入 ApplicationCore。应用地址确认在网络探测和持久化前拒绝该 origin；Web Target Guard 在保留的目标请求边界再次拒绝，防止历史冻结配置或绕过控制面的输入让界鉴检查自身。Worker/Runner 只能通过固定最小环境继承该 origin；CLI 未启动 Serve 时没有保留 origin，不使用固定端口猜测控制面地址。

### 兼容与版本

当前产品入口只服务 Web Target。CLI 的产品命令以实际 help 和启动输出为准；公共 JSON/Schema 版本不是产品代际。`/mcp` 只是当前 Web 产品的控制 ingress，生产 Target 协议仍不保留未实现的 CLI_APPLICATION 或 MCP_AGENT。旧启动模式、旧参数位置和旧路由 alias 不兼容保留。
