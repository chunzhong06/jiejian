# 账号与录制

本页面向维护者，说明能力协作、持久事实、拒绝边界和恢复方式。用户操作从[文档入口](../../README.md)选择；源码定位查[模块索引](../../参考/模块索引.md)。

## 录制

### 这是什么

Recording 把“用户在已登录网页里完成一次真实业务动作”转换为可审阅的 `FlowDraft`。它不是浏览器宏录制器，也不会把登录、导航和偶然请求自动宣布为安全测试流程。提交服务只接受正式 BusinessAction ID/revision 和当前合法 ALLOW 指定的 subject/owner TestIdentity 与对应 slot；服务端解析 endpoint、目标范围和非秘密身份元数据，独立 Worker 再启动独立 Recording Process 与有头 Chromium。

持久 Recording 生命周期、Job 生命周期和 capture 控制阶段是三套不同事实。`STARTING/RECORDING/PROCESSING/PENDING_REVIEW` 表达业务对象状态；Job 表达调度与执行；`capture_phase` 从当前 attempt 的 ready/start/started/stop 标记投影。FlowDraft 只在正式 Recording result 经 `RecordingSubmission.consume_result → FlowDraftProcessor` 后形成。

### 正常修改路线

先画清变化发生在哪一层：浏览器采集边界、Recording application service、FlowDraft 审阅，还是最终 Flow 编译。浏览器层只收集有界脱敏事件和控制标记；workflow 层拥有状态机与幂等；协议层拥有严格根文档；页面只展示权威状态并发出明确开始、停止和审阅命令。

正式 capture 顺序必须保持：Recording Process 发布 `capture.ready`，控制面写入 start，进程确认 `capture.started`，状态进入采集中后才允许业务动作；用户停止后写入 stop，Runner 收口事件与浏览器，Job 成功，Recording 进入 `PENDING_REVIEW`。取消仍走 Job cancel，不得把停止实现为取消。

Recording 应根据录制顺序自动采用唯一且可执行的业务解释；只有多个同级业务解释并存时，页面才让用户在业务动作、有限资源值或来源步骤之间选择。编译后的 Flow 仍保留必要 SETUP 与唯一 TARGET，通过 `CASE_SUBJECT`、`CASE_RESOURCE_ID` 在运行时注入差分事实，但 HTTP method、path 位置、JSONPath、step ID 和 candidate ID 不进入普通审阅。业务资源、真实结果、独立观察和恢复方式在安全准备中形成；权限要求只能由 Human Approval 改变，不能塞回 Recording 或 Flow。

`PreparationBindingService.inspect()` 按当前 Action、实现、endpoint、身份、Recording/Draft 与 Flow 指纹检查四类技术绑定；`PreparationService` 将其与 Assurance 身份和资源需求现场组合。格式 3 的 RecordingRunnerRequest、FlowDraft 与 Flow 绑定精确 business_action_id/action_revision、subject_test_identity_id 与 resource_owner_test_identity_id，不接受旧 action_candidate_id。TARGET 最终化保存唯一 Flow 和当前 owner 的资源；OBSERVATION 开始前指定已有 effect_id，补录继承同动作、同版本、同 subject/owner 的已完成 TARGET；RECOVERY 只用于改变状态的动作。唯一候选按确定性规则采用，歧义仍需审阅，不通过 HTTP method 猜测业务结果。

录制 create/status/capture/review/finalize/discard API 复用当前 ApplicationCore。GET detail 的 supplement_choices 只投影准备服务已经筛选的 OBSERVATION/RECOVERY 待审候选，返回 step_id 和最多160字符的已有业务标签；TARGET、非待审或无草稿时为空。前端只消费该列表，不按 HTTP method 另筛；选择仍经 CONFIRM_TARGET_STEP 与最终化候选校验。POST `/api/jobs/{job_id}/cancel` 只允许 Recording Job，RUN 必须在请求取消前拒绝。Assistant 的 recording-review 必须指定 recording_id，只解释已有 step/resource；它不能生成请求或修改 TARGET、技术绑定。

用户可通过严格格式1的 POST `/api/recordings/{recording_id}/discard` 明确放弃待审草稿。服务在同一UoW内确认关联Job存在、属于该录制且没有run_id、已经SUCCEEDED/FAILED/CANCELLED，才沿现有转换进入CANCELLED；重复放弃幂等。COMPLETED、活动或错关联Job拒绝；录制、草稿、事件、Flow和已有绑定均保留，不改变Job终态、不触发浏览器或秘密清理。活跃录制继续使用原Job取消与fencing退出路径。

页面在最终 Flow 或安全准备事实保存成功后，先刷新 Recording 本地事实，再刷新项目工作区；底部“继续准备”只按这次工作区刷新返回的准备投影续接。Recording 生命周期轮询只更新本页状态，不能在每个 tick 刷新整个工作区。工作区同步失败不回滚已经成立的保存结果，但必须显示可恢复提示。

新录制必须匹配当前完整 ALLOW 和已准备槽位；异 owner 需要 resource_owner_confirmed=true。认证 session 仍使用自身 test_identity_id，且只能等于 subject。旧格式 2 请求、草稿和 Flow 由明确历史 reader 校验原始 canonical/hash 后只读投影 subject=owner，原文件和 draft_json 不改写；新 Worker 输入只接受格式 3。

### 不能破坏

- 登录和页面检查阶段不采集事件；秘密正文、Cookie、Bearer、storage state 和浏览器 profile 不进入协议、日志或 Git。
- 普通 Recording 必须经过正式 API、Worker、独立 Recording Process 和 `BrowserRecordingAdapter`；测试 `controlled_runner` 只服务 L1～L4，不得进入自动 L5。
- start/stop 标记必须绑定当前 recording/job/attempt，原子写入、严格解析且不携带用户输入或秘密。
- Recording 失败先保存主错误，再执行 stop/cancel/进程回收；cleanup issue 不能覆盖 primary failure。
- 普通应用和测试不得直接构造 RecordingEvent、FlowDraft 或调用 processor 伪造成功；不通过测试专用 API、环境变量或 CDP 暴露浏览器控制面。官方样例只能按[官方示例与整链验收](应用与运行.md)冻结的例外，把受控确定性轨迹送入正式 Recording 提交、Job attempt、结果消费与生命周期服务，仍不得直写 Storage。
- FlowDraft revision 冲突、目标范围漂移或回放校验失败必须停止，不猜测兼容。

### 失败先查哪里

停在 `STARTING` 时先区分浏览器未启动、尚未 ready、start 未发布和 started 未确认，不直接改数据库。Job 已终态而 Recording 仍在活动态，检查 result consume 与正式 reconciliation。事件为空时先确认业务动作是否发生在 `capture.started` 之后，再查 collector 预算和脱敏；不要用直接 HTTP 请求补事件。FlowDraft 缺失时沿 `Runner result → submission consume → processor` 顺序查，不从页面重建草稿。

### 当前固定录制事务

受控官方配方通过submit_captured复用正式提交事务：创建、claim、消费和持久完成共用一个UoW，只有真实时钟和单次attempt；普通浏览器路径不变。稳定key先读持久状态，重建Installer可继续PENDING_REVIEW，不重消费已接受结果；回滚不留下半个Job或Recording。TARGET/OBSERVATION/RECOVERY和双身份、具体资源继续严格绑定，秘密只在运行时注入。

### 普通应用文件录制与故障恢复

普通业务录制允许已授权范围内、带完整 Content-Length 且不超过 target_scope.max_response_bytes 的文件响应。无长度、超限、流式、压缩编码和越界重定向仍拒绝。文件先由有界传输完整接收，再将真实响应记为单个 RESPONSE：保留脱敏头、实际字节数和内容摘要，body 为空；摘要仅解释演示，不用作参照文件、Evidence 或 Verdict。下载导航不保证 requestfinished，所以文件响应由 route 接收点记录，并防止回调重复。原始字节只交隔离浏览器内存，accept_downloads=False 防止写入用户下载目录。

文件开关只由业务 Recording 采集层开启；登录准备复用的传输默认继续拒绝下载。目标返回401时保留登录状态未被接受的原因，进入失败恢复，不等待整个录制期限。SSE、长度或编码等具体原因随原有安全停止语义保存；等待开始和正在采集均及时观察安全停止。请求已发出后的失败不意味着目标已回滚，重录前必须核对现场并按既有授权恢复。

普通应用主线保持：确认地址与登录账号 → 在正确资源上开始录制 → 实际执行并停止 → 审阅并保存 Flow → 独立准备参照/记录与恢复 → 原完整计划检查。创建动作的响应对象按下节识别；无可用响应时保留缺口，不改为准备步骤。文件能力不通过固定样例轨迹或 Agent 伪造事件开放。

验证需覆盖真实 fetch 文件及附件导航、二进制不落盘、响应缺失、截断、超限、越界重定向、认证失败、准备期与采集期隔离、重复回调，以及正常下载后的 Flow 与参照检查。界面契约关注失败记录的恢复、创建对象缺口、重新登录、提案返回和显式关联停用；静态截图不能证明这些操作实际成立。

### 创建后出现对象编号

已批准动作包含 OBJECT_CREATION 且会改变状态时，处理器从同一真实目标请求的完整成功响应中列出 JSON 编号字段和同源 Location 指向的对象。创建含义来自正式业务结果，不按 HTTP method 猜测。失败、202、截断、秘密字段、容器、越界地址不形成响应对象候选；多个候选保留歧义。页面由人确认新对象，最终化再次从原事件读取值，不信任标签或自填编号。

含响应候选的 FlowDraft 使用格式4；最终选择响应对象时生成格式4 Flow。TARGET 保持原请求，输出 created_resource_id 提取器，不向创建请求注入演示时的对象编号。演示对象用于保存 ActionResourceBinding 及后续补录来源。仍使用请求对象的旧流程保持格式3，格式2历史 reader 不变。目标后页面刷新才使用的变量不再阻塞 TARGET 保存。

旧待审录制可以显式执行 REFRESH_RESOURCE_CANDIDATES，携带 expected_revision；Lifecycle 校验持久录制、当前授权/业务来源后复用原事件，只追加草稿修订。不重发创建操作、不改写旧草稿、不清除仍有效的其他确认。过期并发请求拒绝；页面刷新后再决定。

动态新建对象的正式 CHECK 使用已采用的独立创建来源：见[证明来源](证明来源.md)。Case 保留录制样本引用，运行格式7冻结输出选择器，证据格式3保存本次实际对象。执行前读取完整集合基线；请求后用宿主关联的创建记录取证，再按已确认恢复模板处理本次对象并核对集合恢复。只读GET、201或响应编号不足以替代创建历史；缺少来源时仍阻塞，原权限和合法对照不变。

直接用例位于 `tests/infrastructure/recording/test_created_resources.py` 和 `tests/infrastructure/execution/test_creation_check.py`：覆盖浏览器创建响应、人工选择、编译与绑定，以及独立创建归因、创建后删除、未闭合窗口、冒用旧编号、并发和编号复用。

## 测试账号

### 这是什么

测试账号是绑定项目和正式 `(actor_id, actor_revision)` 的产品资产。它说明“用哪个已确认业务主体准备会话”，不是角色 Candidate、Contract Subject、运行时 Cookie jar，也不是密码保管器。用户在独立有头浏览器中自行登录；只有明确确认保存后，受控进程才把当前目标所需的有限 Cookie 或单一 Bearer 写入共享 SecretStore，并把非秘密引用交回 ApplicationCore。可以在没有任何 TestIdentity 时先建立或维护 Business Boundary 与 Permission v2；账号只属于后续执行准备。

账号元数据存数据库，秘密正文存 Windows Credential Manager 等受控 SecretStore，短期准备请求与结果走严格协议。Recording/Runner 只按冻结请求解析所需引用并最小注入；API、日志、Evidence、报告和普通数据库字段都看不到秘密值。

### 正常修改路线

先区分账号元数据、秘密存储、浏览器准备、运行时注入和展示。新增状态或动作时从 TestIdentity service 的事务和协议状态机开始；浏览器进程只负责用户登录、目标 scope 校验和有限状态归约；SecretStore 只提供按引用写入/读取/删除；页面只显示账号是否已准备和可恢复动作。

动作准备按确定性 IdentityRequirement slot 选择真实账号，只能为已经存在的正式 BusinessActor revision 创建记录；不得从 role Candidate、名称相似或旧矩阵补猜 Actor。自动创建的空记录仍是未准备状态，不能把权限已确认解释成账号已登录或检查可运行。

当前登录控制由 POST `/api/test-identities/{identity_id}/preparations`、GET `/api/identity-preparations/{preparation_id}`、POST 同地址的 `/confirm` 与 `/cancel` 调用唯一 IdentityPreparationManager。三个 POST 仅接受严格 schema_version='1'，沿用 Host/session 与写请求 Origin 门禁。开始和提交前都核对当前项目、ACTIVE Actor revision、确认 endpoint、源码来源和本次账号状态；过期结果不能提交。

TestIdentity 页面只有一个可见刷新入口。创建、删除、准备成功以及 PREPARED 轮询命中后，先重读账号列表，再调用工作区刷新；底部“继续准备”只能使用该刷新返回的最新准备投影。后台轮询的普通 tick 不刷新整个工作区；工作区同步失败要保留已经完成的账号操作，并给出明确的重试提示。

Cookie 路径最多保存当前目标 host 的 32 个 Cookie，每项只回传名称、域、路径、过期等非秘密元数据和独立 `secret_ref`。Bearer 只允许当前 origin 的单一引用。两者同时存在、多个 Bearer、跨 scope 状态或无法安全归约时 fail closed，并引导高级配置；不能为了“更好用”保存完整 storage state、localStorage 或密码。

准备进程在写入秘密前原子记录 `secret-refs.json` journal。正常提交后删除；进程或服务异常退出时，ApplicationCore 依据已提交 TestIdentity 引用做精确补偿，不枚举全部 Credential Manager，也不靠 PID 猜测是否有效。Manager 先确认进程树释放再消费 stdout，清理失败保留原控制器、active 目录与 journal，不能提前删除运行材料或关闭引擎。

### 不能破坏

- 密码永不保存；Cookie/Token 正文不经 stdout、API、数据库、日志、异常、Evidence 或报告。
- `secret_ref` 不是秘密值，但也只在受控协议和冻结执行输入中传播，不能展示给普通用户。
- 登录阶段不采集 RecordingEvent；身份准备浏览器与 Recording 浏览器是不同进程和生命周期。
- 缺少某个业务主体账号只形成后续 coverage/representative gap，不能阻止或改写已确认 ALLOW/DENY。
- 正式 actor revision 变化时旧账号不可继续冒充 CURRENT；Candidate、endpoint 或源码理解变化不能自动改写业务主体，重新准备也不会复活旧冻结请求。
- Windows Credential Manager 的持久化和当前交互用户身份边界不能因自动测试环境而放宽。

### 失败先查哪里

账号显示未准备先查 TestIdentity revision 与已提交引用，不直接查看秘密正文。保存失败先区分 target scope、Cookie/Bearer 归约、SecretStore 写入和 result 关联；cleanup 问题看 journal 是否仍在。真实 Windows 只在 Codex 沙箱失败而交互用户成功时，应归类为用户会话/凭据上下文边界，不改产品持久化常量或把秘密降级到文件。

## 录制与Flow契约

### 目的与消费者

Recording Runner、GUI/CLI 录制入口、FlowDraft 审阅、动作 Flow 编译和后续回放工作流共享本协议族。录制资产不是 PermissionContract，也不是可直接执行的 Profile。

### 先理解：录制的是业务动作，不是登录过程

用户先选择正式 BusinessAction revision 和已准备 TestIdentity，独立 Recording Process 恢复会话并打开 headed Chromium。页面准备与登录检查阶段不采集；只有 `capture.ready → start → started` 完整成立后，用户执行的真实业务按钮才进入 `RecordingEvent`。停止后正式结果被 ApplicationCore 消费，才形成可审阅 FlowDraft。

FlowDraft 仍只是候选业务流程。唯一且可执行的 TARGET 与资源可以确定性采用，存在歧义时由用户审阅；最终 Flow 保留必要 SETUP、变量和资源位置。OBSERVATION 开始前必须绑定已有 BusinessEffect，RECOVERY 只为改变状态的动作形成恢复模板；录制不创建 Effect 或 ALLOW/DENY。

### 协议边界

- 普通 Recording create 请求只提交正式 `business_action_id + action_revision`、完整 ALLOW 指定的 `subject_test_identity_id`、`resource_owner_test_identity_id`、两者 slot ID 与必要的 owner 确认、时长、purpose、必要 parent/effect 与幂等键；服务端从 ApplicationUnderstanding 和 TestIdentity 解析 endpoint、动作与非秘密身份元数据。GUI 不传 Profile/path、目标范围、SecretStore 引用或 headless 开关。
- `RecordingRunnerRequest` 绑定正式业务动作版本、身份、准备来源指纹、目标范围、预算和单一短期 session 描述。目标授权必须与已确认 endpoint 一致，超时、请求数和响应字节预算只能收紧。session 只包含 Cookie/Bearer 的 `env:` 引用与非秘密元数据；秘密正文只进入本次 Worker/Recording Runner 最小环境和内存中的独立 BrowserContext。
- Recording result 表达一次录制的状态、错误、清理结果与已脱敏事件；不回传登录状态或秘密引用。
- `RecordingEvent` 保存稳定序号、关联标识、事件类型、身份和有界脱敏摘要。
- `FlowDraft` 绑定正式业务动作版本与身份，保存步骤、变量、TARGET/资源推荐与明确确认、revision 和审阅状态；每条 review command 产生新的 revision。
- 审阅通过后，FlowDraft 编译为当前 Flow：只保留唯一 TARGET 与其必要 SETUP，通过 `CASE_SUBJECT` 与 `CASE_RESOURCE_ID` 延迟注入运行时主体和资源。Flow 不保存 alternate identity/resource、ALLOW/DENY、Observer 或 reset 默认；后续确定性编译仍进入普通 ExecutionWorkflow，不建立并行执行链。

### 生命周期与数据流

```text
已确认 action + 已准备 TestIdentity
  → 服务端生成短期 session/env refs
  → 独立 identity 有头 BrowserContext 恢复认证
  → 登录准备与页面检查（不采集）
  → 明确开始 → RecordingEvent（限长、脱敏）
  → 明确停止
  → FlowDraft revision
  → 明确确认唯一 TARGET、有限资源位置和必要变量
  → action-centered Flow（SETUP + TARGET）
  → 后续受控配置编译、执行快照和回放
```

### 失败与安全语义

TargetScope、身份、协议、主机、端口、私网、重定向、响应大小、有界文件响应、SSE、长连接和清理均受限制。写盘前必须脱敏；原始 Cookie、Authorization、storage state、trace 和秘密不发布。审阅缺失、revision 冲突、编译失败或回放重验证失败时停止。

### 控制与状态投影

- 持久 Recording 状态不增加新枚举：`STARTING` 表示准备浏览器或等待开始，`RECORDING` 表示正在采集，停止成功后进入 `PROCESSING` 和 `PENDING_REVIEW`。
- 状态读取可以附加由当前 attempt 控制事实推导的 `capture_phase`，稳定区分准备、等待开始、开始中、采集、停止中与结束；它是控制面投影，不是 Verification Verdict，也不写入 Recording 状态约束。
- 开始与停止端点只控制当前 attempt。开始前不产生 `RecordingEvent`；停止保留事件并生成草稿；取消仍使用 Job cancel，并形成 `CANCELLED`，不得把停止实现为取消。
- ready/start/stop 控制标记不携带秘密或用户输入，必须限定在当前 attempt、原子写入并严格校验录制、Job 与 attempt 关联。

### 版本规则与 Schema 真源

`RecordingRunnerRequest` 的根 `schema_version` 为字符串3。原请求资源模式的 `FlowDraft` 与 `Flow` 保持格式3；含响应对象候选的 `FlowDraft` 及采用响应对象的 `Flow` 使用格式4。`RecordingEvent`、`RecordingRunnerResult` 与审阅命令仍为字符串1。只升级发生不兼容变化的独立根，不按产品版本机械同步。模型、required 和 strict parsing 以：

- `product/protocols/recording/events.py`
- `product/protocols/recording/flow_draft.py`
- `product/protocols/recording/recording_flow.py`
- `product/protocols/schemas/recording/`

为准。版本号只表示机器格式。

格式 2 仅由 recording_legacy.py 的明确历史 reader 读取：先验证原始 canonical/hash，再内存投影 subject=owner；不得重写历史字节或以 v3 投影 hash 替代原 hash。当前 Worker 只接收格式 3。RecordingSessionRef.test_identity_id 保留认证会话自身语义，且必须匹配 subject，不能恢复 owner 会话冒充操作人。

## 测试身份准备契约

### 先理解：账号记录不保存登录秘密

TestIdentity 只把项目、正式 BusinessActor 的稳定 ID/revision、endpoint、认证方式和准备状态连接起来。用户在独立 headed BrowserContext 中登录后，Cookie/Token 正文由准备进程直接写入 SecretStore；控制面只接收非秘密元数据与 `secret_ref`。因此数据库中“账号已准备”不等于数据库持有密码或 Cookie。

Recording/Runner 只解析冻结请求需要的精确引用并最小注入。缺账号形成执行代表 gap，不改变 PermissionIntent；秘密写入失败则准备失败，不能把正文降级保存到文件或 API。

### 消费者与生命周期

`IdentityPreparationManager` 生成格式 1 的 `IdentityPreparationRequest`，冻结 preparation、project、TestIdentity 与已确认 `WebTargetScope`。开始及提交前核验同一当前 ACTIVE BusinessActor revision、endpoint、源码来源与账号状态；不从 Candidate 猜主体，也不让账号重置后的旧结果提交。受控身份准备进程只读取一次请求，在独立 headed BrowserContext 中等待用户登录；控制面通过固定 ready/save/cancel 标记表达显式意图，不把密码或页面输入写入协议。

控制 API 为 POST `/api/test-identities/{identity_id}/preparations`、GET `/api/identity-preparations/{preparation_id}` 及 POST 同地址的 `/confirm`、`/cancel`。写请求严格接收格式 1，认证仍由统一 LocalControl 执行；页面状态不能代替 Manager 来源校验。

用户确认保存后，进程返回格式 1 的 `IdentityPreparationResult`。PREPARED 只允许 COOKIE_SESSION 或 BEARER：Cookie 最多 32 个且每项只返回非秘密元数据和独立 `secret_ref`；Bearer 只返回一个引用。UNSUPPORTED、CANCELLED 和 FAILED 不携带登录状态，FAILED 必须提供稳定错误码。

### 安全与恢复

请求只能包含已确认 target 的 origin、host、port、超时、请求数和响应字节预算。浏览器逐跳重新授权，拒绝跨 scope 重定向、WebSocket、下载、流式/压缩未知响应和越界私网访问。Cookie/Token 正文由身份准备进程直接写入共享 SecretStore，不经过 stdout、API、数据库或日志。

写入前先在 `var/runtime/identity-preparations/<preparation_id>/secret-refs.json` 原子记录精确引用计划。正常提交后删除该 journal；进程或服务异常退出时，下次 `ApplicationCore` 启动按 TestIdentity 当前已提交引用判定并精确补偿，不枚举 Credential Manager，不用 PID 或遗留文件判断秘密有效性。诊断日志只保存异常类型、稳定错误码或 OS 错误号，不保存异常正文。

### 失败语义

未知版本、额外字段、ID 关联不一致、消息超预算、混合 Cookie/Bearer、超过 32 个 Cookie、多个 Bearer、无可安全归约状态或 SecretStore 写入失败均 fail closed。身份准备失败不会生成 RecordingEvent、Permission 结论或 Verification 事实；删除/补偿失败保留 journal 或 TestIdentity 元数据供后续重试。

删除账号时先在未提交事务内执行数据库删除检查，数据库约束拒绝不能提前清除登录秘密；秘密清理成功后才提交，清理失败保留元数据供重试。Recording 和动作技术绑定保留录制时的身份 ID 作为历史来源，不用账号外键阻止删除或级联删除历史；新写入必须验证真实身份，账号删除后现场准备检查返回缺失或失效，历史不能继续充当可执行准备。
