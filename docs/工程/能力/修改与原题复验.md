# 修改与原题复验

本页面向维护者，说明能力协作、持久事实、拒绝边界和恢复方式。用户操作从[文档入口](../../README.md)选择；源码定位查[模块索引](../../参考/模块索引.md)。

## 变化登记与交付

### 修改与直接验证

默认客户端先读取 registration-preview，再用稳定 operation_id 调用 register；GUI 无需手工建立任务。一次登记事务与旧接口兼容边界见[一次登记与可靠回执](#一次登记与可靠回执)。直接回归包括 `test_development.py`、`test_current_mcp.py` 与 `product/frontend/src/pages/checks/report/Report.test.tsx`。

先沿真实链定位：扫描前权限/理解 → 重扫源码 → 同一事务登记 manifest/diff/assessment → inspection → 带精确 change_id 的检查 → publication → 修复与工作台只读投影。

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 test tests/application/changes/test_current_source_changes.py tests/application/checks/test_project_repair_states.py
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 frontend-test src/pages/checks/report/Report.test.tsx src/app/Navigation.test.tsx
```

命令为相关邻域示例，按上表选择真实受影响文件。跨页丢引用时先测“准备 → 返回 → 显式提交”；不要修改后端标准来接受普通 Run。修改 Verification / 公共合同再按[验证规范](../测试.md)选择范围。

### 必须保持

- Agent 的 claimed_paths、理由、Git 和 mtime 不是安全事实；实际差异由授权根内两份服务端内容快照产生，最多接受 128 条相对路径线索。
- 变化登记不审批权限、不自动重绑、不推进 policy_epoch；扫描时发生权限变化则拒绝登记，不回滚人的并发审批。
- 影响分析不裁剪完整当前考题；普通提交和带 change_id 的提交均重新核对 live 源码。
- 原题必须来自本项目已发布 BLOCK / VULNERABLE Case；NEW Run 冻结精确 change 和 repair context。原规则、身份、资源、证明标准及正常能力不能降低。
- VERIFIED 只从两份完整 publication 派生；Agent 声明、关闭功能、改权限或未关联 PASS 均不能替代。
- 回执 RECORDED 只证明登记完成；不要求用户为同批 MCP 交付重复登记。GET 与刷新不创建检查。
- 源码对应只能说明受控扫描范围，不证明目标部署版本。MCP 不输出绝对路径、源码正文、原始 Evidence/Trace、Git 身份或秘密。

### 检查与当前改动的归属

普通检查和复验都继承工作台明确指向 `/tests` 的 `change_id`，提交后固定本轮上下文。源码改动主入口只显示改动列表；修复详情由显式修复参数选择，并提供返回入口。不能凭当前待办静默替换用户打开的页面。

历史检查缺少 `change_context` 时，不补写批次归属。reader 可按同项目、同源码指纹、同权限版本且晚于登记时间找到完整性有效的检查，单独返回 `same_source_run_id` 作为查看线索；`run_id`、安全结论和精确交付关联保持原有事实。GUI 区分“本批尚未关联检查”和“同版源码已检查，未绑定本批”。

## 变化与原题复验契约

### 事实与权限边界

Agent 提交修改理由、至多128条相对 `claimed_paths` 和可选 `CurrentRepairReference`。路径仅为线索：界鉴在已授权源码根内重新扫描，用两份服务端快照的内容hash计算真实增删改。Git、mtime和Agent声明都不是安全事实。密码、Cookie、Token和源码正文不进入变化公共投影。

Actor、Action、Effect、Permission与正式实现映射仍由普通Human Approval批准。变化提交不调用旧 `refresh_bindings`，不自动重绑、不推进 `policy_epoch`，不允许客户端选择Permission、Case或Effect。

### 影响与现场重验

`DIRECTLY_AFFECTED`只表示真实变化与当前Action、subject/owner Actor实现路径相交；`NO_DIRECT_EVIDENCE`不是安全结论。缺基线、绑定失效或映射不可靠形成`MAPPING_REVIEW_REQUIRED`。影响列表准确记录受影响动作，冻结的`required_intent_ids`保守包含全部当前Permission；完整Plan永不裁剪。

Inspection仅有`READY / NO_BASELINE / SOURCE_STALE / POLICY_STALE / MAPPING_REVIEW_REQUIRED`，准备缺口另行结构化保留。所有Check提交，包括不带change_id的普通提交，都在提交前及事务内重新核对live源码；陈旧preview或后续磁盘变化不能绕过。

### 原题修复

引用由`source_run_id/source_case_id/64位repair_fingerprint`构成，必须指向本项目已发布BLOCK中的VULNERABLE Case。服务端从不可变包重建完整合同，不接受客户端合同正文。冻结原Permission集合与epoch、subject/owner真实身份、具体资源、全部禁止效果、选定ALLOW控制和原Run全部实际SAFE的ALLOW_REGRESSION。

superset控制与完整回归分别保留；历史SAFE回归可以为空，但NEW控制仍必须SAFE。路径匹配排除新source/config/Flow等技术标识，保留全部业务身份；每条VERDICT_REQUIRED的完整Observer/HTTP模板、独立观察身份、descriptor、scope/phase/closure/budget等标准必须严格相同，不能降低标准。

NEW Run必须不同于source，并冻结精确change及repair context。权限变化为STALE；可信原禁止效果仍存在为NOT_VERIFIED；路径、归因、观察、控制或完整当前Run不足为INCONCLUSIVE；只有所有原题要求和完整当前Run都成立才VERIFIED。普通未关联PASS不能冒充修复。验证是两份publication的只读派生，不建可变修复结论表。

ProjectRepair按最早BLOCK建立问题族，取最新精确关联变化与NEW Run。状态为`REPAIR_REQUIRED / CHANGE_SUBMITTED / READY_TO_VERIFY / VERIFIED / NOT_VERIFIED / INCONCLUSIVE / STALE`；没有问题时为null。Workspace保留接入、边界、重绑、准备的优先级，再选择登记变化、复验原题、运行当前检查或查看结果，携带精确change_id/run_id。

### 一次登记与可靠回执

默认 GUI 使用只读 `GET /api/projects/{project_id}/source-changes/registration-preview`，MCP 使用 READ 工具 `jiejian_change_registration_preview`。预览返回已批准权限数量、epoch 与登记指纹，不创建任务或扫描源码。写入使用 schema 1 的 `POST /api/projects/{project_id}/source-changes/register`，或 PREPARE 工具 `jiejian_change_register`：传 `operation_id`、`expected_registration_fingerprint`、可选说明、路径线索和精确原题引用，不要求客户端提供 task/context/version。

登记先核对授权、已保存源码起点与正式权限；事务外进行受控扫描，写锁内再次核对预览指纹。没有活动技术上下文时创建最小上下文；已有上下文复用；已批准权限变化时追加新上下文修订，保留历史。上下文、真实变化、交付和 DELIVER 回执同事务提交；失败整体回滚。它不伪造 ACCEPT 回执、不自动批准权限、不执行检查、不加载运行实例。

相同操作键与相同请求先返回原回执，不再次扫描；同键不同内容拒绝。回执不明先按原键查询，查询无回执后只允许显式重试同键同内容；服务端仍核对范围与内容。GUI 会话仅保留操作定位和范围指纹，不持久保存说明正文或凭据。重载后恢复登记需重新填写原内容；旧 schema 2 登记和明确 task/context 的 `change_submit` 继续兼容。已有历史记录不迁移、不重写。

### API与MCP

GUI使用`/api/projects/{id}/source-changes`、`/repair`、`/check-preview?change_id=...`及schema2的`/runs`；原题列表在`/api/runs/{run_id}/repair-contracts`。MCP任务创建、修订、接收、结束和`change_submit`为PREPARE，`check_run/check_cancel`为EXECUTE，其他当前工具READ。项目授权临时保存在当前进程，pause/resume/rotate/forget/close清除；权限审批不开放给MCP。

MCP只返回相对路径、有界影响和业务结果，隐藏绝对路径、源码/config hash、原始Evidence/Trace与秘密。客户端来源从认证SDK会话取，不由Agent自报。

兼容旧登记使用任务、上下文、预期版本与稳定操作标识，回执返回 `SUCCEEDED` 及精确任务/交付/变化引用；变化详情另行提供 `COMPARABLE/NO_BASELINE`。成功回执只证明登记完成，不代表修复通过，也不要求用户重复登记。修复要求的 `must_preserve` 分别列出选定正常对照和全部原安全回归的 Case/Action/Effect 引用，不暴露证据标准指纹或执行模板。

### 源码对应与交付阅读

GUI 的 `GET /api/projects/{project_id}/source-changes/{change_id}/source-identity` 和 `GET /api/projects/{project_id}/runs/{run_id}/source-identity` 经 LocalControl 保护。SourceIdentityReader 从精确变化快照或已校验的发布包读取冻结内容指纹，并在既有分析授权下只读核对当前源码。当前读取投影使用 `SAME/CHANGED/NO_BASELINE/UNAVAILABLE`，GET 不写数据库、不创建历史记录、不参与检查可执行状态或安全判断。缺失文件索引时仍可展示已冻结的 Run 指纹，但不能推算文件数。

实时 Git 读取只补充当前 HEAD 与授权目录内的工作区上下文；不读取远端、提交正文和凭据，不提交、检出、刷新索引或联网。命令的时间和输出有界，禁用 fsmonitor；存在自定义 clean/process 过滤器时不运行 status，保留提交并将工作区状态标为未知。正常换行配置必须保留，防止 Windows CRLF 误报。核对期间源码或 HEAD 变化时，不展示不完整的当前身份。没有精确代码观察关联的旧记录显示未记录，不能用当前 HEAD 回填。Git 信息不进入 MCP。

内容相同只覆盖受控扫描范围，不能单独证明运行目标的部署版本。受控官方实例另经运行身份与检查前后对应核对；普通外部应用仍单独标注尚未独立对应。源码对应读取遇到发布完整性错误时，结果页撤下旧安全结论；普通网络失败只将源码对应标为不可读。

变化总览分开展示 Agent 声明、服务端真实差异与关联修复；缺基线不显示猜测的文件差异，同批部分原题通过不能显示整体通过。修复详情独立展示禁止后果、必须保留的正常业务和全部回归、原始证据、登记回执及服务端七态。历史结果通过“结果与证据 / 源码对应”切换阅读，完整技术引用按需展开；页面读取和刷新均不发起检查。

### 历史代码观察

`product/backend/application/changes/observations.py` 在变化登记和 Run 首次接受事务中采集独立观察。Git 前后核对理解 revision/root/授权和内容指纹；不一致或读取失败只保存期望内容指纹和 UNAVAILABLE，不能拼接部分身份。观察只含 HEAD、工作区变化布尔值、时间与授权扫描范围，不保存绝对目录、远端或正文。

`SourceIdentityReader.recorded` 通过精确 change_id/run_id 关联读取 git_status、head、has_local_changes、observed_at_us、observation_id 和 consistency；已发布 Run 仍先校验 package。无关联的旧历史继续 NOT_RECORDED；当前 Git 不回填历史。`JobQueue.submit` 的可选 on_created 回调仅在新 Run/Job 插入后、commit 前保存这些元数据，幂等回读不执行回调。直接测试为 `test_code_observations.py`、`test_provenance_callback.py` 和既有源码身份/提交测试。

### 连续任务和交付索引

任务历史与交付分页读取分别使用任务稳定游标、批次序号游标；每页有界，所有定位限定当前项目。交付详情从持久起点与源码快照构建相对上一批及任务累计差异，GET 不扫描工作区、不登记新的变化。检查关联来自与 Run 同事务写入的交付索引，不能按时间、同源码或最新 PASS 猜测归属。

预设异步优化和修复进入同一开发任务，来源固定为预设演示，不伪造 Agent 接收。固定操作键供丢失响应后回读；代码已切换但登记未完成时，同版本恢复只补原批次登记，不再次切换代码。任务关闭或取消保留全部历史，也不产生安全结论。

## 开发任务与交付回执

### 对象与版本

一个应用只能有一个 ACTIVE 任务。任务状态仅 ACTIVE、CLOSED、CANCELLED，结束或取消均不表示安全通过。目标、标题与批准权限的冻结引用保存在追加的 `DevelopmentContext` 中，每份上下文同时代表一次不可变目标修订，不另存重复内容的修订表。

`DevelopmentTask.version` 是所有任务写入的乐观并发版本；`revision` 是目标修订。接收、交付和结束递增 version，不改写目标修订。修改目标或刷新已变更的权限引用追加上下文并递增两个版本，旧接收不能沿用。界鉴只记录已批准权限的引用，任务文字不形成新权限，不自动批准权限。

明确接收由客户端操作形成 `DevelopmentAcceptance`；复制、读取和显示任务不会产生接收。客户端名称用于来源展示，不作为认证凭据。每次调用仍须通过既有 MCP 认证和逐应用授权。

每个任务可包含多个 `DevelopmentDelivery`。第一批相对任务最初源码快照，后续相对上一批快照；每批均保留任务最初快照以供累计对照。真实路径变化由既有受控扫描形成，声明路径只作提示，不代表文件作者身份，也不用于裁剪检查计划。

### 原子写入与恢复

所有写操作携带稳定的 32 位十六进制 operation_id。回执主键为 project/kind/operation_id；请求指纹包含操作内容及预期任务版本。相同键和正文返回原回执，同键异文拒绝。重放先于当前版本、源码或准备状态核对，所以响应丢失后可用原请求恢复，即使后续工作区已变化也不会再次扫描或登记。

变化登记先在事务外形成只读扫描候选，再在 SQLite 写锁下重读权限、任务和源码理解版本。源码理解与快照、Change、影响记录、Delivery、任务版本更新和 SUCCEEDED 回执在同一 Unit of Work 提交。任何一步失败整体回滚；不依赖进程内 RLock 来实现跨进程幂等。

成功响应只返回持久回执，不在提交后同步读取 Workspace。下一步同步失败应单独重读。没有回执仅表示尚无已登记成功事实，不能据此认定请求从未执行或生成新操作键；有界扫描尚在执行时也可能没有成功回执。长时执行必须走现有 Job/lease/fence，不能以此同步事务替代执行队列。

### 持久化与范围

开发任务、上下文、接受记录、交付与回执直接进入完整工作区基线。任务关联必须来自真实操作，不按名称或时间补造。唯一活动任务由数据库部分唯一索引约束；已有工作区结构不匹配时只读拒绝。

五个独立根记录使用格式 1，并登记公共 Schema。所有读写继续经过严格模型及秘密过滤。开发模块不持有 Verdict，不能将普通 PASS 自动标记为修复成功；正式检查和原题修复仍是各自结论的唯一所有者。运行对应另见[受控运行对应](应用与运行.md)。

`development_check_runs` 在正式 Run/Job 创建事务内保存交付关联。查询交付结果通过这条索引和完整发布包，不按最新时间或源码指纹匹配。运行加载具有独立回执，保存实际来源及实例对应，不混入普通交付成功回执。

当前日常GUI先读取registration-preview，再向source-changes/register提交格式1的SourceChangeRegistrationRequest，携带稳定operation_id和expected_registration_fingerprint；用户无需手工创建或接收开发任务。底层source-changes提交仍提供格式2的SourceChangeCreateRequest，明确绑定task/context/operation/expected_version；MCP的显式交付工具使用对应任务合同，两条入口不能混称为日常人工前置。MCP 提供 task_list/show/context/create/accept 与 receipt_show，变化登记返回持久回执，再由 change_show 查看事实。任务修订、结束和取消保留本机GUI控制API，当前日常工作面不挂载手工任务流程。客户端身份取当前 SDK 请求，无法取得时显示 MCP Agent，不复用上一客户端名称。

浏览器会话存储仅保留操作键及必要的任务/上下文/交付引用；不存正文、草稿或秘密。刷新后查询原键；查询暂未发现成功回执时可以用同键原请求继续，不能偷偷生成新键。切换项目由页面身份隔离。

## 变化与修复协作

### 一次修改的完整链

1. 原Agent或用户修改授权源码。GUI/MCP先读registration-preview，得到当前登记依据，再以稳定operation_id登记。
2. CurrentSourceChangeService形成受控扫描候选；DevelopmentService在写锁内重读权限、理解与任务版本，将内容快照、真实diff、影响、交付、版本和成功回执同UoW提交。claimed_paths仅是线索。
3. DevelopmentReader读取已保存的交付与精确检查关联；读取不能扫描出新交付。成功回执返回后Workspace刷新失败，是另一次读取失败。
4. 若运行尚未加载，用户明确加载本批源码，取得当前实例引用；有效材料可沿用，失效来源重新准备。Workspace选择下一步并保留change_id。
5. CheckService提交完整当前考题，冻结精确change/repair上下文；development_check_runs在同事务保存交付与Run关联。
6. 执行发布后，结果reader从不可变证据构建Story。修复reader对比原BLOCK和精确NEW Run：原规则、身份、资源、证明标准与全部正常回归不降低。
7. ProjectRepair聚合问题族与当前任务，Workspace展示下一步；不能按时间接近、源码相同或最新PASS猜关联。

### 对象和边界

| 事实 | writer/owner | reader | 保持的关系 |
| --- | --- | --- | --- |
| snapshot/change/assessment | changes＋development命令事务 | inspection、检查构建、交付阅读 | 实际内容摘要形成差异，Git/mtime/Agent文字不是证据 |
| task/context/delivery/receipt | DevelopmentService | DevelopmentReader、GUI/MCP | 目标revision与写入version分开；回执按原键恢复 |
| delivery→Run | CheckService的交付记录回调 | 交付验证reader | 精确索引，不能事后按最新时间匹配 |
| 原题合同/复验 | CurrentRepairService等只读派生 | 项目修复、结果与Agent修复依据 | 原题从已发布BLOCK重建，Agent不能改合同 |

### 失败与收尾
