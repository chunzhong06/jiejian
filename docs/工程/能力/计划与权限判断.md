# 计划与权限判断

本页面向维护者，说明能力协作、持久事实、拒绝边界和恢复方式。用户操作从[文档入口](../../README.md)选择；源码定位查[模块索引](../../参考/模块索引.md)。

## 权限判断

### 判断的是哪些事实

用户的PermissionIntent说明允许或禁止什么；独立观察说明实际发生了什么；Verification判断事实是否足以支持结论。HTTP403本身不能证明安全。如果禁止效果已被可靠、关联、权威的必需来源确认，结果应保留BLOCK；关键来源缺失或“没有发现”不闭合时不能PASS。

DENY的PASS需要拒绝事实、全部禁止效果不存在且闭合、有效ALLOW对照和一致基线。其他不足情形保留INCONCLUSIVE及明确原因。合法业务不能为了消除漏洞而被一并关闭。精确规则以当前纯算法和对照用例为准。

支持/佐证观察可以运行和发布，但不能自动成为PASS必需通道；关键禁止效果已确认时，辅助观察失败不能抹去BLOCK。恢复是否建立等价基线要有事实证明，调用reset本身不是证明。

### 修改与验证

先区分意图/计划、HTTP执行分类、观察事实与闭合、三态算法、结果投影。只修改所属owner，同时核对直接输入与消费者。纯规则先覆盖ALLOW正常对照、403但发生副作用、关键观察不完整、baseline/closure不足及辅助观察失败等有意义的场景。

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 test tests/domain/verification/test_checks.py
```

这是纯判断变化的直接入口；协议或执行事实变化再扩到对应workflow/Runner消费者。没有跨进程影响时不重跑L4/L5。LLM、页面、报告均不能决定或更改Verdict。

### 失败定位

BLOCK消失先看禁止效果是否仍CONFIRMED；PASS变INCONCLUSIVE先找必需通道、control、baseline或closure缺口。结果与证据矛盾先校验publication与CheckResultReader，不能在GUI改颜色或改文案伪装修复。Fixture事实失配应修测试输入，不放宽生产判断。

## 计划与提交

### 一次提交的事务

CheckService.preview调用冻结逻辑产生当前完整计划，但不创建执行任务。submit先核对预览指纹和现场源码，再在Job创建事务的checkpoint中重读权限、准备与冻结输入，校验canonical请求、bundle和源码仍一致。交付关联回调复用该UoW，不能在提交后凭最近Run补关联。

请求与bundle保存冻结事实及必要指纹。Worker持有Job租约，独立Runner执行当前输入；它不能读取可变页面配置重新解释旧检查。结果先暂存、校验、发布，再由reader提供结果故事。详见[检查与发布协作](#检查与发布协作)及[权限与检查计划](#权限与检查计划)。

### 改动边界与排障

- can_execute为false：定位精确材料/证明/正常对照/恢复缺口；不能删除缺失Case缩减完整计划。
- CHECK_PLAN_CHANGED：对比本次basis、权限revision、源码、运行与材料，不重用旧预览强行提交。
- 改冻结字段：先决定所属独立根及兼容语义，再一起改构建器、parser、Runner、publication校验、Schema与fixture。
- 提交响应未知：查幂等键和当前Run/Job事实，不重新执行TARGET来判断是否成功。
- 只读结果失败：校验已发布包和关联，不在GET中补写或重跑Verification。

验证按纯计划→应用提交→直接Runner/发布消费者逐层扩展。只有跨进程/真实流程变化使原检查点失效时才扩大。纯三态判断另查[权限判断](#权限判断)。

## Web执行配置与冻结快照

### 当前CHECK冻结合同

当前配置统一为 `CheckRuntimeBundle`；`runtime.kind` 明确外部 Web、受控 Python 或受控 Node，`proof_sources` 冻结已采用的证明来源。请求为 `ExecutionRequest`。两个根分别携带格式身份与版本，冻结完整计划、双身份、资源、证明、恢复、预算及配置指纹。builder 先核验持久 Flow、草稿和原始字节摘要，不运行目标。

提交前及事务内重核live源码、当前权限和准备事实。`ChangeContext`冻结精确change_id、impact fingerprint和全部Permission引用范围；`RepairContext`冻结原题引用、原epoch/Permission、selected control、身份/资源、禁止效果、决定性标准与全部历史SAFE回归。两者为嵌套DTO不重复schema_version，空历史回归显式为空集合。

当前TARGET的保守401/403缺省及唯一合格Task完成绑定规则见[修改Web执行](Web执行与观察.md)。202仅在原响应谓词与精确可信EVENTUAL终态同时成立时重新分类，不重发TARGET、不用ZIP效果代替Task终态；无缺省404。

Worker/Runner只消费冻结输入，秘密按受控引用最小注入。CheckEvidence/CheckRunnerResult经canonical/hash、租约/fence、原子publication与Reader核验后供ResultStory/Repair读取。当前 reader 只接受明确登记的根格式，不回退到旧输入或补造默认事实。

## 权限与检查计划

### 目的与消费者

当前协议连接正式 Business Boundary、Permission v2、完整纯计划与 CHECK 后端；旧 Contract 家族只作为保留协议，不进入当前执行。

### 先理解：用户需求、执行计划和结论不是同一份数据

用户确认“普通协作成员不得导出项目负责人的完整项目交付包”时，`PermissionIntentRevision` 引用正式 `BusinessActorRevision`、`BusinessActionRevision`，保存关系、DENY 预期与受保护 effect IDs，不保存 Candidate、具体账号、Cookie、HTTP 或 Observer。Actor/Action implementation binding 独立保存当前 Candidate 定位；`MISSING` binding 不阻止业务语义确认，只阻止后续把它冒充为可验证实现。

执行后形成的 Evidence 与 Verdict 不回写 PermissionIntent。换一个测试账号可能让既有技术绑定失效，却不能静默改变用户已经确认的权限需求；缺代表形成 coverage gap，也不能删除 DENY。

### 当前执行计划边界

`ExecutionRequest` 冻结完整动作、用例、同题对照、正常回归、证明及来源与策略身份。`CheckRuntimeBundle` 通过组合冻结运行方式和证明配置，以 config_fingerprint 关联请求。正式角色、动作与权限修订独立于技术绑定；身份、资源、合法对照、恢复或证明的缺口阻止提交，不能缩减完整计划。

当前消费入口为 `product/backend/application/checks/service.py`、`product/backend/infrastructure/runtime/check_runner/` 与 `product/backend/domain/verification/checks.py`，Schema 为 `schemas/runner/persisted-execution-request-v3.schema.json` 和 `check-*.schema.json`。

## 权限验证与结果

### 组件与边界

- 正式 Actor/Action revision、Effect catalog 和 PermissionIntentRevision 是业务语义真源。人工批准事务决定 revision、binding 和 policy_epoch；模型建议没有 writer 权限。
- PreparationService 现场核对身份、演示 Flow、资源、结果证明与恢复绑定。纯计划保留完整 ALLOW 集合、DENY Case 和同题合法对照，不按变化影响裁剪。
- CheckService 预览并提交当前计划；CheckRuntimeRegistry 显式注册证明能力、观察来源和独立身份映射。缺失注册形成 gap，不扫描 provider 或猜测账号含义。
- ExecutionRequest 冻结完整计划；CheckRuntimeBundle 冻结 Web 叶配置、预算、身份受控引用、Flow、proof、恢复和业务标签。两者分别 canonical/hash 后关联，不构造旧 Contract/Profile。
- CheckExecutor 在独立 Runner 内串行执行完整计划，每 Case TARGET 至多一次；同一会话在 TARGET 前独立核验实际身份，计划账号名不能代替实际身份。
- CheckObservation 分别保存主证明、辅助和诊断来源的级别、阶段、关联、可靠性和闭合。只有精确匹配的 VERDICT_REQUIRED 来源参与必需效果判断，辅助材料不能升级为安全证明。
- evaluate_check_case 是当前 Case Verdict 唯一规则入口。DENY 下可靠、完整、关联且权威的禁止效果已确认时优先 VULNERABLE；请求仅被接受而效果未确认，保持 INCONCLUSIVE。ALLOW SAFE 需要执行接受、全部必需效果确认及有效身份、基线和恢复；DENY SAFE 还需要拒绝、闭合的效果缺席及同题 SAFE 合法对照。
- aggregate_check_verdict 将任何 VULNERABLE 汇总为 BLOCK，完整 SAFE 集合汇总为 PASS，其余为 INCONCLUSIVE。取消、租约和进程错误由独立生命周期与发布规则处理。
- CheckPublisher 复核唯一规则后，在有效 attempt/fence/lease 下提升不可变文件并提交收据。CheckResultReader 只校验收据、Run、Job、manifest、文件与索引，不重新裁决；完整性异常隐藏 Verdict 并拒绝详情。
- 当前 Continuity 和 BreakpointLocator.locate_current 消费冻结动作、Twin、Case 与已发布事实，不拼旧 PermissionContract。六类因果分析只在孤儿效果确认后运行；显式父边和受控 namespace 不足时降低精度。合法委托和服务端内部 actor 变化不能自动成为身份替换。
- CheckStoryBuilder 使用冻结业务标签和既有 story_text，确定性输出实际 Case、执行情况、效果、证据说明和断裂诊断。证据索引与完整文档分层；读取不访问当前目标、Observer 或 live 业务数据。
- 结果解释 Assistant 只消费服务端裁剪的 Story 实体；GET 不调用 Provider，POST 显式生成。越权 Verdict、位置、类型、精度、证据和修复字段被拒绝；禁用或失败不改变确定性故事。

### 关键数据流

```text
人工批准业务边界与权限 → 当前准备事实 → 完整纯计划
→ CheckService 冻结 request/runtime → Job/Run
→ 独立 Worker → Runner → Web/Observer → 当前纯规则
→ CheckEvidence/CheckRunnerResult → fenced publication
→ CheckResultReader → CheckStoryBuilder → 可选受限解释
```

### 关键不变量

来源、身份、Case、Run marker、资源和 proof 引用必须精确关联。披露证明只保留受保护投影的临时密钥 HMAC 结果，不发布原始敏感字段。审计 Trace 只采用显式因果、效果和权限范围，缺失节点不补造，已有禁止效果不因诊断缺口消失。

当前审计适配器按封闭字段集合接受 `allowed_action_ids`、`allowed_resource_ids` 的有界严格数组；缺失或空数组不证明范围，非法值不截断为有效事实。采集与投影约束见[Observer 观察协议](Web执行与观察.md)，核心算法测试不能替代真实采集证据。

### 失败语义

准备缺口阻止提交；执行不确定、基线/恢复失败和观察不闭合不能形成 PASS。结果篡改表示完整性失败，不替换原始持久结论。恢复只按既有租约和 publication 对账，不重放已执行 TARGET。

### 安全约束

秘密只经精确运行时引用注入；API 不执行目标或 Observer。模型不能生成 Verdict、Finding、Gate、权限或自动批准，结果解释没有写权限。

### 兼容与版本

旧 PermissionContract、MutationPlan、Profile、Finding/Report/Baseline/Gate 实现不进入 CURRENT Check writer/reader/factory，旧 accepted-alone 判定不是当前规则。根协议各自带版本，嵌套 DTO 不重复版本。Evidence 内容地址与文件字节 hash 分开校验。

## 检查与发布协作

### 正常链

1. CheckService.preview读取正式规则与有效材料，通过纯计划和RuntimeBuilder构建完整当前考题，不创建Run/Job。
2. GUI或获EXECUTE授权的MCP提交预览指纹和幂等键。提交checkpoint在UoW内重读规则、准备和源码，冻结ExecutionRequest与对应runtime bundle；Run、Job及精确交付关联一起形成。
3. Supervisor承担启动责任，Worker获取系统锁/进程树与当前lease/fence。Check Handler把固定输入和最小环境交给独立Check Runner。
4. CheckExecutor组织Case/Twin；WebRuntime执行scope和预算内的步骤、唯一TARGET、独立Observer与恢复。Verification根据执行、效果、闭合与合法对照事实决定三态。
5. Runner写受限staging与严格结果；进度文件是非权威旁路。Worker校验Run/Job/request、attempt/fence、大小、秘密、路径和hash，再发布不可变目录及数据库收据。
6. CheckResultReader校验完整publication，Story/History/Repair提供只读投影。读取不再访问目标或重算Verdict。

### 谁拥有哪个边界

| 边界 | owner | 对外交换 |
| --- | --- | --- |
| 正式计划和提交 | core/checks、workflows/checks | 完整纯计划、ExecutionRequest、runtime bundle |
| 执行责任 | runtime/jobs与worker | Job/attempt/lease/fence、取消请求与事件 |
| 目标行为与观察 | Check Runner、execution、observers | Execution/Observation事实、CheckEvidence、严格结果 |
| 安全结论 | core/verification/checks | PASS/BLOCK/INCONCLUSIVE；独立于运行错误 |
| 发布与读取 | artifacts/checks、jobs、checks/reading | manifest/hash、DB收据、已发布事实投影 |

### 失败后由谁收口

- 预览与提交间漂移：CheckService拒绝新提交；不裁剪Case或沿用过期输入。
- Worker在claim前退出：Supervisor以等待态＋无lease条件结束关联任务；条件已变则接受当前DB，不覆盖已claim任务。
- claim后取消/租约失效：受控进程树收口，旧fence不可发布；清理未确认不能当作可安全重试。
- TARGET后恢复失败：保留先前事实、主错误和cleanup问题；不能覆盖原主错误或据清理失败造新Verdict。
- 文件发布成功而DB提交失败：reconciliation校验原manifest及执行身份补齐收据；不重放TARGET。
- reader发现缺失/hash/关联不符：拒绝投影，不在GET中修复或回退到旧结果链。
