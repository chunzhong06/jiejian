# 协议与持久化

界鉴把可交换文档、数据库事实和页面状态分开管理。输入表达本次任务，证据表达已经观察到的事实，页面投影负责阅读与操作。三者各自有明确的所有者。

## 根文档与 reader

只有独立持久化、跨进程或对外交换，且有独立 reader 的根文档携带 `schema_version`。嵌套 DTO 不重复声明版本。产品版本、数据库修订、外层 API 回执与业务格式版本各自独立。

协议从实际声明模块导入，注册表和 JSON Schema 是可核对投影。当前运行输入、证据和结果根显式携带 `document_type` 与 `schema_version`，reader 从原始字节核对格式身份，不依赖模型默认值猜测版本。旧检查与证明来源格式不在当前 reader 的支持范围内。

### 按职责组合，避免按功能叠版本

`ExecutionRequest` 冻结规则修订、执行用例、同题对照、本次要求范围及修改或复验上下文。`CheckRuntimeBundle` 冻结身份、请求、预算和证明来源，运行方式用 `EXTERNAL_WEB`、`MANAGED_PYTHON`、`MANAGED_NODE` 的带标签联合表达。文件响应、事务记录和对象创建由证明来源的类型表达，不再用运行根的第几个版本推断。

`CheckEvidence` 统一保存观察结果、有限业务事实和事实引用；详细事实可以为空，但已有事实必须精确关联本次请求、用例和证明。`CheckRunnerResult` 把生命周期、三态结论、错误和运行对应分别保存。发布者复核冻结来源与事实归约，不能仅信任 Runner 给出的外层摘要。

API 操作 DTO、Worker 输入及长期证据服务于不同消费者，分别声明，不复用一个大模型承载所有边界。相同语义的叶模型可以共享；不同根通过组合关联，不通过继承旧版本获得新格式。

### 四种修订各自解决什么问题

| 标识 | 回答的问题 | 变化时的处理 |
| --- | --- | --- |
| 产品版本 | 用户运行的是哪一版程序 | 随产品发布维护，不触发格式或数据库自动变更 |
| 根文档 `schema_version` | 独立 reader 应按哪套字段和语义解析 | 评估存量字节、支持 reader 和转换；不支持的版本明确拒绝 |
| 数据库 revision | 这个文件完成了哪些结构与数据转换 | 通过签入迁移图升级，不由产品版本推算 |
| 权限及其他业务 revision | 当时采用的要求是什么 | 追加业务事实，旧报告继续引用当时修订 |

例如，更换报告布局只改变显示；新增可选页面投影不修改冻结执行请求。若改变根文档必需字段、事实含义或 canonical 计算，则需要明确格式兼容决策。新增持久列属于数据库迁移；修改权限要求属于业务修订。不能为其中一种变化同时机械提升所有版本。

### 格式由声明、reader 和历史样本共同约束

`product/protocols/schema.py` 登记 Schema 生成来源，具体 reader 留在所属格式模块。根格式只有存在真实兼容责任时才保留多个 reader；新增业务能力优先用有明确语义的类型与可选结构表达。未知格式明确拒绝，不能从当前环境补造缺少的运行证明。

`product/protocols/codec.py` 统一检查重复键、BOM、非有限数、根对象、大小、格式身份及确定性 JSON 字节。模型继续负责关联、预算和秘密边界。编码采用固定 UTF-8、键排序、紧凑分隔符及禁止 NaN 的 JSON 规则；这是项目内部的确定性编码约定，不声称等同于 RFC 8785。

格式变更先确认四项：谁写入、谁读取、哪些旧文档仍需读取、拒绝或转换的结果是什么。保留独立历史样本和恶意输入；不能从当前 writer 重新生成全部样本，再宣称旧格式仍兼容。格式版本的精确值和旧字节摘要属于兼容合同，仍应准确断言。

兼容责任划分参考 [Stripe 对 API 契约演进的说明](https://stripe.com/blog/api-versioning)。界鉴的冻结证据与进程输入采用严格解析，新增未知字段也可能被现有 reader 拒绝，因此不直接套用一般 Web API“新增字段一定兼容”的假设。

## 指纹与冻结

业务标识确定对象，修订确定语义，内容指纹核对精确输入，操作标识定位一次写入。名称和文案不能代替它们。

预览形成当前计划，提交核对期望指纹，再保留执行输入。只读展示新增字段不应无意进入摘要或改变冻结语义。历史结果继续关联当时的项目、规则、代码、身份与证明范围。

## 事务和发布

用例决定事务边界，Repository 执行持久化约束。批准、任务提交和关联更新要么形成完整事实，要么失败回滚；长时间浏览器工作不占用 API 事务。

执行产物经过受控发布和严格 reader 才供报告使用。核对项目、运行、规则、来源和摘要，不能仅凭文件存在判断可信。查询索引便于定位，不能替代发布包及其完整性。

### 数据由谁拥有

| 数据 | 所有者及寿命 | 不能混入的内容 |
| --- | --- | --- |
| 业务角色、动作、权限 revision | 边界聚合追加语义，提案与人的决定保留对应指纹 | 实时登录可用性、候选页面状态 |
| 实现绑定与准备材料 | 精确业务 revision、录制、资源所有者与来源指纹 | 伪造的当前可用状态和未经确认的恢复方式 |
| 测试身份 | 稳定 Actor revision、有限登录元数据和受控秘密引用 | Cookie、Token 正文和跨身份共享会话 |
| Job 与 Run | 队列、attempt、租约、fence和冻结请求关联 | 从任务生命周期推导安全结论 |
| 发布包与回执 | 已验证的 request、runtime、result、Evidence及清单关联 | 可变页面配置、事后追加或修正的证据 |
| 源码变化与规则目标 | 实际差异、明确权限及原问题引用 | 当前 HEAD 冒充历史内容、修改者自行声明修复成功 |
| 索引、界面投影与缓存 | 读取和定位已有事实，可按规则重建 | 第二份 Verdict、持久化的页面进度或陈旧授权 |

一个 UoW 内的 Repository 共享 Session 与事务。长时间网络、浏览器和进程执行通过持久任务离开短事务，完成后以明确身份和前置条件写回；跨数据库与文件的收敛由发布协议承担，不靠包裹更多代码假装成单一事务。

### 发布与恢复的条件

Runner 只能写本 attempt 的受限 staging。发布者核对 Run、Job、attempt、fence、request/config 指纹、路径与文件预算、脱敏及内容摘要，再发布不可变包。文件字节摘要和语义内容地址分别校验，不能用重新序列化后的字节替换历史摘要。

文件已发布而数据库事务失败时，reconciliation 只能按同一身份、清单与摘要幂等补齐收据。缺失、孤儿、篡改或未知格式进入明确拒绝或恢复路径，不能回读当前环境补造旧事实。索引清理和重建不得触发目标执行，也不得重算既有安全结论。

Storage 聚合直接拥有 Row、Record 和 Repository，消费者从实际声明模块导入。ORM 全量登记由 `product/backend/infrastructure/storage/orm_registry.py` 显式完成。新库采用完整基线，正常启动不重放旧迁移或转换旧协议，具体见[数据库与迁移](数据库与迁移.md)。

协议组合参考 [Pydantic 带标签联合](https://docs.pydantic.dev/latest/concepts/unions/#discriminated-unions)，API 与持久格式的边界参考 [Protocol Buffers 的模型分离建议](https://protobuf.dev/best-practices/dos-donts/#do-use-different-messages-for-rpc-apis-and-storage)。采用的是边界方法，项目仍使用 Python 模型和 JSON。

## 秘密与错误

秘密仅使用受控引用和最小运行时注入，结束后清理短期材料。密码、Cookie、Token、API Key 不得进入普通数据库字段、公共协议、Evidence、Finding、Report、源码、日志或异常正文。

外部错误映射为稳定代码和脱敏上下文。不要通过原始异常、完整命令参数或响应体帮助调试而突破秘密边界；日志与测试报告同样受此约束。

## 回执未知的恢复

写请求超时只能说明调用方未取得结果。先以原操作标识、幂等键或已知运行查询持久事实；不得生成新键重复批准、删除、启动或提交检查。指纹失配时重新预览并核对变化，不能自动接受扩大后的范围。

调用方还须区分尚未处理、已失败和查询本身失败。具体调用约定见[本地接口](../参考/本地接口.md)，状态含义见[状态与回执](../参考/状态与回执.md)。
