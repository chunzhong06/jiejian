# 交互规则

> 状态：CURRENT。维护已接受的交互规则；功能入口见[产品入口](../../总览/产品入口.md)。

## 先判断谁拥有事实

页面展示一个值之前，先确定它的权威来源。前端只能翻译或组织事实，不能因为页面上“看起来合理”而补推断。

| 页面问题 | 权威来源 | 前端可以做什么 | 前端不能做什么 |
| --- | --- | --- | --- |
| 工作区区域状态与本版主待办 | 后端 `WorkspaceService` | 按 Project、ApplicationUnderstanding、pending Proposal、正式 Boundary、Permission 与实时 implementation inspection 展示区域和唯一 `PrimaryTask` | 从旧 Preparation、Run、mapping count 或页面本地状态伪造 tests ready、check runnable 或 delivery ready |
| Candidate、Actor、Action、Effect 与 Permission | Business Boundary preview/current/proposal API | Candidate 仅作建议；草稿使用业务语言；审批前展示完整摘要 | 从名称自动合并、把 Candidate ID 写入正式语义、在浏览器构造 revision 或审批主体 |
| 动作准备与下一项 | 后端 `PreparationView` 与 `WorkspaceView.primary_task` | 按 action 展示身份、执行、资源、结果证明、恢复及服务端主任务 | 重算 requirement/优先级、调用旧 prepare-safe、自动登录或用齐备状态创建 Run |
| 业务权限与实现定位 | 正式 Business Boundary View 及 Actor/Action binding | 分开显示“业务权限已确认”和 `CURRENT/MISSING/STALE` 代码定位 | 把缺 TestIdentity/Flow 或 binding MISSING 写成权限未确认 |
| 生命周期和执行错误 | Run、Job、ErrorDiagnosis | 区分运行中、完成、失败、安全停止并给恢复入口 | 把执行失败显示成发现漏洞 |
| PASS/BLOCK/INCONCLUSIVE | 后端 Verification 与 `ResultStory` | 原样组织结论和解释 | 根据 HTTP 状态、标签或 Evidence 文本重算 Verdict |
| 当前修复状态 | 后端 `ProjectRepair`、不可变原题合同与复验投影 | 展示七态、精确源 Run/变化/复验入口 | 用 Agent 声明、单次普通结果或修改权限推导修复完成 |
| 计划使用的账号 | 已验证的冻结请求快照 | 显示计划账号名称；技术 ID 只进入 Machine 输出、证据、报告或开发文档 | 把页面选择值说成目标实际识别身份 |
| 目标实际识别的账号 | 独立可信执行或观察事实 | 有事实才显示；当前缺失时明确“无法独立确认” | 用计划身份、subject binding 或角色名称冒充实际身份 |
| 检查记录与原题结果 | 当前 Run 列表、ResultStory 与 ProjectRepair | 按精确 Run 读取已发布结果并关联原题 | 因某次记录缺失就推断问题已解决 |

秘密边界始终成立：密码、Cookie、Token 和 API Key 只通过受控输入与 secret reference 使用，不进入普通 DTO、浏览器持久化、日志、错误正文或 Git。模型服务 API Key 只写入秘密存储，页面不回显。


## 页面怎样组成连续任务

普通页面采用同一结构：

```text
PageTaskHeader
→ 当前任务或阶段说明
→ 后端事实形成的主要内容
→ 必要时提供具体的识别依据或证据入口
→ 需要提交时提供 TaskActionBar
```

`PageTaskHeader` 只放标题、短说明和状态。普通返回、只读刷新放在内容流内，不悬浮；确有提交的长表单才使用粘滞 TaskActionBar，保持表单范围、内容对齐和最后一项可见。刷新不能产生新检查或覆盖输入；有副作用的重新开始需说明后果并明确确认。

概览、权限要求、修改与验证、检查记录沿用结果页的页头轴线、紧凑列表与单项详情层级；连接与授权是有明确返回入口的次级页面。来源记录区分别说明过程记录已采集、阶段不适用、观察尚未闭合、读取不完整和效果投影不支持；初始与恢复条件另按服务端核对事实展示，不能用业务效果 UNKNOWN 代替恢复状态。

表单主确认统一放在操作区右端；返回、放弃等次级动作在前。候选业务信息没有新变更时不再展示重复确认，保存成功且下一步已同步后直接进入权限建立，正式权限批准仍独立由用户确认。短期成功回执只在发起操作的页面与应用内显示，离开即清除，最长显示六秒；检查进度和正式结果由持久事实单独展示。

材料已保存但下一步同步失败时保留写入回执，自动重读材料与 Workspace，不重复提交。背景轮询复用在途读取，写后显式刷新取得新快照；旧响应不得覆盖新任务或被误报为写入失败。加载指示位于所属工作面内，不能因空内容而漂到边框外。

RetainedWorkPages 在当前项目会话内保留工作输入、权限草稿、历史筛选和返回位置。导航隐藏工作页时关闭 Evidence Portal；项目切换或明确重试重建。设置与密钥页面不保留，以上工作状态不写 localStorage。

历史筛选仅在检查列表与该列表打开的结果之间返回时保留。从其他模块重新进入检查历史时清空筛选并立即回读；无筛选的空列表自动接收新记录，不显示误导性的“清除筛选”。已有记录正在阅读时保留行位置，对新增记录显示更新入口。

工作台保留业务全局进展，以单一任务工作面呈现 PrimaryTask 的原因、操作、完成条件和后续读取。taskDestination保留精确proposal/task/run/change引用；位置条只消费Workspace.journey；新任务到达时通过 useTaskGuard 保留可见页面的未保存输入，取消或提交后才释放，不在前端另选主任务。活动 Run 作为当前上下文；REGISTER_SOURCE_CHANGE 可直接进入本地登记；有授权的 Coding Agent 可用 MCP 一次登记，不要求用户先新建任务或接单。保存登录只证明准备状态，不是实际身份 MATCH。操作成功与权威同步失败分开提示，重试同步不能重复提交。

Business Boundary编辑入口通过GET editor一次读取正式边界、候选、维护草稿和有界待审摘要，随后按精确proposal_id读取不可变提案。存在多份记录而没有指定ID时，要求用户选择，不自动采用最后一份。提案前后对照只消费服务端review；原始版本缺失时标记UNAVAILABLE并关闭批准入口，当前状态漂移另列。

Business Boundary 编辑页只维护浏览器内草稿。HIGH/MEDIUM Candidate 可预选但不显示技术 ID，LOW 只列为可能项；用户可以明确合并、排除、重命名或手工补充。Effect 使用业务语言映射固定枚举，权限关系使用“自己的资源 / 同权限组另一个账号 / 其他权限组的资源”。提交后 review 页面正文不可编辑；返回修改创建新草稿，Approve 携带服务端 Proposal 的 ID 与 fingerprint，并在成功后刷新 Boundary 和工作区状态。

接入候选的权限组和业务动作共用一份选择：编辑页只有一个“下一步：核对业务总览”入口。总览替换编辑内容，分别列出两类信息的纳入、排除和保留待审，明确确认后才保存；返回修改保留选择与焦点。正式提案审批不要求输入原因，仅保留核对勾选和明确确认，审计记录保存实际勾选确认行为，不伪造用户填写的解释。维护页有草稿修改时使用“下一步：核对修改”；没有修改时，顶部次要入口“核对代码关联”仅用于审阅业务与当前代码定位，不能用“全部变更”暗示已有修改。

测试账号页将简短说明、带标签的新增表单与已有账号列表分开，普通说明不使用占据整行的大型警告。检查页只在实际发出请求且回执不明时显示提交未知；写入前门禁的明确拒绝恢复普通操作状态。历史结果的工作台同步提示仅属于该结果视图，离开后不得残留到新检查，也不得声称用户刚刚提交过检查。

权限总览使用左侧动作索引与右侧规则摘要，业务结果与实现定位按需展开。已有规则的单条编辑由 `PermissionRuleForm` 保存独立副本，取消不改变草稿；保存只合并该规则，统一审阅时仍提交完整 desired state。业务角色和动作在列表—详情工作面管理，默认显示业务含义、效果和引用，点击编辑才展开完整字段。每个对象的未保存副本保留在同一草稿会话，取消只撤回该副本；停用和调整效果后仍需核对关联权限。实现定位按需展开。首次建立边界按业务对象、权限规则分开编辑。权限按当前 `BusinessAction` 组织完整句子，分别说明谁操作、资源属于谁、执行什么动作及允许或拒绝的业务结果。切换草稿中的动作时保留其他动作的未提交内容；显式采用 AI 建议只更新草稿。Proposal 审阅展示服务端确认的真实前后差异，仍须由用户显式 Human Approval 才形成正式权限，不能把 AI 采用或草稿切换当作批准。

### 当前检查与结果

普通接入恢复期间先读取服务端事实；读取失败只显示重读入口，不退回新建应用表单。接入完成后以单一任务工作面进入业务审阅：宽屏左侧放已确认的应用状态与详情，右侧放下一步说明和主操作，中间以细线分隔；窄屏按状态、下一步的顺序上下排列。已经保存但 Workspace 同步失败时，只重读状态，不重复提交；未保存的审阅和手工输入保留离开提醒。

项目菜单的“应用与示例环境”直达 `/environment`。普通应用只提供连接核对；官方环境消费持久生命周期与操作回执，界鉴服务健康单独显示。未知回执关闭写入口，重新核对只读。已停止环境通过精确原项目 ID 打开只读历史；发布完整性失效时不显示历史结论，也不创建新检查。

证明材料内的“管理补充材料”采用先预览、再明确保存的路径。仅保存结构化用户记录和追加说明修订，不满足准备条件、不改 Verdict。丢失回执后保留原请求 ID；明确输入或版本拒绝则保留可修正输入。修订历史按 `before_revision` 继续读取，不能把第一页当作全部历史。

`api/checks/currentChecks.ts` 是当前检查客户端。总览只读 `check-preview` 与项目 Run 列表；只有服务端 `can_execute` 才启用开始检查，不能从 Preparation 完成标记推算。显式提交先回读活动 Run 与最新计划指纹，POST 使用格式 2 和同一次请求的幂等键；回执不明时先读记录，重试不生成新键。

选中 Run 后只在活动状态有限刷新，停止、失败或读取异常后不继续轮询；达到自动刷新上限后保留手动刷新入口。显式提交和终态结果读取后刷新服务端 Workspace，使工作台恢复最新主任务；同步失败保留已发布故事并提供独立重试，不在前端猜下一步。只有 `result_integrity=VALID` 且 Story 与所选项目/Run/结论相符时展示安全判断；进度、HTTP 状态与准备材料不能形成结论。

运行中只显示已知阶段、计数和 `progress.current_case` 对应的计划考题；该字段只来自同 Run 经校验的冻结 request/bundle，并可能为空。计划账号、资源所有者及正常对照/拒绝验证不是即时执行证据；发布前的页面响应、后台执行和最终效果仍标为未确认，不能据进度制造逐节点事实或安全结论。

`CurrentResultStory` 默认展示逐项结果表：业务要求、实际业务结果、本项判断与依据入口。整轮结论与唯一右侧续接操作由 `ResultOverviewHeader` 展示，结果和源码页签共用；运行适用性与原题复验保持独立说明。单项判断只翻译服务端已发布文案；未识别文案原样中性显示，不从 HTTP、效果或计数反推安全结论。

点击“查看依据”进入该 Case 的调查工作面，以“事实与证明 / 执行过程 / 证据记录”平级切换，不默认展开路径，不常驻右侧证明卡，也不在窄屏叠加证据抽屉。事实视图就近对照人的要求、实际后果、必要证明、独立确认的实际身份、接口响应以及初始和恢复条件。执行过程按服务端显式父边排版，保留 partial 与精度；缺 Trace 不补图。证据记录区将必要证明与辅助观察分开，详情重新核验 Run/Action/Case 和节点归属，Esc 或返回按钮恢复原入口焦点。底部仅保留一份整轮范围说明；具体限制放到范围入口及相应证明附近。

Case 深链携带精确 Run，返回总览保留分页和原行焦点；结果超过 10 项时分页，不能只展示问题项而隐去正常业务。证据读取或完整性校验失败时，CurrentTestsPage 撤下当前 Run 故事与安全结论，并显示明确错误。隐藏页面或切换 Case 会丢弃旧的详情响应；已校验历史记录不随当前配置变化。

结果 AI 复用 AssistantPanel，但调用当前 `assistant/result-explanation`；GET 冷读取，用户点击 POST 才生成受限解释。它不修改 Verdict、Breakpoint、精度或证据。当前组件直接测试覆盖提交幂等、指纹漂移、活动 Run 恢复、旧项目响应隔离、完整性失效和证据两次点击路径。

### 动作准备与当前检查的边界

动作准备展示必须消费 GET preparation 的 `PreparationView`，使用 SATISFIED/NEEDS_USER/STALE/BLOCKED/NOT_REQUIRED；下一材料操作只读取 Workspace 的 PrimaryTask。`/tests` 携精确 `task_id` 直达当前缺口，Preparation 只展开这项缺口；完成后重读局部材料与 Workspace，再根据最新主任务续接，不按旧 task_id 或列表顺序自行选择下一项。材料齐备后返回检查总览，由服务端预览确认是否可以执行。旧 ProjectPreparation 的 AUTO、next_item_key、prepare-safe 与“全部 READY 即可运行”不再是当前合同。真实账号按 slot 展示，不写死两个账号；身份和录制写入后先刷新局部事实，再刷新 Workspace。

当前业务边界维护写入成功后先重读当前 Boundary，再调用工作区 `refreshCurrent()`；该方法返回精确的 `{projects, selectedProjectId, workspace}`，页面以服务端的新 Workspace 快照续接。同步失败时保留已成功操作并给出重试提示。TestIdentity 与 Recording 展示同样必须先刷新本地事实，再读取最新 Workspace；不能依赖进入页面前固定好的 `onNext`。

当前 CHECK Worker 已接通，但具体项目仍须满足服务端预览的运行配置与准备条件。OfficialSamplePanel 只控制官方环境启停、重置及可选观察条件；修改与验证中按需展开的 OfficialDevelopmentJourney 承载同步起点、预设异步优化与原题修复，实际推进由已发布事实决定。源码出现外部修改时进入普通协作，预设操作不能覆盖用户或 Agent 的代码。ControlShell 只有在真实活动 experience 的 project_id 精确匹配时，才提供演练、权限提案与测试材料入口。提案仍须 Human Approval，材料不是检查结果，预设变更不冒充真实 Codex 交付。原题修复经普通 `/tests` 显式执行；普通应用不按项目名称套用示例。

当前结果、证据与修复使用普通 CurrentTestsPage、ResultStory、局部 Evidence 区和 Changes/RepairComparison。修复要求按需展开，保留全部合法回归；精确引用链接使用 `/history?run_id=...&case_id=...`。不保留 Sample 专用展示页，也不从预期结果补结论。


## 权限页面的状态核对

首次建立支持 Candidate 与手工草稿；Proposal 审阅不可原地编辑，返回修改后提交新 Proposal，批准后回读正式 Actor、Action、Effect 与 Permission。权限已确认但缺少完整 ALLOW 对照时应说明具体缺口，不以旧合同完整度字段代替当前检查条件；缺少测试账号或 Flow 也不能将业务权限显示为未确认。官方合同仍由两个 Actor、两个 Action 和三条 Permission 构成。

自动回读 Workspace、MCP、Run 时，连接与授权不等于活动工作，结束不自动导航；短检查可通过新 latest_result 的精确 Run 确认完成，首次读取历史结果不发新完成通知。自由导航复用当前编辑会话，不创建第二份草稿或主任务。诊断跳转使用服务端结构化 route，不从错误文字猜页面。


## 展示用语标准

界面使用“专业、直接、以业务事实为中心”的书面表达：普通用户不需要先理解系统内部模块，评委也能从页面直接看到规则、身份、响应、真实后果和结论。正式但不官样，不使用“搞定了”“一键封神”等过度口语或营销表达。

用语分三层：

1. 主界面先用业务主体、动作、资源、状态和下一项可执行任务，例如“Bob 不得导出完整项目交付包”“后台任务已创建”“还需准备 Bob 的测试账号”。
2. 证据详情在用户主动展开后使用必要技术词，例如 HTTP 403、后台任务、消息、ZIP、Evidence；每个技术词都必须同时说明它证明什么，不能用术语代替结论。
3. Machine、报告和开发文档保留 `ALLOW/DENY`、Verdict、revision、policy epoch、ID、Schema 与 reason code；普通页面翻译为“允许/拒绝”“检查结论”“权限规则版本”，不直接堆叠内部字段。

结果页面和展示模式必须复用同一条事实链：“人确认的权限规则 → 目标实际识别的账号 → 页面或接口回应 → 后台真实后果 → 正式结论”。403 只表示表面请求被拒绝，不能使用代表安全的绿色，也不能替代真实业务后果。状态色固定为蓝色信息、红色问题、绿色已由证据确认符合规则、黄色证据或准备不足、灰色尚无事实；颜色之外必须有文字结论。
