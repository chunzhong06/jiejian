# 设计依据与采用边界

本页记录工程组织与实现取舍。界面的参考、采用理由和限制见[前端设计依据](前端/设计依据.md)；具体规则分别由布局、交互和实现规范负责，不在依据中重复维护参数。

## 调查与采用的方法

调查按当前工作层分别选择和核验参考：后端实现查阅相应协议、框架和成熟工程机制，前端实现另查任务交互、组件与视觉模式。一次产品设计调查不能代替后续各层的实现依据；资料说明采用理由，运行证据核对本地结果。

先确认当前问题及其对完整任务的影响，再研究参考设计在什么条件下采用相应机制。重要选择应说明“当前问题 → 参考机制 → 适配理由 → 方案与代价 → 可观察的完成条件”，写入已有方案或所属事实所有者，不强制另建调查台账。参考的规模、平台与使用条件需要明确，引用链接或采用某个组件本身不构成设计合理的依据。

调查同时检验现有结构是否值得保留，按真实职责、有效能力、维护成本与实际效果决定保留、合并或重建。既有代码和说明用于恢复当前事实，已接受的基础设计及公共语义仍按授权保护；不以代码行数、参考数量或增加架构层级作为改进结果。界面参考的优先顺序与适配由[前端设计依据](前端/设计依据.md)维护。

## 权限验证资产的持续维护

产品目标是让业务权限标准、验证材料、检查方案与结果在后续开发中持续可用。用户已接受“要求到验证方案、方案到可靠执行、变化到持续回归、扩大真实适用范围”的方向。完整流程、实现依赖及当前验收由[产品改进方案](产品改进方案.md)维护；本页只维护采用理由，实施状态不在此复制。当前能力由所属契约及实际实现负责。

已有线索核对、局部材料影响、来源复用、原题跨版本接续、Agent 持续任务及 CLI 执行继续复用。设计重点是要求遗漏引导、要求级验证评估、组合准备和跨层变化解释。完整任务从用户的本次意图进入，围绕业务要求接续到准备、执行、修复与后续变化；首次检查是其中一种入口。

| 当前问题与参考机制 | 采用与适配理由 | 代价和可观察结果 |
| --- | --- | --- |
| 已发现线索与规则可管理，未写出关系仍需主动核对；[OpenFGA 模型测试](https://openfga.dev/docs/modeling/testing)按用户、对象、关系和条件组织正反断言 | 根据已有业务依据提出有限问题，并将正式要求对应到可读场景；真实应用行为和受保护结果仍由现有检查链取得事实 | 维护适用维度、问题依据和等价要求判断。验收遗漏核对、正反例及证明需求；不引入 OpenFGA 服务或第二套正式标准 |
| 准备方式及代价出现较晚；已有要求级评估仍需进一步结合项目当前条件 | 以准确要求/候选、效果、环境和现有材料形成只读验证评估，提前说明证明、正常对照、恢复与缺项 | 需要集中组合各能力事实并处理依据过期；以具体效果、草稿/正式修订、支持缺口和准确回程验收 |

| 持续维护需要区分原题与新标准；[OpenFGA 不可变模型及固定版本](https://openfga.dev/docs/getting-started/immutable-models)保留明确模型身份 | 延续现有规则修订和冻结检查；代码修复接原题，标准调整审阅新修订并安排继任检查 | 保持新旧要求与结果关联；验收无关新增、相关标准改变、正常对照及历史只读 |

长过程继续使用下节的既有长任务、请求身份与回执机制，API 只编排，目标执行仍属于 Worker/Runner。准备候选与组合计划引用原能力产物，程序依据权威状态判断完成，Agent 负责理解、整理、解释及已授权接续；用户集中决定业务歧义和独立授权。

真实适用范围按实际项目分别接受目标环境和证明子范围：外部 HTTP 路径提供其合同内的事实，受控增强路径承接相应提交、创建、文件与异步证明。新增适配按业务事实和 reader 责任划分，不逐语言复制整套流程。能力说明、公共格式和平台支持在实际实现及验证后同步；前端组织由[持续使用工作面设计](前端/工作面模式.md#持续使用工作面设计)维护。

### 结果解释与后续工作的理由

完整流程的价值在于减少遗漏和重复准备，同时让用户理解这次结果能支持什么判断。审计发现的顶层原因是：要求适用范围、实际样本、配置存在、当前可用及运行对应在部分读取中被压缩或混用。改进先恢复这些事实的关系，再安排界面；不靠改状态名称扩大结论。

| 设计问题 | 参考与采用机制 | 本地取舍及可观察结果 |
| --- | --- | --- |
| 规则写出多个条件，但本次只执行其中的样本 | [OpenFGA 模型测试](https://openfga.dev/docs/modeling/testing)用具体用户、对象、关系与条件描述断言；本地按冻结 case 和条件观察解释覆盖 | 正式规则仍是业务标准，case 仍按原算法判断。另列计划、实际样本及未覆盖条件；不默认枚举全部组合，也不把代表样本 PASS 扩成整个适用集合已经验证 |
| 业务结果被运行对应或当前材料状态覆盖 | 使用现有独立事实所有者，读取层组合结果完整性、业务判断、当前适用性与运行对应 | 增加明确的读模型与消费者迁移成本；界面先给任务相关摘要，需要时深入。无独立源码对应的外部 HTTP 结果仍能准确交付，运行对应事实继续可见 |
| 定义变化后用户难区分原配置和新缺项 | [Terraform plan](https://developer.hashicorp.com/terraform/cli/commands/plan)将当前事实、期望差异和拟执行动作分开 | 复用已有材料和兼容约束，细分语义变化、配置存在、复用依据及待核验项；新定义不得直接继承旧 READY。运行核验继续由原 Worker/Runner 和提交前预览承担 |
| 未查和未决项可统计，却难继续处理 | [GOV.UK check answers](https://design-system.service.gov.uk/patterns/check-answers/)提供具体修改入口、预填已有回答并返回原核对位置 | 采用具名对象、准确引用、处理入口和回程；不将每次操作改为多页向导。历史名称来自冻结内容或准确历史版本，当前对象只提供接续信息 |
| Agent 结束与用户目标交付之间需要可检查关系 | [AIP-151](https://google.aip.dev/151)将长任务状态和结果分离；本地保留原任务、操作与权威业务产物 | 平时轻量读状态，收口时才核对指定目标、范围和可读取正式产物。业务 BLOCK 与检查交付完成可以同时成立；修复仍由原题及正常功能证明 |

对使用成本的判断沿相同业务要求、正常对照、环境与证据口径展开，分别观察新增决定、重复输入/录制、定位求助、中断恢复及等待。原路径与改进路径尚无可比实测时，只陈述实际变化及待验证收益，不用工具调用数或测试数量替代价值。

## 上游复用的核对与维护

复用分歧按“本地现象与最小复现 → lock/实际版本与用法 → 官方文档 → Issue/PR → 版本源码/测试 → 合并与发布 → 本地适配和邻域验证”调查。搜索没有命中时，先检查调用条件和实现前提；它是缩小原因的线索，不是上游不存在问题的证明。PR 已关闭也要区分合并、拒绝及已发布版本，旧版本相似现象须重新比对根因。

2026-11-13 审计基线的 Python 实际环境与锁定版本为 FastAPI 0.141.1、Starlette 1.6.0、Pydantic 2.13.4、SQLAlchemy 2.0.51、HTTPX 0.28.1、MCP 2.1.1；前端版本和具体适配由[前端组件依据](前端/设计依据.md#组件复用与版本适配)维护。这是调查定位条件，未来依赖变化时先重核，不把该组版本固化为长期升级目标。

| 复用点及官方核对 | 本地采用理由与边界 | 修改/升级时的直接验收与退出条件 |
| --- | --- | --- |
| FastAPI lifespan：[PR #2944](https://github.com/fastapi/fastapi/pull/2944)引入 lifespan，[官方生命周期说明](https://fastapi.tiangolo.com/advanced/events/)明确装配方式；[MCP SDK v2.1.1 ASGI](https://github.com/modelcontextprotocol/python-sdk/blob/v2.1.1/docs/run/asgi.md)说明挂载子应用生命周期需宿主显式管理 | 现有 [HTTP app](../../product/backend/interfaces/http/app.py) 使用 AsyncExitStack 管理共享资源，进入 session_manager.run，关闭协作/Worker/批次后释放。该做法有官方依据，保留；不混用 MCP v1 或其他 FastMCP 项目的故障结论 | 宿主启动、部分启动失败及正常退出时资源准确获得/释放；不重复运行 session manager，不让共享资源先于任务退出。只有升级后官方生命周期责任及本地装配同时改变时再调整 |
| HTTPX [Transports](https://www.python-httpx.org/advanced/transports/) 与 httpcore [sni_hostname 扩展](https://www.encode.io/httpcore/extensions/#sni_hostname) | 固定 loopback 连接使用公开 BaseTransport，并保留逻辑 Host、Cookie 与 TLS 主机名；信任环境关闭。目标请求留在 Worker/Runner。当前授权适配限 localhost 的受控本机合同，不扩成任意域名或写入历史证明 | 核对固定连接、主机名、重定向、解析漂移、证书拒绝、超时和预算的直接邻域。新可信 TLS/远程范围需单独授权与证据；上游升级破坏公开扩展或明确目标合同变化才重设计 |
| Pydantic [历史 Issue #418](https://github.com/pydantic/pydantic/issues/418)与 [v2.13.4 model_copy 源码](https://github.com/pydantic/pydantic/blob/v2.13.4/pydantic/main.py) | model_copy 的 update 按可信数据复制而不执行输入校验，这是明确语义。现有可信构造、冻结模型及摘要构造可保留；外部输入、跨进程根文档和独立 reader 的接受由原校验边界负责，不能拿 copy 充当 validate | 审查实际跨边界构造点及非法输入邻域；未复现穿透不记为安全漏洞。发现不可信数据进入可信复制时修该接受边界，不全局覆盖 copy 或给每次可信内部复制增加重验 |
| SQLAlchemy [Session 并发契约](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks)与 [SQLite legacy transaction mode](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#legacy-transaction-mode-with-the-sqlite3-driver) | [StorageUnitOfWork](../../product/backend/infrastructure/storage/unit_of_work.py) 每用例创建 Session、同用例仓储共享，退出 rollback/close。只读快照显式 BEGIN、写入早锁 BEGIN IMMEDIATE 服务于 SQLite 的真实事务语义；保留 | 回查一致快照、并发修订冲突、回滚及退出清理。不得因外层已有 session.begin 就直接删除 SQLite 显式动作；若未来驱动事务模式改变，先实测等价性再收敛，不引入全局共享 Session |

维护责任随事实所有者走：组件适配由前端共享层负责，生命周期由宿主装配负责，网络适配由执行基础设施负责，校验由接受边界负责，事务由 Unit of Work 负责。记录准确来源、版本条件、接管范围及退出条件即可；不为每个依赖建立永久调查文件，不因复用本身增加微服务、通用工作流总线或新框架。

## 运行质量如何改进

本地后端的可靠性采用[Google AIP-155请求标识](https://google.aip.dev/155)、[AIP-193错误](https://google.aip.dev/193)和[AIP-151长任务](https://google.aip.dev/151)中的稳定请求身份、可解释失败与提交/结果分离。检查重试先读原冻结请求和回执，新请求才重建当前材料；它不授权未知副作用重放。错误分类由HTTP与MCP共享，日志只传递有界诊断关联，不创建通用命令总线。排队按事务内预算接纳，采用[Google SRE过载处理](https://sre.google/sre-book/handling-overload/)的明确拒绝思路，不增加分布式调度服务；执行并发、批准与Runner隔离保留。

查询按照准确对象、最新目录与完整历史分工，参考[AIP-158分页兼容要求](https://google.aip.dev/158)；旧全量接口不静默截断。长期协作的逐条读取明显降低本地峰值分配，耗时收益较小，因此保留原文档表和严格接受，不新增重复索引或拆表。新增接纳计数和输出校验分别测量，结论见[性能与读取](性能与读取.md)。这些取舍贯彻[SRE简单性](https://sre.google/sre-book/simplicity/)；未在当前单机规模引入微服务、全局缓存、通用重试框架或额外遥测平台。

[Google SRE 的监控实践](https://sre.google/sre-book/monitoring-distributed-systems/)区分用户遇到的症状与内部原因，强调延迟、错误和资源负载。[简单性原则](https://sre.google/sre-book/simplicity/)要求改动服务于实际业务，减少额外复杂度。界鉴采用分段计时、真实就绪检查和明确资源所有者，不照搬分布式监控平台、微服务或额外缓存层。

启动调查发现，调用方提交的阶段、耗时和浏览器打开状态曾被日志格式化器丢弃；服务导入还位于锁清理范围之外。现将冷导入、应用装配、Worker启动与浏览器打开分别记录，导入失败也恢复环境并释放锁。日志只接收固定阶段、有限非负耗时及布尔状态，继续脱敏，不透传任意上下文。代价是维护少量固定事件字段；它们用于诊断，不改变公共协议、就绪和安全结论。

[Google Apigee 的API实现指导](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/best-practices-api-proxy-design-and-development)说明大载荷会放大CPU和内存成本，应设置范围并按需求流式处理。这里不引入网关，只将六处原本完整缓冲后检查大小的字节入口改为逐块限量，原参照上传复用同一读取机制，继续使用原限额和错误。依据[Starlette线程池](https://www.starlette.io/threadpool/)与[请求流](https://www.starlette.io/requests/)，配置接口的同步存储放入既有线程池，网络接收继续异步；不创建新线程池，不把目标执行迁回API。代价是相邻配置可能并发进入，依旧由现有事务、预期修订和幂等回执约束，不让调度方式替代业务一致性。

优化必须以完整路径实测决定。移除重复动画子进程降低进程创建，未在真实终端对照中证明整体显著提速；全局字节码缓存原型反而增加准备成本，因此未采用。后续性能改动先定位主要耗时，再验证相同输入与负载下的完整启动，不以局部微测量推断整体收益。准确契约见[启动与退出](能力/启动与退出.md)和[性能与读取](性能与读取.md)。

## 文档如何组织

[GitHub Docs 内容模型](https://docs.github.com/en/contributing/style-guide-and-content-model/about-the-content-model)与[文章结构](https://docs.github.com/en/contributing/style-guide-and-content-model/contents-of-a-github-docs-article)把操作拆成必要条件、动作和读者可观察结果。[Django 文档规范](https://docs.djangoproject.com/en/dev/internals/contributing/writing-documentation/)强调教程应让读者尽早完成实际工作，背景与参考保持可查而不淹没主线。

正文区分连续学习步骤、具体操作、原因解释与准确参考。产品指南按业务任务聚合，小型概念与演练放在所属指南中，工程契约和声明参考分别维护；不为内容类型机械增加目录。代价是需要维护任务、实现与验证之间的对应关系，因此用检查器保护本地依赖、标题和静态参考，语义正确性仍由维护者核对。

## 测试如何选择

[Sentry 测试指南](https://develop.sentry.dev/development-infrastructure/testing/)重点保护接口的角色、跨组织访问和非法输入，并允许按目录、文件或用例执行；其[前端测试规范](https://develop.sentry.dev/frontend/using-rtl/)以使用场景和可见结果组织断言。界鉴据此保留真实业务边界与历史回归，不因模块拆分删掉角色、归属、事务、秘密或证据场景。

[GitLab 测试策略](https://docs.gitlab.com/development/testing_guide/testing_strategy/)要求明确所有者、先运行相关范围、逐步扩大，并在新建用例前核对已有覆盖。它与 Sentry 的测试分布不同，因此这里不照搬固定比例；每份测试需有具体风险与合适的验证层级。

[Grafana 的端到端组织](https://github.com/grafana/grafana/blob/main/contribute/style-guides/e2e-playwright.md)区分页面、组件和可复用业务流程，并按功能组织所有权。采用资源夹具、业务场景和界面读取分工；不照搬其跨版本选择器设施，当前界面优先使用可访问角色与名称。

[Google 测试大小说明](https://testing.googleblog.com/2010/12/test-sizes.html)按资源与执行成本区分测试；[提高测试真实性](https://testing.googleblog.com/2024/02/increase-test-fidelity-by-avoiding-mocks.html)讨论过度替身与真实协作之间的差距。这里采用范围与 L1 至 L5 程度组合，不规定测试比例，不自动逐级跑满。

纯判断以确定性用例保护，HTTP 和事务用实际相邻组件，真实浏览器与官方目标只放在显式高等级场景。这样减少无关执行，同时保留无法由低成本用例证明的边界；范围选择仍需基于改动分析，工具不会替人证明影响分析完整。

[pytest 夹具指南](https://docs.pytest.org/en/stable/how-to/fixtures.html)用于将资源获得与清理放在同一所有者。[Playwright 最佳实践](https://playwright.dev/docs/best-practices)与[浏览器上下文隔离](https://playwright.dev/docs/browser-contexts)用于独立场景、可访问定位与等待实际内容。场景分别拥有服务、官方业务和浏览器，不以任意休眠、CSS 类名或重复写入判断成功。独立启动增加成本，因此只在相应资源或协作变化时运行。

## 模块为何这样划分

[Django 的设计哲学](https://docs.djangoproject.com/en/dev/misc/design-philosophies/)以高内聚和低耦合解释模块边界，[Feature-Sliced Design 的层级规则](https://feature-sliced.design/docs/reference/layers)则区分前端所有者及依赖方向。这里按共享状态、真实消费者和共同变化原因调整模块：源码检测显式共享候选收集器，账号登录的任务执行与进程监督归同一用例，纯录制事实与数据库、浏览器夹具分离。不按文件行数机械拆分，也不把纯类型引用环当成运行时循环。代价是重组时必须同步注册、导入和测试消费者，保留公共格式及执行语义。

[Bulletproof React 的目录说明](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)允许集中测试工具，也要求只创建实际需要的层级。界鉴将构建配置、全局测试初始化和编辑器解析器归入前端的 tooling，行为测试与模块相邻。[Vite 的配置机制](https://vite.dev/config/)允许通过 `--config` 显式定位；[TypeScript 的配置规则](https://www.typescriptlang.org/tsconfig/)需要考虑相对路径和编辑器发现，因此 tsconfig 保留在前端根。测试初始化遵循 [Vitest setupFiles](https://vitest.dev/config/setupfiles) 的加载机制，不进入产品入口。

[pytest 的目录实践](https://docs.pytest.org/en/stable/explanation/goodpractices.html)支持测试与应用分开组织。界鉴的 Python 行为测试留在仓库测试树，跨能力夹具集中在 `tests/support`，局部辅助保留就近性。[FastAPI 大型应用说明](https://fastapi.tiangolo.com/tutorial/bigger-applications/)将路由和依赖拆分后统一装配；这里将 HTTP、CLI 与 Worker 命令视为不同入口，基础设施只提供机制，不反向导入组合根。

这些参考共同提供职责和依赖判断，不能证明某个固定目录名适合所有项目。采用逐级职责分组、共享输入单一所有者和无运行导入环的规则，避免空占位目录、重复指纹计算和相互导入的装配。代价是移动时需要同步入口字符串、夹具引用和生成参考；验证保护实际调用及安全边界，不固定文件数量。

[Python JSON 文档](https://docs.python.org/3.13/library/json.html)说明默认解码可接受重复对象名和非有限数，并提供成对读取、数值解析等扩展入口。界鉴将这些共同的拒绝规则集中在协议 codec，格式版本、模型关联和秘密检查继续由独立 reader 负责。这样可以统一修复字节解析缺口，同时保留不同格式的消费者和错误语义；公共 codec 的变化需要验证全部直接使用者。

[Feature-Sliced Design](https://feature-sliced.design/docs/reference/layers)和 [Bulletproof React](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)提供按职责聚合和限制依赖的方法。前端采用 app、pages、entities、shared，保留真实共用部分，不为凑层次建立空壳。

[FastAPI 大型应用](https://fastapi.tiangolo.com/tutorial/bigger-applications/)与 [lifespan](https://fastapi.tiangolo.com/advanced/events/)用于显式接口装配和资源生命周期；[Cosmic Python 服务层](https://www.cosmicpython.com/book/chapter_04_service_layer.html)用于区分用例和外部机制。界鉴还必须保留受控 Worker、Runner、秘密和发布边界，普通 Web 示例不能直接替代这些约束。

## 工程工具如何组织

[Python的子进程生命周期](https://docs.python.org/3.13/library/subprocess.html#subprocess.Popen.poll)区分进程结束与调用者回收状态。POSIX监督先回收自己拥有的根，再查询进程组中的后代，避免把僵尸根当作仍在执行；不以根返回码代替整组退出。[OCI Linux配置](https://github.com/opencontainers/runtime-spec/blob/main/config-linux.md)用于明确容器的用户映射、进程、挂载与网络命名空间；容器实跑证据只覆盖声明组合，不能代替宿主资源约束或任意恶意目标隔离保证。[uv离线缓存说明](https://docs.astral.sh/uv/concepts/cache/)用于区分注册表元数据缓存与锁定wheel；离线装配接受显式本地wheel来源，仍核验锁文件哈希。

[VS Code 的启动脚本](https://github.com/microsoft/vscode/blob/main/scripts/code.bat)将准备工作交给[独立准备模块](https://github.com/microsoft/vscode/blob/main/build/lib/preLaunch.ts)，[FastAPI 的维护工具](https://github.com/fastapi/fastapi/tree/master/scripts)将文档、测试与发布操作留在产品之外，[CPython 的目录职责](https://devguide.python.org/getting-started/setup-building/#directory-structure)则分别说明维护工具、可执行程序源码与平台构建文件。这里采用入口调度、工具实现和产品运行组件分属不同所有者的方法，不照搬它们的目录规模。

PowerShell 保留 Python 就绪前的引导能力；环境恢复和文件身份机制共用，阶段展示与普通命令输出分别维护。发行组装按运行环境、资源、启动器、校验和归档分工，产品说明只有一份正文来源。代价是移动模块时必须同步装配、包资源和真实入口验证，因此测试保护参数、失败清理、环境恢复及独立启动行为，不固定内部文件数量。

## 数据库为何采用完整基线

[Alembic Cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html#building-an-up-to-date-database-from-scratch)说明从当前结构直接初始化与后续结构演进可以分开。界鉴采用完整基线、工作区代际和原子初始化，已结束旧库正常运行支持。相关且尚未发布的变更集中完善基线；发布后的真实结构变更才追加有明确数据处理和恢复条件的迁移。
