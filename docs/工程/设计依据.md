# 设计依据与采用边界

外部资料用于提出有理由、可验证的选择。以下说明采用了什么、解决什么问题以及付出的代价；资料不能代替本产品的实现和验证。

## 文档如何组织

[GitHub Docs 内容模型](https://docs.github.com/en/contributing/style-guide-and-content-model/about-the-content-model)与[文章结构](https://docs.github.com/en/contributing/style-guide-and-content-model/contents-of-a-github-docs-article)把操作拆成必要条件、动作和读者可观察结果。[Django 文档规范](https://docs.djangoproject.com/en/dev/internals/contributing/writing-documentation/)强调教程应让读者尽早完成实际工作，背景与参考保持可查而不淹没主线。

正文区分连续学习步骤、具体操作、原因解释与准确参考。产品指南按业务任务聚合，小型概念与演练放在所属指南中，工程契约和声明参考分别维护；不为内容类型机械增加目录。代价是需要维护任务、实现与验证之间的对应关系，因此用检查器保护本地依赖、标题和静态参考，语义正确性仍由维护者核对。

## 测试如何选择

[Sentry 测试指南](https://develop.sentry.dev/development-infrastructure/testing/)重点保护接口的角色、跨组织访问和非法输入，并允许按目录、文件或用例执行；其[前端测试规范](https://develop.sentry.dev/frontend/using-rtl/)以使用场景和可见结果组织断言。界鉴据此保留真实业务边界与历史回归，不因模块拆分删掉角色、归属、事务、秘密或证据场景。

[GitLab 测试策略](https://docs.gitlab.com/development/testing_guide/testing_strategy/)要求明确所有者、先运行相关范围、逐步扩大，并在新建用例前核对已有覆盖。它与 Sentry 的测试分布不同，因此这里不照搬固定比例；每份测试需有具体风险与合适的验证层级。

[Grafana 的端到端组织](https://github.com/grafana/grafana/blob/main/contribute/style-guides/e2e-playwright.md)区分页面、组件和可复用业务流程，并按功能组织所有权。采用资源夹具、业务场景和界面读取分工；不照搬其跨版本选择器设施，当前界面优先使用可访问角色与名称。

[Google 测试大小说明](https://testing.googleblog.com/2010/12/test-sizes.html)按资源与执行成本区分测试；[提高测试真实性](https://testing.googleblog.com/2024/02/increase-test-fidelity-by-avoiding-mocks.html)讨论过度替身与真实协作之间的差距。这里采用范围与 L1 至 L5 程度组合，不规定测试比例，不自动逐级跑满。

纯判断以确定性用例保护，HTTP 和事务用实际相邻组件，真实浏览器与官方目标只放在显式高等级场景。这样减少无关执行，同时保留无法由低成本用例证明的边界；范围选择仍需基于改动分析，工具不会替人证明影响分析完整。

[pytest 夹具指南](https://docs.pytest.org/en/stable/how-to/fixtures.html)用于将资源获得与清理放在同一所有者。[Playwright 最佳实践](https://playwright.dev/docs/best-practices)与[浏览器上下文隔离](https://playwright.dev/docs/browser-contexts)用于独立场景、可访问定位与等待实际内容。场景分别拥有服务、官方业务和浏览器，不以任意休眠、CSS 类名或重复写入判断成功。独立启动增加成本，因此只在相应资源或协作变化时运行。

## 模块为何这样划分

[Bulletproof React 的目录说明](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)允许集中测试工具，也要求只创建实际需要的层级。界鉴将构建配置、全局测试初始化和编辑器解析器归入前端的 tooling，行为测试与模块相邻。[Vite 的配置机制](https://vite.dev/config/)允许通过 `--config` 显式定位；[TypeScript 的配置规则](https://www.typescriptlang.org/tsconfig/)需要考虑相对路径和编辑器发现，因此 tsconfig 保留在前端根。测试初始化遵循 [Vitest setupFiles](https://vitest.dev/config/setupfiles) 的加载机制，不进入产品入口。

[pytest 的目录实践](https://docs.pytest.org/en/stable/explanation/goodpractices.html)支持测试与应用分开组织。界鉴的 Python 行为测试留在仓库测试树，跨能力夹具集中在 `tests/support`，局部辅助保留就近性。[FastAPI 大型应用说明](https://fastapi.tiangolo.com/tutorial/bigger-applications/)将路由和依赖拆分后统一装配；这里将 HTTP、CLI 与 Worker 命令视为不同入口，基础设施只提供机制，不反向导入组合根。

这些参考共同提供职责和依赖判断，不能证明某个固定目录名适合所有项目。采用逐级职责分组、共享输入单一所有者和无运行导入环的规则，避免空占位目录、重复指纹计算和相互导入的装配。代价是移动时需要同步入口字符串、夹具引用和生成参考；验证保护实际调用及安全边界，不固定文件数量。

[Feature-Sliced Design](https://feature-sliced.design/docs/reference/layers)和 [Bulletproof React](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)提供按职责聚合和限制依赖的方法。前端采用 app、pages、entities、shared，保留真实共用部分，不为凑层次建立空壳。

[FastAPI 大型应用](https://fastapi.tiangolo.com/tutorial/bigger-applications/)与 [lifespan](https://fastapi.tiangolo.com/advanced/events/)用于显式接口装配和资源生命周期；[Cosmic Python 服务层](https://www.cosmicpython.com/book/chapter_04_service_layer.html)用于区分用例和外部机制。界鉴还必须保留受控 Worker、Runner、秘密和发布边界，普通 Web 示例不能直接替代这些约束。

## 界面如何保持连续

[Fluent 2 动效](https://fluent2.microsoft.design/motion)与 [Atlassian 动效](https://atlassian.design/foundations/motion/applying-motion/)强调功能、方向和连续性。采用零延迟命中的短悬停、可打断页面交接与分开的局部反馈，不把所有变化设为整页淡入。

[View Transitions](https://developer.chrome.com/docs/web-platform/view-transitions/same-document)用于只捕获工作面；[Carbon 加载模式](https://carbondesignsystem.com/patterns/loading-pattern/)用于已知结构占位；[字体建议](https://web.dev/articles/font-best-practices)用于提前发现字体并控制迟到替换。当前字体选择保留短等待和后备方案，原生过渡保留回退及减少动效路径。参数正确不能保证主观流畅，仍需真实动态观察。

## 工程工具如何组织

[VS Code 的启动脚本](https://github.com/microsoft/vscode/blob/main/scripts/code.bat)将准备工作交给[独立准备模块](https://github.com/microsoft/vscode/blob/main/build/lib/preLaunch.ts)，[FastAPI 的维护工具](https://github.com/fastapi/fastapi/tree/master/scripts)将文档、测试与发布操作留在产品之外，[CPython 的目录职责](https://devguide.python.org/getting-started/setup-building/#directory-structure)则分别说明维护工具、可执行程序源码与平台构建文件。这里采用入口调度、工具实现和产品运行组件分属不同所有者的方法，不照搬它们的目录规模。

PowerShell 保留 Python 就绪前的引导能力；环境恢复和文件身份机制共用，阶段展示与普通命令输出分别维护。发行组装按运行环境、资源、启动器、校验和归档分工，产品说明只有一份正文来源。代价是移动模块时必须同步装配、包资源和真实入口验证，因此测试保护参数、失败清理、环境恢复及独立启动行为，不固定内部文件数量。

## 数据库为何采用完整基线

[Alembic Cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html#building-an-up-to-date-database-from-scratch)说明从当前结构直接初始化与后续结构演进可以分开。界鉴采用完整基线、工作区代际和原子初始化，已结束旧库正常运行支持。相关且尚未发布的变更集中完善基线；发布后的真实结构变更才追加有明确数据处理和恢复条件的迁移。
