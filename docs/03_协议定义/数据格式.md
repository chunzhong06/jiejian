# 数据格式

## 配置 YAML

| 文件 | 内容 | 真源 |
| --- | --- | --- |
| `project.yaml` | Project slug、目标范围、身份秘密引用、资源、Flow/Contract 相对路径、观察器和 seed。 | `verification/inputs.py`、`verification/models.py` |
| `flow.yaml` | 有序 HTTP 步骤、身份/资源关系、期望状态和测试 reset。 | `verification/models.py` 的 `Flow`/`FlowStep` |
| `contract.yaml` | ACTIVE Contract、版本、RuleKind、观察者和严重度。 | `verification/models.py` 的 `SecurityContract` |

`flow` 和 `contract` 必须是相对 `project.yaml` 所在目录的路径，解析后不得越界。样例因此各自保留完整 bundle，不跨目录共享同名文件。

阶段 5.1 的数据库 Contract Version 不替换上述 YAML 执行格式：它保存同一 `SecurityContract` 内容快照和治理 provenance，Runner V1 仍只消费持久执行请求中的快照。

## 阶段 6.1～6.2 V2 权限模型与关系覆盖计划

`backend/src/jiejian/verification/permissions.py` 已实现独立的 `PermissionContractV2` 和 `NormalizedPermissionPlan`。V2 Contract 显式保存 `role_ids`、subject、action、resource、relation、context、expected result 和 required observers，并对角色/动作/状态引用、关系端点、从主体连续到资源的有向关系路径、context 与资源事实、租户/部门边界、父子与继承图、冲突 ALLOW/DENY 和观察器要求执行严格校验。模型使用规范 JSON 和 SHA-256 指纹；集合字段按稳定规则规范化。

公共机器 Schema 为 `schemas/contracts/permission-contract-v2.schema.json`、`schemas/contracts/normalized-permission-plan-v2.schema.json` 和 `schemas/contracts/permission-mutation-plan-v2.schema.json`，由模型 Schema 漂移测试保护。`compile_permission_plan` 保持每条 V2 rule 一个规范用例；`build_permission_coverage_plan` 另行按显式 ROLE/TENANT/DEPARTMENT/RELATION/WORKFLOW/BULK 维度生成确定性最近禁止邻居，普通规则同时记录 ALLOW/DENY baseline 和维度覆盖，按 seed+engine 对同优先级候选排序，记录覆盖、缺口、去重和预算结果，并保存不是阶段 7 最终 Finding ID 的 finding 前置身份。批量资源按资源 ID 规范排序；缺失前置条件和超出关系深度均形成带目标的 gap。`adapt_v1_ownership_plan` 只将既有 `MutationPlan` 投影到同一中间表示，保留原 case、fingerprint、rule、step、identity、resource、seed 和 engine 信息，不改变 V1 规划或执行路径。

V2 模型、Schema、覆盖计划和 `samples/*_apps/permissions_v2/` 资产已由正式无秘密 Permission Profile 入口接入；阶段 6 已由稳定 `python -m jiejian.runner` 入口按 schema_version 分派 Runner V2，并在 staging 生成 Evidence/Result 工件。6.3B 的只读 SQLite observer 仍是 Runner 隔离域内的独立观察边界。Worker supervision、持久请求、staging 校验、原子 publication 和基础 V2 结果读取已复用既有生命周期接线。当前新增无秘密 `PermissionExecutionProfileV2` 源文件、0008 Profile 摘要表、共享 Application 服务及显式 API/CLI V2 入口；完整 Profile、计划和运行快照仍只保存在源文件与 request/publication 链，jobs/runs 不新增协议字段。样例 Contract 不伪装成 V1 `project.yaml`；正式样例仅绑定回环地址并通过环境凭据运行，V1 ownership Contract/Runner、API/CLI V1 仍保持原有可执行路径。

## 阶段 6.3A Observer V2 公共协议与 owner_api 兼容投影

`backend/src/jiejian/protocols/observer_v2.py` 提供严格 `ObserverSpecV2`、`ObservationEnvelopeV2` 和 `ObserverOutcomeV2`，签入 Schema 位于 `schemas/observer/`。协议支持 OWNER_API 与 READ_ONLY_SQLITE 的 tagged locator；locator、phase、window、correlation、脱敏规范状态、source hash、causality 和 COMPLETE/PARTIAL/MISSING/TIMED_OUT/UNSUPPORTED/ERROR 矩阵均拒绝越界或秘密。

现有 V1 `SnapshotRunExecutor._observe_owner` 仍通过 `HttpExecutor` 执行相同 GET、token、TargetGuard、预算、超时、重定向和响应脱敏；`OwnerApiObserverV2Adapter` 只在该边界内构造 envelope，并立即由 `project_owner_envelope_to_v1` 恢复原 `Observation(observer="owner_api", phase=小写, status_code, data)`。V1 Runner Schema、Observation/Evidence、历史工件和 Verdict 不变。required 观察不完整只产生既有 INCONCLUSIVE/缺失语义，不隐式降级到 HTTP；Runner V2 另行生成 V2 Evidence/Result staging 工件，Profile 后端入口与 0008 非秘密摘要迁移在后续独立批次实现，数据库 observation 明细和样例仍未实现。

## 阶段 6.3B Runner 隔离域只读 SQLite 观察

`backend/src/jiejian/runner/sqlite_observer.py` 是 Runner-side supervisor，`backend/src/jiejian/runner/observer_process.py` 是包内专用子进程入口。监督器在 attempt 临时目录写入无秘密 `ObserverInvocationV2`，只从 `database_secret_ref=env:NAME` 选择一个环境变量启动固定解释器；输入、输出和子进程标准流不承载数据库定位之外的秘密，完成或失败后精确清理。正式 `jiejian.runner` V1 入口不变。

本批仅注册 `resource-state` → `resource_state` 模板，固定参数化查询 `resource_id`，禁止调用方提供 SQL、DDL/DML、PRAGMA、多语句或其他表。子进程以 SQLite URI `mode=ro` 打开并启用内部 `PRAGMA query_only=ON`，使用 progress handler、父进程墙钟监督、行数和规范状态字节预算；成功为 `COMPLETE/AVAILABLE`，required 的缺失、不可用、未支持、超时、部分或查询错误为 `INCONCLUSIVE`，子进程崩溃/输出损坏为 `EXECUTION_ERROR`。这些 envelope 只表达观察完整性，不决定 SAFE/VULNERABLE/PASS/BLOCK；Runner V2 输入/结果、Profile 0008 摘要迁移及后端入口属于独立接线批次，SQLite observer 本身不改变样例、Evidence 或报告格式。

## 阶段 6.3C 多观察器配对验收

现有 `permission_sample_app` 可由定向测试提供测试临时 SQLite 路径；服务仍只绑定 loopback，目标库不是界鉴 storage。fixed 与 vulnerable 使用同一 Contract、请求、`resource-state` 模板和预算：同一禁止 `PATCH` 均返回 HTTP 403，fixed 的 BEFORE/AFTER envelope 状态/hash 相同，vulnerable 的目标资源状态/hash 改变。比较只在 required SQLite outcome 为 `AVAILABLE` 且 envelope 为 `COMPLETE/CORRELATED` 时进行；HTTP 状态不替代数据库观察。配对资产只保存非秘密观察模板和预期，不保存路径、secret、SQL 或 V1 `project.yaml`。

## 阶段 6.4 结构化审计日志观察

Observer V2 现支持 `STRUCTURED_AUDIT_LOG`、`AUDIT_LOG_WINDOW` provenance 和 `EVENTUAL` phase。审计 locator 由 `authorized_root_ref=env:NAME`、固定 `relative_file_pattern`、字段 allowlist 和独立 `AuditLogScanBudgetV2` 组成；审计调用使用独立 `AuditLogObserverInvocationV2`，以有界内容锚点 cursor 支持轮转续读。旧 `ObserverBudgetV2` 与 `ObserverInvocationV2` 的 6.3 字段及 canonical bytes/hash 不变。

Observer V2 另支持 `ASYNC_TASK_STATUS` 与 `ASYNC_TASK_API` provenance。异步 locator 使用固定 IPv4 origin、恰一次 `{request_marker}` 的相对路径、`env:` 只读凭据引用、显式 loopback/private 授权和独立 `AsyncTaskPollBudgetV2`；异步调用使用独立 `AsyncTaskObserverInvocationV2`。目标响应只允许有限 schema 和六态任务状态，`NOT_CREATED` 的权威负观察与 `QUEUED/RUNNING` 的观察超时严格区分；输出不含 URL、凭据或原始响应。三类本机异步样例通过四面 faceted facts 验证，并已由 Runner V2 生成 Evidence/Result；V1 Runner 不变。

阶段 6.5A 已冻结 `AZURE_QUEUE_PEEK` 与 `AZURE_BLOB_OBJECT` Observer V2 locator/provenance。Queue locator 使用规范 Azure account endpoint 或显式授权的 loopback Azurite endpoint、独立测试队列、`env:` Queue SAS 引用、有限字段和 `QueuePeekBudgetV2`，只允许 `EVENTUAL` Peek；Blob locator 使用独立测试 container、`env:` Container SAS 引用、恰一次 `{request_marker}` 的安全 prefix、metadata allowlist 和 `BlobObjectScanBudgetV2`，只允许 `BEFORE/AFTER/EVENTUAL`。嵌套预算必须不超过通用观察预算，required 不完整仍为 `INCONCLUSIVE`。六份 Observer Schema 均由对应模型原生 Schema 签入；共享 spec 定义扩展会机械反映到 audit/async invocation Schema，不改变旧实例 canonical/hash 或 V1 行为。Queue Peek 与 Blob Object Runner 隔离 REST 适配器均已实现并通过本机 Azurite 动态验证；Runner V2 现可调度这两类适配器并生成对应 Evidence/Result 工件，测试页高级复杂权限入口与验证页 V2 Evidence 展示已接线，动态样例和正式产品入口仍未实现。

Runner-side 审计观察器只在授权根顶层读取固定 JSONL 轮转族，使用 stat/offset/快照大小和文件、字节、行预算，拒绝子目录、链接、UNC/device/相对路径、BOM、重复键、非有限数字、嵌套字段、部分尾行和 event/task/sequence/resource 冲突。envelope 只携带匹配记录摘要、next offset、扫描计数和相对文件窗口 hash，不携带绝对路径或秘密。required 观察不完整或无法用显式 case correlation 闭合时为 `INCONCLUSIVE`；不使用时间邻近补因果。Runner V2 input/result 与 Evidence V2 已接入 Runner、Worker、staging/publication、Profile/API/CLI 和验证页；0008 migration 只保存非秘密 Profile 摘要，不保存 observation 明细。

## 契约治理记录

| 记录 | 核心字段 | 约束 |
| --- | --- | --- |
| Requirement | `schema_version`、requirement/project ID、来源类型/定位/SHA-256、文本、security tags、创建审计 | 冻结；拒绝秘密、Bearer 和凭据赋值文本 |
| ContractCandidate | `schema_version`、candidate/project ID、来源、一个 `ContractRule`、Requirement 引用、创建审计；LLM 来源另有 `LLMGenerationMetadata` | 始终不可信；引用不得跨 Project；不能直接 ACTIVE；非 LLM 来源不得携带 LLM metadata |
| ContractVersion | `schema_version`、project/contract/version、status、`SecurityContract` 快照、provenance、上一版本、审计轨迹 | 规则非空且 Rule ID 唯一；ACTIVE/SUPERSEDED 正文不可原地修改 |

Contract Version 状态只允许 `DRAFT → REVIEW → ACTIVE/REJECTED` 和 `ACTIVE → SUPERSEDED`。激活新版本时旧 ACTIVE 与新 ACTIVE 的状态变化同事务提交。同一 Project/Contract 只有一个 ACTIVE。

真源：`backend/src/jiejian/contracts/models.py`、`contracts/governance.py`、`contracts/governance_service.py`、`storage/models/`，决策见 [ADR-0011](../02_技术决策/ADR-0011-阶段5契约治理基础.md)。Contract 内部模型不是 `schemas/` 公共机器契约。

LLM 候选输出只接受 `schema_version=1`、有界 JSON：每项仅含授权 `requirement_ids` 与现有 `ContractRule`。`LLMGenerationMetadata` 保存 provider/model、adapter、prompt template 身份与 hash、规范 input/output hash；原始 prompt 和模型响应不持久化。`contract_candidates.llm_metadata_json` 由迁移 `0005_stage5_llm_candidate_metadata` 可空增加，旧非 LLM 记录读取为 `None`。项目治理绑定由 `0006_stage5_governed_project_binding` 增加。

### LLM profile、秘密与 provider 协议

阶段 5.6 的模型服务设置不是新的用户业务阶段。非秘密 profile 由 `0007_stage5_llm_profiles` 新增的 `llm_profiles` 表保存，字段为 `schema_version`、`profile_name`、`provider`、`model`、可选 `base_url`、`timeout_ms`、`max_input_bytes`、`max_output_bytes`、`max_budget_microusd`、`enabled`、`secret_ref`、`allow_local_http`、`created_at_us` 和 `updated_at_us`。旧数据库向前升级后新增表为空；迁移不提供 downgrade，恢复旧程序依赖备份或旧版本新库。

provider 只允许 `openai`、`deepseek`、`gemini`、`openai_compatible`。OpenAI/DeepSeek/compatible 使用同一 OpenAI-compatible HTTP 协议族但 profile provider 显式区分；Gemini 使用独立传输边界。当前服务仍默认离线，启动不访问模型、不测试连接、不自动降级或切换 profile。

`secret_ref` 只保存 `env:NAME` 或 `cred:jiejian/llm/<profile_name>` 引用；Windows 本机秘密使用 Credential Manager 泛型凭据 `CredWriteW`/`CredReadW`/`CredDeleteW`。写入 API 的 `secret` 是 write-only，不序列化回显；读取响应仅返回 `secret_ref` 和 `secret_configured`。数据库、配置文件、日志、provenance、报告和前端不得出现密钥。

`base_url` 默认只允许 HTTPS，禁止 userinfo、query、fragment、控制字符和无效 authority，并规范化 scheme/host/port/path。只有 profile 显式 `allow_local_http=true` 且 host 是 IP loopback 时允许 HTTP；该授权不影响 Runner/TargetScope。后续 httpx 客户端必须禁用自动重定向，跨 host 重定向不得携带凭据。provider wire code 固定为 `llm_auth_failed`、`llm_rate_limited`、`llm_timeout`、`llm_invalid_response`、`llm_budget_exceeded`、`llm_provider_unavailable`，通过现有 `JiejianError` 和 API `error` envelope 返回。

阶段 5.6 新 provenance 使用同一 `contract_candidates.llm_metadata_json` 列中的可选 `provenance_schema_version="2"` 扩展，保存 provider/profile、model、adapter/version、prompt version、input/output hash、UTC 时间、耗时和预算信息，不保存 secret、secret_ref、原始 prompt 或原始响应。ADR-0013 的 `LLMGenerationMetadata` schema 1 字段继续保留；旧 Candidate 缺少扩展字段时仍按 `None` 读取，不新增表迁移或签入新的公共 JSON Schema。LLM 始终只能生成不可信 Candidate，不能决定 Verdict 或绕过 assessment、REVIEW、ACTIVE。

## 契约分析与漂移派生结果

阶段 5.2 的 `CandidateBatch`、`CandidateMergeResult`、`ContractReviewAssessment`、`ContractVersionDiff` 和 `DriftReport` 都是 `schema_version=1` 的冻结结果。候选 ID、规则指纹、问题排序和结果 `canonical_sha256` 由规范 JSON 计算；结果不写入数据库，不改变 Run verdict。

需求模板只允许：

```text
rule id=foreign-read kind=foreign_read observers=http severity=high
```

解析失败返回 `AMBIGUOUS_SOURCE`；源码 bytes 与声明 hash 不一致返回阻断 `SOURCE_HASH_MISMATCH`。Flow、OpenAPI 和 FastAPI AST 候选保留来源定位；Application 只向 Domain 提供已确认 Flow 或已授权源码文本/bytes。FastAPI 文件根目录、大小、后缀、秘密路径分量和 UTF-8 边界在 Application 校验，Domain 不读取、不 import 或执行源码。

`ContractReviewAssessment` 的阻断问题包括候选冲突、来源歧义、规则不可执行、观察器不足和 LLM 候选与显式 Requirement 冲突。`DriftReport` 固定表达需求未覆盖、规则消失、路径/字段能力变化、观察器不足、已验证行为指纹变化和 LLM 冲突六类漂移。行为漂移只接受调用方提供的完整性已验证 `VerifiedBehaviorFingerprint`。

`ContractVersionDiff` 输出规则 `added`、`removed`、`changed`、状态和 provenance 差异。历史 Run 以 Run 关联 Job 的 `request_hash` 校验持久执行请求作为执行时 Contract 快照，`ContractHistorySource=EXECUTION_REQUEST`，并附带精确治理版本；无请求时才退回治理版本，不读取当前 YAML。

真源：`backend/src/jiejian/contracts/analysis/`、`contracts/llm/`、`contracts/analysis/service.py`，决策见 [ADR-0012](../02_技术决策/ADR-0012-阶段5确定性候选与漂移.md)。六类 Drift 由 `tests/contracts/` 固定测试；单个 sample 不制造全部六类。

## RunnerInputV1 与 RunnerResultV1

RunnerInputV1 加入 run/job/attempt/lease owner/Fencing Token 和完整执行快照；RunnerResultV1 返回结果类型、生命周期、Job state、verdict、reason codes、清理结果、有限错误和工件清单。

- 人类字段协议：[Runner 执行协议 V1](Runner执行协议V1.md)
- 可执行模型：`backend/src/jiejian/protocols/runner_v1.py`
- 机器 Schema：`schemas/runner/runner-input-v1.schema.json`、`runner-result-v1.schema.json`

V1 使用 UTF-8 规范 JSON，拒绝 BOM、重复键、未知字段、未知版本、NaN/Infinity 和超限字节。

## 阶段 6 Runner V2 输入、Evidence V2 与 Runner Result V2

`backend/src/jiejian/protocols/runner_v2.py` 是独立 V2 wire DTO 真源，Schema 为 `schemas/runner/runner-input-v2.schema.json`、`evidence-v2.schema.json` 和 `runner-result-v2.schema.json`。RunnerInputV2 保存带显式 subject/action/observer binding 的权限快照、规范化计划和匹配指纹；EvidenceV2 保存单 case 的 request fact、Observer V2 envelope/outcome、不可变 case snapshot、前置身份和语义 hash；RunnerResultV2 保存覆盖/gap 计数、Evidence、工件和 V1 等价的生命周期/清理矩阵，并按 SAFE/VULNERABLE/INCONCLUSIVE 聚合为 PASS/BLOCK/INCONCLUSIVE。

三个模型均严格拒绝未知字段、重复键、BOM、非有限数字、超限和已知秘密，使用独立 canonical/parser。Evidence 嵌入本 case 的完整 requirement binding，通过显式 observer_id/type 映射 outcome；观察 binding 只允许 BEFORE/AFTER/EVENTUAL，OWNER_API binding 保存非秘密 `owner_api_credential_ref`，真实凭据不进入 wire；批量 case 要求每个 resource_id×phase 都有完整、相关联的 envelope。`evidence_id` 固定为语义 hash 前缀，RequestFact 未收到响应时使用稳定 `failure_code`，该事实只能产生 INCONCLUSIVE。当前 Runner V2 执行编排按固定 BEFORE→请求→AFTER→EVENTUAL 时序调用既有观察器、投影 Verification V2 事实并原子写入 Evidence/Result staging 工件；Profile 服务负责源文件治理、确定性计划和 V2 请求冻结；0008 只保存 profile/project/source/contract/plan/engine 摘要，不保存完整配置、秘密或 observation 明细。显式 `/api/v2` Profile/Run 路由和 `permission-run` CLI 共用该服务；测试页高级复杂权限入口、验证页 V2 Evidence 展示和无秘密样例 Profile 已接线，7.1 Finding 与 7.2 Baseline/Gate 已通过稳定 Results v2、v2 API 和新 CLI 路径接线。V1 Runner 输入、结果、Schema、canonical/hash 和历史工件不变；阶段 8 统一报告仍未实现。

## Recording 与 FlowDraft 机器 Schema

Recording Runner、Recording Event 和 FlowDraft 的代码真源分别为 `backend/src/jiejian/protocols/recording_v1.py`、`flow_draft_v1.py`；签入机器 Schema 位于 `schemas/runner/` 与 `schemas/recording/`，包括 Runner input/result、Recording request/result/event、FlowDraft 和 review command。Producer/consumer 与漂移测试位于 `tests/execution/protocol/`、`tests/execution/recording/` 和 `tests/architecture/`，均保持 `schema_version="1"` 和严格未知字段拒绝。

## Evidence

Evidence 是内容寻址 JSON，包含 run/case/rule、关系变异、观察、reason codes、verdict、fingerprint 和语义内容哈希。Evidence 正文位于发布工件，SQLite 只保存 Evidence Index。

真源：`verification/models.py`、`verification/evaluation.py`、`verification/artifacts.py`。

## publication manifest

`publication-manifest.json` 随最终 Run 目录发布，记录 project/run/job/attempt/owner/Fencing Token、租约截止、发布时间、结果哈希和精确文件清单。Worker 必须验证路径、reparse point、字节数和 SHA-256；不同 manifest 不能覆盖同一 Run。

真源：`execution/published_artifacts.py`，决策见[ADR-0007](../02_技术决策/ADR-0007-阶段2工件发布与恢复.md)。

## 数据库记录与索引

SQLite 当前有十六张业务表：`projects`、`runs`、`jobs`、`job_events`、`evidence_index`、`recordings`、`flow_draft_revisions`、`requirements`、`contract_candidates`、`contract_versions`、`llm_profiles`、`permission_execution_profiles`、`findings`、`finding_occurrences`、`regression_baselines` 和 `gate_results`。它保存公共 ID、状态、时间、租约、审计、有限治理正文、非秘密 profile 配置/摘要、Finding 稳定身份、Evidence 文件引用、基线摘要和 GateResult 原因，不保存响应正文、真实秘密或大型 Evidence。

`projects.governed_contract_id` 与 `governed_contract_version` 必须同时为空或同时存在。存在时，API 新 Run 必须解析完全匹配且 ACTIVE 的治理版本；不存在时使用已校验 YAML Contract。治理绑定不改变旧持久执行请求。`findings.identity_json` 只保存规范化稳定身份，`finding_occurrences` 只保存有界状态、上下文和一个或多个已发布 Evidence ID；`regression_baselines` 只保存显式接受的 Run、Finding/Occurrence/Evidence 引用、覆盖摘要和版本，`gate_results` 只保存确定性输入 hash、逐条原因和决策；阶段 7.1/7.2 的 `0009`/`0010` 均只向前新增，历史 V1 表和工件不改写。

真源：`storage/models/` 和 `backend/migrations/versions/0001_stage2_storage.py`～`0010_stage7_gate.py`；事务边界是 `StorageUnitOfWork`。0008 只保存 Profile 治理摘要，0009 只保存稳定 Finding 索引与 Occurrence 索引，0010 只保存基线摘要和 GateResult，完整 Profile/计划/运行快照和 Evidence 正文不入库；jobs/runs 不增加版本字段。安装包通过构建期映射携带同一 migration 真源，不在源码树复制内容。
