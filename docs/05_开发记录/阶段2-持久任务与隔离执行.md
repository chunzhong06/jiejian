# 阶段 2：持久任务与隔离执行

## 目标

把阶段 1 的同步验证迁移为可持久化、可恢复、由 Worker 调度并在隔离 Runner 中执行的链路，同时保持 PASS/BLOCK/INCONCLUSIVE 规则不变。

## 2.0 协议冻结

- 固定 Project、Run、Job、Evidence ID 和 UTC Unix 微秒时间。
- 定义 RunnerInputV1/RunnerResultV1、规范 JSON、大小限制和结果矩阵。
- 固定幂等、租约、attempt、Fencing Token、取消和发布顺序。

## 2.1 持久化映射

- 引入 SQLAlchemy 2 与 Alembic。
- 创建 Project、Run、Job、Job Event、Evidence Index 五表。
- SQLite 每个连接启用 foreign keys、WAL 和 5000 ms busy timeout。
- Repository 返回冻结 record，UnitOfWork 不暴露 ORM Session。

## 2.2 Job 控制面

- 幂等提交创建 QUEUED Run、PENDING Job 和首个事件。
- 原子 claim 增加 attempt/Fencing Token 并设置租约。
- 支持续租、首次取消、有界重试、致命失败和过期租约恢复审计。
- 所有状态变化和连续 Job Event 在同一事务。

## 2.3 隔离 Runner

- 将不可变执行请求持久化为 request.json，不重读可变 YAML。
- Worker 使用最小子进程环境启动 `python -B -m jiejian.runner`。
- 所有目标请求只由 Runner 发出；CLI 和 Worker 不导入目标 HTTP 能力。
- Runner 只写当前 attempt staging，进程退出码不编码安全 verdict。

## 2.4 发布与恢复

- Worker 复验 receipt/result/Job 关联、Fencing Token、文件集合和哈希。
- 完整 staging 原子发布后，才用 UnitOfWork 写 Run/Job/Event/Evidence 完成态。
- reconciliation 幂等补齐发布后数据库提交失败。
- 旧 token 与孤儿目录不得写完成态，只进入受控 quarantine。

## 当前结果

阶段 2 基础链已贯通：CLI 提交 → Worker claim → Runner 验证 → Evidence staging → 原子发布 → 数据库完成态 → CLI/report。详细决策见 [ADR-0002 至 ADR-0007](../03_技术决策/)，字段协议见[Runner 执行协议 V1](../04_协议定义/Runner执行协议V1.md)。
