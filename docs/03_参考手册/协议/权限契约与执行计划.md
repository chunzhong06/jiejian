# 权限契约与执行计划

> 状态：CURRENT。本文解释权限数据族之间的安全边界，不复制 JSON Schema 字段表。

## 目的与消费者

本协议族连接 Business Boundary、Permission v2 与保留的执行协议。消费者需要区分用户确认的稳定业务语义、当前代码绑定、后续可执行契约、覆盖用例和观察要求；当前完整新检查主链尚未重新接入 GUI。

## 先理解：用户需求、执行计划和结论不是同一份数据

用户确认“普通协作成员不得导出项目负责人的完整项目交付包”时，`PermissionIntentRevision` 引用正式 `BusinessActorRevision`、`BusinessActionRevision`，保存关系、DENY 预期与受保护 effect IDs，不保存 Candidate、具体账号、Cookie、HTTP 或 Observer。Actor/Action implementation binding 独立保存当前 Candidate 定位；`MISSING` binding 不阻止业务语义确认，只阻止后续把它冒充为可验证实现。

执行后形成的 Evidence 与 Verdict 不回写 PermissionIntent。换一个测试账号可能让旧 Profile 失效，却不能静默改变用户已经确认的权限需求；缺代表形成 coverage gap，也不能删除 DENY。

## 协议边界

- `BusinessActorRevision` 与 `BusinessActionRevision` 是不可变、可退休的业务边界历史；Action revision 拥有 Effect catalog。
- `PermissionIntentRevision` 是不可变、可退休的人类权限语义历史；`ProjectPolicyState.policy_epoch` 只随 Human GUI 批准的真实语义变化递增。
- `ActorImplementationBinding` 与 `ActionImplementationBinding` 保存 Candidate 映射；不可变 `BoundaryProposalBundle` 保存尚未生效的完整待审语义。它们不能自行改写 revision 或推进 epoch。
- `PermissionContract`/`ContractVersion` 是唯一可执行安全意图，包含 Security Effect Manifest；Action 只通过 `effect_ids` 引用效果，不包含 transport 细节。
- `NormalizedPermissionPlan` 是规范化计划。
- `PermissionMutationPlan` 是带 fingerprint、seed、预算、cases、coverage、gaps 和 required observations 的 Contract-only 覆盖计划。
- `DifferentialExperimentPlan` 在 Coverage 之后为风险 case 冻结 ALLOW 控制、DENY 变体、允许变化维度和必须相同的不变量。
- `Coverage` 说明规则、subject、action、resource、relation 和覆盖范围；不包含 HTTP transport 细节。

## 生命周期与数据流

```text
BoundaryProposal + LOCAL_GUI Human Approval
  → BusinessActor/Action revisions + Effect catalog
  → PermissionIntentRevision + Actor/Action bindings
  → PermissionPolicySnapshot（后续执行接线）
  → SecuritySetupCompiler（后续执行接线）
  → PermissionContract/ContractVersion 内部审阅并激活
  → NormalizedPermissionPlan
  → PermissionMutationPlan/Coverage
  → DifferentialExperimentPlan
  → WebExecutionSnapshot
```

确定性 canonical、ID、排序和指纹必须稳定。只有 Human GUI 服务端批准事务能同时改变业务 revision、Permission、binding、Decision 与 epoch；CLI、MCP、Machine、AI、Compiler 和 Run 不能成为审批人，也不能创建平行 Requirement/Candidate 治理链。当前编译执行接线尚未完成，不允许把 Permission v2 dual write 回旧表。

## 失败与安全语义

空规则、重复 ID、跨项目引用、观察器不足、规则漂移、非法状态转换和 canonical/hash 不一致均阻止进入执行。内部 ContractVersion 不能跳过审阅自动激活，也不能决定 Verdict、Finding 或 Gate。

## 版本规则与 Schema 真源

`PermissionContract`、`NormalizedPermissionPlan`、`PermissionMutationPlan` 与 `DifferentialExperimentPlan` 当前根 `schema_version` 都以字符串 1 作为 Web V1 发布基线；`PermissionContract.version` 继续表示独立的业务治理版本。完整字段、required、枚举和严格解析以：

- `product/backend/core/`
- `product/protocols/schemas/contracts/`
- `product/protocols` 中对应模型

为准。本文只说明边界，不复制完整 Schema。
