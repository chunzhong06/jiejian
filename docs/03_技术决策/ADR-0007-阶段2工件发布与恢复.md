# ADR-0007：阶段 2.4 工件发布与恢复

- 状态：已接受
- 日期：2026-08-09
- 适用阶段：2.4

## 背景

阶段 2.3 已把目标流量隔离到 Runner。SUCCESS 与 SAFETY_STOPPED 在 Worker 严格校验后只形成可信 attempt staging，Job 暂留 RUNNING，以免在最终工件发布前伪造数据库完成态。

阶段 2.4 需要实现 ADR-0002 固定的顺序：Runner staging、Worker 校验、原子发布、数据库完成事务，并收敛“目录已发布但数据库提交失败”的崩溃窗口。Runner V1、五表 Schema 和首版迁移已足够，本阶段不修改它们。

## 决策

### 1. 发布目录与不可变清单

一次成功或安全停止的最终目录固定为：

```text
<var_dir>/projects/<project_id>/runs/<run_id>/
```

Worker 在有效租约内向 staging 写入 `publication-manifest.json`，随后在同一文件系统中原子重命名整个 staging。最终目录保留：

- `result.json`；
- Runner 声明的全部 `artifacts/`；
- Worker 生成的 `publication-manifest.json`。

清单使用严格、冻结模型，记录 project、run、job、attempt、lease owner、fencing token、发布时租约截止、发布时间、结果哈希及完整文件清单。最终目录和清单不可原地修改；同一 run 已存在不同清单时稳定拒绝覆盖。

### 2. 发布前安全校验

Worker 在生成可信回执时校验一次，并在 promote 前独立重验：

- receipt、result、Job 的 job_id、run_id、attempt、lease owner 和 fencing token 完全一致；
- Job 仍为 RUNNING，租约有效且 token 是数据库当前 token；
- 每个相对路径继续满足 Runner V1 的 Windows 安全规则；
- staging 中只允许 `result.json` 和 RunnerResult 声明的文件，不得缺失或额外增加；
- 每个文件字节数和 SHA-256 与声明一致；
- 文件和所有目录组件不得是符号链接、junction 或其他 reparse point；
- 当前尝试的已知秘密不得作为字节子串出现在发布内容中。

Worker 写入清单后再次以受控父目录和同卷原子重命名完成发布。任何旧 token、过期租约、路径越界、哈希漂移或目录别名都不得到达最终目录。

### 3. 发布后的数据库事务

只有最终目录已经存在且可重新完整校验时，Worker 才开启完成态 UnitOfWork。该事务同时：

1. 以 job_id、run_id、attempt、lease owner、fencing token 做数据库条件更新；
2. SUCCESS 写 Run=COMPLETED、Job=SUCCEEDED 和 PASS/BLOCK/INCONCLUSIVE；
3. SAFETY_STOPPED 写 Run=SAFETY_STOPPED、Job=SUCCEEDED、verdict=null；
4. 只为最终目录中的规范 Evidence 文件写 Evidence Index；
5. 连续追加一次 `JOB_SUCCEEDED` 事件；
6. 提交后清除 Job 租约，不清除单调 fencing token。

Evidence Index 的 SHA-256 是 Evidence 模型的语义内容哈希，与内容寻址 ID 一致；最终文件字节哈希另由 publication manifest 固定。数据库不存在“完成态指向未发布目录”的路径。

CANCELLED、RETRYABLE_ERROR 和 FATAL_ERROR 不占用确定性最终 run 目录：它们继续通过阶段 2.2 的 fenced 事务分别进入 CANCELLED、RETRY_WAIT/FAILED、FAILED。RETRYABLE_ERROR 可能产生下一 attempt，不能把中间失败目录误当最终发布。

### 4. 崩溃窗口与 reconciliation

唯一允许的中间状态是“最终目录已原子发布，数据库仍为当前 token 的 RUNNING”。`RunReconciliationService` 不执行 Runner、不发目标流量，只做：

- 已发布 manifest 与当前 job/run/attempt/token 匹配：幂等补齐完成事务；即使原租约此后过期，也只消费已经在有效租约内发布的不可变结果，不产生新目标副作用；
- 数据库已经是匹配完成态：重新校验文件、Evidence 索引和状态后返回，不重复事件或索引；
- 已发布目录属于旧 token、缺少对象或内容失配：原子移动到 `<var_dir>/quarantine/published/`，不删除；
- staging 已不属于当前 RUNNING attempt：移动到 `<var_dir>/quarantine/staging/`；
- staging 仍属于当前有效 attempt：保留；若租约已过期，只报告需要既有恢复审计，不自动 claim、重试或删除。

清单在 promote 前记录 `published_at_us < lease_expires_at_us`，因此 reconciliation 只能补写曾在有效租约内完成的发布。数据库 token 已变化时永远不能补完成态。

### 5. CLI 与报告可见性

`run` 和 `ci` 等待 Worker 完成发布及数据库终态后才展示结果。`report` 对阶段 2.4 的新布局读取 `artifacts/report/report.json`，校验 publication manifest 中的文件哈希，并要求数据库 Run 已为 COMPLETED。阶段 1 旧报告布局继续可读。

## 崩溃窗口

| 崩溃点 | 可见状态 | 恢复 |
| --- | --- | --- |
| 写清单前 | 只有 attempt staging | 当前 attempt 可继续；失效后隔离 |
| 写清单后、promote 前 | staging 含完整清单 | 有效当前 fence 可幂等继续 promote |
| promote 后、DB commit 前 | 最终目录存在，Job 仍 RUNNING | reconciliation 补齐同一完成事务 |
| DB commit 后 | 最终目录与数据库终态一致 | 重跑只校验，不重复副作用 |

## 影响与后续边界

- Runner V1、签入 JSON Schema、五表和 Alembic revision 不变。
- `var/` 新增最终 publication manifest 与 quarantine 运行态，不提交 Git。
- 阶段 2 的基础链路至此具备持久提交、租约、隔离执行、原子发布、完成态和恢复。
- API、GUI、浏览器录制、LLM、插件、完整报告格式及后续产品化能力仍属于未来阶段；本 ADR 不实现或冻结这些能力。
