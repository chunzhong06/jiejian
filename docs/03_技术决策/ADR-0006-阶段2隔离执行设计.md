# ADR-0006：阶段 2.3 持久请求与隔离 Runner 进程

- 状态：已接受
- 日期：2026-08-09
- 适用阶段：2.3

## 背景

阶段 2.2 已实现持久 Job、原子 claim、租约、取消、重试和恢复审计，但没有执行目标请求。阶段 2.3 需要把阶段 1 的同步验证移入隔离 Runner，同时保持 Runner V1、五表 Schema、领域判定和 CLI 对外结果不变。

Runner V1 已能表达本阶段所需的执行内容、预算、安全范围、租约关联、结果类型、清理结果和暂存工件，因此不增加协议字段或数据库迁移。缺少的是：提交进程退出后仍可读取的请求真源、Runner 进程入口、最小秘密环境、Worker 监督，以及 2.4 发布前的可信暂存交接。

## 决策

### 1. 持久执行请求

CLI 在严格加载 YAML、校验项目和契约后，构造冻结的 `PersistedExecutionRequestV1`。该对象只包含：

- `schema_version="1"`；
- 执行预算；
- `ExecutionProjectSnapshotV1` 内容快照。

快照不携带 YAML 路径或真实秘密，只保留 `env:NAME` 引用。规范 JSON 位于：

```text
<var_dir>/jobs/<job_id>/request.json
```

请求在写入前执行严格校验和已知秘密扫描，以临时文件、`fsync`、SHA-256 校验和原子替换写入。数据库 `jobs.request_hash` 等于该文件规范字节的 SHA-256。相同 Job 与哈希幂等复用；已有文件内容不同则返回固定冲突，不覆盖。

路径由合法 `job_id` 唯一确定，不在五表中增加第二份快照或路径字段。Worker 只用 Job、该快照和当前子进程环境构造 `RunnerInputV1`，不重新读取 YAML。

### 2. 共享执行核心

`verification/execution.py` 是唯一快照执行核心，接收路径无关的 `VerificationSnapshot`。它复用既有计划、HTTP、观察判定、脱敏和证据实现。

- 阶段 1 的 `verification/pipeline.py` 只负责把已加载 YAML bundle 适配为快照；
- Runner 把 `RunnerInputV1.project` 适配为同一个快照；
- 计划、Oracle、证据和门禁规则不复制。

目标 HTTP 能力只存在于 Runner 导入链。CLI 和 Worker 不导入 `verification.http` 或 `httpx`。

### 3. Runner 进程边界

Runner 的入口为：

```text
python -B -m jiejian.runner --input <runner-input.json> --staging <attempt-staging>
```

一次进程执行一个完整 Run。Runner：

1. 在读取前检查输入大小；
2. 严格解析 Runner V1，拒绝重复键、未知字段、未知版本、非有限数和秘密泄漏；
3. 只从当前进程环境解析输入中的 `env:NAME`；
4. 在安全点观察取消标记，并在退出前执行必要清理；
5. 只写当前 attempt 的 staging，不写数据库或最终发布目录；
6. 原子写入 `RunnerResultV1` 结果候选。

Runner 退出码只表示进程/协议边界：

| 退出码 | 含义 |
| --- | --- |
| 0 | 已形成可信、可严格解析的结果文件 |
| 64 | 输入或协议无效，未形成可信结果 |
| 70 | Runner 内部致命故障，未形成可信结果 |
| 74 | staging 或结果文件 I/O 故障 |

PASS、BLOCK 和 INCONCLUSIVE 不编码在进程退出码中。

### 4. 最小环境与监督

Worker 子进程环境采用固定系统允许列表，加当前快照引用的秘密环境变量；不得复制整个父环境。真实秘密不进入 argv、快照、RunnerInput、数据库、事件、日志、stdout、stderr、结果或回执。

`WorkerSupervisor` 负责一次 Job 的 claim、输入构建、Runner 启动、租约续期、取消通知、超时终止和结果校验。所有续租和结果接收继续匹配 `job_id`、`lease_owner`、`fencing_token`。旧 token、过期租约或关联字段不匹配的结果不被接受。

取消先通过 attempt 目录中的固定标记通知 Runner；超时或 Runner 未正常退出时，Worker 依次执行有界 terminate/kill。启动失败、超时、协议错误、结果缺失按既有 Job 错误和重试/致命失败边界处理，不映射为 INCONCLUSIVE。

独立 Worker 入口为 `python -B -m jiejian.worker.runtime`。CLI 启动与自身进程组分离的 Worker；提交进程退出不主动取消 Worker。Worker 可从 SQLite 和持久请求恢复执行所需内容。

### 5. 可信 staged-result 与 CLI

Worker 对 RunnerResult 和每个工件执行关联 ID、attempt、owner、fencing token、规范路径、大小和 SHA-256 校验。校验通过后，在 attempt 目录原子写入 `trusted-result.json`，供提交者等待或重连读取。

阶段 2.3 不执行 2.4 的原子 promote 和数据库完成态提交：

- SUCCESS 或 SAFETY_STOPPED 只形成可信 staged result；Job 仍保持当前 fenced RUNNING；
- CLI `run`/`ci` 可从可信 staging 展示本次结果，并保持既有 JSON 与退出码；
- `report <run_id>` 仍只读取最终稳定报告。2.3 新运行在 2.4 发布前返回 `REPORT_NOT_FOUND`；
- CANCELLED、RETRYABLE_ERROR 和 FATAL_ERROR 使用阶段 2.2 已有事务入口收敛状态；
- 任何路径都不得提前写 SUCCEEDED/COMPLETED。

该中间边界保证本提交不违背“先发布工件、后提交数据库完成态”的顺序。阶段 2.4 必须消费可信回执，完成 promote、Evidence 索引、Run/Job 完成态和 reconciliation。

## 影响

- CLI `run` 与 `ci` 不再在自身进程内发出目标流量。
- Runner V1、签入 Schema、五表 Schema 和 Alembic revision 不变。
- 同步 `RunService` 保留为测试和内部路径适配器，但 CLI 不再调用它执行目标请求。
- 运行态新增 `jobs/<job_id>/request.json` 与 attempt staging，均位于 `var/` 且不得提交。
- 2.3 的成功结果可展示但尚未最终发布；这是进入 2.4 前明确且受限的过渡状态。

## 未采用方案

- 把 YAML 路径存入 Job 并由 Runner 重读：输入可变且提交进程退出后不可靠。
- 把真实秘密写入请求快照：违反最小秘密边界。
- 由 CLI 直接调用验证核心：违反 ADR-0002 的进程隔离决定。
- 在 2.3 提前实现成功完成态：会绕过 ADR-0002 固定的工件发布事务顺序。
- 为请求快照增加数据库列或新表：当前由 job_id 确定的原子文件和 request_hash 已足够，本阶段无迁移必要。

## 后续

阶段 2.4 负责可信 staging 的原子发布、Evidence 索引、Run/Job 成功完成态与 reconciliation。完成 2.4 后，CLI 等待逻辑应以已发布结果和数据库终态为稳定真源，`report` 应能读取新运行。
