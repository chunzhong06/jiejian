# 验证与提交规范

> 状态：CURRENT。适用范围：界鉴代码、协议、脚本、前端、文档的验证合同与提交前检查。

## 1. Python 验证

- Python 检查必须同时设置 `PYTHONDONTWRITEBYTECODE=1` 并使用 `python -B`。
- 语法检查优先使用 `ast.parse`，不使用 `py_compile` 或 `compileall`。
- 不得在源码目录生成或修改 `__pycache__` 与 `.pyc` 文件。
- 需要导入检查时，使用项目解释器的 `-B` 参数，并确认检查前后没有新增缓存文件。
- 仓库 pytest 的唯一正式入口是 `powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 test ...`。该入口先准备并复核项目专用 Conda、editable 当前源码和运行身份，再使用绝对解释器、`-B`、`-p no:cacheprovider` 与 `var/test/` 下唯一 basetemp 运行测试并精确清理。
- 不得把裸 `python -m pytest`、PATH 中的 `pytest` 或仅激活 Conda 后直接执行 pytest 的结果作为正式验证证据。Conda 激活只选择解释器，不会自动建立界鉴要求的项目根、运行模式、用户包隔离和主子进程指纹。
- 测试若启动 Worker、Runner、Observer 或其他真实 Python 子进程，fixture 必须从 `os.environ` 复制已确认的完整父环境，再叠加本用例授权的秘密；不得用只含秘密的字典替代完整父环境。预期验证环境拒绝行为的负向测试除外。
- 只有需要 `--lf`、`--ff` 或 `--stepwise` 排错时才临时启用 `.pytest_cache`；子阶段结束后只清理已确认的仓库内缓存，不递归清理上级目录或仓库外路径。

## 2. 前端验证

- 前端 Vitest 的唯一正式入口是 `powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\dev.ps1 frontend-test ...`。
- 该入口从 `product/frontend` 的同一源码输入集合排除明确生成物，形成构建指纹并镜像到 `var/runtime/build/frontend-workspace`；pnpm install、TypeScript、Vite 和 Vitest 都只在该工作区运行。
- pnpm store 与 Vite cache 分别进入 `var/cache/pnpm-store` 和 `var/cache/vite`，production build 只进入 `var/runtime/frontend`。不得把直接在 `product/frontend` 运行 pnpm 的结果作为正式证据。
- Vitest 通过不能替代 TypeScript 宿主接口与生产构建证据。修改生产 TS/TSX，尤其是 DTO、callback、API contract 或页面壳接口时，按风险至少执行受控 TypeScript/Vite build；普通/高级等共享表单模式还必须验证进入与退出、字段挂载互斥、状态恢复、最终请求 payload，以及 `secret`/`secret_ref` 等秘密字段互斥。
- 修改前端输入同步、构建或打包边界后，必须验证源码树不存在 `node_modules`、`dist` 和 `*.tsbuildinfo`，并分别证明工作区构建、指纹复用以及必要时的 Wheel 映射。

## 3. 模块范围与验证程度

测试范围由两个独立维度共同决定：

`测试范围 = 模块范围 × 验证程度`

模块范围按生产责任选择：`core`、`workflows`、`infra`、`api`、`cli`、`protocols`、`scripts`、`frontend`、`architecture`，或真正跨能力域的 `e2e`。测试目录继续表示模块责任，不建立 L1～L5 目录。

- **L1 最小验证**：用于边界明确的局部修改，只运行必要语法/类型检查、`git diff --check` 和直接保护该行为的少量测试。
- **L2 模块验证**：用于一个生产模块内的完整能力；先验证新增或失败项，再运行该模块对应集合，只按真实依赖补直接相关协议或边界测试。
- **L3 集成验证**：用于跨多个生产责任的能力链；选择涉及模块、边界协议和一个或少量代表性闭环，不扩大为仓库全量。
- **L4 全量回归**：只用于公共协议兼容、canonical/hash、Verification 判定、ApplicationCore 组合根、Worker/Runner 公共生命周期、Storage schema/migration、大规模共享基础设施、测试体系重构等共享高风险边界，或阶段最终稳定树。阶段最终树只执行一次；同一代码与测试状态不得重复全量。
- **L5 真实动态验收**：用于真实终端、PowerShell、`start.cmd`、浏览器/GUI、Worker 子进程、Runner、真实 Target/Observer、数据库或竞态。L5 是独立真实运行维度，可与 L1～L4 任一级组合，不表示更大的测试集合；由主线程负责最终产品验收。

依赖当前交互用户专属操作系统状态的 L5（例如 Windows Credential Manager）必须在对应用户上下文执行。专用沙箱用户中的失败只能作为环境诊断，不能冒充产品失败或真实用户验收；测试专属的授权、命令和清理要求记录在 `tests/README.md`。

- 启动会产生真实副作用的 GUI、浏览器、Worker、外部服务、Credential Manager、目标应用或其他有状态 L5 前，必须一次性完成只读 preflight，覆盖本轮真正依赖的数据/业务状态、运行身份、依赖与凭据、外部服务与端口、现有监听进程与控制会话、写入边界、后续页面或步骤所需状态，以及清理或恢复条件；任一必要条件缺失时先停止，不得制造副作用后再逐项发现缺口。
- 把 GUI 手工验收交给用户前，除证明入口可操作外，还必须证明后续步骤所需状态或候选已经产生。同端口切换服务实现或实例时，依次确认旧监听消失、新进程仍存活、监听 PID 属于新进程，再验证健康或业务响应；端口仍能返回 health 不能单独证明新实例启动成功。
- L5 结果必须绑定本轮实例、控制会话和起始状态，不得把旧进程、陈旧状态或前一次运行事实当成本轮证据。

修改 Windows 启动 readiness、FastAPI lifespan、缓存启动维护或源码/package 边界时，直接测试至少证明：软等待不冒充浏览器失败、浏览器只在精确 `/ready` 后调用、ready 前进程退出形成启动失败、缓存维护不阻塞或撤销 ready、clean 本地运行态首次 editable 与前端准备一次成功。对应 L5 只重验受影响的启动场景：已有大量文件缓存、受控慢 startup、ready 后浏览器调用失败；不得用增加固定超时、预建空前端目录或第二次运行成功代替证据。

`essential` 是稳定的跨模块重要回归集合，不等于 L1。L1、L2 默认不运行 `essential`；L3 只有确实触及核心跨模块边界或需要阶段中间门禁时才考虑；L4 已包含它，不得在同一代码状态下先跑 `essential` 再立即跑全量。不得创建 L1～L5 pytest marker，少量 marker 只表示稳定测试属性。

## 4. 验证合同与升级

每个非平凡验证批次开始前必须明确：实际受影响的测试模块、L1～L4 程度、是否需要 L5、当前程度为何足够，以及出现什么证据才升级。

验证按证据逐级扩大。局部修改先 L1，完整模块再到 L2，实际跨模块再到 L3，只有共享高风险边界或阶段最终树才到 L4；需要证明真实运行边界时在对应等级追加 L5，不按改动行数或主观规模直接选择全量。

开发子阶段以直接相关测试和一个代表性功能闭环为默认上限。执行线程不得因“保险”超过交接给定的验证程度上限或自行运行 L4；若实现实际触及更大共享边界，应停止扩大并把证据交回主线程。

最近一次 L4 必须绑定明确 HEAD 与 working-tree 状态。生产代码和测试未变化时禁止重复；之后只修改 README、注释或无行为影响文案，不机械重跑产品全量。L4 失败后先修复并运行失败项与直接影响范围，只有修复触及共享核心或使原证据失效时才重新决定是否执行第二次 L4。

阶段最终稳定树的完整 L4 依次运行后端全量、前端全量、公共 Schema 漂移检查和强制生产准备；`schema` 默认只读，只有显式 `schema -Update` 才允许更新签入文件。

## 5. 失败处理

测试失败后先判断是产品逻辑、测试/fixture 还是环境工具问题。修复后的第一步只重跑失败项；通过后只按修复真实影响补直接邻域。只有修复本身触及更大的共享边界，才重新执行完整 L2/L3 或评估 L4。

- 不得为了让测试转绿而擅自提高安全预算、请求数、超时、大小限制或重试次数，不得放宽 fail-closed 条件，也不得把阶段专用权限或 flag 扩展到非目标阶段。修改阶段专用 flag、预算、权限或清理标记时，测试必须同时证明目标阶段启用和非目标阶段禁用。
- 失败定位必须优先修复错误调用点；不得用扩大预算掩盖额外调用或错误阶段的副作用。“测试变绿”本身不能证明安全边界正确。

错误解释器、缺失依赖、框架限制、jsdom 能力缺口、浏览器 locator、错误路径和陈旧 fixture 不得算作产品失败，也不得为了适配验证工具而修改正确的生产行为。

失败方案必须记录所用方法、失败原因、根因和错误假设。可重复模式转化为规则、测试、ADR、校验项或交接检查项，不能只以“下次注意”结束。

## 6. 提交前检查

每次实现至少确认：

- 是否遵守当前权威规范和已接受决策。
- 是否引入新的秘密、未脱敏日志或越界网络访问。
- 状态转换、失败恢复和取消路径是否有测试。
- 副作用动作是否具备预算、观察和清理策略。
- 文档、Schema、API 客户端和实现是否保持一致。
- 实际开发若改变了设计，规范是否已经同步更新。
- 修改项目自有源码或测试时，是否按 `.agents/skills/jiejian-comments/SKILL.md` 完成注释校准，并确认触及的项目自有 Python 文件具备职责性 `#` 文件头。
